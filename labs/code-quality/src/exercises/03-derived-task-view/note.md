## 목적

사용자가 목록을 검색 및 필터로 조회할 수 있어야 한다

## 사용자 행동

- 사용자가 검색어를 입력한다
- 사용자가 상태 필터를 선택한다
- 사용자가 할 일의 완료 여부를 변경한다
- 사용자가 완료된 할 일을 정리한다

## 사용자 행동에 따른 UI 변화

- 검색어나 필터가 변경되면 두 조건에 만족하는 할 일 목록을 보여준다.
  - 목록이 비어있으면 다음 행동을 선택할 수 있는 빈 상태를 보여준다
- 할 일의 완료 상태가 변경되면 할 일, 완료 개수가 업데이트 된다.
- 완료한 일을 정리하면 완료 항목을 제거하고 개수, 진행률, 목록이 업데이트 된다.
- 정리 후 제거된 할 일 개수를 안내한다.
- 완료한 일이 없으면 버튼이 비활성화 된다.

## 설계 판단 과정

### 화면이 기억해야 할 정보

- 할 일 목록
- 필터(전체, 할 일, 완료)
- 검색어
- 정리 피드백 안내

### 파생 데이터

- 전체, 할 일, 완료 개수
- 진행률
- 검색과 필터링에 맞는 할 일 목록

할 일 목록으로 전체의 개수를 구할 수 있고, 완료 상태를 기준으로 할 일과 완료 개수를 파악할 수 있다. 진행률도 `완료 개수 / 전체 개수`로 구할 수 있다.

검색과 필터링은 "두 조건에 맞는 어떠한 데이터를 보여주는가"이기 때문에 현재 할 일 목록 데이터로 필터링 할 수 있다

### 책임

`Problem` 컴포넌트의 문제점:

- UI 렌더링
  - 오늘의 진행 상황
  - 완료한 일 정리, 검색, 필터,
  - 할 일 목록
- 상태 관리
- 도메인 로직
- 사용자 행동 처리
- 조회 / 필터 로직
- 결과 피드백

하나의 컴포넌트가 많은 관심사를 가지고 있게되어, "내가 필요로 하는 부분만" 파악하기가 힘들다는 문제가 있다. 명확한 구조는 탐색 비용은 발생할 수 있지만, 시점 이동에 비해 내가 알고싶은 부분만 파악할 수 있고 구조적으로 분리되어 가독성이 더 좋다고 판단했다.

#### UI 화면 영역 분리

- 할 일 목록의 진행률을 나타내는 요약 정보 영역
- 검색, 상태, 완료한 일 정리하는 영역
- 할 일 목록을 보여주는 영역

화면에 보여주는 UI가 위와 같이 역할이 달라, 하나의 컴포넌트가 모든 것을 다 알고있는것 보다 컴포넌트로 분리하여, 해당 UI 영역이 무엇을 하는지를 나타내도록 의도했다.

#### 할 일 관리의 흐름을 훅으로 분리

할 일의 완료 상태를 변경하고, 완료한 일을 정리하면 `할 일 목록`, `정리 피드백`, `할 일 개수`, `진행률`이 영향을 받는다. 사용자 행동에 따른 영향받는 범위들을 `useDailyTasks` 훅으로 분리했다.

#### 검색과 필터링 로직 분리

두 조건을 만족한 할 일을 보여줘야한다는 정책이 있다. 따라서 상태는 상위 컴포넌트에서 작성하고, 화면에 어떤 데이터를 보여줄지 결정하는 로직을 `filterVisibleTasks` 함수로 분리했다.
