# Exercise 02: 추상화 레벨별 힌트

이 문서는 코드 조각을 먼저 제시하지 않는다. 막힌 지점에 맞는 레벨만 읽고, 가능한 한 높은 레벨에서 먼저 판단한다.

## 높은 추상화 레벨: 사용자 의도와 도메인

- 이 화면에서 사용자는 아직 공개할 준비가 되지 않은 `행사 초안`을 계속 수정한다.
- `임시 저장`은 작성 중인 초안을 잃지 않기 위한 행동이고, `게시`는 참여자에게 보이도록 공개하는 행동이다.
- 두 행동이 공유하는 것은 “행사 초안을 가지고 요청을 수행한다”는 흐름이다. 공개 가능 여부를 판단하는 정책은 서로 다르다.

먼저 답해 보세요.

1. 행사 자체의 정보와 사용자가 지금 수행 중인 행동은 같은 종류의 개념인가요?
2. 행사 정책이 추가될 때 바뀌는 부분과, 요청이 끝날 때까지 기다리는 방식은 함께 바뀔까요?

## 중간 추상화 레벨: 행동, 규칙, 책임

- 입력값을 모아 정리하는 일, 게시 가능 여부를 확인하는 일, 요청 중인 행동을 기록하는 일, 결과를 알리는 일은 각각 다른 변경 이유를 가질 수 있다.
- 임시 저장과 게시 모두 요청 전후에 `처리 중 표시 → 요청 → 성공 또는 실패 안내 → 처리 종료`라는 흐름을 갖는다.
- 반대로 게시만 제목과 현재 행사 유형에 필요한 값을 확인한다.

먼저 답해 보세요.

1. 공통 요청 흐름과 게시 검증 정책을 한 함수에 둘 때, 다음 정책 변경은 어디를 수정하게 되나요?
2. `processingAction`은 행사 정보인가요, 아니면 사용자가 요청을 수행하는 흐름의 상태인가요?
3. 결과를 토스트로 보여 주도록 바꿔도, 결과 메시지를 결정하는 책임은 바뀌나요?

## 낮은 추상화 레벨: 현재 구현 세부사항

- `eventType`, `title`, `onlineUrl`, `offlineLocation`은 입력값이 바뀔 때 갱신된다.
- `getFormData`는 입력값을 요청에 사용할 행사 초안 형태로 정리하고 공백을 제거한다.
- `runAction`은 임시 저장과 게시의 공통 요청 흐름을 담고, `getPublishValidationMessage`는 게시 전 규칙을 확인한다.
- `processingAction`은 동시에 두 요청이 시작되지 않게 하고, `resultMessage`는 사용자가 확인할 결과를 보관한다.

먼저 답해 보세요.

1. 지금의 `runAction`에서 실제로 함께 바뀌는 코드와 우연히 같은 곳에 있는 코드는 무엇인가요?
2. 검증 함수가 `Problem` 안에 있어도 이해하기 쉬운가요? 분리한다면 어떤 변화가 그 분리를 정당화하나요?

## 현재 요구사항에 대한 설계 답안

현재 요구사항만으로는 커스텀 훅, 다수의 인터페이스, 유형별 컴포넌트를 반드시 만들 이유가 없다. 가장 작은 설계 답안은 다음과 같다.

- 행사 초안 데이터는 하나의 모델로 둔다.
- 임시 저장과 게시의 실행 상태는 `어떤 행동을 처리 중인지`로 둔다.
- 게시 검증은 `게시 정책`으로 표현하고, 임시 저장에는 적용하지 않는다.
- 공통 요청 흐름은 한 곳에 두되, 정책이 달라지는 지점은 이름으로 드러낸다.
- `Problem`은 화면과 React 생명주기를 연결하고, 나머지 구조 분리는 실제 변경 요구사항이 생긴 뒤 판단한다.

즉, 이 답안은 “무조건 `useEventRegistration`을 만든다”가 아니다. 다음 요구사항에서 폼 상태·정책·요청 흐름 중 무엇이 독립적으로 변하는지 확인한 뒤에 경계를 만들면 된다.

## 답안을 요청하는 방법

`높은 레벨 답안`, `중간 레벨 답안`, `낮은 레벨 답안`, `전체 설계 답안`, `코드 예시`처럼 원하는 범위를 말할 수 있다. 코드 예시는 먼저 현재 구현과 변경 시나리오를 확인한 뒤 제공한다.
