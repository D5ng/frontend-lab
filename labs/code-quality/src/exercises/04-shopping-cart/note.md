### Problem 컴포넌트

현재 Problem 컴포넌트에는 UI와 비즈니스 로직 관심이 섞여있다. 지금과 같이 간단한 경우라면 이대로 두어도 충분할 것 같다. 하지만 비즈니스 로직이 더 섞이고 상태 관리가 복잡해진다면 훅으로 빼는게 좋아보인다.

여기서 복잡하다는건, 관리해야할 상태가 여러개가 되거나, 비즈니스 로직이 더 많아지는것이다. 물론 장바구니 도메인에 대해 깊게 생각해보지 않아 얼마나 많아질지 알 수 없다. 내 수준에서는 관리할 대상이 많아져 코드의 길이가 늘어난다면 "읽고싶지 않은 코드"가 될 것 같았다. 음.. 조금 더 자세하게 말하자면 "무엇을" 하는지보다 "어떻게"에 가깝게 되어 내가 읽고자 하는 부분을 파악하기 어려워진다. 로직이 어디에서 쓰이는지 UI를 살펴볼 때 시점 이동의 격차가 크면 클수록 스크롤하다가 잊게되는것 같다. (내 집중력 이슈일 수 있다..)

UI와 상태 및 비즈니스 로직에 관심사를 분리하는것이 미래에 더 나은 유지보수라는 생각이 들어, 분리하는게 맞다는 생각도 든다. 하지만 "너무 먼 미래를 보는걸까" 라는 의문이 드는데 아직은 잘 모르겠다.

### cart.ts

cart.ts에서는 장바구니에 대한 정책과 비즈니스 로직이 들어가 있다.

- 기본 수량과 최소 수량은 1개 이상이여야 한다
- 현재 수량이 1이하가 아니라면 감소할 수 있어야 한다

#### 내 생각

만약 최대 수량에 대한 정책이 추가된다면? cart.ts와 Problem.ts 파일에 수정이 필요하다. 이렇게 분리하는게 맞는지에 대한 의문이 들지만, 이것도 내가 늘 이렇게 작업을 해왔고 많은 프로젝트에서도 그렇게하다보니 이렇게 분리한것 같다.. 사실 위 Problem 내용에 마지막 내용대로 진행한거다

### formatPrice

formatPrice는 utils로 빼두었다. 천 단위로 쉼표로 구분하는것이기에 어디서든 범용적으로 사용할 수 있다고 판단해 분리해두었다.

하지만 여기서 고민인건 "어디서든 범용적으로 사용할 수 있다" 고해서 분리를 해야할까? 어떠한 기준보다 경험이나 주관에 의해 분리한 느낌이 강하다. 다소 근거가 약하다고 볼 수 있다.

## 2단계

구현 전:

- 하나의 상품을 상태로 관리하지 않고, 수량을 상태로 관리했었다. 따라서 여러 상품의 수량을 변경하기 위해서는 상품을 상태로 관리하도록 변경해야 한다
- 총 결제 금액도 모든 상품의 `quantity * price`가 되도록 변경해야 한다

구현 후:

현재 장바구니 UI에서 `map`으로 렌더링하여 상품 목록과 수량에 대한 정보를 표시하고 있다. JSX에서 `map`을 사용하는 일반적인 이유는 각 배열에 들어있는 요소들을 화면에 보여주기 위함이지만 "무엇을 하는지" 잘 나타내기 위해서는 컴포넌트로 추상화하는게 좋아보인다. 가독성 측면으로도 무엇을 하는지 역할을 알 수 있고, `Problem` 컴포넌트에서 구조적으로도 파악 가능하도록 설계하는 것이 DX적으로 더 좋다고 판단된다.

따라서 이 부분만 추상화를 하는것보다 각 UI에서 맡은 역할들에 맞게 동일한 수준의 추상화를 진행하는게 사람이 코드를 읽는 수준이 같아져 좋다고 판단되어 진행했다.

- CartProductList => 장바구니 상품 목록 렌더링
  - CartProductItem => 장바구니 상품 렌더링
- CartTotalPrice => 총 결제 금액 렌더링

관심사가 분리되며 여러 컴포넌트에서 `CartProduct` 인터페이스를 사용하고 있다. 따라서 `cart.model.ts`에서 `CartProduct interface`를 작성했다.

상태의 데이터가 숫자에서 배열로 변경되다보니 `수량 늘리기`, `수량 줄이기`, `총 금액` 데이터가 함께 변경되었다. 같이 변경되는 부분들을 묶고 이를 사용하는 곳은 `Problem` 컴포넌트이니 해당 컴포넌트는 무엇을에만 집중하면 될 것 같다.

#### 내 생각

같이 변경되는 데이터를 왜 묶어야할까? 관심사가 달라서 그런걸까? 그렇다면 왜 관심사가 다르다는 이유로 분리해야 할까?

위 질문에 대한 답은 "수행하는 목적이 다르기 때문이지 않을까"라는 생각이 든다. UI는 정제된 데이터를 렌더링한다. 그러면 UI가 필요로하는건 `어떻게`보다 `무엇`에 가깝다. 그리고 UI 변경사항이 아니여도 `Problem`에서 수정해야한다.

코드 리뷰할 때 불편함이 있을 수 있다는 생각도 들고, 관심사를 하나로 묶는다는건 변경 영향 범위도 한 곳이기 때문에 코드 맥락을 쉽게 이해할 수 있다.
