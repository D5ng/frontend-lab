# Code Quality Lab

실제 제품에 가까운 React 화면을 변경하면서 가독성, 예측 가능성, 응집도, 결합도를 판단하는 실험 공간입니다.

좋은 코드는 특정 모양을 뜻하지 않습니다. 컴포넌트 수나 코드 길이로 정답을 결정하지 않고, 요구사항이 바뀔 때 함께 수정되어야 하는 코드와 독립적으로 바뀌어야 하는 코드를 관찰합니다.

## 실습 원칙

1. 먼저 사용자가 관찰할 수 있는 요구사항을 읽는다.
2. 상태의 원본, 현재 코드의 책임, 예상되는 변경 이유를 적는다.
3. 테스트로 현재 행동을 확인한다.
4. 첫 요구사항을 만족하는 가장 작은 변경을 구현한다.
5. 추가 요구사항을 받은 뒤 실제 변경 범위를 기록한다.
6. 변경 근거가 생겼을 때만 책임을 나누거나 공통화한다.

스타터 코드가 이미 동작하더라도 현재 구조가 정답이라는 뜻은 아닙니다. 반대로 파일이 크거나 코드가 반복된다는 이유만으로 분리해야 하는 것도 아닙니다.

## 제품 품질 기준

- 화면은 실제 사용자가 있는 모바일 제품의 한 장면으로 구성한다.
- 너비 375px을 기준으로 정보 위계, 여백, 터치 영역과 피드백을 확인한다.
- 브랜드를 그대로 복제하지 않고, 익숙한 사용 흐름과 명확한 문장을 사용한다.
- 키보드 접근, 명확한 이름, 빈 상태와 결과 안내를 기본 품질로 포함한다.
- UI 완성도와 코드 구조 판단은 별개로 검토한다. 화면이 아름답다고 구조가 좋은 것은 아니다.
- Montage 컴포넌트와 토큰을 우선 사용하되, 학습 질문을 가리거나 부적절한 컴포넌트를 억지로 사용하지 않는다.

## 힌트와 답안

막힌 정도에 따라 다음 수준으로 요청할 수 있습니다.

- 높은 레벨: 사용자 의도와 도메인 개념
- 중간 레벨: 행동, 정책, 책임과 변경 이유
- 낮은 레벨: 현재 코드의 구현 세부사항
- 전체 설계 답안: 대안과 트레이드오프를 포함한 판단

답안은 코드보다 판단 근거를 먼저 설명합니다. 실습자가 구현 중이면 완성 구조를 먼저 제공하지 않습니다.

## Exercise 01: 같이 실행되지 않는 코드 분리하기

배달과 매장 픽업처럼 동시에 실행되지 않는 흐름을 어디까지 분리할지 판단합니다.

핵심 질문은 “분기문이 있으니 나눌 것인가”가 아니라 “어떤 요구사항이 각 흐름을 독립적으로 바꾸는가”입니다.

## Exercise 02: 임시 저장과 게시의 책임 나누기

하나의 행사 초안을 사용하는 임시 저장과 게시가 어떤 요청 흐름을 공유하고, 어떤 검증 정책을 따로 가져야 하는지 판단합니다.

요구사항은 [Exercise 02 문서](./src/exercises/02-draft-and-publish/requirements.md)에 있습니다.

## Exercise 03: 원본 상태와 파생 화면 구분하기

생활 할 일 앱에서 검색, 상태 필터, 완료 처리, 진행률과 완료 항목 정리를 다룹니다. 이전보다 화면과 상호작용은 커졌지만 학습 질문은 하나입니다.

> 어떤 값을 상태의 원본으로 보관하고, 어떤 값은 원본에서 계산해야 하는가?

요구사항은 [Exercise 03 문서](./src/exercises/03-derived-task-view/requirements.md), 시각 기준은 [디자인 방향](./src/exercises/03-derived-task-view/design-direction.md)에 있습니다. 구현 전에 [학습 기록](./src/exercises/03-derived-task-view/note.md)의 첫 세 항목을 작성합니다.

## 실행

```bash
pnpm dev
pnpm test
pnpm lint
pnpm build
```

저장소 루트에서 실행하면 `@frontend-lab/code-quality` 패키지를 대상으로 동작합니다.
