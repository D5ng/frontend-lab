# Code Quality Lab

[Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성, 예측 가능성, 응집도, 결합도를 실제 React 코드 변경으로 비교하는 실험 공간입니다.

문서의 사례를 그대로 따라 쓰지 않습니다. 같은 판단 기준이 필요한 독자적인 요구사항을 구현하고, 변경 요구사항에서 처음 설계의 장단점을 관찰합니다.

## UI 기준

- 실습 화면은 실제 사용자 서비스의 모바일 흐름을 모델로 한다.
- 디자인은 Montage 컴포넌트와 토큰을 우선 사용한다.
- 모든 화면은 너비 375px 뷰포트를 기준으로 구현하고 검증한다. 데스크톱 또는 다른 화면 너비 대응은 실습 범위에 포함하지 않는다.

## 힌트와 답안 방식

실습자는 원하는 수준의 도움을 요청할 수 있다.

- 높은 추상화 레벨: 도메인 개념, 사용자 의도, 비즈니스 의미
- 중간 추상화 레벨: 행동, 정책, 책임과 변경 이유
- 낮은 추상화 레벨: 현재 코드의 구현 세부사항

문제를 풀 때는 가능한 한 높은 레벨에서 먼저 판단한다. 답안은 코드만 제시하지 않고, 요구사항·책임 경계·변경 시나리오·대안의 트레이드오프를 함께 설명한다.

## Exercise 01: 같이 실행되지 않는 코드 분리하기

`Problem`은 배달과 매장 픽업이라는 두 흐름의 상태, 입력, 검증과 결과 생성을 한 컴포넌트에서 처리합니다. 현재 동작은 테스트로 고정되어 있습니다.

### 관찰 가능한 요구사항

- 첫 화면은 배달을 선택하고 배달 주소 입력만 보여준다.
- 매장 픽업을 선택하면 배달 주소 대신 픽업 매장 입력을 보여준다.
- 현재 수령 방법에 필요한 값이 없으면 해당 입력 안내를 보여준다.
- 유효한 값을 입력해 요청하면 선택한 방법에 맞는 결과를 알려준다.

### 학습 질문

- 동시에 실행되지 않는 두 흐름을 지금 분리해야 하는가?
- 분리한다면 UI, 상태, 검증, 제출 중 어디까지 같은 책임인가?
- 공통 제출 인터페이스는 가독성을 높이는가, 다른 흐름을 결합하는가?
- 현재 테스트는 구조 변경을 방해하지 않고 행동을 보호하는가?

정답 컴포넌트는 제공하지 않습니다. 먼저 현재 코드의 책임과 변경 이유를 기록한 뒤 직접 수정합니다.

## Exercise 02: 임시 저장과 게시의 책임 나누기

모바일 행사 관리 서비스의 `행사 만들기` 첫 단계입니다. `Problem`은 행사 유형별 입력값, 게시 검증, 임시 저장과 게시 요청, 실행 중 상태와 결과 안내를 한 컴포넌트에서 처리합니다. 현재 동작은 테스트로 고정되어 있습니다.

문제의 기준은 [요구사항](./src/exercises/02-draft-and-publish/requirements.md)에 있습니다. 설계 메모와 학습 기록은 실습자가 직접 작성합니다.

### 관찰 가능한 요구사항

- 온라인과 오프라인 행사 유형을 전환해도 각 입력값을 보존한다.
- 임시 저장은 빈 입력값도 허용한다.
- 게시는 제목과 현재 행사 유형에 필요한 입력값을 요구한다.
- 한 작업이 진행 중이면 다른 작업도 시작하지 않는다.
- 완료 결과를 사용자에게 알려준다.

### 학습 질문

- 폼 데이터와 요청 상태는 같은 경계에 있어야 하는가?
- 임시 저장과 게시의 공통된 요청 흐름은 가독성을 높이는가, 서로 다른 정책을 숨기는가?
- 유형별 입력과 검증을 나누면 다음 변경의 영향 범위는 실제로 줄어드는가?
