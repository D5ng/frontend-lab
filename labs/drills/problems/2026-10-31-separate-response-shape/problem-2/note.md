# 풀이 기록 · 원룸 매물 목록과 상세

답은 질문마다 2~3줄이면 충분합니다.

## 화면이 쓰는 방의 모양은 무엇인가요? 응답의 어떤 필드를 그대로 두고, 어떤 필드를 다른 모양으로 바꿨나요?

`api` 레벨에서는 서버에서 내려주는 응답 타입을 그대로 사용하고, 서버에서 받은 응답값을 프론트에서 변환하는 함수를 만들어, 해당 함수로 화면을 그리도록 구성했어요.

- 그대로 둔 필드: `title`, `deposit`
- 이름만 카멜케이스로 바꾼 필드: `id`, `monthlyRent`, `maintenanceFee`, `areaM2`, `availableFrom`
- 모양을 바꾼 필드: `floor`(지금 층), `totalFloor`(전체 층)
- 추가한 것: `monthlyCost`, `pyeong`

#### (리뷰)

거의 됐다. 그대로 둔 것, 이름만 바꾼 것, 새로 만든 것으로 갈래를 나눠서 질문에 바로 답한다.

남은 건 `floor` 하나다. `floor`는 "추가한 것"이 아니라 **이름은 그대로인데 뜻이 바뀐 필드**다. 응답에서는 `'3/5'`였고, 화면에서는 `'3'`이다. 둘 다 `string`이라 누가 `room.floor`를 예전 뜻(`'3/5'`)으로 읽어도 타입 검사가 잡아 주지 못한다. 이름만 바꾼 필드보다 오히려 조심할 필드라서 "모양을 바꾼 것"으로 따로 두는 게 정확하다. `totalFloor`는 거기서 나온 새 필드다.

"왜 이렇게 나눴나"(해석하는 곳이 몇 군데인가)까지 쓰면 더 좋지만, 질문이 묻는 건 아니라 여기서 멈춰도 된다.

참고 답:

> 이름만 카멜케이스로 바꾼 필드: `id`, `title`, `deposit`, `monthlyRent`, `maintenanceFee`, `areaM2`, `availableFrom`.
> 모양을 바꾼 필드: `floor`의 `'3/5'`를 `floor`(`'3'`)와 `totalFloor`(`'5'`)로 나눴다.
> 새로 계산한 필드: `monthlyCost`(정렬과 상세가 씀), `pyeong`(목록과 상세가 씀).
>
> 기준은 "이 필드를 해석하거나 계산하는 곳이 몇 군데인가"였다. 두 곳 이상이 같은 계산을 하면 `toRoom`으로 옮겼고, 이름만 다른 필드는 바꿔도 타입 검사가 잡아 주니 옮겨 담기만 했다. `available_from`은 "`null`이면 바로 입주"라는 뜻 그대로 두었다. `isAvailableNow`를 따로 두면 같은 사실을 두 필드가 들게 되고, 둘의 관계를 TypeScript가 몰라서 `?? ''` 같은 가짜 값이 생겼기 때문이다.

## 응답을 그 모양으로 바꾸는 일은 어디에서 하나요? 목록과 상세가 같은 모양을 쓰나요, 다른 모양을 쓰나요? 그렇게 정한 이유는 무엇인가요?

응답을 바꾸는 일은 `toRoom.ts`에서 바꿨어요, 목록과 상세는 같은 모양은 아니지만, 목록을 기반으로 잡고, 상세에서는 2개의 필드를 추가했어요. 목록을 기반으로 잡은 이유는, 해당 목록과 상세가 다른건 2개의 필드뿐이였고, 만약 목록을 기반으로 잡지않았더라면, 공통된 값이 다를 수 있고 수정또한 2곳을 찾아다녀야 했어요.

#### (리뷰)

완성이다. "목록을 기반으로 잡았다"가 결론이 되었고, 그렇게 한 이유도 둘 다 들어갔다.

- **공통된 값이 다를 수 있다**: 두 화면이 같은 방을 다른 숫자로 보여 주는 위험이다.
- **수정도 두 곳을 찾아다녀야 한다**: 바꿀 때 드는 비용이다.

지난번에 빠졌던 "나머지를 같이 쓰는 이유"가 바로 이것이다.

덧붙인다면 "공통된 값이 다를 수 있다"를 한 번만 구체적으로 써 보면 좋다. 예를 들면 "목록은 7평, 상세는 8평"이다. 평수처럼 계산해서 만든 값일수록 두 곳이 따로 계산하면 반올림 하나로도 어긋난다.

참고 답:

> `room/toRoom.ts`에서 바꾼다. 상세 모양 `DetailRoom`은 목록 모양 `Room`에 `description`, `options`만 더한 것이고, `toDetailRoom`도 `toRoom`을 부른 뒤 두 필드를 붙인다.
>
> 같은 방을 두 화면이 보여 주니, 층·평수·매달 드는 돈을 한 곳에서 계산해야 두 화면이 다른 숫자를 보여 주지 않는다. 상세에만 필요한 두 필드는 상세 응답에만 오니 상세 쪽에서만 붙였다.

### (리뷰) 다음에 비슷한 문제를 볼 때

1. **"이 필드를 해석하거나 계산하는 곳이 몇 군데인가?"** 두 곳 이상이면 변환 함수로 옮기고, 이름만 다르면 옮겨 담기만 한다. 오늘 "서버가 바꾸면 몇 군데를 열어야 하나는 모든 필드에 해당하지 않나?"라고 물었던 데서 이 기준이 나왔다. 이름 변경은 타입 검사가 잡아 주지만, 뜻과 모양이 바뀌면 조용히 틀린다.
2. **"같은 사실을 두 값으로 들고 있나?"** `isAvailableNow`와 `availableFrom`, `isLoading`과 `data`가 그랬다. `?? ''`나 `?? []` 같은 가짜 값을 쓰고 싶어지면 이 질문으로 돌아온다.
3. **"화면 타입이 아직 응답 타입에 기대고 있나?"** `Pick<RoomSummaryResponse, ...>`처럼 응답 타입에서 필드를 빌려 오면, 끊으려던 연결이 타입 쪽으로 다시 들어온다. 변환을 다 했다고 느낄 때 `Room` 타입의 import 줄을 한 번 본다.
