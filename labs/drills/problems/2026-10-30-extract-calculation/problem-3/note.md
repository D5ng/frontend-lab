# 풀이 기록 · 변경 요청: 자동이체 우대 금리

답은 질문마다 2~3줄이면 충분합니다.

## 고치기 전에: 몇 곳을 고칠 것 같나요? 파일 이름으로 적어 주세요.

- formatAnnualRate 함수
- SavingsHome에서 자동이체 선택 상태
- savings.ts => calculateAppliedRate(rate: number): number
- TermCompareSheet.tsx => 자동 이체 여부를 파악하여 시트에서 계산
- SavingsConfirm.tsx => 자동 이체 여부에 따른 화면 표시가 다름

### (리뷰)

규칙을 더할 곳(`savings.ts`)과 그 값을 받아야 할 세 화면을 모두 짚었어요. 예상이 꽤 정확했어요.

빠진 곳은 **가입 요청이 나가는 길**이에요. 기획이 "가입 요청에도 자동이체 여부를 같이 보내 주세요"라고 했으니, 화면에서 서버까지 값이 어디를 거쳐 가는지 따라가 봐야 했어요. 이 코드에서는 `SavingsConfirm` → `useOpenSavingsAccount` → `api.ts`예요.

반대로 `formatAnnualRate`는 고치지 않아도 됐어요. 숫자를 글자로 바꾸는 함수라서 그 숫자가 기본금리인지 적용금리인지 몰라도 되거든요.

참고 답:

> - `savings.ts`: 기본금리에 우대 0.5%p를 더하는 함수를 새로 만든다.
> - `SavingsHome.tsx`: 체크 상태를 두고, 적용금리로 계산한다.
> - `TermCompareSheet.tsx`: 기간마다 적용금리로 계산한다.
> - `SavingsConfirm.tsx`: "우대 포함" 문구를 보여 주고, 요청에 자동이체 여부를 넘긴다.
> - `useOpenSavingsAccount.ts`, `api.ts`: 요청 본문에 `autoTransfer`를 더한다.

## 고친 뒤에: 실제로 고친 곳은 어디였나요? "기본 금리 + 0.5%p"를 더하는 일은 어디에서 하게 했나요?

- calculateAppliedRate 함수에서 계산 했어요. 시트 같은 각 개월수에 따라 자동이체 여부에 따라 계산되어야하기 때문이였어요.

### (리뷰)

"더하는 일은 한 함수에서"라는 판단과 그 이유가 맞아요. 시트는 지금 고른 기간뿐 아니라 모든 기간의 적용금리가 필요해서, 계산기가 구한 값 하나를 넘겨받는 것으로는 부족해요. 그래서 시트가 직접 부를 수 있는 함수여야 했어요.

다만 질문의 앞부분, **실제로 고친 곳**이 빠졌어요. 이걸 적어야 첫 질문의 예상과 비교할 수 있어요. 실제로는 여섯 파일을 고쳤어요.

여섯 곳이라고 해서 많이 흩어진 건 아니에요. 고친 곳을 두 종류로 나눠 보면 보여요.

- **규칙이 바뀐 곳**: `savings.ts` 한 곳 (0.5%p를 더한다)
- **값을 실어 나르는 곳**: 나머지 다섯 곳 (`autoTransfer`나 `appliedRate`를 받아서 넘긴다)

0.5%p가 0.7%p로 바뀌면 `savings.ts`만 고치면 돼요. 나머지 다섯 곳은 "자동이체 여부라는 값이 새로 생겼다"는 이유로 한 번 고친 것이라, 우대 폭이 바뀌어도 다시 고칠 일이 없어요.

참고 답:

> `savings.ts`, `SavingsHome.tsx`, `TermCompareSheet.tsx`, `SavingsConfirm.tsx`, `useOpenSavingsAccount.ts`, `api.ts` 여섯 곳을 고쳤어요. 0.5%p를 더하는 일은 `savings.ts`의 `calculateAppliedRate` 한 곳에서만 해요. 비교 시트는 기간마다 적용금리가 필요해서 계산기가 넘겨줄 수 없고 직접 불러야 하거든요. 나머지 다섯 곳은 자동이체 여부와 적용금리를 받아 넘기기만 해요.

## 예상과 실제가 달랐다면, 문제 2에서 무엇을 다르게 했으면 좋았을까요?

기획에서 0.5%p를 0.7%p로 올려달라는 요구사항이 발생하면, 화면에 0.5%p가 그대로 노출되는 문제가 있었다. 해당 문제는 정의해둔 `AUTO_TRANSFER_RATE`를 사용하지않고, 내용에 퍼센트포인트가 그대로 노출되어있었다.

### (리뷰)

0.5가 문구 두 곳에 따로 적혀 있다는 걸 찾아서 상수로 이은 건 좋은 발견이에요. 이렇게 숫자를 상수로 묶어 두면 기획이 우대 폭을 바꿔도 상수 하나만 고치면 돼요.

그런데 이 문구들은 문제 3에서 새로 넣은 거라, 질문이 묻는 **문제 2의 결정**과는 조금 달라요. 이 질문은 "문제 2에서 만든 구조가 문제 3을 쉽게 했나, 어렵게 했나?"로 읽으면 답하기 쉬워요. 이번에는 문제 2의 결정 덕분에 쉬워진 곳이 더 많았어요.

- `calculateSavingsMaturity`가 금리를 인자로 받으니, 적용금리만 넘기면 됐어요. 함수 안은 한 줄도 안 고쳤어요.
- 가입 확인이 계산 결과를 params로 받으니, 가입 확인에서 다시 계산할 필요가 없었어요.
- 요청 보내는 코드가 `useOpenSavingsAccount` 한 곳에 있어서, `autoTransfer`를 더할 곳이 바로 보였어요.

"다르게 했으면 좋았을 것"이 없다면, **무엇이 이번 변경을 쉽게 만들었는지**를 적는 것도 좋은 답이에요.

참고 답:

> 예상에는 `formatAnnualRate`를 넣었지만 고치지 않았고, 가입 요청 경로(`useOpenSavingsAccount`, `api.ts`)는 예상에서 빠졌어요. 문제 2에서 다르게 했어야 할 곳은 크게 없었어요. 오히려 만기 계산 함수가 금리를 인자로 받게 만든 덕분에 적용금리만 넘기면 됐고, 계산 함수는 고치지 않았어요. 다음에는 고칠 곳을 예상할 때 화면만 보지 말고, 값이 서버까지 가는 길도 함께 따라가 봐야겠어요.

## (리뷰) 더 써 볼 만한 코멘트

**우대 폭 상수 이름**

`AUTO_TRANSFER_RATE`는 "자동이체 금리"로 읽혀서, 0.5%가 금리 전체인 것처럼 보여요. 실제로는 기본금리에 **더해 주는 몫**이니 `AUTO_TRANSFER_BONUS_RATE`가 더 정확해요. 용어집의 "우대 금리 → `bonusRate`"와도 맞아요. 이건 nit이에요.

**`formatAnnualRate`로 `%p` 만들기**

`` `${formatAnnualRate(AUTO_TRANSFER_RATE)}p` ``는 지금 "0.5%p"가 잘 나와요. 그런데 이 함수는 **연 금리**를 위한 함수예요. 나중에 연 금리 표시를 "3.50%"처럼 두 자리로 바꾸면, 우대 문구도 의도와 달리 "0.50%p"가 돼요. 연 금리와 금리 차이는 바뀌는 이유가 달라요. 지금은 이대로 두어도 괜찮고, 표시가 갈라질 일이 생기면 그때 `%p`용 format 함수를 따로 만들면 돼요.

## (리뷰) 다음에 비슷한 변경 요청을 볼 때

"기존 계산에 조건 하나가 더해지는" 요청은 이 순서로 보면 돼요.

**1. 이 숫자를 쓰는 곳이 어디어디인가?**

바뀌는 값(여기서는 `annualRate`)을 검색해서 쓰는 곳을 모두 찾아요. 오늘 계산기, 시트, 가입 확인 세 화면은 혼자 다 찾았어요.

**2. 그 값이 서버까지 가나?**

요청에 무언가를 "같이 보내 달라"는 말이 있으면, 버튼 → 훅 → api 함수까지 따라가요. 오늘 예상에서 빠진 곳이 여기였어요.

**3. 숫자가 글자에도 들어 있나?**

`0.5` 같은 숫자를 검색하면 계산뿐 아니라 문구에도 나와요. 계산은 상수를 따라 바뀌어도 문구는 안 바뀌어서, 화면과 실제 계산이 어긋나요. 오늘은 리뷰를 보고 찾았으니, 다음에는 고치기 전에 한 번 검색해 보세요.
