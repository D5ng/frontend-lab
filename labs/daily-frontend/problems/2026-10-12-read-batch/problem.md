# 요청에 보낸 선택과 지금의 선택

- 유형: 행동 보존 리팩터링
- 예상 시간: 30~40분
- 사용자 목표: 확인한 알림만 일괄 읽음 처리하면서, 기다리는 동안 다음 알림을 고른다.

## 핵심 설계 질문

**현재 선택과 요청에 보낸 선택을 구분하는 규칙을 어디에 모아야, 성공·실패의 변경 범위를 쉽게 확인할 수 있을까요?**

`pages/NotificationInboxPage.tsx`는 이미 동작합니다. 알림의 읽음 여부·선택·처리 대상·버튼 허용 조건·안내가 한 화면에 섞이고, 같은 조건이 여러 위치에서 반복됩니다. 파일이나 훅을 몇 개로 나눌지는 정하지 않습니다. [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성·예측 가능성·응집도·결합도를 참고하여 **외부 행동을 유지**하며 재구성하세요. 기능 추가나 버그 수정은 기본 과제가 아닙니다.

## 보존할 사용자 행동

1. 최초 알림은 안 읽은 3개와 이미 읽은 1개입니다. 아무것도 선택하지 않았고 버튼은 비활성입니다. 읽은 알림도 목록에 남으며 선택할 수 없습니다. 선택 수는 안 읽은 선택만 셉니다.
2. 안 읽은 행 전체를 누르면 선택·해제됩니다. 실제 선택 변경은 진행 중이 아닐 때 이전 결과 안내를 지웁니다. 선택된 항목이 없으면 `읽음 처리할 알림을 선택해 주세요.`를 표시합니다.
3. 실행 시 선택한 안 읽은 ID를 **목록 순서**의 배열로 한 번 보냅니다. 그 요청에 포함된 행만 잠그고 버튼은 `읽음 처리 중`으로 잠급니다. `${요청 개수}개 처리 중이에요. 다른 알림은 계속 선택할 수 있어요.`를 표시합니다. 읽음 표시는 아직 바꾸지 않습니다. 다른 안 읽은 행의 선택·해제는 계속 가능합니다. 동시 일괄 요청은 허용하지 않습니다.
4. 성공은 **요청에 포함된 알림만** 읽음으로 바꾸고 현재 선택에서 그 ID만 제거합니다. 기다리는 동안 새로 선택한 다른 알림을 지우거나 읽음으로 바꾸지 않습니다. `${요청 개수}개 알림을 읽음 처리했어요.`를 표시합니다. 성공 수는 현재 선택 수가 아닙니다. 남은 선택이 있다면 다음 일괄 처리가 가능합니다.
5. 실패는 읽음 여부와 **실패한 순간의 현재 선택**을 그대로 유지하고 `읽음 처리하지 못했어요. 현재 선택으로 다시 시도해 주세요.`를 표시합니다. 시작 당시 선택으로 되돌리지 않습니다. 버튼은 현재 선택으로 재시도할 수 있으며 새 요청 시작 시 이전 안내를 지웁니다.
6. 이미 읽은 행은 계속 잠겨 있습니다. 모두 읽은 경우 목록은 유지하고 `모든 알림을 확인했어요.`를 표시하며 버튼은 잠깁니다. 성공 안내는 새 선택 변경 또는 다음 요청 전까지 유지합니다.

실행 예: 거래 약속만 선택 → 읽음 처리 요청 → 진행 중 가격 알림을 선택 → 성공 → 거래 약속만 읽음, 가격 알림은 선택된 채 안 읽음. 실패했다면 두 선택을 모두 유지하고 다음 요청에 두 ID를 보냅니다.

## 실행 환경·API

`features/notificationInbox/types/notification.ts`의 `MarkRead`는 `(ids: string[]) => Promise<void>`입니다. `Problem`의 모의 API는 첫 요청을 1.8초 뒤 실패시키고 이후 요청은 성공시킵니다. 요청 취소·실제 외부 통신·서버 저장은 없습니다. 다른 문제로 이동하면 초기화됩니다. 최신 origin/develop의 실행 환경을 사용하며 아직 병합되지 않은 다른 출제 PR의 MSW 전환 변경을 섞지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily
pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-12-read-batch/pages/NotificationInboxPage.spec.tsx
pnpm --filter @frontend-lab/daily-frontend build
```

Daily에서 오늘 항목을 선택하거나 `#2026-10-12-read-batch`로 진입하세요. 오늘 테스트는 전부 활성입니다. `NotificationInboxPage`의 주입 경계 `markRead`를 유지하세요. 테스트는 구조나 훅 이름이 아니라 행 조작·요청 ID·읽음 표시·선택 보존을 검증합니다.

## 화면 맥락·SEED 구성

알림 목록 → 행 복수 선택 → 일괄 읽음 처리의 인라인 흐름입니다. 상세 화면을 열거나 삭제하는 목적이 아니므로 추가 시트·다이얼로그는 두지 않습니다. 선택만으로 서버 상태를 바꾸지 않으므로 Switch 대신 Checkbox 기반 공식 `List/ListCheckItem` 스니펫을 사용합니다. 전체 행이 라벨이며 내부에 별도 버튼을 넣지 않습니다. 공개 `Checkbox.Control/Indicator`를 공식 Checkmark 조합과 동일하게 사용하며, 선택 필수가 아닌 3개 항목이라 ghost·neutral·large를 사용합니다. 잠긴 읽음 행도 같은 정보 계층을 유지합니다.

요청 진행은 공식 ActionButton large·neutralSolid의 loading, 실패·성공은 공식 Callout critical/positive·alert/status입니다. 처리를 기다리는 동안 다음 선택을 할 수 있으므로 **요청에 포함되지 않은 행을 잠그지 않는 것**은 일반 폼 전체 잠금 규칙에 대한 의도적인 예외입니다. 결과와 남은 선택을 함께 확인하도록 안내는 사라지는 토스트 대신 인라인으로 유지합니다. VStack/Text와 공개 x2/x4/x6 토큰으로 배치합니다. native 컨트롤 대체재·추가 공통 스니펫은 만들지 않습니다. 지정된 SEED 기준을 출제 스킬 Montage 기준보다 우선합니다.

| 상태     | 관찰 가능한 동작                                        |
| -------- | ------------------------------------------------------- |
| Empty    | 선택 없음 또는 모두 읽음, 이유 안내·버튼 비활성         |
| Loading  | 요청 대상만 잠금, 다른 선택 가능·버튼 진행 표시         |
| Error    | 현재 목록·선택 보존, 현재 선택으로 다시 시도            |
| Disabled | 읽은 행·처리 중 행·처리 중 또는 선택 없는 버튼          |
| Success  | 요청 대상만 읽음 확정·선택 제거, 새 선택 보존·결과 유지 |

## 완료 조건

1. 활성 행동 테스트를 모두 통과하고 요청 중 새 선택·성공·실패·재시도를 화면에서도 확인합니다.
2. 변경 이유에 따라 모은 규칙과 남겨 둔 경계의 비용을 `note.md`에 직접 기록합니다.
3. 반복 조건을 줄인 것 자체보다 실제로 읽기·수정하기 쉬워진 근거를 설명합니다.

범위 밖: 전체 선택·삭제·필터·낙관적 읽음·새 알림 수신·부분 성공·실제 서버·요청 취소. 첫 검토 후 필요할 때 추가 변경 시나리오로 설계를 점검합니다.

## 출제 시 검증 범위

- 최신 origin/develop에서 별도 worktree로 작업하고 frozen lockfile 설치와 정상 훅을 사용했습니다. 오늘 문제와 최소 등록·목록 외의 변경, 다른 PR의 MSW 전환, 원본 체크아웃의 풀이를 포함하지 않습니다.
- 전체 lint·format·test·build(TypeScript 검사 포함) 통과. 오늘 테스트 7개는 전부 활성·통과, Daily 전체 32개 통과·기존 직접 구현 문제 4개 skip, code-quality 22개 통과입니다.
- 실제 브라우저 375×812에서 행 전체 선택·라벨, 요청 대상만 잠금·다른 행 선택, 실패 후 현재 선택 보존, 재시도 시 오류 제거, 성공 후 새 선택 보존, 다음 요청·모두 읽음 상태를 확인했습니다. 행 높이 66px·버튼 52px, 가로 넘침 없음(scrollWidth 375px), error/warn 로그 없음도 확인했습니다. 요청 배열·순서는 행동 테스트로 검증했습니다. 실제 휴대폰·스크린리더 음성 출력과 실제 서버는 미검증입니다.
- 설치본 React 2.5.1·CSS 2.8.3 및 CSS peer ^2.8.0을 확인했습니다. 설치된 공식 ui:list 스니펫 metadata는 React/CSS ^2.0.0 요구이며 오늘 사용하는 ListCheckItem·Checkbox.Control/Indicator·ActionButton·Callout의 타입·실제 동작은 통과했습니다. **`seed-design compat` 전체 검사는 최신 registry의 ui:list가 CSS ^3.0.0을 요구해 실패**합니다. 설치 스니펫 자체 요구 범위와 최신 registry 진단을 구분하고, 패키지·lockfile·공통 스니펫을 변경하지 않은 채 이 제한을 명시한 Draft PR로 제공합니다.
