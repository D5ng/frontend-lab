# 도착지는 바뀌었는데 이전 경로가 도착한다면?

- 날짜: 2026-10-23 (Asia/Seoul)
- 유형: **직접 구현형 · 한 페이지 과제**
- 예상 시간: **40~60분** (AUTHORING 기준 우선)
- 사용자 목표: 도착지를 바꾸어 경로를 비교하고, 선택한 한 경로의 이동 계획을 확인합니다.

## 과제 범위

`pages/RoutePlannerPage.tsx`의 페이지를 처음부터 완성하세요. 시작 코드는 SEED 제목·설명·레이아웃 골격만 있으며 조회·선택·상태 처리는 구현하지 않았습니다. 정답 코드·훅 이름·분리 구조를 제공하지 않습니다. 파일 수나 훅 수를 정답으로 삼지 않습니다.

재료는 **도착지 선택, 서버 경로 조회, 경로 단일 선택과 결과 영역**입니다. 시간 상한 입력·필터·정렬은 추가하지 않습니다. 출발지는 가상의 `우리 동네 정류장`으로 고정하며 지도·실제 교통 정보·위치 권한·예매·저장 API는 없습니다. 도착지와 노선은 실습용 가상 데이터입니다.

## 기능별 요구사항

### 1. 도착지와 조회

- `도착지` 그룹에서 강변공원(`park`), 시립미술관(`museum`), 새벽부두(`pier`) 중 하나를 선택합니다. 기본값은 강변공원입니다. 진입하면 기본 도착지를 조회합니다.
- 다른 도착지를 선택하면 즉시 해당 도착지를 조회합니다. 이미 선택된 같은 라디오를 다시 누르는 것은 새 조회가 아닙니다. 이전 도착지로 돌아오는 실제 변경은 새 조회입니다. 캐시는 사용하지 않습니다.
- `경로 다시 불러오기` 버튼은 현재 도착지를 다시 조회합니다. 조회 중에는 이 버튼을 비활성화해 중복 재조회를 막습니다. 버튼의 접근성 이름에 이 문구를 유지하세요.
- **조회 중에도 도착지는 바꿀 수 있습니다.** 다른 목적지로 빠르게 비교할 수 있게 하기 위한 의도적인 예외입니다. 제출 폼이 아니며 도착지 변경을 막는 방식으로 경쟁 응답 문제를 없애지 마세요.
- 새 조회는 이유에 관계없이 이전 목록·선택·이동 계획·조회 오류를 즉시 지웁니다. 같은 도착지 재조회도 동일합니다. 이전 목록을 대기 중에 남기거나, 실패 후 복원하지 않습니다.
- 조회 중에는 `경로를 불러오고 있어요.`를 표시합니다. 경로 목록은 아직 없으므로 경로 선택은 할 수 없고 이동 계획은 미선택 안내를 표시합니다. 조회 중을 빈 결과 성공으로 표현하지 않습니다.
- **마지막으로 시작한 조회만** 목록·오류·로딩 종료를 반영합니다. 오래된 성공·실패·종료 처리는 현재 화면을 바꾸면 안 됩니다. 공원 → 미술관 → 공원처럼 같은 도착지로 돌아와도 첫 공원 조회와 마지막 공원 조회는 다른 요청입니다.
- 현재 요청이 실패하면 `경로를 불러오지 못했어요. 다시 시도해 주세요.`를 표시합니다. 도착지는 유지하고 재조회 버튼과 다른 도착지 선택을 허용합니다. 자동 재시도는 하지 않습니다.
- 현재 요청이 성공하면 응답 배열 순서 그대로 경로를 표시합니다. `[]`면 `이 도착지로 가는 경로가 없어요. 다른 도착지를 골라 주세요.`를 표시하고 도착지 선택과 재조회를 허용합니다. 오류와 빈 성공은 다른 상태입니다.

### 2. 경로와 이동 계획

- 각 경로에는 제목, `N분`, `환승 N회`를 표시하며 라디오 방식으로 하나만 선택할 수 있습니다. 선택 컨트롤의 접근성 이름에 제목을 포함합니다. 노선별 별도 상세 화면은 만들지 않습니다.
- 접근성 이름이 `이동 계획`인 region을 둡니다. 미선택이면 `아직 경로를 고르지 않았어요.`를 표시합니다. 선택하면 **현재 도착지 이름·경로 제목·소요 시간·환승 횟수**를 보여 줍니다.
- 다른 도착지에는 같은 경로 ID가 있을 수 있습니다. 이전 도착지의 제목이나 시간을 새 도착지의 계획으로 재사용하면 안 됩니다.
- 이 과제에서 **조회 성공 직후 첫 경로를 자동으로 고를지는 정하지 않았습니다.** 미선택으로 시작하거나 새 응답에서 일관된 기준으로 고르는 것 중 하나를 선택하고 note에 이유를 적으세요. 이 판단 자체를 고정하는 테스트는 없습니다. 다만 조회 시작 시 이전 선택을 지우는 규칙은 반드시 지킵니다.
- 선택만 바꾸는 동작은 API를 호출하지 않습니다. 경로를 고르면 이동 계획이 바뀌는 것으로 사용자 목표가 끝나며 별도 완료·신청 버튼은 없습니다.

## 작은 상황

공원 조회 A가 진행 중일 때 미술관 B로 바꾸고, 다시 공원 C로 돌아왔습니다. A의 성공이 C보다 먼저 왔다면 공원이라는 이유만으로 표시해도 될까요? 화면이나 테스트에서 순서를 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**현재 도착지의 결과라는 약속은 ‘도착지 값이 같다’만으로 지킬 수 있을까요? 조회와 경로 선택이 서로 다른 시점의 데이터를 섞지 않도록 책임을 어디에 두겠어요?**

원본 데이터와 파생 결과, 선택 기준의 해석, 변경 시 지워야 할 범위와 그 비용을 note에 직접 설명하세요. 특정 구현 기법을 답으로 지정하지 않습니다.

## API 명세

```ts
type Destination = 'park' | 'museum' | 'pier'
interface Route {
  id: string
  title: string
  minutes: number
  transfers: number
}
type LoadRoutes = (destination: Destination) => Promise<Route[]>
```

`GET /api/daily/2026-10-23/routes?destination=park` 형식으로 요청하며 본문은 없습니다. `features/routePlanner/apis/fetchRoutes.ts`는 공통 HTTP 클라이언트를 사용하고 `Problem.tsx`가 세션별 `loadRoutes`를 페이지에 주입합니다. `handlers.ts`는 공통 MSW에 자동 등록됩니다. API/MSW는 제공 환경이며 화면 상태나 응답 반영 여부를 대신 관리하지 않습니다. AbortSignal은 제공하지 않습니다.

| 도착지     | 지연·응답                                                   |
| ---------- | ----------------------------------------------------------- |
| 강변공원   | 약 1.2초. 세션의 첫 공원 요청만 HTTP 503, 이후 아래 두 경로 |
| 시립미술관 | 약 0.35초. 첫 요청부터 아래 두 경로                         |
| 새벽부두   | 약 0.65초. 성공 `[]`                                        |

| 도착지     | ID       | 제목          | 소요 시간 | 환승 |
| ---------- | -------- | ------------- | --------- | ---- |
| 강변공원   | direct   | 강변 버스     | 32분      | 0회  |
| 강변공원   | transfer | 공원 환승선   | 25분      | 1회  |
| 시립미술관 | direct   | 미술관 순환선 | 28분      | 0회  |
| 시립미술관 | transfer | 미술관 급행선 | 19분      | 1회  |

실패 횟수는 도착지와 API 세션별로 구분합니다. 화면 재진입 시 공원 첫 실패부터 다시 시작합니다. 함수 주입 행동 테스트는 기본 시나리오에 없는 늦은 성공·실패·재조회 실패도 만듭니다. 실제 지연 시간에 의존하지 않고 Promise의 완료 순서를 제어합니다.

## UI와 상태 설계

375px에서 목적 → 고정 출발지·도착지 → 조회 상태·재조회 → 경로 목록 → 이동 계획 순으로 읽습니다. 짧은 목적지·경로 선택은 비교 맥락을 유지하도록 인라인으로 두며 모달·시트·다음 단계는 추가하지 않습니다.

| 역할                          | 설치된 공식 SEED 대응                                  |
| ----------------------------- | ------------------------------------------------------ |
| 도착지 3개 선택               | RadioGroup/RadioGroupItem 공식 스니펫, 그룹 라벨       |
| 경로 단일 선택·제목·세부 정보 | RadioGroup/RadioGroupItem 또는 ListRadioItem 공식 조합 |
| 재조회·대기·비활성            | ActionButton 공식 스니펫, 대기 안내와 비활성 이유      |
| 조회 오류·빈 성공             | Callout 공개 파츠와 재시도/다른 도착지 액션            |
| 목록 대기·정보 계층·요약      | Skeleton/진행 안내, Text/VStack 등 공개 API            |

같은 역할을 native Radio/Button에 토큰만 입혀 대신하지 마세요. 설치된 스니펫의 실제 props·공개 타입을 확인하고 48px 이상의 선택 영역을 확보하세요. 기본 스타일보다 최소 높이가 실제로 우선하는지 실측합니다. 라디오·버튼 외 텍스트 입력은 요구하지 않으므로 TextField를 장식용으로 추가하지 않습니다.

진입·변경·재조회 → 목록/선택 초기화 + Loading → 최신 Success 또는 Error입니다. 성공 목록에서 경로를 고르면 이동 계획이 표시됩니다. 빈 성공은 다른 목적지 선택을 안내합니다. 조회 중 재조회 비활성/도착지 활성의 차이를 화면에서 설명합니다. 기능 UI는 실습자가 구현하므로 골격에서 이러한 상태가 동작한다고 주장하지 않습니다.

## 실행과 완료 조건

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-23-route-planner
```

오늘 PR의 별도 worktree에서 실행하고 Daily 메뉴 또는 `http://localhost:5173/#2026-10-23-route-planner`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 백엔드 설치는 필요 없습니다.

1. `pages/RoutePlannerPage.spec.tsx`의 실습자 블록 `describe.skip`을 `describe`로 바꾸어 행동 테스트 9개를 통과하세요. 제목 골격 1개와 HTTP 계약 5개도 유지합니다. 구현 전 행동 9개는 의도적으로 실행하지 않으며 통과했다고 간주하지 않습니다.
2. 375px 화면에서 첫 실패·재시도, 조회 중 도착지 변경, 공원 → 미술관 → 공원 순서, 빈 결과·경로 선택을 확인하세요. 오래된 성공·실패·종료 처리도 테스트로 확인합니다.
3. note의 빈 항목에 직접 해석·책임·선택·검증을 기록하세요. 행동을 삭제하거나 테스트를 다시 skip해 통과시키지 않습니다.

AUTHORING은 로컬 `docs/daily-assignment-guide` 브랜치에서 읽어 적용했습니다(원본/develop에는 아직 없음). 그 브랜치나 다른 출제 PR 변경은 포함하지 않았습니다. 외부 문제·코드·풀이를 사용하지 않았습니다. 정확한 검증 범위와 미완료 상태는 `verification.md`에 기록합니다.
