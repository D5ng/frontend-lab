# 시간에 맞는 오늘의 강좌 고르기

- 날짜: 2026-10-21 (Asia/Seoul)
- 유형: **직접 구현형 · 한 페이지 과제**
- 예상 시간: **40~60분** (AUTHORING 기준 우선)
- 사용자 목표: 오늘 쓸 수 있는 시간에 맞는 강좌 하나를 골라 학습 계획을 확인합니다.

## 과제 범위

요구사항을 읽고 한 페이지를 처음부터 완성하세요. 제공된 페이지는 제목·설명·SEED 레이아웃만 있으며 조회·입력·필터·선택을 구현하지 않았습니다. 별도 완성 UI나 상태·훅 구조, 로직 답안을 제공하지 않습니다. 파일·훅 개수나 중복 제거 자체는 정답이 아닙니다.

재료는 **서버 목록 조회, 학습 시간 입력, 조건에 따른 목록, 단일 선택** 네 가지입니다. 결제·수강 신청·다음 페이지·선택 저장 API는 없습니다. 강좌를 고르면 이 페이지의 학습 계획이 바뀌는 것이 최종 결과입니다.

## 기능별 요구사항

### 1. 강좌 조회

- 진입하면 제공 API를 한 번 호출합니다. 최초 완료 전에는 `강좌를 불러오고 있어요.`를 표시합니다.
- `강좌 다시 불러오기` 버튼을 둡니다. 조회 중에는 재조회·시간 입력·모든 강좌 선택을 잠그고 중복 요청을 보내지 않습니다.
- 최초 조회 실패는 `강좌를 불러오지 못했어요. 다시 시도해 주세요.`와 재시도 액션을 제공합니다. 실패를 빈 목록 성공으로 표시하지 않습니다. 실패 뒤 재시도 버튼은 사용할 수 있어야 합니다.
- 이미 성공한 목록이 있는 상태에서 재조회하면 **기존 목록과 계획을 표시한 채** 조작을 잠급니다. 새 요청을 시작할 때 이전 조회 오류를 지웁니다.
- 재조회 실패는 기존 목록·시간 입력·선택·계획을 보존하고 같은 오류 문구를 추가합니다. 자동 재시도하지 않습니다.
- 재조회 성공은 최신 목록으로 교체합니다. 새 목록과 현재 시간 조건에 맞는 기존 선택 ID가 있으면 유지하고 **새 제목·시간**으로 계획을 갱신합니다. ID가 없어졌거나 새 재생 시간이 상한을 넘으면 선택을 해제합니다.

### 2. 학습 시간과 목록

- 이름이 `학습 시간 상한`인 입력을 둡니다. 단위는 분입니다. 처음에는 비어 있고 모든 강좌를 보여 줍니다.
- 숫자만 남기며 최대 3자리로 제한합니다. 빈 값은 제한 없음이고, 값이 있으면 1~180의 정수만 유효합니다. 즉시 입력 상태를 반영합니다.
- 범위 밖이면 필드에 `1분부터 180분까지 입력해 주세요.`를 표시하고 선택 가능한 강좌를 비웁니다. 이때 선택도 해제합니다. 올바른 값으로 바꾸면 필드 오류를 지웁니다.
- 유효한 상한 이하의 강좌만 표시합니다. 예를 들어 30이면 30분 강좌도 포함합니다. 상한 입력 자체로 API를 다시 호출하지 않습니다.
- 목록은 재생 시간이 짧은 강좌부터 정렬합니다. **같은 시간의 강좌를 어떤 순서로 둘지는 정해지지 않았습니다.** 일관된 기준을 정하고 이유를 note에 적으세요. 이 판단을 채점하는 고정 순서 테스트는 없습니다.
- 서버 응답 자체가 `[]`면 `등록된 강좌가 없어요.`를 표시합니다. 원본 목록은 있는데 조건에 맞는 강좌가 없으면 `시간에 맞는 강좌가 없어요. 상한을 늘려 보세요.`를 표시합니다. 입력 오류일 때는 이 두 정상 빈 결과 문구로 대체하지 않습니다.

### 3. 강좌 선택과 학습 계획

- 각 강좌는 제목·재생 시간을 표시하고, 라디오 방식으로 하나만 고를 수 있습니다. 선택 컨트롤의 접근성 이름에 강좌 제목을 포함합니다.
- 이름이 `학습 계획`인 영역을 둡니다. 미선택이면 `아직 강좌를 고르지 않았어요.`, 선택하면 해당 강좌 제목과 `N분`을 표시합니다.
- 시간 입력이 바뀌어 선택한 강좌가 보이지 않게 되면 선택을 해제합니다. 조건을 다시 늘려 그 강좌가 나타나도 자동으로 재선택하지 않습니다. 선택한 강좌가 계속 보이면 선택과 계획을 유지합니다.
- 입력은 매 조작마다 반영됩니다. 예를 들어 30을 타이핑하는 중 잠시 3이 되면 3분 조건이 적용될 수 있습니다. 경계값 단독 확인은 붙여넣기로 해도 됩니다. 입력 확정 시점이나 debounce는 추가하지 않습니다.

## API 명세

```ts
interface Course {
  id: string
  title: string
  minutes: number
}
type LoadCourses = () => Promise<Course[]>
```

`GET /api/daily/2026-10-21/courses`를 호출하며 요청 본문·query는 없습니다. `features/coursePlan/apis/fetchCourses.ts`가 공통 fetch 클라이언트를 사용하고 `Problem.tsx`가 페이지에 `loadCourses`를 주입합니다. `handlers.ts`는 공통 MSW에 자동 등록됩니다.

모의 환경은 요청마다 약 0.8초가 걸립니다. 세션 첫 요청은 HTTP 503, 두 번째는 다음 4개 강좌입니다. 세 번째 이후는 `story`가 빠지고 `voice`가 `발표 호흡 다듬기`/25분으로 바뀝니다. API 공장 세션은 페이지 재진입마다 분리됩니다.

| ID     | 제목                 | 재생 시간 |
| ------ | -------------------- | --------- |
| photo  | 사진 구도 익히기     | 60분      |
| voice  | 발표 목소리 연습     | 30분      |
| sketch | 색으로 정리하는 메모 | 15분      |
| story  | 짧은 글 구조 잡기    | 30분      |

API는 화면 필터·정렬·선택을 관리하지 않습니다. 함수 주입 테스트에서는 빈 응답과 재조회 실패도 만듭니다. 기본 모의 시나리오만 보고 오류 처리를 생략하지 마세요.

## 핵심 설계 질문

**입력 조건과 서버 목록이 각각 바뀔 때, ‘현재 고른 강좌’가 여전히 유효하다는 약속을 누가 지켜야 할까요? 원본 데이터와 계산 결과를 어디까지 나눌까요?**

같은 시간 정렬의 해석, 보존할 데이터와 파생할 값, 선택한 경계의 장단점을 직접 설명하세요. 특정 상태 구조·함수 이름·폴더 분리를 답으로 지정하지 않습니다.

## UI와 실행 환경

375px 모바일에서 제목 → 시간 조건 → 조회 상태·다시 불러오기 → 강좌 목록 → 학습 계획 순으로 구성합니다. 조건과 선택은 같은 맥락에서 읽을 수 있도록 두고, 단일 선택에 모달·다음 단계·저장 버튼은 추가하지 않습니다.

설치된 공식 SEED를 사용합니다. 같은 역할을 native로 대체하지 마세요. 텍스트 필드는 `TextField`/`TextFieldInput`, 강좌 단일 선택은 `RadioGroup`/`RadioGroupItem` 또는 공식 ListRadioItem 조합, 재조회는 `ActionButton`, 오류·안내는 `Callout`, 조회 중 표현은 `Skeleton`/진행 안내, 제목·배치는 공개 `Text`/`VStack`을 검토하세요. 입력 라벨·그룹 이름·비활성 이유를 제공하고 모바일 터치 영역은 48px 이상 확보합니다. UI 골격은 이 컴포넌트 분할을 미리 구현하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-21-course-plan
```

별도 worktree에서 실행하고 Daily 메뉴 또는 `http://localhost:5173/#2026-10-21-course-plan`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 서버 설치는 필요 없습니다.

## 완료 조건

1. `pages/CoursePlanPage.spec.tsx`의 실습자 행동 블록 `describe.skip`을 `describe`로 바꿔 8개를 통과합니다. 제공 제목 검사 1개·HTTP 계약 3개도 유지합니다. 구현 전 행동 8개는 의도적으로 실행하지 않습니다.
2. 실제 화면에서 최초 실패·재시도, 시간 조건 변경에 따른 선택 해제, 재조회 성공 후 변경된 강좌/사라진 강좌를 확인합니다. 구현을 대신해서 테스트를 삭제하거나 skip하지 않습니다.
3. `note.md`의 지정된 빈 항목에 상태·해석·책임·검증 근거를 직접 기록합니다. 후속 점검 질문은 풀이 후 별도로 다룹니다.

AUTHORING은 로컬 `docs/daily-assignment-guide` 브랜치에서 읽었습니다(원본/develop에는 아직 없음). 해당 브랜치의 다른 변경은 포함하지 않았습니다. 문제는 저장소 실습만 참고해 새로 작성했고 외부 과제·코드·풀이를 사용하지 않았습니다. 정확한 출제 검증 범위는 `verification.md`에 기록합니다.
