# 기기마다 따로 끝나는 연결 해제

- 날짜: 2026-10-26 (Asia/Seoul)
- 유형: **리팩터링형**
- 예상 시간: **30~40분**
- 사용자 목표: 현재 기기는 유지하고 사용하지 않는 다른 기기의 가상 연결을 끊습니다.

## 과제

`pages/DeviceSessionsPage.tsx`는 이미 동작합니다. 외부 행동을 유지하면서 가독성·예측 가능성·응집도·결합도를 근거로 재구성하세요. 기능 추가나 버그 수정은 과제가 아닙니다. 먼저 현재 책임과 상태의 원본, 함께 바뀌는 규칙을 설명한 뒤 필요한 경계만 선택하세요. 파일·훅 개수나 중복 제거 자체는 정답이 아니며 권장 정답 구조는 제공하지 않습니다.

**실습용 가상 기기와 모의 API만 사용합니다. 실제 계정·토큰·로그인·기기 연결은 바뀌지 않습니다.** 실제 서비스의 보안 정책을 재현하거나 제안하는 과제가 아닙니다.

## 관찰 가능한 요구사항

### 목록과 현재 기기

- 시작 목록은 집 노트북(`current`, 현재 기기), 외출용 휴대폰(`phone`), 서재 태블릿(`tablet`)입니다. 별도 초기 조회는 없습니다.
- 이름이 `연결된 기기`인 목록에 이름·현재/다른 기기 설명을 표시합니다. 버튼의 접근성 이름은 `기기명 연결 끊기`입니다.
- 현재 기기 버튼은 항상 비활성화하고 `현재 기기`라고 표시합니다. 화면에서 현재 기기의 해제 요청을 보내지 않습니다. 제공 모의 API도 해당 ID를 거절합니다.
- 목록 순서는 유지합니다. 해제 성공한 항목만 제거하고 나머지를 재정렬하지 않습니다.

### 기기별 요청과 결과

- 다른 기기의 버튼을 누르면 그 ID 한 개를 API에 보냅니다. 성공 전에는 목록에 남아 있으며 낙관적으로 제거하지 않습니다.
- 요청 중에는 **그 기기의 버튼만** 로딩·비활성 상태로 바꿉니다. 같은 기기에 중복 요청하지 않습니다. 다른 기기는 계속 요청할 수 있습니다. 기기별 요청은 서로 독립적이므로 전체 화면을 잠그지 않습니다.
- 요청 시작 시 해당 기기의 이전 오류만 지웁니다. 다른 기기의 오류·진행 상태는 유지합니다.
- 성공하면 해당 기기를 목록에서 제거하고 해당 기기 오류를 지웁니다. 이미 성공해서 사라진 다른 기기를 다시 복원하지 않습니다.
- 실패하면 해당 기기를 목록에 남기고 버튼을 다시 활성화합니다. `기기명 연결을 끊지 못했어요. 다시 시도해 주세요.`를 표시하며 같은 버튼으로 재시도합니다. 자동 재시도는 없습니다.
- 오류는 목록 아래에 기기 이름을 포함한 안내로 표시합니다. 두 기기가 실패하면 두 오류를 모두 표시합니다. 한 기기의 성공·재시도가 다른 기기의 오류를 지우면 안 됩니다.
- 완료 순서는 요청 순서와 다를 수 있습니다. 늦은 실패·성공·종료 처리가 다른 기기의 제거·진행 상태를 덮어쓰지 않아야 합니다. 같은 시점에 두 성공이 도착해도 두 항목이 모두 사라져야 합니다.
- `연결을 끊은 기기 N개`는 성공해서 제거된 수를 나타냅니다. 실패·대기 중에는 수가 늘어나지 않습니다.
- 다른 기기가 모두 제거되면 `다른 기기 연결을 모두 끊었어요.`를 표시합니다. 현재 기기는 계속 목록에 남으므로 전체 목록이 빈 화면이 되지는 않습니다.
- 재진입하면 고정 초기 목록과 실패 시나리오부터 다시 시작합니다. 기기 추가·이름 변경·재조회·복구·전체 해제·확인 모달·실제 인증은 범위 밖입니다.

## 작은 상황

휴대폰 A와 태블릿 B의 해제를 차례로 눌렀습니다. B는 먼저 성공해 사라지고 A는 나중에 실패했습니다. A의 오류가 표시될 때 B가 다시 나타나거나 성공 수가 0이 되면 어떤 약속이 깨진 걸까요? 화면과 테스트를 실행해 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**목록에서의 존재, 진행 중 여부, 오류가 각각 같은 기기를 가리켜야 합니다. 서로 다른 시점에 끝나는 작업이 남의 상태를 건드리지 않도록, 변경 책임과 사용하는 쪽의 약속을 어디에 두겠어요?**

현재 코드가 무엇을 함께 갱신하는지부터 확인하세요. 분리로 읽기 쉬워지는 부분과 호출자의 인자·간접 참조·동기화 약속이 늘어나는 비용을 비교합니다. 특정 저장 방식·상태 개수·훅 구조를 답으로 지정하지 않습니다.

## API와 실행 환경

```ts
interface DeviceSession {
  id: string
  name: string
  current: boolean
}
type EndSession = (id: string) => Promise<void>
```

`DELETE /api/daily/2026-10-26/sessions/:id`이며 query·본문은 없습니다. 성공은 HTTP 204입니다. `features/deviceSessions/apis/endSession.ts`는 공통 HTTP 클라이언트를 사용하고 `Problem.tsx`가 세션별 API를 페이지에 주입합니다. `handlers.ts`는 공통 MSW에 자동 등록됩니다. API/MSW는 제공 환경이며 이번 리팩터링 대상이 아닙니다.

| ID      | 모의 응답                                        |
| ------- | ------------------------------------------------ |
| phone   | 약 1.1초. 세션의 해당 기기 첫 요청 503, 이후 204 |
| tablet  | 약 0.4초. 세션의 해당 기기 첫 요청 503, 이후 204 |
| current | 403                                              |
| 그 외   | 404                                              |

실패 횟수는 기기와 API 세션별로 분리합니다. 태블릿 요청이 휴대폰의 첫 실패를 소비하지 않습니다. HTTP 오류는 Error로 변환하고 204는 undefined로 반환합니다. 행동 테스트에서는 Promise 완료 순서를 직접 제어하며 실제 타이머를 암기할 필요는 없습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-26-device-sessions
```

오늘 PR의 별도 worktree에서 실행하고 Daily 메뉴 또는 `http://localhost:5173/#2026-10-26-device-sessions`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 서버 설치는 필요 없습니다.

## 화면 맥락과 SEED 대응

375px에서 목적 → 현재 기기 보호/진행 단위 안내 → 기기 목록과 개별 액션 → 기기별 오류 → 완료 수/전체 완료 순으로 읽습니다. 짧은 세 항목은 인라인 목록으로 비교하고, 가상 연결 해제의 결과는 항목 제거·완료 수·지속되는 안내로 확인합니다. 되돌릴 수 없는 실제 데이터 삭제는 없으며 확인 모달은 학습 주제 밖이라 추가하지 않습니다.

| 역할                            | 설치된 공식 대응                              |
| ------------------------------- | --------------------------------------------- |
| 기기명·현재 기기 설명·개별 액션 | 공식 List/ListItem 스니펫, detail/suffix 슬롯 |
| 연결 해제·기기별 로딩/비활성    | 공식 ActionButton, large/neutralWeak          |
| 기기별 오류·모두 완료           | 공개 Callout, critical/alert·positive/status  |
| 제목·설명·완료 수·여백          | 공개 Text/VStack, 완료 수의 aria-live         |

native 컨트롤 대체 예외는 없습니다. 필드나 라디오 선택이 없는 과제이므로 장식용으로 추가하지 않습니다. 현재 기기·요청 중 기기의 비활성 이유를 설명하고, 같은 요청에 관련된 조작은 그 기기 단위로 잠급니다. 초기 조회 로딩·전체 빈 목록은 해당하지 않습니다.
