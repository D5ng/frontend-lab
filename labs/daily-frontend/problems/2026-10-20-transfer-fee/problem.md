# 받는 금액과 출금액은 언제 달라질까?

- 날짜: 2026-10-20 (Asia/Seoul)
- 유형: **리팩터링형**
- 예상 시간: **30~40분**
- 사용자 목표: 보낼 금액과 수수료를 확인하고, 선택한 계좌로 연습용 송금 신청을 한 번 완료합니다.

## 과제

`pages/TransferPage.tsx`는 이미 동작합니다. 외부 동작을 유지하면서 가독성·예측 가능성·응집도·결합도를 근거로 재구성하세요. 기능 추가나 버그 수정은 과제가 아닙니다. 현재 규칙과 책임을 먼저 설명하고 필요한 경계만 선택합니다. 파일·훅 개수나 중복 제거 자체는 정답이 아닙니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-20-transfer-fee
```

오늘 PR의 별도 worktree에서 실행합니다. Daily 메뉴 또는 `http://localhost:5173/#2026-10-20-transfer-fee`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 백엔드는 필요 없습니다. 실제 계좌·개인정보를 입력하지 않으며 실제 돈도 이동하지 않습니다. 모든 금액과 수수료는 실습 전용 가상 규칙입니다.

## 입력과 관찰 가능한 요구사항

### 계좌와 금액

- 출금 계좌는 생활비 계좌(잔액 60,000원), 용돈 계좌(잔액 10,000원) 두 개이며 생활비가 기본값입니다. 별도 목록 조회는 하지 않습니다.
- 받는 은행은 같은 은행/다른 은행 두 개이며 같은 은행이 기본값입니다. 수취인은 가상으로 고정하며 계좌번호 입력은 없습니다.
- 금액은 처음에 비어 있습니다. 숫자가 아닌 문자는 제거하고 최대 7자리 숫자로 입력을 제한합니다. 화면에는 한국어 천 단위 구분 기호를 표시합니다. 빈 금액이면 제출할 수 없습니다.
- 제출 가능한 금액은 **1,000원 이상 1,000,000원 이하의 정수**입니다. 범위를 벗어나면 필드에 `1,000원부터 1,000,000원까지 입력해 주세요.`를 표시하고 요청하지 않습니다.

### 수수료·잔액·요청의 일관성

- 같은 은행은 수수료 0원입니다. 다른 은행은 보낼 금액이 50,000원 미만이면 500원, **50,000원 이상이면 0원**입니다. 금액이 비어 있거나 0이면 화면 수수료와 총 출금액은 0원입니다.
- 받는 금액은 입력 금액이고 총 출금액은 입력 금액 + 수수료입니다. 출금 요약을 즉시 갱신합니다.
- 총 출금액이 선택한 계좌 잔액보다 많으면 `수수료를 포함한 출금액이 잔액보다 많아요.`를 표시하고 요청하지 않습니다. **잔액과 같으면 허용**합니다. 금액 범위 오류를 먼저 검사합니다.
- 요청은 선택한 계좌·은행·입력 금액·수수료·총 출금액을 전송합니다. 화면 요약과 요청 금액이 달라지면 안 됩니다.
- 계좌·은행·금액을 바꾸면 이전 실패·검증 안내를 지웁니다. 계좌나 은행을 바꾸어도 작성한 금액은 유지합니다.

### 비동기 신청

- 요청 중 계좌·은행·금액·제출을 모두 잠그고 `신청 중`과 대기 안내를 표시합니다. 중복 클릭으로 요청을 늘리지 않습니다.
- 실패하면 `송금 신청을 완료하지 못했어요. 다시 시도해 주세요.`를 표시하고 모든 입력을 보존합니다. 자동 재시도하지 않고 같은 버튼으로 다시 신청합니다.
- 성공하면 **서버 응답의 금액**으로 신청 완료 안내를 표시합니다. 입력·요약은 유지하고 모든 조작과 재신청을 잠급니다. 성공 상태를 지우거나 새 신청을 시작하는 기능은 없습니다. 화면을 다시 열면 초기 상태로 돌아갑니다.
- 이번 과제는 한 건의 가상 신청이므로 잔액 재조회·차감 화면, 실제 은행 연결, 환율, 인증, 예약 송금, 반복 송금은 범위 밖입니다.

### 작은 상황

용돈 계좌에서 다른 은행으로 10,000원을 보낸다면 받는 금액은 잔액과 같습니다. 그래도 신청이 거절되는 이유는 무엇인가요? 은행만 바꾸면 같은 입력으로 신청할 수 있을까요? 화면을 보거나 테스트를 실행해 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**화면 요약·잔액 검증·요청 데이터는 같은 수수료 규칙을 지켜야 합니다. 이 규칙의 변경이 한쪽에만 적용되는 실수를 줄이려면 책임을 어디에 두겠어요?**

가독성은 결과와 판단 흐름을 찾기 쉬운지, 예측 가능성은 이름과 실제 동작이 맞는지, 응집도는 함께 바뀌는 규칙이 가까운지, 결합도는 쓰는 쪽이 지킬 약속이 얼마나 남는지로 점검해 보세요. 공통화가 오히려 인자·간접 참조를 늘리는 비용도 비교합니다. 권장 정답 구조는 제공하지 않습니다.

## API

`features/transfer/apis/sendTransfer.ts`는 공통 HTTP 클라이언트를 인자로 받아 요청 한 건을 전송합니다. `Problem.tsx`가 화면 재진입별 세션을 만들고 페이지에 API 함수를 주입합니다.

```ts
interface TransferInput {
  accountId: string
  bank: 'same' | 'other'
  amount: number
  fee: number
  totalDebit: number
}
interface TransferReceipt extends TransferInput {
  id: string
}
type SendTransfer = (input: TransferInput) => Promise<TransferReceipt>
```

`POST /api/daily/2026-10-20/transfers`에 JSON 본문을 보냅니다. 약 0.9초 뒤 세션 첫 요청은 HTTP 503, 이후 요청은 보낸 본문과 신청 ID를 포함한 성공 응답입니다. 공통 MSW가 브라우저와 테스트에서 같은 HTTP 경로를 모킹합니다. API/MSW는 수수료 계산이나 화면 상태를 관리하지 않으며 이번 풀이 대상이 아닙니다.

## 화면 맥락과 SEED 대응

375px에서 출금 계좌 → 받는 은행 → 금액 → 요약 → 결과 → 주요 신청 액션 순으로 읽습니다. 선택·입력·요약·제출은 같은 form 안에 있습니다. 두세 개의 고정 선택은 인라인으로 두고 모달·시트·장식용 카드를 추가하지 않습니다. 신청 결과는 다시 확인할 수 있도록 인라인에 남깁니다.

| 역할                  | 설치된 공식 대응                                                                |
| --------------------- | ------------------------------------------------------------------------------- |
| 출금 계좌·은행 선택   | 공식 `RadioGroup`/`RadioGroupItem` 스니펫, 각각 그룹 라벨과 선택 이름           |
| 금액·형식·검증        | 공식 `TextField`/`TextFieldInput` 스니펫, numeric 입력 모드·필드 라벨·오류·단위 |
| 주요 신청·로딩·비활성 | 공식 `ActionButton`, large/neutralSolid                                         |
| 성공·오류             | 공개 `Callout` 파츠, positive/status·critical/alert                             |
| 제목·요약·여백        | 공개 `Text`/`VStack`와 공개 props                                               |

공식 역할을 native 요소로 대체한 예외는 없습니다. 성공 후 모든 조작을 잠그는 이유와 빈 입력·요청 중 비활성 이유를 화면에 표시합니다. 별도 서버 목록이 없으므로 목록 빈 결과·초기 조회 로딩은 해당하지 않습니다.
