# 풀이 기록

구현하면서 내린 결정마다 멘토가 "어떤 근거로, 왜 그렇게 했어요?"를 묻습니다. 각 항목의 **상황**은 문제나 코드에 있는 사실이고, 그 아래 질문에 본인 말로 답합니다. 꼬리 질문은 첫 답을 쓴 뒤에 읽어도 됩니다. 줄 번호는 `neighborhoodFeed/useNeighborhoodPosts.ts` 기준입니다.

## 1. 늦게 도착한 성공 응답

**상황**: 성수동 응답은 1.8초, 망원동 응답은 0.7초가 걸리고 망원동은 빈 목록을 돌려준다. 진입하자마자 망원동을 누르면 망원 응답이 먼저 오고 성수 응답이 나중에 온다. 오래된 응답을 거르는 장치가 하나도 없는 아래 코드에서 출발한다.

```ts
useEffect(() => {
  setLoading(true)
  setError('')
  setPosts([])

  func(neighborhood)
    .then((data) => setPosts(data))
    .catch(() => setError(NEIGHBORHOOS_ERROR_MESSAGE))
    .finally(() => setLoading(false))
}, [func, neighborhood])
```

> "위 코드라면 0.7초와 1.8초에 화면이 각각 어떻게 보여요? 1.8초에 제목은 어느 동네고 목록은 어느 동네 거죠?"

0.7초 시점에는 망원 동네와, 망원에 게시글이 보여요. 정확히는 망원에 게시글이 없기 때문에 빈 목록으로 화면에 보여요. 그리고 1.8초가 지난 시점에는 성수에 대한 응답이오면서 상태를 업데이트해요. 따라서 동네는 망원이지만, 성수에 대한 글 목록 데이터가 보여요

---

**멘토**: 정확해요. 0.7초에는 빈 목록 안내가 맞게 뜨고, 1.8초에 늦은 성수 응답이 그걸 덮어서 "망원동 게시글" 제목 아래에 성수 게시글이 깔려요. 시점을 둘로 나눠 답한 덕분에 "처음엔 맞았는데 나중에 틀어진다"는 게 잘 보여요. 사용자 입장에서는 망원동 중고거래를 보러 들어왔는데 성수 물건을 보고 연락하게 되는 장면이에요.

> 꼬리 질문: "지금 코드는 이 성수 응답을 어떻게 버려요? 요청을 보낼 때 무엇이 생기고(16번째 줄), 망원동을 누른 순간 무엇이 바뀌고(41~43번째 줄), 응답이 왔을 때 무엇을 확인하는지(25번째 줄) 순서대로 답해 보세요."

진입 시 성수동이 먼저 요청되고, 망원을 누르면 망원에 대한 요청이 진행돼요. 이때 중요한건 요청 자체를 막을 순 없어요. 상태가 업데이트되는것을 막아야해요. 따라서 ignore 변수를 사용해 요청을 보낼 때 이전 요청을 무시하지 않는다면 상태를 업데이트 하도록 했어요.
망원동을 누른 순간 cleanup 함수가 실행되어 성수에 진입했던 useEffect에 ignore 변수를 true로 돌려요. 따라서 성수는 응답이와도 이전 요청을 무시하기 때문에 상태를 업데이트하지 않아요.

---

**멘토**: "요청 자체는 막을 수 없고 상태 업데이트를 막아야 한다"는 문장이 이 문제 전체의 핵심이에요. 이걸 스스로 써낸 게 이번 풀이에서 가장 좋은 대목이에요. 망원을 누른 순간 cleanup이 성수 effect의 `ignore`를 `true`로 바꾼다는 설명도 정확해요.

질문의 첫 칸인 "요청을 보낼 때 무엇이 생기나"만 채워 볼게요. effect가 실행될 때마다 `let ignore = false`가 **새로** 만들어져요. 성수 요청에는 성수의 `ignore`가, 망원 요청에는 망원의 `ignore`가 따로 생기는 거예요. 이게 있어야 cleanup이 망원 것은 두고 성수 것만 `true`로 바꿀 수 있어요. 그리고 같은 동네 요청이 두 개 떠 있어도 서로 헷갈리지 않아요. 동네 이름이 아니라 요청마다 따로 생긴 변수로 구분하니까요.

## 2. 늦게 도착한 실패와 완료

**상황**: 요구사항 4번의 예시를 `Problem.spec.tsx`의 "늦은 이전 실패와 완료가 현재 요청의 로딩을 끝내거나 오류를 표시하지 않는다" 테스트가 그대로 만든다. 실제 모의 API에서는 연남(0.45초)이 성수(1.8초)보다 먼저 끝나고 성수는 실패하지 않아서 이 순서가 생기지 않는다. 테스트가 응답 순서를 직접 정해서 만드는 장면이다.

| 순서 | 일어난 일                                                       |
| ---- | --------------------------------------------------------------- |
| 1    | 진입, 성수 요청 시작                                            |
| 2    | 연남 선택, 연남 요청 시작                                       |
| 3    | 처음 보낸 성수 요청이 **실패로 끝나 도착**. 연남은 아직 대기 중 |
| 4    | 연남 요청이 빈 목록으로 끝나 도착                               |

요청 하나는 세 갈래로 끝난다. `try`에서 `await` 다음 줄로 가는 **성공**, `catch`로 가는 **실패**, 둘 중 어느 쪽이든 마지막에 지나는 `finally`의 **완료**다. 아래는 성공에만 검사를 둔 코드다.

```ts
try {
  const data = await func(neighborhood)
  if (!ignore) setPosts(data)
} catch {
  setError(NEIGHBORHOOS_ERROR_MESSAGE)
} finally {
  setLoading(false)
}
```

> "위 코드라면 3번 순간에 늦게 온 성수 실패가 `catch`와 `finally`를 지나가요. 그때 화면은 어떻게 돼요? 4번에서 연남이 도착한 뒤에는요?"

에러를 업데이트하기 때문에 에러 화면이 보여지고, 연남 요청이 대기 중이여도 로딩이 꺼지게 돼요. 연남이 도착한 뒤에는 빈 목록으로 보여져야하지만, `PostStatusMessage`에서 error를 먼저 검사하기 때문에 여전히 에러 화면이 보여요.

---

**멘토**: 4번 순간까지 따라간 게 좋아요. 대부분 "로딩이 일찍 꺼진다"에서 멈추는데, 연남이 도착한 뒤에도 오류가 남는다는 것까지 찾았어요. 그것도 `PostStatusMessage`의 `if` 순서를 근거로요. 직접 짠 컴포넌트를 근거로 화면을 예측한 거라 설득력이 있어요.

한 걸음만 더 가면 "왜 오류가 안 지워지나"도 설명할 수 있어요. 지금 코드에서 `setError('')`는 **요청을 시작할 때만** 불려요. 연남 요청은 2번 순간에 이미 시작했으니 오류를 지울 기회를 그때 써 버렸고, 3번에 늦게 들어온 오류를 지워 줄 코드가 없어요. 그래서 사용자가 다른 동네를 누르거나 다시 불러오기를 누를 때까지 오류가 남아요.

> 꼬리 질문: "위 코드는 성공에만 `if (!ignore)`가 있어요. 실제로 짠 `useNeighborhoodPosts.ts`에서는 실패와 완료에도 이 검사가 있죠. 그 두 검사 덕분에 3번 순간의 화면은 위 코드와 비교해 어떻게 달라졌어요?"

이전의 요청을 무시하지 않을 때에 에러를 업데이트하고, 로딩을 끄도록 되어있어요. 따라서 이전의 요청이 현재의 요청에 값을 바꾸지 않아요. 3번 순간의 처음 보낸 성수 요청이 실패로 끝나도 상태를 업데이트 하지않아요. 왜냐하면 성수 선택 후 연남을 선택했기 때문에 무시되고 지나가요.

---

**멘토**: 성수 실패가 무시되는 이유는 정확히 짚었어요. 질문이 묻는 건 그 결과 **화면이 어떻게 달라졌나**라서, 마지막에 그 장면을 한 줄 붙이면 완성돼요. 위 답에서 그린 화면(오류 문구, 로딩 꺼짐, 연남 뒤에도 남는 오류)과 나란히 놓아 보세요. 3번 순간에 로딩이 그대로 돌고 `다시 불러오기`도 잠겨 있어요. 4번에 연남이 오면 그때 빈 목록 안내가 떠요. 사용자 눈에는 3번 순간에 **아무 일도 일어나지 않아요**. 그게 이 두 검사가 해 준 일이에요.

## 3. 다시 불러오기를 effect로 보낸 이유

**상황**: 처음 구현에서 `reloadPosts`는 effect 밖에서 요청을 직접 보냈다. 동네 변경은 effect가 보내고 `cancelled`로 걸렀지만, 이 함수에는 거르는 검사가 없었다.

```ts
const reloadPosts = useCallback(async () => {
  setLoading(true)
  setError('')
  setPosts([])

  try {
    const data = await func(neighborhood)
    setPosts(data)
  } catch {
    setError(NEIGHBORHOOS_ERROR_MESSAGE)
  } finally {
    setLoading(false)
  }
}, [func, neighborhood])
```

지금은 `reloadPosts`가 `reloadCount`만 1 올리고(46~48번째 줄), 그 값이 effect 의존성 배열(44번째 줄)에 들어 있어서 effect가 다시 실행되며 요청을 보낸다. 요구사항 3번에 따라 성공한 뒤에도 `다시 불러오기`를 누를 수 있다.

> "위 처음 코드에서 성수 게시글을 받은 뒤 `다시 불러오기`를 누르고, 바로 망원동을 누르면 1.8초쯤에 화면이 어떻게 돼요? 제목과 목록이 각각 어느 동네 것인지로 답해 보세요."

제목은 망원으로 나오고 목록은 성수로 나와요

> 꼬리 질문: "지금 코드의 `reloadPosts`는 이름은 '다시 불러온다'인데 실제로는 숫자만 올려요. 상태를 바꿔서 effect가 대신 요청하게 만든 이 방식이 막아 준 것은 뭐고, 대신 치른 비용은 뭐예요?"

다시 불러오기를 누르면 `fetchPosts`와 같이 클로저로 동작해야 했어요. 그래야 이전 요청을 업데이트하지 않고 무시할 수 있어요. 해당 방식이 막아준건 최근 선택한 값이 업데이트되도록 보장해요. 대신 치른 비용은, `reloadPosts`에 네이밍과 안에 들어간 코드가 매칭이 되지않아요. 그래도 이런 부분은 주석을 통해 맥락을 남길 수 있을것 같아요.

---

**멘토**: 비용을 정확히 짚었어요. 이름과 동작이 어긋나는 걸 비용으로 보고, 주석으로 메운다는 대책까지 냈어요.

첫 문장의 "클로저로 동작해야 했어요"만 같이 다시 볼게요. 처음 `reloadPosts`도 클로저였어요. `func`와 `neighborhood`를 붙잡고 있었으니까요. 문제는 클로저가 아니었어요. 그 요청이 **effect를 지나가지 않아서 cleanup의 보호를 못 받은** 게 문제였어요. 동네가 바뀌어도 React가 그 요청의 `ignore`를 바꿔 줄 방법이 없었던 거죠. 그래서 `reloadCount`로 바꾼 진짜 이유는 "재요청도 같은 effect를 지나가게 해서, 오래된 요청을 무시하는 일을 cleanup 한 곳에 맡긴다"예요. 이렇게 쓰면 "막아 준 것"도 더 구체적이 돼요. 처음 코드에서 본 "제목은 망원, 목록은 성수"를 재요청 경로에서도 막아 줬다고요.

## 4. 상태로 둔 것과 계산한 것

**상황**: 출제 때 `FeedView`는 `neighborhood`, `posts`, `busy`, `loaded`, `error`를 받았다. `starter.tsx`의 주석은 "props 하나마다 상태 하나가 필요한 것은 아니다"라고 했다. (풀이하면서 `busy`는 `isLoading`으로 바꾸고 `loaded`는 지웠다. 질문은 출제 때 이름으로 묻는다.)

> "이 다섯 개 중 `useState`로 둔 건 뭐고 다른 값에서 계산한 건 뭐예요? 특히 `loaded`는 어느 쪽이죠? `posts`가 빈 배열인 것만으로는 구분할 수 없는 두 화면이 뭔지부터 답해 보세요."

상태로 둔 값은 아래와 같아요.

- `posts`
- `error`
- `neighborhood` => `selectedNeighborhood`
- `busy` => `loading`

`loaded`는 로딩이 완료된 것을 의미해요. busy는 로딩 중인지를 나타내요. 따라서 "로딩 중인가?"에 대한 값을 알면 다른 하나는 파생 데이터로 활용할 수 있어요.

`posts`가 빈 배열이라면 "비어있는 게시글"과 "보여줄 게시글"을 구분할 수 없어요.

---

**멘토**: 상태 목록과 `loaded`가 `busy`에서 계산된다는 판단은 맞아요. 실제로 코드에서 `loaded`를 지운 것도 이 판단에서 나왔죠.

마지막 문장은 조금 더 구체적으로 만들 수 있어요. `posts`가 `[]`인 순간을 세어 보면 하나가 아니라 세 화면이에요. 불러오는 중일 때(요청 시작에서 비웠으니까), 실패했을 때, 그리고 불러왔는데 정말 0개일 때요. 사용자에게는 "게시글을 불러오고 있어요", "불러오지 못했어요", "아직 게시글이 없어요"로 전부 다른 화면이죠. `posts`만 보고는 셋을 가를 수 없어서 `loading`과 `error`가 원본 상태로 따로 필요한 거예요. "구분할 수 없는 화면"을 사용자가 보는 문구로 적어 두면, 왜 상태가 이 세 개인지가 한 번에 설명돼요.

> 꼬리 질문: "지금 구조에서 `busy`가 `true`이면서 `error`도 있는 상태를 만들 수 있나요? 만들 수 없다면 무엇이 막고 있고, 만들 수 있다면 화면에는 뭐가 보이죠?"

아니요 만들 수 없다고 생각해요. 요청이 성공 및 실패 여부에 따라 화면에 보여주기 때문이에요. 성공과 실패를 했다는 이미 결과를 받은 시점이라 `busy`가 true일 수 없어요.

---

**멘토**: "만들 수 없다"는 결론은 맞아요. 이유는 한 겹 더 들어가 볼 만해요. "결과를 받은 시점이라 `busy`가 `false`"는 **그 요청 하나**만 볼 때 맞는 말이에요. 요청이 둘이면 이야기가 달라져요. 연남 요청이 대기 중이라 `busy`가 `true`인데, 늦게 온 성수 실패가 `setError`를 부르면요? 그 순간 `busy`도 `true`, `error`도 있는 상태가 돼요. 처음 코드에서 `catch`에 검사가 없던 때가 정확히 이 상태였어요.

그러니 지금 이 조합을 막고 있는 건 `catch` 안의 `if (!ignore)`예요. 하나 더 있다면, 요청을 시작할 때 `setLoading(true)`와 `setError('')`를 같은 자리에서 함께 부르는 것도 막는 데 한몫해요. "무엇이 막고 있나"를 물으면 이렇게 줄을 짚어 답할 수 있으면 돼요.

## 5. 동네 선택을 훅 밖에 둔 이유

**상황**: 동네 선택 상태는 `NeighborhoodFeed`에 있고(`starter.tsx` 8번째 줄), 훅은 `neighborhood`를 인자로 받기만 한다. 10월 3일에는 반대로 예약 선택 상태를 `useCancelReservationForm` 안으로 옮겼다. 그때는 예약을 바꿀 때 쓰는 쪽이 `reset()`을 같이 불러야 했다.

> "두 문제 모두 '선택이 바뀌면 이전 결과를 지운다'는 요구가 있었는데, 10월 3일에는 선택을 훅 안으로 옮기고 이번에는 밖에 뒀어요. 결론이 갈린 이유는 뭐예요? 이번에 동네가 바뀔 때 이전 게시글과 오류를 지우는 일은 누가 하고 있는지로 답해 보세요."

이전 게시글과 오류를 지우는 일, 로딩을 관리하는 일은 훅에서 담당하고 있어요. 훅에서는 게시글 목록과 상태를 가져오는 책임으로 봤어요. 고민을 해보았을 때, 게시글을 가지고 올 때 동네를 선택하고 알아야하는건 아니라고 판단했어요. 따라서 게시글은 어떤 동네인지만 알면 해당하는 게시글 목록을 준다고 생각했어요.

---

**멘토**: "훅은 동네만 받으면 그 동네의 게시글을 준다"는 책임 정의가 깔끔해요. 훅 이름 `useNeighborhoodPosts`와도 정확히 맞고요.

질문의 앞부분인 "10월 3일과 왜 결론이 갈렸나"를 첫 문장과 이어 보면 답이 나와요. 첫 문장에 "지우는 일은 훅이 담당한다"고 쓰셨죠. 더 정확히는 `neighborhood`가 의존성 배열에 있어서 **effect가 알아서** 지워요. 쓰는 쪽은 바뀐 동네를 넘기기만 하면 되고, 따로 불러야 할 함수가 없어요. 10월 3일에는 쓰는 쪽이 `reset()`을 같이 불러야 했고, 빠뜨려도 타입 검사가 못 잡았어요. 그 약속을 구조로 막으려고 선택을 훅 안으로 넣은 거예요. 이번에는 그런 약속이 처음부터 없으니 옮길 이유도 없었던 거고요. "쓰는 쪽에게 지킬 약속이 남느냐"가 두 결론을 가른 기준이에요.

## 6. 취소하지 않고 무시하기

**상황**: 모의 API의 `LoadPosts`는 `(neighborhood) => Promise<Post[]>`라서 `AbortSignal`을 받을 자리가 없다. 동네를 바꿔도 이전 요청은 끝까지 가고, 지금 코드는 그 결과를 `ignore`로 반영하지 않을 뿐이다. `src/api/client.ts`의 `request`는 두 번째 인자 `init`을 `fetch`에 그대로 넘긴다.

> "이 모의 API는 `AbortSignal`을 지원하지 않아요. 지원했다면 구조가 어디서 달라졌을까요? 요청을 취소하지 않고 결과만 무시하는 지금 방식이 치르는 비용은 뭐죠?"

지금과 크게 달라지는건 없다고 생각해요. `ignore` 변수가 제거되고, `AbortSignal` 코드로 적용될 것 같아요. cleanup 함수도 마찬가지고요. 그리고 api 함수에도 abortSignal을 받을 수 있도록 params로 열어놓을것 같아요. 현재는 요청을 취소하지 않기 때문에 실제 요청이 들어가는 네트워크와 서버 통신 비용이 발생해요.

---

**멘토**: 구조가 크게 안 달라진다는 판단과, 비용이 네트워크와 서버 쪽이라는 정리 모두 맞아요. 시점만 하나 붙이면 더 정확해져요. 성수 요청은 보낼 때는 필요했고, 연남을 누른 **뒤에** 필요 없어졌어요. 그래서 이 비용은 "보낸 것"이 아니라 "필요 없어진 뒤에도 응답을 끝까지 받는 것"이에요. 취소를 지원하면 그 순간 연결을 끊어서 남은 응답을 받지 않을 수 있어요.
