# 2026-10-04 · 빠른 동네 선택과 늦은 게시글

- 유형: 직접 구현형
- 예상 시간: 30~40분

## 사용자 목표

이웃이 동네를 빠르게 바꾸어도 **현재 선택한 동네의 게시글만** 확인하고, 실패하면 같은 동네를 다시 불러온다.

## 핵심 설계 질문

> 선택한 동네와 진행 중인 요청의 수명은 어떻게 연결할까요? 오래된 요청의 성공·실패·완료가 현재 화면을 바꾸지 않게 하려면, 그 책임을 어디에서 관리해야 할까요?

`starter.tsx`의 `NeighborhoodFeed`를 직접 구현합니다. 요청 시작·결과 반영·재시도 로직은 제공하지 않습니다. `view.tsx`는 화면 표현만 제공하며, 표현용 props와 같은 이름의 상태를 각각 만들 필요는 없습니다. 컴포넌트·훅·함수의 경계는 자유롭게 선택합니다. 이전 async-search와 비슷한 비동기 경계를 **빈 로직에서 직접 설계하고 실패까지 다루는** 연습입니다.

## 관찰 가능한 요구사항

1. 진입 시 성수동을 선택하고 `loadPosts('seongsu')`를 호출합니다. 다른 동네를 선택하면 제목·선택 표시를 즉시 갱신하고 새 요청을 시작합니다. 새 요청 시작 시 이전 게시글과 오류를 제거합니다. 로딩 중에도 동네 선택은 가능합니다.
2. 현재 요청 대기 중 `게시글을 불러오고 있어요.`를 표시하고 `다시 불러오기`를 비활성화합니다. 가장 최근 요청의 성공만 목록에 반영합니다. 결과가 빈 배열이면 `아직 게시글이 없어요. 다른 동네를 골라 주세요.`를 표시합니다. 게시글이 있으면 제목·동네·원화 가격과 개수를 표시합니다.
3. 현재 요청 실패 시 목록은 비우고 `게시글을 불러오지 못했어요. 다시 불러오거나 다른 동네를 골라 주세요.`를 표시합니다. `다시 불러오기`는 현재 동네로 새 요청을 시작하고 이전 오류·목록을 지웁니다. 성공 뒤나 빈 결과에서도 다시 불러올 수 있습니다. 같은 요청 대기 중 버튼 연타로 중복 요청하지 않습니다.
4. 이전 요청의 성공·실패·완료는 현재 목록·오류·로딩을 변경하지 않습니다. 예를 들어 성수 요청 → 연남 요청 → 성수 실패 순서일 때, 연남 요청이 아직 끝나지 않았다면 로딩을 유지해야 합니다. 화면을 나간 뒤의 응답도 더 이상 해당 화면에 반영하지 않습니다.

재선택이나 새로고침 후 캐시는 없습니다. 같은 동네가 이미 선택되어 있는 상태에서 그 선택지를 다시 누르는 것은 별도 새로고침이 아닙니다. 명시적 새로고침은 `다시 불러오기`를 사용합니다.

## 입력과 모의 API

```ts
type Neighborhood = 'seongsu' | 'yeonnam' | 'mangwon'
type Post = { id: string; title: string; price: number; neighborhood: Neighborhood }
type LoadPosts = (neighborhood: Neighborhood) => Promise<Post[]>
```

| 동네   | 응답 시간 | 모의 응답                       |
| ------ | --------- | ------------------------------- |
| 성수동 | 1.8초     | 게시글 2개                      |
| 연남동 | 0.45초    | 첫 요청만 실패, 이후 게시글 1개 |
| 망원동 | 0.7초     | 빈 배열                         |

`api.ts`에 타입·샘플 입력·`createDemoLoader`를 제공합니다. 모의 API는 요청 취소나 AbortSignal을 지원하지 않습니다. 실제 네트워크·서버 저장은 없으며, 문제를 나갔다 다시 들어오면 연남 호출 횟수가 초기화됩니다. 테스트에서는 요청 함수를 주입해 완료 순서를 직접 제어합니다. 테스트의 요청 주입 경계는 유지하세요.

## 상태와 화면 맥락

375px에서 제목 → 동네 필터 → 선택 동네 제목 → 목록 또는 상태 안내 → 재요청 액션 순서입니다. 짧은 세 동네 선택은 [Segmented Control](https://seed-design.io/components/segmented-control)의 콘텐츠 필터 패턴으로 구성합니다. 목록 상세 페이지나 작성 폼은 학습 범위 밖입니다.

| 상태             | 화면과 조작                                                 |
| ---------------- | ----------------------------------------------------------- |
| 스타터           | 요청 미연결 안내; 동작 미완성                               |
| 요청 중          | 이전 목록 제거, 진행 표시, 재요청 버튼 잠금, 동네 선택 가능 |
| 성공             | 현재 동네 목록·개수 표시, 조작 가능                         |
| 빈 결과          | 다른 동네 선택 안내, 조작 가능                              |
| 실패             | 오류·재시도 안내, 조작 가능                                 |
| 오래된 요청 완료 | 현재 화면 변화 없음                                         |

출제 스킬의 일반적인 “로딩 중 입력 잠금”보다 **동네를 바꿀 수 있어야 한다는 이 문제의 요구사항**을 우선합니다. 저장 폼이 아니라 읽기 필터이므로, 이전 요청이 끝나기 전에 다음 동네를 고르는 것이 정상 사용자 행동입니다.

### UI 요소별 공식 컴포넌트 확인

- 동네 선택: 설치본 SegmentedControl의 Root·Item·ItemHiddenInput·Indicator. 공식 React 문서와 registry 스니펫의 파츠 구성을 확인했습니다. 공개 라벨·radiogroup 이름을 제공합니다.
- 게시글: 설치본 List의 Root·Item·Content·Title·Detail. 클릭 동작 없는 정보 목록입니다. 기존 List 스니펫을 복제하거나 수정하지 않습니다.
- 재요청: 공식 ActionButton 스니펫, neutralWeak·large·disabled.
- 로딩: 공식 ProgressCircle 스니펫과 상태 텍스트. [Progress Circle](https://seed-design.io/react/components/progress-circle) API를 사용합니다.
- 오류·빈 목록 안내: 설치본 Callout 파츠. 안내가 사라지지 않아야 하므로 인라인으로 둡니다.
- 제목·간격: Text·VStack과 공개 x 토큰. CSS는 가로 배치·긴 문구 줄바꿈·터치 영역만 보완합니다. native Radio·Button 등 대체 구현은 없습니다. 자유 입력 필드가 없어 TextField는 필요하지 않습니다.

독립된 실습은 article로 구성해 기존 native section 전용 CSS의 영향을 받지 않습니다. SEED 공식 스킬의 문서 라우팅과 설치본 타입을 기준으로 작성했습니다.

## 실행과 풀이 확인

별도 worktree에서 실행합니다. 원본의 미커밋 풀이를 이 문제에 복사하지 마세요.

```sh

pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-04-neighborhood-feed/Problem.spec.tsx
pnpm --filter @frontend-lab/daily-frontend build
```

앱에서 `빠른 동네 선택과 늦은 게시글`을 선택하거나 `#2026-10-04-neighborhood-feed`로 진입합니다.

`Problem.spec.tsx`의 제공 UI·API 테스트 5개는 즉시 실행합니다. 구현할 행동 테스트 5개는 `describe.skip`으로 표시했습니다. **구현 시작 시 `.skip`을 제거하고 실패부터 확인**하세요. 비동기 순서 테스트는 요청을 취소하지 않고 오래된 요청도 완료시키므로, API 취소 기능이 있다고 가정해서는 통과할 수 없습니다. 화면을 나갔다 재진입하는 동작은 직접 추가 확인합니다.

화면 검수용 정적 상태는 `?feed-preview=initial`, `loading`, `error`, `empty`, `success`로 확인할 수 있습니다. 예: `/?feed-preview=loading#2026-10-04-neighborhood-feed`. 이 값들은 상태 전이를 구현하지 않으며, 정답 로직이 아닙니다. 풀이할 때는 query를 지웁니다.

## 출제 시 검증 범위

- 최신 `origin/develop`에서 만든 별도 worktree에서 frozen lockfile 의존성 설치와 정상 설치 훅을 완료했습니다. 패키지·lockfile·보안 정책·훅은 변경하지 않았습니다.
- 전체 `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm build` 통과. build의 TypeScript 검사 포함. Daily 테스트는 기존 10개와 오늘 UI·API 5개 통과, 구현 행동 5개 건너뜀입니다. code-quality 테스트 22개도 통과했습니다. **건너뛴 테스트는 풀이가 통과했다는 뜻이 아닙니다.**
- Chromium 375×812 실제 브라우저에서 정적 initial·loading·error·empty·success 상태와 미완성 스타터를 확인했습니다. 각 상태에서 가로 넘침 없음(문서 폭 375px), 동네 라벨과 radiogroup 이름, 선택 영역 48px·재요청 버튼 52px, 로딩의 재요청 비활성 및 동네 선택 활성 상태를 확인했습니다. 콘솔 오류·경고와 pageerror는 없었습니다.
- **브라우저 검수는 정적 표현 검수**입니다. 실제 요청 시작·오래된 응답 무시·실패 후 재시도·화면 이탈의 상태 전이는 사용자 구현 전이므로 미검증입니다. 다른 브라우저·스크린리더·실제 서버도 확인하지 않았습니다.
- `seed-design compat`는 기존 `ui:list`에 최신 registry의 CSS ^3.0.0 필요 범위를 보고하며 실패했습니다. 오늘은 기존 List 스니펫 대신 설치된 React 2.5.1의 공식 List 파츠와 CSS 2.8.3을 사용해 타입·실제 렌더를 확인했습니다. 사용한 ActionButton·ProgressCircle 스니펫에는 호환 경고가 없었습니다. 기존 스니펫이나 의존성을 변경하지 않았으며, 전역 호환성 경고를 숨기지 않기 위해 Draft PR로 제공합니다.

원본 미커밋 풀이·별칭 설정과 아직 머지되지 않은 PR #20·#21의 변경은 포함하지 않았습니다. 원본 checkout의 현재 풀이를 검증한 결과가 아니라 이 문제 worktree의 결과입니다.
