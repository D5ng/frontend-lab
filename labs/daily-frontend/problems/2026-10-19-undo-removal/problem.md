# 마지막으로 뺀 상품을 되돌린다면?

- 날짜: 2026-10-19 (Asia/Seoul)
- 유형: **직접 구현형**
- 예상 시간: **30~40분**
- 사용자 목표: 다 본 관심 상품을 정리하고, 실수로 뺀 마지막 상품 한 개를 되돌립니다.

## 시작하기

`pages/ProductRemovalPage.tsx`의 `ProductRemovalPage`에 로직과 구조를 직접 구현하세요. `features/productRemoval/components/RemovalView.tsx`는 표시와 이벤트 전달만 제공하고 `features/productRemoval/apis/`/`handlers.ts`는 실제 fetch/MSW 환경만 제공합니다. 시작 코드는 목록만 보여 주며 삭제·복구 요청은 아직 하지 않습니다. 완성 로직이나 권장 상태·훅 구조는 제공하지 않습니다. view의 props 수와 상태 수가 같아야 하는 것도 아닙니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-19-undo-removal
```

오늘 PR의 별도 worktree에서 실행하고 Daily 메뉴에서 선택합니다. 직접 주소는 `http://localhost:5173/#2026-10-19-undo-removal`입니다. 실제 포트는 Vite 출력을 참고하세요. 별도 백엔드는 필요 없습니다.

## 관찰 가능한 요구사항

1. 처음에는 원목 의자 → 책상 조명 → 작은 책장 순서로 3개를 표시하며, 진입 시 요청하지 않습니다. 되돌릴 상품과 결과 안내는 없습니다.
2. 상품의 **빼기**를 누르면 `remove(id)`를 한 번 호출합니다. 성공 응답 전에는 목록을 유지하고, 모든 빼기·되돌리기 액션을 잠급니다. 진행 상태와 잠금 이유를 보여 주세요. 두 요청을 동시에 보내지 않습니다.
3. 삭제 성공 후 해당 상품만 목록에서 빼고 `상품명을 목록에서 뺐어요.`를 표시합니다. 이 상품이 **마지막으로 되돌릴 수 있는 상품**이 됩니다. 다른 상품을 성공적으로 빼면 이전 복구 대상은 새 상품으로 대체됩니다.
4. 새 삭제가 진행 중일 때 기존 복구 대상은 보이는 채로 잠깁니다. 삭제 실패 시 목록과 기존 복구 대상을 모두 유지하고 `목록에서 빼지 못했어요. 다시 시도해 주세요.`를 표시합니다. 실패한 삭제로 복구 대상을 바꾸지 않습니다. 같은 빼기 버튼으로 재시도할 수 있습니다.
5. **마지막 상품 되돌리기**는 현재 복구 대상의 ID로 `restore(id)`를 한 번 호출합니다. 성공 전에는 해당 상품을 목록에 미리 넣지 않고, 모든 액션을 잠급니다.
6. 복구 성공 시 상품을 **처음 목록에서의 상대 순서**에 한 번만 복구합니다. `상품명을 다시 담았어요.`를 표시하고 복구 대상과 되돌리기 버튼을 없앱니다. 더 오래전에 뺀 상품을 다음 복구 대상으로 되살리지 않습니다.
7. 복구 실패 시 현재 목록과 복구 대상을 유지하고 `되돌리지 못했어요. 다시 시도해 주세요.`를 표시합니다. 되돌리기 버튼으로 같은 상품을 재시도할 수 있습니다. 자동 재시도는 하지 않습니다.
8. 새 요청이 시작되면 이전 성공·오류 안내를 지웁니다. 완료 후 다시 조작할 수 있어야 합니다. 목록이 비어도 `관심 상품을 모두 정리했어요.`와 마지막 복구 대상·되돌리기 액션을 함께 표시합니다.

위 문구의 `상품명`에는 상품 제목을 넣고 조사를 맞춥니다. 의자는 `원목 의자를`, 조명과 책장은 `책상 조명을`·`작은 책장을`로 연결합니다(예: `원목 의자를 다시 담았어요.`).

### 작은 상황

의자를 뺀 뒤 조명 빼기를 시도했는데 실패했습니다. 지금 되돌리기를 누르면 무엇이 돌아와야 할까요? 반대로 조명 빼기도 성공했다면 의자와 조명 중 어느 것만 돌아와야 할까요? 그 뒤 또 되돌리기를 할 수 있나요?

화면을 그리거나 테스트를 실행하며 답해도 됩니다. 암산 과제가 아닙니다. 최근에 연습한 오래된 조회 결과 무시하기와 달리, 이번에는 **이미 성공한 변경의 복구 권한이 언제 교체되는지**를 다룹니다.

## 핵심 설계 질문

**현재 목록과 ‘마지막으로 되돌릴 수 있는 상품’은 어떤 성공·실패에서 함께 바뀌고, 어떤 경우에는 그대로 남아야 할까요? 이 약속을 한쪽만 바꾸는 실수를 줄이려면 책임을 어디에 둘까요?**

특정 파일·훅 개수나 자료구조는 정답이 아닙니다. 먼저 현재 상태의 원본과 각 요청의 영향을 설명하고, 변경하기 편해지는 점과 추가된 복잡성을 비교해 보세요.

## 제공 API와 범위

```ts
interface RemovalApi {
  remove: (id: string) => Promise<void>
  restore: (id: string) => Promise<void>
}
```

- 고정 입력 `initialProducts`와 `Product { id, title, detail }`을 제공합니다. 서버 목록 조회는 필요 없습니다.
- 삭제: `DELETE /api/daily/2026-10-19/items/:id`.
- 복구: `POST /api/daily/2026-10-19/items/:id/restore`.
- 약 0.7초 후 응답합니다. 의자 삭제의 첫 시도와 의자 복구의 첫 시도는 각각 HTTP 503, 같은 작업의 이후 시도는 204입니다. 나머지 상품은 첫 시도부터 204입니다.
- API 공장마다 세션이 분리되며, 삭제·복구의 실패 횟수도 독립적입니다. 실패는 서버 변경이 적용되지 않았다는 계약이고, 성공은 보낸 ID의 작업이 완료됐다는 계약입니다. API는 요청만 전달하고 화면 상태·복구 이력을 관리하지 않습니다.
- MSW는 지연과 성공·실패 응답만 모킹합니다. 서버 목록의 영속화나 작업 이력을 저장하는 서버 구현은 아닙니다. 화면을 떠났다 돌아오면 고정 목록과 새 세션으로 시작합니다.
- 다중 단계 실행 취소, 시간 제한, 재실행(redo), 낙관적 삭제, 상품 추가, 외부 상태 라이브러리, 브라우저 새로고침 후 영속화는 범위 밖입니다.

## 화면 맥락과 SEED 대응

375px 모바일에서 제목 → 목록별 정리 액션 → 처리 결과 → 마지막 복구 대상 순으로 읽습니다. 삭제가 아닌 관심 목록 제외이며 복구가 가능한 작업이라 위험 확인 모달을 더하지 않습니다. 되돌릴 대상은 사라지면 안 되는 정보여서 자동으로 닫히는 토스트 대신 화면에 남깁니다. 정리와 복구는 명령 액션이며 별도의 입력 폼·선택 컨트롤은 필요하지 않습니다.

UI 출제 스킬의 Montage 지침보다 사용자 지정 SEED 기준을 우선합니다.

| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 상품 목록          | 설치된 공식 v2 `List`/`ListItem` 스니펫, ul/li 의미 구조. 행 자체는 클릭하지 않고 suffix 버튼만 조작               |

### 고정 표현 미리보기

개발 서버에서 query를 hash **앞에** 붙입니다: `?removal-preview=error#2026-10-19-undo-removal`. 지원 값은 `idle`, `pending`, `removed`, `restorePending`, `error`, `restored`, `empty`입니다. 고정 props로 표현만 검수하며, 버튼을 눌러도 API나 상태 전이가 발생하지 않습니다. query를 제거하면 실제 풀이 스타터입니다. 프로덕션 빌드에서는 적용되지 않습니다.
