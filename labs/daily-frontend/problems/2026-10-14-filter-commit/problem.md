# 선택한 조건과 적용된 목록

- 날짜: 2026-10-14 (Asia/Seoul)
- 유형: **리팩터링형** — 기능 추가나 버그 수정이 아닙니다.
- 예상 시간: **30~40분**
- 사용자 목표: 관심 카테고리를 고르고, 마지막으로 적용에 성공한 조건의 물건을 둘러봅니다.

## 시작하기

`pages/ListingFilterPage.tsx`는 아래 요구사항이 이미 동작하는 스타터입니다. 먼저 화면을 조작하고 `note.md`에 현재 이해와 설계 가설을 적어 주세요. 동작을 유지하면서 가독성·예측 가능성·응집도·결합도를 기준으로 재구성하세요. 파일 수, 훅 개수, 중복 제거 자체는 정답이 아닙니다. 공통 앱과 API·모킹 환경은 풀이 대상이 아닙니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-14-filter-commit
```

화면: `http://localhost:5173/#2026-10-14-filter-commit` (포트가 사용 중이면 Vite 출력 참고). 공통 Daily 선택 메뉴에서도 선택할 수 있습니다. 이 PR의 worktree에서 실행하세요. 아직 머지되지 않은 다른 날짜의 PR은 포함하지 않습니다.

## 관찰 가능한 요구사항

1. 최초에는 가구·생활용품·도서가 선택되어 있고 물건 3개가 보입니다. 최초 조회 요청은 없습니다. 도서에는 등록된 물건이 없습니다.
2. 체크박스 변경은 **선택 중인 조건**만 바꿉니다. **적용된 조건과 목록**은 적용 요청이 성공할 때만 함께 바뀝니다. 조건이 같으면 적용 버튼은 비활성입니다. 선택 순서는 의미가 없으며 요청 순서는 가구 → 생활용품 → 도서입니다.
3. 아무것도 선택하지 않고 적용하면 `카테고리를 하나 이상 선택해 주세요.`를 안내하고 요청하지 않습니다. 선택을 바꾸면 이전 오류·성공 안내를 지웁니다.
4. 요청 중에는 적용 버튼이 비활성이고 진행 안내와 기존 목록이 보입니다. **체크박스는 계속 편집할 수 있습니다.** 추가 요청은 발생하지 않습니다.
5. 성공하면 **요청을 시작할 때 보낸 조건**과 그 응답 목록을 표시합니다. 요청 중 바꾼 선택은 그대로 남습니다. `선택한 조건으로 목록을 바꿨어요.`를 안내합니다. 현재 선택이 적용된 조건과 다르면 다시 적용할 수 있습니다.
6. 실패하면 적용된 조건·기존 목록·현재 선택을 유지하고 `목록을 바꾸지 못했어요. 선택을 확인하고 다시 적용해 주세요.`를 안내합니다. 재시도는 현재 선택을 보냅니다.
7. 빈 목록도 정상 성공입니다. 적용된 조건과 0개 표시를 갱신하고 다른 카테고리를 선택하도록 안내합니다.

### 작은 상황

전체 목록에서 **가구만 선택 → 적용 → 응답 대기 중 도서도 선택**해 보세요. 응답이 성공했을 때 선택 요약, 적용된 조건, 물건 목록, 버튼은 각각 무엇을 보여줘야 할까요? 실패라면 무엇이 달라질까요? 화면과 테스트로 확인해도 좋습니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**현재 선택, 요청한 조건, 목록에 적용된 조건을 읽는 코드들이 서로의 갱신 시점까지 알아야 하지 않으려면, 어떤 규칙을 함께 두고 어떤 변경은 독립시킬까요?**

이름·상태·처리 흐름 중 가장 설명하기 어렵다고 느낀 한 곳부터 바꾸세요. 분리하지 않는 선택도 근거가 있다면 가능합니다. [Frontend Fundamentals의 네 기준](https://frontend-fundamentals.com/code-quality/code/)은 서로 충돌할 수 있는 판단 도구이지 파일 분리 체크리스트가 아닙니다.

## 제공 환경과 요청

- `features/listingFilter/types/listing.ts`: 입력/응답 타입.
- `features/listingFilter/apis/`: 최초 샘플(`categories.ts`, `initialListings.ts`)과 실제 fetch API 공장(`createListingsApi.ts`).
- `handlers.ts`: `POST /api/daily/2026-10-14/listings`, 본문 `{ categories: Category[] }`, 응답 `Listing[]`.
- MSW가 브라우저와 테스트에서 HTTP를 가로챕니다. 별도 백엔드는 필요하지 않습니다.
- 화면 진입마다 새 API 세션을 사용합니다. 유효한 첫 요청은 1.8초 후 503, 이후 요청은 1.8초 후 성공합니다. 재진입하면 시나리오를 다시 시작합니다. 잘못된/빈 카테고리는 400입니다.
- 함수 주입 테스트는 지연 Promise로 순서를 고정합니다. 실제 핸들러 HTTP 테스트도 활성화되어 있습니다. 건너뛴 신규 테스트는 없습니다.
- API 호출은 한 번에 하나만 허용합니다. 자동 조회, 요청 취소, 페이지네이션, 즐겨찾기, 조건 추가는 범위 밖입니다.

## 화면 맥락과 상태

375px 모바일에서 제목 → 관심 카테고리 → 주요 적용 액션 → 적용된 목록 순으로 읽습니다. 별도 시트 없이 세 항목을 인라인으로 선택하며, 저장 전 선택이므로 Switch가 아닌 Checkbox를 사용합니다. 기존 결과가 유효하므로 요청 중 목록 전체를 Skeleton으로 교체하지 않고 버튼에 진행 상태를 표시합니다.

| 상황           | 화면과 다음 행동                                      |
| -------------- | ----------------------------------------------------- |
| 진입/조건 동일 | 기존 목록과 적용 조건, 버튼 비활성 이유               |
| 편집           | 선택 요약만 변경, 기존 결과 유지                      |
| 빈 선택 적용   | 선택 영역 오류, 요청 없음, 선택하면 해소              |
| 요청 중        | 진행 안내, 적용 잠금, 기존 결과와 다음 조건 편집 유지 |
| 실패           | 오류, 현재 선택으로 재시도 가능                       |
| 성공           | 보낸 조건과 결과 반영, 현재 선택 유지, 성공 안내      |
| 결과 없음      | 0개와 다른 카테고리 적용 안내                         |

UI 출제 스킬의 Montage보다 Daily의 SEED 기준을 우선합니다. 일반적인 요청 중 입력 잠금 원칙은 이 문제에 그대로 적용하지 않습니다. 다음 조회 조건을 미리 편집하는 것이 명시적 제품 동작이며, 중복 적용만 잠급니다. 요청값과 현재 선택은 요약으로 구별합니다.

### UI 요소별 공식 대응 확인

| 역할              | 사용 컴포넌트                                       | 근거                                                                                   |
| ----------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 복수 선택/행 터치 | 공식 `ListCheckItem` + `Checkbox.Control/Indicator` | 행 전체가 label, HiddenInput 제공; 설치된 v2 스니펫 활용                               |
| 선택 그룹/설명    | `List`의 div/group 합성과 이름·설명 연결            | 텍스트 입력이 아닌 선택 리스트, Field/CheckboxGroup의 별도 폼 틀 없이 리스트 합성 사용 |
| 주요 액션/진행    | 공식 `ActionButton` 스니펫                          | large/neutralSolid, loading/disabled                                                   |
| 목록              | 공식 `List`/`ListItem`                              | 의미 있는 ul/li, 클릭 없는 정보 행                                                     |
| 오류/성공/빈 결과 | 공식 `Callout` 파츠                                 | critical/positive/neutral; 오류 alert, 성공 status                                     |
| 정보 계층/여백    | `Text`, `VStack`                                    | 공개 텍스트·색·간격 props, 신규 CSS 없음                                               |

공식 컴포넌트를 native 컨트롤로 대체한 예외는 없습니다. 기존 공통 Daily 메뉴도 SEED Select입니다. 최신 스니펫과 설치본의 호환 검사는 `verification.md`에 별도로 기록합니다.

공식 참고: [Checkbox](https://seed-design.io/components/checkbox), [React List](https://seed-design.io/react/components/list), [Action Button](https://seed-design.io/react/components/action-button), [Callout](https://seed-design.io/react/components/callout).
