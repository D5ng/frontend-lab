# 금액 확인과 예약 확정의 경계

- 날짜: 2026-10-16 (Asia/Seoul)
- 유형: **리팩터링형** — 기능 추가·버그 수정이 아닙니다.
- 예상 시간: **30~40분**
- 사용자 목표: 도예 클래스의 참여 인원에 맞는 금액을 확인한 뒤 그 조건으로 예약합니다.

## 시작하기

`Problem.tsx`는 이미 동작합니다. 인원 선택부터 확인·확정·실패·재시도까지 행동을 보존하며 구조를 개선하세요. 먼저 화면과 테스트를 실행하고 현재 이해·설계 가설을 `note.md`에 직접 적어 주세요. 완성된 **동작**을 제공하는 것이며, 재구성한 정답 구조는 제공하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-16-reservation-review
```

별도 worktree에서 실행하고 공통 Daily 메뉴의 오늘 문제를 선택하세요. 직접 주소는 `http://localhost:5173/#2026-10-16-reservation-review`입니다. 포트가 사용 중이면 Vite 출력 참고. 실제 예약·결제가 아닌 로컬 학습 시뮬레이션이며 별도 백엔드는 필요 없습니다.

## 관찰 가능한 요구사항

1. 진입 시 1명 선택, 확인한 금액은 없습니다. 자동 요청은 없습니다. 1~3명 중 하나를 고를 수 있습니다.
2. **예약 금액 확인**은 선택한 인원으로 서버 금액만 요청합니다. 응답의 인원과 금액을 표시하되 아직 예약 완료로 안내하지 않습니다. 금액은 클라이언트에서 다시 계산하지 않습니다.
3. 확인된 결과가 있을 때만 **이 금액으로 예약 확정** 단계로 진행합니다. 확정 요청에는 확인 응답의 `quoteId`만 보내고, 현재 입력 인원이나 화면 금액을 새로 보내지 않습니다.
4. 인원을 실제로 바꾸면 이전 확인 결과와 오류를 지우고 금액 확인부터 다시 시작합니다. 예전 인원으로 돌아와도 새 확인이 필요합니다. 같은 인원을 다시 누르는 것은 변경이 아닙니다.
5. 금액 확인 중과 예약 확정 중에는 인원 선택과 버튼 모두 잠깁니다. 진행 안내는 두 단계를 구별하고, 같은 요청을 중복 전송하지 않습니다.
6. 금액 확인 실패: 입력 인원 유지, 확인 결과 없음, `금액을 확인하지 못했어요. 다시 확인해 주세요.` 안내. 같은 인원으로 다시 확인 가능합니다.
7. 예약 확정 실패: 확인한 인원·금액·quoteId 유지, `예약을 확정하지 못했어요. 확인한 금액으로 다시 시도해 주세요.` 안내. 같은 quoteId로 재시도하며 금액 확인 요청을 반복하지 않습니다. 대신 인원을 바꾸면 요구사항 4로 돌아갑니다.
8. 확정 성공: 서버 영수증의 인원·금액을 표시하고 `예약을 완료했어요. 클래스에서 만나요.`를 안내합니다. 버튼은 **예약 완료**로 비활성화하고 인원도 잠급니다. 입력이나 기존 확인 금액으로 영수증 값을 덮어쓰지 않습니다.

### 작은 상황

2명 금액 확인 성공 → 확정 실패 → 3명으로 변경하는 경우를 실행해 보세요. 실패 직후와 인원 변경 직후에 각각 무엇이 남고 무엇이 사라지나요? 그다음 버튼은 같은 일을 하나요?

화면과 테스트를 보며 판단해도 됩니다. 암산 과제가 아닙니다. 테스트에서는 모의 서버와 다른 금액을 반환해 서버 결과를 그대로 표시하는지도 확인합니다.

## 핵심 설계 질문

**한 버튼의 “예약 처리”에 섞인 금액 확인과 예약 확정은, 어떤 변경 이유를 기준으로 함께 두거나 나눠야 할까요?**

현재 각 상태의 원본과 변경되는 이유부터 살펴보세요. [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성·예측 가능성·응집도·결합도로 선택의 이득과 비용을 비교합니다. 단계별로 무조건 훅이나 파일을 만들라는 뜻은 아닙니다. 그대로 둔 부분도 이유를 설명할 수 있으면 됩니다.

## 제공 환경

- `api.ts`: `getQuote(count): Promise<Quote>`, `confirm(quoteId): Promise<Receipt>`를 제공하는 API 공장. 실제 fetch 요청을 사용합니다.
- `handlers.ts`: 기존 MSW 자동 탐색에 등록됩니다. 요청·응답 환경은 풀이 대상이 아닙니다.
- `POST /api/daily/2026-10-16/quotes` 본문 `{ count }`, 응답 `{ quoteId, count, totalPrice }`.
- `POST /api/daily/2026-10-16/reservations` 본문 `{ quoteId }`, 응답 `{ reservationId, count, totalPrice }`. 같은 API 세션에서 발급된 quoteId만 받습니다.
- 각 세션의 **첫 금액 확인**은 0.9초 후 503, 이후 성공합니다. 1명 15,000원, 2명 28,000원, 3명 42,000원입니다. 가격 규칙은 모의 서버에만 있습니다.
- **첫 예약 확정**은 1.4초 후 503, 이후 성공합니다. 금액 확인 실패와 확정 실패의 횟수는 독립적입니다. 다른 문제로 갔다 돌아오면 새 API 세션과 초기 화면으로 시작합니다.
- API 만료, 결제·환불, 날짜 선택, 추가 필드, 새 예약 시작, 전역 저장, 서버 캐시, 중복 확정에 대한 실서비스 보장 등은 범위 밖입니다. 테스트는 화면의 중복 클릭 방지를 확인하며 실제 서버의 결제 멱등성을 보장하지 않습니다.

## UI 맥락과 공식 컴포넌트 대응

375px 모바일에서 제목 → 참여 인원 → 확인 결과/확정 내역 → 주요 액션 순으로 읽습니다. 선택지가 세 개이므로 세로 인라인 선택을 사용하고, 금액 확인 결과를 같은 화면에 보여줍니다. 별도 시트·다이얼로그를 더하지 않아 학습 주제와 무관한 포커스·오버레이 복잡성을 피합니다. 예약은 금액 확인 후 별도 버튼 클릭으로만 확정됩니다.

UI 출제 스킬의 Montage 지침보다 Daily의 SEED 기준을 우선합니다. 정해진 인원 선택이므로 텍스트 필드나 native Select는 사용하지 않습니다.

| 역할                | 공식 컴포넌트·판단                                                                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| 참여 인원 단일 선택 | 기존 `RadioGroup`/`RadioGroupItem` 공식 스니펫. Field 구조·이름·설명·HiddenInput 연결 포함, 기본 1명, 세로 배치 |
| 확인/확정 주요 액션 | 기존 공식 `ActionButton` 스니펫. large/neutralSolid, loading/disabled, 화면에 주요 액션 하나                    |
| 오류와 성공 안내    | 공개 `Callout` 파츠. critical/positive, alert/status                                                            |
| 단계별 제목·값·배치 | `Text`/`VStack`과 공개 타이포·색·간격 props                                                                     |

라디오 label은 공개 x12 토큰으로 최소 48px 높이를 확보합니다. 공식 역할을 native 컨트롤로 대체한 예외는 없습니다. 공통 문제 메뉴도 기존 SEED Select를 유지합니다.

공식 참고: [Radio](https://seed-design.io/components/radio), [React Radio Group](https://seed-design.io/react/components/radio-group), [Action Button](https://seed-design.io/react/components/action-button), [Callout](https://seed-design.io/react/components/callout).

| 상태           | 화면과 다음 행동                          |
| -------------- | ----------------------------------------- |
| 확인 결과 없음 | 안내와 금액 확인 액션                     |
| 금액 확인 중   | 입력 잠금, 확인 진행 표시                 |
| 확인 실패      | 입력 유지, 금액 다시 확인                 |
| 금액 확인 성공 | 인원·금액, 아직 예약 전 안내, 확정 액션   |
| 인원 변경      | 확인 결과·오류 제거, 다시 확인 단계       |
| 예약 확정 중   | 확인 결과 유지, 입력 잠금, 확정 진행 표시 |
| 예약 확정 실패 | 확인 결과 유지, 같은 조건으로 확정 재시도 |
| 예약 완료      | 영수증과 성공 안내, 모든 조작 잠금        |

## 완료 조건

1. 활성 행동 테스트 8개와 HTTP 테스트 3개를 유지하며 요구사항과 문구·요청 계약을 바꾸지 않습니다.
2. 구조·이름·상태 중 한 곳 이상을 검토하고, 실제 변경 이유와 영향 범위를 근거로 개선합니다. 파일 수나 훅 수는 평가 기준이 아닙니다.
3. `note.md`에 변경 전 가설, 선택한 경계의 이득·비용, 실제 검증 결과를 직접 기록합니다. 새 기능 구현은 요구하지 않습니다.

첫 풀이 검토 후 필요할 때만 추가 변경 시나리오로 설계를 점검합니다. 출제 검증 결과와 한계는 `verification.md`에 따로 기록합니다.
