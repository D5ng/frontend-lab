# 듣는 순서와 저장된 순서의 경계

- 날짜: 2026-10-24 (Asia/Seoul)
- 유형: **리팩터링형**
- 예상 시간: **30~40분**
- 사용자 목표: 먼저 듣고 싶은 에피소드를 위로 옮기고 그 재생 순서를 저장합니다.

## 과제

`pages/PlaylistPage.tsx`는 이미 동작합니다. 아래 사용자 행동을 유지하며 가독성·예측 가능성·응집도·결합도를 근거로 재구성하세요. 기능 추가나 버그 수정은 과제가 아닙니다. 먼저 현재 책임, 상태의 원본과 변경 이유를 설명하고 필요한 경계를 선택합니다. 파일·훅 개수나 중복 제거 자체는 정답이 아닙니다. 정답 구조는 제공하지 않습니다.

## 입력과 관찰 가능한 요구사항

### 순서 편집

- 에피소드는 산책 이야기(`walk`), 저녁 음악(`music`), 짧은 인터뷰(`talk`) 세 개이며 이 순서로 시작합니다. 최초 편집 순서와 마지막 저장 순서는 같습니다. 별도 초기 조회는 하지 않습니다.
- 이름이 `편집 중인 순서`인 순서 목록에 위치 번호와 제목을 표시합니다. 에피소드마다 `제목 위로`와 `제목 아래로`라는 접근성 이름의 버튼을 제공합니다.
- 이동은 인접한 항목과 한 칸 교환합니다. 맨 위의 위로, 맨 아래의 아래로는 비활성화합니다. 항목 추가·삭제·드래그는 없습니다.
- 순서만 바꾸면 API를 호출하지 않습니다. 마지막 저장 순서는 저장 성공 전까지 바뀌지 않습니다.
- 현재 편집 순서가 마지막 저장 순서와 다르면 `저장하지 않은 변경이 있어요.`, 같으면 `저장된 순서와 같아요.`를 표시합니다. 여러 번 움직였어도 다시 같은 순서가 되면 변경 없음입니다.
- 이름이 `마지막 저장 순서`인 영역에 제목을 `→`로 이어 표시합니다. 이 영역은 현재 편집값이 아니라 마지막으로 확정된 순서를 보여 줍니다.

### 되돌리기와 안내

- `마지막 저장으로 되돌리기`는 편집 순서를 **마지막 성공 응답의 순서**로 되돌립니다. 앱 최초 순서로 고정하지 않습니다. API는 호출하지 않습니다.
- 변경이 없으면 저장·되돌리기를 모두 비활성화합니다. 비활성 이유와 이동 경계를 화면에서 설명합니다.
- 실제 이동이나 되돌리기를 하면 이전 성공·오류 안내를 지웁니다. 이동 경계의 비활성 버튼을 누르는 것은 변경으로 취급하지 않습니다.

### 비동기 저장

- `순서 저장하기`는 화면에 보이는 순서대로 ID 배열 하나를 전송합니다. 제목·위치 번호·변경 여부는 요청에 넣지 않습니다.
- 저장 중 모든 이동·되돌리기·저장 버튼을 잠급니다. 버튼의 로딩 표시와 `저장 중에는 순서를 바꾸거나 되돌릴 수 없어요.`를 표시합니다. 중복 요청을 보내지 않습니다. 요청 시작 시 이전 안내는 지웁니다.
- 실패하면 `순서를 저장하지 못했어요. 다시 시도해 주세요.`를 표시합니다. 편집 순서와 마지막 저장 순서를 각각 보존하며 변경은 남아 있습니다. 자동 재시도하지 않고 같은 버튼으로 같은 순서를 재시도할 수 있습니다.
- 성공하면 `재생 순서를 저장했어요.`를 표시합니다. **서버 응답의 확정 순서**로 편집과 마지막 저장을 함께 맞춥니다. 성공 후 변경 없음이므로 저장·되돌리기는 잠기고, 경계에 해당하지 않는 이동은 다시 가능합니다.
- 응답 순서는 요청과 다를 수 있습니다. 제공 계약은 항상 세 ID가 중복 없이 한 번씩 포함된 유효한 순서입니다. 성공 응답의 알 수 없는 ID나 부분 응답 처리는 범위 밖입니다.
- 실제 오디오 재생, 재생 위치, 여러 플레이리스트, 항목 조회·추가·삭제, 서버 동시 편집 충돌과 장기 저장은 범위 밖입니다. 모의 API에 순서 한 번을 저장하는 화면입니다. 재진입하면 고정 초기 순서부터 시작합니다.

## 작은 상황

저녁 음악을 위로 올려 저장한 다음, 짧은 인터뷰를 위로 올렸습니다. 이번 저장이 실패한 뒤 되돌리기를 누르면 최초 순서가 나올까요, 직전 성공 순서가 나올까요? 직접 화면을 조작하거나 테스트를 실행해 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**이동·저장 성공·되돌리기는 편집 순서와 변경 안내를 함께 바꿉니다. 한 경로만 수정해서 화면·요청·되돌리기 기준이 어긋나는 실수를 줄이려면 무엇을 같은 책임으로 다뤄야 할까요?**

각 데이터가 무엇을 뜻하는지, 함께 바뀌는 규칙과 독립적인 규칙은 무엇인지부터 설명하세요. 분리로 얻는 이점뿐 아니라 호출자가 지킬 약속이나 간접 참조가 늘어나는 비용도 비교합니다. 원본·파생 값의 선택과 구조는 실습자가 판단합니다.

## API와 실행 환경

```ts
interface PlaylistInput {
  orderedIds: string[]
}
interface PlaylistReceipt {
  orderedIds: string[]
}
type SavePlaylist = (input: PlaylistInput) => Promise<PlaylistReceipt>
```

`PUT /api/daily/2026-10-24/playlist`에 JSON 본문을 보냅니다. `features/playlist/apis/savePlaylist.ts`는 공통 HTTP 클라이언트를 사용하고 `Problem.tsx`가 세션별 API를 페이지에 주입합니다. API/MSW는 제공 환경이며 이번 리팩터링의 대상이 아닙니다.

모의 API는 약 0.85초 뒤 세션 첫 요청에 HTTP 503, 이후에는 받은 순서 그대로 성공합니다. 세 ID가 빠지거나 중복되면 HTTP 400입니다. 함수 주입 행동 테스트는 서버가 다른 유효한 순서를 확정하는 경우도 검사합니다. 모의 API가 같게 돌려준다는 이유로 응답을 무시하지 마세요.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-24-playlist-order
```

오늘 PR의 별도 worktree에서 실행하고 Daily 메뉴 또는 `http://localhost:5173/#2026-10-24-playlist-order`로 접근합니다. 실제 포트는 Vite 출력 기준입니다. 별도 서버 설치는 필요 없습니다.

## 화면 맥락과 공식 SEED 대응

375px에서 목적 → 변경 여부·이동 경계 안내 → 순서 목록과 이동 액션 → 마지막 저장 요약 → 결과 안내 → 되돌리기·저장 순서로 읽습니다. 짧은 3개 항목을 직접 비교하므로 인라인 목록을 사용합니다. 드래그·모달·시트를 추가하지 않습니다. 저장은 주요 액션, 되돌리기·이동은 보조 액션으로 표현합니다.

| 역할                              | 설치된 공식 대응                                                  |
| --------------------------------- | ----------------------------------------------------------------- |
| 순서 목록·에피소드·이동 액션 배치 | 공식 List/ListItem 스니펫, suffix 슬롯과 공개 HStack              |
| 이동·되돌리기·저장·로딩           | 공식 ActionButton, large 크기, 보조 neutralWeak/주요 neutralSolid |
| 성공·오류 안내                    | 공개 Callout, positive/status·critical/alert                      |
| 제목·설명·저장 요약·여백          | 공개 Text/VStack                                                  |

native 컨트롤 대체 예외는 없습니다. 텍스트 입력·선택 필드가 없는 과제이므로 TextField/Radio를 장식용으로 넣지 않습니다. 이동 버튼은 제목을 포함한 접근성 이름을 갖습니다. 목록이 고정 세 개라 빈 목록·최초 조회 로딩은 해당하지 않습니다. 변경 없음·경계·저장 중의 비활성, 오류와 성공 상태는 위 규칙대로 유지합니다.
