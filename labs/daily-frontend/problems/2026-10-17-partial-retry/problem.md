# 가게 소개는 성공했는데 후기만 실패한다면?

- 날짜: 2026-10-17 (Asia/Seoul)
- 유형: **직접 구현형**
- 예상 시간: **30~40분**
- 사용자 목표: 동네 가게의 소개와 방문 후기를 살펴보고, 일시적으로 실패한 정보만 다시 확인합니다.

## 시작하기

`starter.tsx`에서 두 조회의 시작·결과 반영·실패·재시도를 직접 구현하세요. `view.tsx`는 표현만, `api.ts`와 `handlers.ts`는 실제 fetch/MSW 환경만 제공합니다. 시작 코드는 미조회 화면만 렌더하며 아직 요청하거나 재시도하지 않습니다. 정답 로직이나 권장 상태·훅 구조는 제공하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-17-partial-retry
```

오늘 PR의 별도 worktree에서 실행하고 공통 Daily 메뉴에서 선택합니다. 직접 주소는 `http://localhost:5173/#2026-10-17-partial-retry`이며 실제 포트는 Vite 출력을 참고하세요. 별도 백엔드는 필요 없습니다.

먼저 `note.md`에 현재 이해와 설계 가설을 적어 보세요. 최근의 “한 요청이 끝났다고 다른 요청의 로딩까지 꺼도 될까?”라는 판단을, 이번에는 **동시에 유효한 두 조회**에 적용합니다. 오래된 요청을 버리는 문제와는 다릅니다.

## 관찰 가능한 요구사항

1. 진입하면 `loadProfile()`과 `loadReviews()`를 **서로의 완료를 기다리지 않고** 각각 한 번 시작합니다. 가게 소개와 방문 후기는 서로 다른 요청입니다.
2. 두 영역은 자기 요청의 로딩·성공·실패를 따릅니다. 먼저 성공한 영역은 다른 요청이 끝나지 않았더라도 즉시 내용을 표시합니다. 어느 하나의 실패가 화면 전체를 오류로 바꾸면 안 됩니다.
3. 가게 소개 실패 문구는 `가게 소개를 불러오지 못했어요. 다시 시도해 주세요.`, 후기 실패 문구는 `방문 후기를 불러오지 못했어요. 다시 시도해 주세요.`입니다. 오류와 재시도 액션은 해당 영역에만 표시합니다.
4. 실패한 영역의 **다시 불러오기**는 그 영역의 요청만 한 번 시작합니다. 이전 오류를 지우고 로딩을 표시하되, 다른 영역의 데이터·오류·로딩은 그대로 유지합니다. 성공한 영역을 함께 다시 요청하지 않습니다.
5. 요청 중인 영역의 재시도는 비활성화하고 중복 요청을 만들지 않습니다. 다른 영역도 실패했다면 그쪽의 재시도는 독립적으로 가능합니다. 양쪽 재시도가 동시에 진행되어도 됩니다.
6. 빈 후기 배열 `[]`은 정상 성공입니다. `아직 방문 후기가 없어요. 가게 소개를 먼저 살펴보세요.`를 표시하며 오류나 재시도로 바꾸지 않습니다. 아직 조회하지 않음과 빈 후기 성공을 구별하세요.
7. 재시도가 성공하면 해당 내용으로 바꾸고 그 영역의 오류·로딩을 해제합니다. 자동 재시도·전체 새로고침은 없습니다. 화면을 떠났다 돌아오면 초기 조회부터 다시 시작합니다.

### 작은 상황

소개는 성공했고 후기만 실패했습니다. 사용자가 후기 재시도를 누른 순간, 소개는 계속 읽을 수 있어야 할까요? 그 후 소개 요청을 다시 보낼 이유가 있나요?

반대로 소개가 아직 로딩 중인데 후기 재시도가 성공했다면, 어느 영역의 로딩을 끝내야 할까요? 화면을 그리거나 테스트를 실행하면서 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**같은 화면에 있다는 이유로 두 조회의 생명주기를 하나로 묶어야 할까요? 각각의 재시도가 다른 영역의 약속까지 알아야 하지 않으려면 어떤 경계가 필요할까요?**

`ShopView`의 props 하나마다 상태 하나가 필요한 것은 아닙니다. 표시 계약도 필요하면 바꿀 수 있습니다. 파일·훅 개수나 중복 제거 자체가 정답은 아닙니다. 먼저 독립적으로 바뀌어야 할 것과 함께 바뀌어야 할 것을 실제 흐름으로 설명해 보세요.

## 제공 API와 범위

```ts
interface ShopApi {
  loadProfile: () => Promise<ShopProfile>
  loadReviews: () => Promise<Review[]>
}
// ShopProfile: { name, neighborhood, description }
// Review: { id, author, body }
```

- `GET /api/daily/2026-10-17/shop/profile`: 1.2초 후 소개 성공.
- `GET /api/daily/2026-10-17/shop/reviews`: 첫 요청은 0.45초 후 503, 이후 0.45초 후 후기 2개 성공.
- API 공장마다 세션을 분리하므로 재진입하면 후기 첫 실패를 다시 경험합니다. 공통 MSW가 브라우저와 테스트에서 같은 HTTP 경로를 모킹합니다.
- 함수 주입 테스트에서는 소개만 실패, 양쪽 모두 실패, 완료 순서 역전, 빈 후기 응답도 만듭니다. 기본 모의 시나리오에서 소개가 성공한다고 실패 처리를 생략하지 마세요.
- 제공 API는 캐시·자동 재시도·요청 상태 관리를 하지 않습니다. API/MSW 작성은 풀이 대상이 아닙니다.
- 가게 전환, pagination, 후기 작성, 데이터 편집, 전역 캐시·TTL, 외부 데이터 패칭 라이브러리 추가는 범위 밖입니다. 이번에는 고정된 가게 한 곳만 다룹니다.

## 화면 맥락과 SEED 대응

375px 모바일에서 제목 → 가게 소개 → 방문 후기 순으로 읽습니다. 상세 내용은 인라인으로 표시하며, 일부 실패 때문에 이미 도착한 정보를 가리지 않습니다. 별도 모달·시트는 추가하지 않습니다. 소개와 후기를 읽는 것이 목적이라 성공 시 토스트나 확인 버튼을 더하지 않고 내용 자체를 보여줍니다.

UI 출제 스킬의 Montage 지침보다 사용자 지정 Daily SEED 기준을 우선합니다. 정보 조회 화면이므로 입력 필드·선택 컨트롤은 없습니다. 재시도 버튼은 영역 이름으로 구별되며 전체 화면 입력 잠금은 없습니다.

| UI 역할             | 공식 대응과 이유                                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 정보 영역·제목·소개 | 공개 `VStack`/`Text`, section 이름 연결과 공개 여백·타이포 props                                                            |
| 후기 목록           | 설치된 공식 v2 `List`/`ListItem` 스니펫, 이름 있는 ul/li 목록                                                               |
| 로딩 윤곽           | 공개 `Skeleton`, 전체 화면이 아닌 해당 영역에만 표시                                                                        |
| 영역별 재시도/진행  | 공식 `ActionButton` 스니펫, large/neutralWeak, loading/disabled. 독립된 보조 액션이므로 주요 버튼 여러 개를 경쟁시키지 않음 |
| 오류/빈 후기 안내   | 공개 `Callout` 파츠, critical/neutral, alert/status                                                                         |

같은 공식 역할을 native 요소로 대체한 예외는 없습니다. 이름과 상태는 영역 section과 버튼에 연결합니다. 공통 Daily 문제 선택도 기존 SEED Select를 유지합니다.

공식 참고: [List](https://seed-design.io/react/components/list), [Skeleton](https://seed-design.io/react/components/skeleton), [Action Button](https://seed-design.io/react/components/action-button), [Callout](https://seed-design.io/react/components/callout).

| 상태             | 표현과 다음 행동                                  |
| ---------------- | ------------------------------------------------- |
| 시작 코드        | 두 영역 미조회. 구현 후 최초 조회가 시작되어야 함 |
| 양쪽 로딩        | 각 영역의 진행 문구·Skeleton·비활성 진행 버튼     |
| 부분 성공        | 성공 영역 내용 + 다른 영역 로딩 또는 오류         |
| 부분 실패 재시도 | 실패한 영역만 로딩, 다른 내용/오류 유지           |
| 양쪽 오류        | 오류와 재시도 액션 각각 제공                      |
| 성공             | 소개 내용과 후기 목록                             |
| 빈 후기          | 정상 빈 목록 안내, 불필요한 재시도 없음           |

### 고정 표현 미리보기

개발 서버에서 `?partial-retry-preview=partial#2026-10-17-partial-retry`처럼 query를 hash **앞에** 붙일 수 있습니다. 값은 `idle`, `loading`, `partial`, `retrying`, `profileError`, `success`, `empty`입니다. 고정 props의 **표현 검수 전용**이며 클릭해도 상태가 전이되거나 API 요청이 발생하지 않습니다. query를 제거하면 실제 풀이 화면으로 돌아갑니다. 프로덕션 빌드에는 미리보기가 적용되지 않습니다.
