# 작성 중인 코드와 확인된 쿠폰

- 유형: 직접 구현형
- 예상 시간: 30~40분
- 사용자 목표: 현재 입력한 코드로 확인된 쿠폰만 할인에 적용한다.

## 핵심 설계 질문

**입력 원본·확인 요청·사용 가능한 쿠폰의 유효 기간은 어디에서 구분해야 할까요?**

`pages/CouponFormPage.tsx`의 `CouponFormPage`를 직접 구현하세요. 입력만 연결되어 있으며 요청·할인 적용은 미구현입니다. `features/couponForm/components/CouponView.tsx`의 props는 화면 표현 계약이지 상태 구조의 정답이 아닙니다. 주입 경계 `checkCoupon`은 유지하고 그 밖의 파일·훅 개수는 자유입니다.

## 요구사항

1. 최초 입력은 비어 있습니다. 확인 버튼은 활성, 할인 적용 버튼은 비활성입니다. 빈 값 또는 공백만 확인하면 필드 오류 `쿠폰 코드를 입력해 주세요.`를 표시하고 요청하지 않습니다. 자동 요청은 없습니다.
2. 확인 시 원본을 `trim().toUpperCase()`한 문자열 하나로 API를 요청합니다. 화면 입력 원본은 공백·소문자까지 그대로 유지합니다. 요청 시작 시 이전 확인·적용·오류 안내를 제거합니다. 확인 중 확인·적용 버튼을 잠그지만 **입력은 계속 가능합니다**.
3. 실제 입력 변경은 이전 쿠폰·적용·오류·확인 중 안내를 즉시 무효화하고 새 확인을 가능하게 합니다. 같은 원본 값은 변경이 아닙니다. **정규화 결과가 같아도 원본이 달라지면 재확인이 필요합니다.** WELCOME → SALE → WELCOME으로 돌아오는 것도 새 입력 이력입니다. 이전 요청은 실제로 취소되지 않습니다.
4. 현재 유효한 확인 요청의 성공·실패·완료만 반영합니다. 오래된 성공이 적용을 활성화하거나, 오래된 실패가 현재 쿠폰을 지우거나, 오래된 완료가 새 요청의 진행 상태를 끝내면 안 됩니다. 같은 코드의 이전 요청도 재사용하지 않습니다.
5. available=true면 응답의 쿠폰 코드·할인 금액을 표시하고 적용을 활성화합니다. available=false는 API 오류가 아닙니다. `사용할 수 없는 쿠폰이에요. 다른 코드를 입력해 주세요.`를 표시하며 적용은 잠급니다. 요청 실패는 `쿠폰을 확인하지 못했어요. 다시 확인해 주세요.`를 표시합니다. 두 경우 모두 원본을 유지하고 다시 확인할 수 있습니다.
6. 할인 적용은 현재 유효한 확인 결과를 로컬 화면에 확정하는 동작입니다. API 요청은 추가하지 않습니다. `{code} 쿠폰으로 {discount를 천 단위 포맷한 값}원 할인을 적용했어요.`를 유지하고 반복 적용을 잠급니다. 실제 입력 변경 또는 새 확인으로 이 적용 확인을 제거합니다. 확인 성공만으로 적용 완료라고 표시하지 않습니다.

## 제공하는 입력·API·환경

모의 API는 정규화된 문자열을 받습니다. WELCOME은 1.6초 뒤 2,000원, SALE은 0.6초 뒤 3,000원 쿠폰을 반환합니다. RETRY는 첫 요청만 실패하고 이후 3,000원 쿠폰을 반환합니다. 그 밖의 코드는 0.6초 뒤 사용 불가를 반환합니다. 모의 서버는 요청 취소를 지원하지 않습니다. API가 결과를 주더라도 현재 화면에 쓸지 판단하는 로직은 제공하지 않습니다. HTTP 요청은 MSW가 가로채며 실제 결제·서버 저장은 없습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily
pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-11-coupon-check/pages/CouponFormPage.spec.tsx
pnpm --filter @frontend-lab/daily-frontend build
```

Daily에서 오늘 문제를 선택하거나 `#2026-10-11-coupon-check`로 진입합니다. 행동 테스트의 `describe.skip`을 `describe`로 바꾸어 풀이를 확인하세요. 활성 UI/API 검사는 준비물 검증일 뿐 풀이 완료를 뜻하지 않습니다.

## 화면 맥락·상태·SEED

짧은 코드 입력 → 확인 → 할인 적용의 인라인 폼입니다. 선택 목록·상세 화면이 없는 목적이라 List·Radio·Select·시트는 필요하지 않습니다. 즉시 확인 결과와 적용 완료를 구분하기 때문에 두 액션을 분리하고 공식 ActionButton neutralWeak/neutralSolid large로 위계를 줍니다. 단일 입력은 공식 TextField/TextFieldInput underline, 라벨·설명·필드 오류는 통합 Field 스니펫을 사용합니다. API 실패는 공식 Callout critical·alert, 사용 불가는 neutral·status, 적용 성공은 positive·status입니다. 사용자가 이후 판단할 정보이므로 사라지는 토스트 대신 인라인으로 유지합니다. 배치는 공식 VStack/HStack/Text와 공개 x2/x4/x6 토큰을 사용합니다. 지정된 SEED 기준이 출제 스킬의 Montage 기준보다 우선합니다.

| 상태     | 화면 계약                                                   |
| -------- | ----------------------------------------------------------- |
| Empty    | 빈 입력, 먼저 확인하라는 안내, 적용 비활성                  |
| Loading  | 확인 진행 안내·버튼 스피너, 입력 활성·두 버튼 비활성        |
| Error    | 필드 오류 또는 확인 실패, 원본 유지·재확인 가능             |
| Disabled | 유효한 확인 결과가 없거나 진행·적용 완료면 적용 비활성      |
| Success  | 확인 성공은 적용 가능, 적용 성공은 확정 안내·반복 적용 잠금 |

UI 검수용 `?coupon-preview=empty`, `invalid`, `checking`, `error`, `unavailable`, `verified`, `applied`는 **정적 화면**입니다. 예: `/?coupon-preview=checking#2026-10-11-coupon-check`. 조회나 상태 전이를 구현하지 않으며 콜백은 비어 있습니다. 풀이할 때 query를 지우세요. 확인 중 입력 활성은 이 문제의 의도적 요구사항으로, 일반 폼 전체 잠금 규칙과 다릅니다.

## 출제 시 검증 범위

- 별도 worktree에서 frozen lockfile 설치, 전체 lint·format·test·build(TypeScript 검사 포함)를 실행했습니다. 오늘 UI·API 테스트 10개 통과, 구현할 행동 8개는 의도적 skip입니다. Daily 전체 35개 통과·12개 skip(오늘 8개와 이전 10월 2일 4개), code-quality 22개 통과입니다. skip은 풀이 완료가 아닙니다.
- 실제 브라우저 375×812에서 스타터 입력·빈 콜백 동작과 정적 상태 7개를 확인했습니다. 라벨 연결·버튼 52px, 가로 넘침 없음(scrollWidth 375px), 확인 중 입력 활성·버튼 비활성, 필드·API 오류와 사용 불가·확인 성공·적용 성공의 표시를 확인했습니다. error/warn 로그는 없었습니다. **요청 순서·입력 무효화·재확인·적용 상태 전이는 미구현·미검증**이며 실제 휴대폰·스크린리더 음성 출력은 확인하지 않았습니다.
- 설치본 React 2.5.1의 CSS peer ^2.8.0과 CSS 2.8.3 조합을 확인했습니다. 오늘 사용하는 TextField·ActionButton 스니펫과 Callout의 타입·실제 렌더링을 확인했습니다. `seed-design compat` 전체 검사는 기존 ui:list의 최신 registry 요구 CSS ^3.0.0과 설치본 ^2.8.3의 차이로 실패합니다. 오늘은 List를 사용하지 않으며 기존 스니펫·의존성·lockfile은 변경하지 않았습니다. 미완성 행동과 이 호환성 검사 실패를 명시한 Draft PR로 제공합니다.

## MSW 요청 환경

`features/couponForm/apis/`의 함수는 실제 `fetch`를 호출하고, 문제 폴더 바로 아래의 `handlers.ts`가 기존 지연·첫 실패·성공 응답을 HTTP로 모킹합니다. 함수 주입 경계와 실습 요구사항은 유지합니다. HTTP 503 응답의 `message`는 API 함수가 Error로 변환하고, 사용 불가나 빈 목록은 정상 JSON 응답으로 처리합니다.

API 공장 함수마다 독립적인 모의 서버 세션을 사용하므로 화면 재진입 시 첫 실패 횟수가 초기화됩니다. 요청 취소나 오래된 응답의 화면 반영 여부는 MSW가 해결하지 않습니다. 기존 함수 주입 행동 테스트로 응답 순서를 제어하고, 제공 API 테스트는 실제 HTTP 경로를 검증합니다. MSW 작성은 풀이 대상이 아닙니다.

기존 출제 시 검증 기록은 전환 전 기록입니다. MSW 전환 후의 검증 결과는 PR의 검증 항목에서 확인합니다.
