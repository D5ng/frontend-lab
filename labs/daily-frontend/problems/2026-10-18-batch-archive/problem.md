# 일부만 보관됐다면 무엇을 남길까?

- 날짜: 2026-10-18 (Asia/Seoul)
- 유형: **리팩터링형**
- 예상 시간: **30~40분**
- 사용자 목표: 다 본 관심 상품을 정리하고, 보관하지 못한 상품만 다시 시도합니다.

## 시작하기

`starter.tsx`는 이미 동작합니다. 기능 추가나 버그 수정이 아니라 **외부 동작을 유지하는 재구성**이 과제입니다. 먼저 화면과 테스트를 실행하고 `note.md`에 현재 책임과 설계 가설을 적어 보세요. 암산으로 실행 순서를 맞히는 과제가 아닙니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-18-batch-archive
```

오늘 PR의 별도 worktree에서 실행합니다. 공통 Daily 메뉴에서 선택하거나 `http://localhost:5173/#2026-10-18-batch-archive`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 백엔드는 필요 없습니다.

## 관찰 가능한 요구사항

1. 처음에는 원목 의자·책상 조명·작은 책장이 모두 미선택입니다. 선택 개수와 남은 상품 개수를 표시합니다. 선택이 없으면 보관 버튼은 비활성입니다.
2. 제출하면 **선택한 ID만 한 번** 보냅니다. 요청 중에는 선택과 제출을 잠그고 `보관 중`을 표시합니다. 응답 전에 상품을 미리 제거하지 않습니다.
3. 응답의 `succeededIds`에 있는 상품만 목록에서 제거합니다. `failedIds`에 있는 상품은 선택된 채 남깁니다. 요청하지 않은 상품은 미선택 상태로 그대로 남습니다. 이후 같은 버튼을 누르면 남은 선택만 보냅니다.
4. 전체 성공은 `N개를 보관했어요.`, 부분 성공은 `N개를 보관했어요. M개는 다시 시도해 주세요.`, 전부 실패한 응답은 `보관하지 못했어요. 선택한 상품을 다시 시도해 주세요.`로 알립니다. N/M은 **이번 응답**의 개수입니다.
5. 요청 자체가 거절되면 목록·선택을 바꾸지 않고 `요청을 완료하지 못했어요. 선택은 그대로예요. 다시 시도해 주세요.`를 표시합니다. 완료 후 다시 조작할 수 있어야 합니다.
6. 새 요청을 시작하거나 선택을 바꾸면 이전 결과 안내를 지웁니다. 목록이 모두 비면 `모든 상품을 정리했어요. 더 보관할 상품이 없어요.`와 마지막 성공 안내를 함께 남기고 제출을 비활성화합니다.

### 작은 상황

의자와 조명을 선택해 보관했는데 의자만 성공했습니다. 목록에는 조명과 책장이 남고, 조명만 선택되어야 합니다. 다시 보낼 ID는 무엇일까요? 성공한 의자를 다시 보내거나, 요청하지 않은 책장을 선택해 버리지 않는지 관찰하세요.

## 핵심 설계 질문

**한 응답으로 목록 제거·재시도 선택·결과 안내가 함께 바뀝니다. 이 규칙들이 서로 어긋나지 않도록 어떤 책임 경계를 두겠어요?**

[Frontend Fundamentals의 네 기준](https://frontend-fundamentals.com/code-quality/code/)으로 변경 이유를 설명해 보세요. 결과 해석이 읽기 쉬운지(가독성), 이름과 동작이 맞는지(예측 가능성), 함께 바뀌는 규칙이 가까운지(응집도), 다른 코드가 알아야 할 약속이 줄었는지(결합도)를 참고합니다. 파일·훅 개수, 중복 제거 자체는 정답이 아닙니다. 작은 코드를 그대로 두는 선택도 근거로 설명할 수 있습니다. 권장 파일 분할이나 완성 구조는 제공하지 않습니다.

## API와 실행 환경

```ts
type ArchiveProducts = (productIds: string[]) => Promise<{
  succeededIds: string[]
  failedIds: string[]
}>
```

- `api.ts`는 공통 HTTP 클라이언트, `handlers.ts`는 브라우저/Vitest 공통 MSW를 사용합니다. `POST /api/daily/2026-10-18/archive`, body는 `{ productIds: string[] }`입니다.
- 약 1초 후 응답합니다. 세션의 **첫 요청에 조명이 포함되면 조명만 실패**, 나머지는 성공합니다. 이후 요청은 모두 성공합니다. 화면에 다시 진입하면 새 세션입니다.
- 응답의 두 배열은 요청 ID를 중복·누락 없이 나눕니다. 요청하지 않은 ID는 오지 않는다는 API 계약입니다. API/MSW는 풀이 대상이 아닙니다.
- UI 테스트는 전체 실패와 네트워크 거절도 주입합니다. 기본 모의 서버에 없는 경로도 유지하세요.
- 필터·전체 선택·낙관적 제거·실행 취소·동시 배치·새로고침 후 영속화·외부 상태 라이브러리 추가는 범위 밖입니다. 보관은 삭제가 아닌 목록 정리이며 실제 서비스의 복구 화면은 이번 범위에서 다루지 않습니다.

## 화면 맥락과 공식 SEED 대응

375px에서 제목 → 상품 선택 → 선택 수·결과 → 주요 보관 액션 순으로 읽습니다. 체크 행 전체가 선택 영역이고, 행 안에 별도 액션을 넣지 않습니다. 재시도 판단에 필요한 결과는 사라지는 토스트 대신 인라인으로 남깁니다. 입력·요약·제출은 같은 form 안에 있습니다. 장식용 카드·모달은 추가하지 않습니다.

UI 출제 스킬의 Montage 지침보다 사용자 지정 SEED Design 기준을 우선합니다.

| 역할                | 공식 컴포넌트와 선택 이유                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 상품 목록·복수 선택 | 설치된 공식 v2 `List`/`ListCheckItem` 스니펫 + 공개 `Checkbox.Control`/`Indicator`. 3개 이하 선택 행에 ghost/neutral/large 사용 |
| 제출·로딩·비활성    | 공식 `ActionButton` 스니펫, large/neutralSolid 한 개의 주요 액션                                                                |
| 결과 안내           | 공개 `Callout` 파츠, 성공 positive/status, 부분·전체 실패 critical/alert                                                        |
| 제목·설명·배치      | 공개 `Text`/`VStack`, 공개 타이포·색·여백 props                                                                                 |

같은 역할의 공식 컴포넌트를 native로 대체한 예외는 없습니다. 별도 텍스트 필드나 단일 선택은 필요 없습니다. 목록의 체크 행은 label이므로 부모는 이름 있는 `div role="group"`으로 구성합니다.

공식 참고: [List](https://seed-design.io/react/components/list), [Checkbox](https://seed-design.io/react/components/checkbox), [Action Button](https://seed-design.io/react/components/action-button), [Callout](https://seed-design.io/react/components/callout).

| 상태                    | 표현과 다음 행동                                 |
| ----------------------- | ------------------------------------------------ |
| 진입·선택 없음          | 3개 목록, 선택 0개, 비활성 이유                  |
| 선택                    | 선택 수 갱신, 제출 가능, 이전 안내 제거          |
| 요청 중                 | 기존 목록 유지, 체크·버튼 잠금, 진행 문구        |
| 부분 성공               | 성공 항목 제거, 실패 항목 선택 유지, 재시도 안내 |
| 전체 실패·네트워크 오류 | 목록·선택 유지, 원인별 안내, 재시도 가능         |
| 성공·빈 목록            | 이번 성공 수, 남은 목록 또는 빈 목록 안내        |

## 완료 조건

1. 기존 행동 테스트 8개와 HTTP 환경 테스트 3개를 유지하고 통과합니다. 구조에 맞춰 import를 조정할 수 있지만 행동을 삭제하거나 skip하지 않습니다.
2. 화면에서 부분 성공 → 실패한 상품만 재시도 → 성공을 확인합니다. 구조 변경 전후의 외부 동작이 같아야 합니다.
3. `note.md`에 선택한 경계, 대안과 비용, 실제 확인한 근거를 직접 기록합니다. 추가 기능은 요구하지 않습니다.

출제 시 실행한 검사와 375px 검수 범위·한계는 `verification.md`에 기록합니다. 추가 변경 시나리오는 첫 풀이 검토 후 필요할 때만 다룹니다.
