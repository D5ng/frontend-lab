# 숨겨진 내보내기 옵션은 어디까지 보낼까?

- 날짜: 2026-10-22 (Asia/Seoul)
- 유형: **리팩터링형**
- 예상 시간: **30~40분**
- 사용자 목표: 함께 한 작업의 활동 기록을 원하는 형식으로 내보내기 신청합니다.

## 과제

`pages/ExportPage.tsx`는 이미 동작하는 화면입니다. 아래 외부 동작을 유지하면서 가독성·예측 가능성·응집도·결합도를 근거로 재구성하세요. 기능 추가나 버그 수정이 과제가 아닙니다. 현재 책임과 변경 이유를 먼저 읽고, 필요한 경계만 선택하세요. 파일 수·훅 수·중복 제거 자체는 평가 기준이 아닙니다. 정답 구조는 제공하지 않습니다.

## 입력과 관찰 가능한 요구사항

### 형식과 옵션

- 파일 형식은 CSV/PDF 중 하나이며 기본값은 CSV입니다.
- CSV는 열 구분(쉼표/탭), PDF는 문서 내용(작업 제목만/작업 제목과 메모)을 고릅니다. 기본값은 각각 쉼표/작업 제목만입니다.
- 현재 형식의 옵션만 화면에 표시합니다. **숨겨진 옵션은 보존**하며 형식을 왕복하면 직전 선택으로 돌아옵니다. CSV의 탭을 고르고 PDF에서 메모 포함을 고른 뒤 CSV로 돌아오면 탭입니다.
- 숨겨진 값은 보존하더라도 요약이나 요청에 섞이지 않습니다. CSV 요청에는 `detail`이, PDF 요청에는 `delimiter`가 없어야 합니다.

### 이름과 요약

- 파일 이름 기본값은 `활동 기록`입니다. 입력 자체의 공백은 유지합니다. 요약과 요청에는 앞뒤 공백을 제외한 이름을 사용합니다. 확장자는 현재 형식에 맞춰 자동으로 붙입니다.
- 공백 제외 후 비어 있으면 신청 버튼을 비활성화합니다. 빈 상태 안내는 이름 입력을 유도합니다.
- 제출 시 공백 제외 이름의 길이는 1~20이며 마침표(`.`), 슬래시(`/`), 역슬래시(`\`)를 허용하지 않습니다. 길이는 JavaScript 문자열의 `.length` 기준입니다. 확장자를 직접 입력하지 않습니다.
- 잘못된 이름이면 필드에 `이름은 1~20자로, 마침표와 슬래시 없이 입력해 주세요.`를 표시하고 요청하지 않습니다. 입력을 잘라내거나 자동 교정하지 않습니다.
- `내보내기 요약`에는 이름+확장자와 현재 옵션 설명을 즉시 표시합니다. 이름이 비면 `이름을 입력해 주세요`에 확장자를 붙여 표시합니다. 유효하지 않은 이름도 수정 중인 내용 그대로 보여 주며 요약이 검증 성공을 의미하지 않습니다.
- 이름·형식·현재 옵션을 변경하면 기존 필드 오류, 요청 실패, 성공 안내를 지웁니다. 이름이나 다른 형식을 바꾸어도 각 형식의 옵션은 유지합니다.

### 비동기 접수

- 신청 중 이름·형식·옵션·신청 버튼을 모두 잠급니다. `접수 중`과 비활성 이유를 표시하고 중복 클릭으로 요청을 늘리지 않습니다.
- 실패하면 `내보내기를 접수하지 못했어요. 다시 시도해 주세요.`를 표시합니다. 모든 입력을 보존하고 같은 버튼으로 같은 내용을 재시도할 수 있습니다. 자동 재시도는 하지 않습니다.
- 성공하면 **서버 응답의 파일 이름**으로 접수 사실을 알립니다. 입력과 옵션은 그대로이며 조작은 다시 열립니다. 같은 설정으로 중복 신청하지 못하도록 신청 버튼만 비활성화합니다.
- 성공 후 이름·형식·현재 옵션을 변경하면 이전 성공 안내를 지우고 새 신청을 허용합니다. 원래 값으로 되돌렸더라도 실제 변경이 있었다면 새 신청할 수 있습니다.
- 실제 파일 생성·다운로드·진행률·인증·서버 작업 큐·기록 목록 조회는 범위 밖입니다. 모의 API의 접수 완료까지만 표현합니다.

## 작은 상황

CSV에서 탭을 선택한 다음 PDF에서 메모 포함을 선택했습니다. 지금 서버로 보내야 하는 옵션과 화면이 기억해야 하는 옵션은 같을까요? 화면을 직접 오가거나 테스트를 실행해 확인해도 됩니다. 코드를 암산하는 문제가 아닙니다.

## 핵심 설계 질문

**화면이 기억할 편집 값과 현재 형식으로 보낼 값은 다릅니다. 이 경계를 어디에서 책임지게 하면, 새 옵션을 바꿀 때 화면 요약과 요청이 서로 어긋나는 실수를 줄일 수 있을까요?**

선택한 경계가 읽는 흐름을 얼마나 쉽게 하는지, 호출자가 지켜야 할 약속이나 불필요한 인자가 늘지는 않는지도 비교하세요. 이름·검증·요청·결과 안내가 함께 있다는 사실만으로 전부 분리할 필요는 없습니다.

## API와 실행 환경

```ts
type ExportInput = { format: 'csv'; name: string; delimiter: 'comma' | 'tab' } | { format: 'pdf'; name: string; detail: 'summary' | 'full' }
interface ExportReceipt {
  id: string
  fileName: string
}
type RequestExport = (input: ExportInput) => Promise<ExportReceipt>
```

`POST /api/daily/2026-10-22/exports`에 JSON 본문을 보냅니다. `features/exportRequest/apis/requestExport.ts`는 공통 HTTP 클라이언트를 사용하고 `Problem.tsx`는 세션별 API를 페이지에 주입합니다. API와 MSW는 제공 환경이며 풀이 대상이 아닙니다.

모의 API는 약 0.9초가 걸립니다. 화면 재진입마다 첫 요청은 HTTP 503, 이후 요청은 `{ id, fileName: 이름.형식 }`으로 성공합니다. 이름과 옵션 검증·요약은 서버가 대신하지 않습니다. 행동 테스트는 서버가 다른 파일 이름을 확정하는 상황도 고정합니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-22-export-request
```

오늘 PR의 별도 worktree에서 실행합니다. Daily 메뉴 또는 `http://localhost:5173/#2026-10-22-export-request`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 서버 설치는 필요 없습니다.

## 화면 맥락과 SEED 대응

375px에서 목적 → 형식 → 이름 → 현재 옵션 → 요약 → 결과 → 신청 순으로 읽습니다. 선택지가 두 개이고 서로 비교하며 설정하는 짧은 흐름이므로 인라인 RadioGroup을 사용하며 모달·시트는 추가하지 않습니다. 결과는 설정 변경 전까지 다시 확인할 수 있도록 인라인에 남깁니다.

| 역할                | 설치된 공식 대응                                                     |
| ------------------- | -------------------------------------------------------------------- |
| 형식·세부 옵션      | 공식 RadioGroup/RadioGroupItem 스니펫, 그룹 라벨·48px 최소 터치 영역 |
| 이름·필드 오류      | 공식 TextField/TextFieldInput 스니펫, 라벨·설명·invalid 상태         |
| 신청·로딩·비활성    | 공식 ActionButton, large/neutralSolid                                |
| 성공·요청 오류      | 공개 Callout 파츠, positive/status·critical/alert                    |
| 정보 계층·요약·배치 | 공개 Text/VStack, 의미 있는 header/form/aside                        |

native 컨트롤로 대체한 예외는 없습니다. 빈 입력은 신청 불가와 안내로, 요청 대기는 버튼과 이유로, 오류는 필드/접수 오류로, 성공은 서버 파일명으로 표시합니다. 고정 입력만 있는 화면이라 목록 빈 결과·초기 조회 로딩은 해당하지 않습니다.

## 완료 조건

1. 활성 페이지 행동 테스트 7개와 HTTP 계약 테스트를 통과하고 유지합니다. 구조에 맞춰 import를 바꿀 수 있지만 행동을 삭제하거나 skip하지 않습니다.
2. 실제 화면에서 CSV/PDF 왕복, 숨겨진 값 보존과 요약 변경, 이름 오류, 실패 → 재시도 → 성공 → 설정 변경 후 새 신청을 확인합니다.
3. `note.md`의 빈 항목에 본인이 선택한 책임·경계·트레이드오프와 검증 근거를 기록합니다. 기능 추가는 요구하지 않습니다.

로컬 `docs/daily-assignment-guide` 브랜치의 AUTHORING을 읽어 적용했습니다(원본/develop에는 아직 없음). 그 브랜치의 변경은 포함하지 않았습니다. 문제는 저장소 실습만 근거로 새로 작성했고 외부 과제·코드·풀이를 사용하지 않았습니다. 출제 검증 범위는 `verification.md`에 기록합니다.
