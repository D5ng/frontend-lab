# 새 재고와 작성 중인 장바구니

- 날짜: 2026-10-25 (Asia/Seoul)
- 유형: **직접 구현형 · 한 페이지 과제**
- 예상 시간: **40~60분** (AUTHORING 기준 우선)
- 사용자 목표: 담을 상품의 수량을 정하고 현재 가격·재고로 유효한 장바구니 합계를 확인합니다.

## 과제 범위

`pages/CartStockPage.tsx`를 요구사항만 보고 완성하세요. 제공 페이지에는 SEED 제목·설명·레이아웃만 있습니다. 조회·상품별 입력·검증·합계 로직은 없습니다. 정답 코드, 훅 이름, 권장 분리 구조를 제공하지 않습니다. 파일 수나 훅 수는 정답이 아닙니다.

재료는 **서버 목록 조회, 상품별 숫자 입력, 현재 재고 검증, 합계 결과** 네 가지입니다. 필터·정렬·체크박스 선택·주문·결제·배송비·장바구니 저장 API는 없습니다. 수량이 양수인 상품이 담긴 것으로 해석하고 합계를 확인하는 한 페이지에서 끝냅니다. 상품과 가격은 실습용 가상 데이터이며 실제 거래는 일어나지 않습니다.

## 기능별 요구사항

### 1. 상품 정보 조회

- 진입하면 API를 호출합니다. 최초 완료 전에는 `상품을 불러오고 있어요.`를 표시합니다. 대기·실패를 빈 성공으로 표시하지 않습니다.
- 접근성 이름에 `가격·재고 새로고침`이 포함된 버튼을 제공합니다. 조회 중 재조회 버튼과 존재하는 모든 수량 입력을 잠그고 중복 재조회를 하지 않습니다. 조회 중에는 입력할 수 없다는 이유도 표시합니다.
- 최초 실패는 `상품을 불러오지 못했어요. 다시 시도해 주세요.`와 재시도 가능한 같은 버튼을 제공합니다. 자동 재시도는 없습니다.
- 재조회가 시작되면 이전 조회 오류를 지웁니다. 이미 목록이 있으면 기존 목록·수량·합계를 표시한 채 조작을 잠급니다. 그 합계는 아직 이전에 조회한 정보 기준입니다.
- 재조회 실패는 기존 목록·입력·합계를 보존하고 조회 오류를 추가합니다. 재조회와 입력을 다시 허용합니다. 수량을 편집하는 것만으로 조회 실패 안내를 숨기지 않습니다.
- 성공하면 목록을 서버 응답 순서대로 최신 데이터로 교체합니다. 같은 ID가 남아 있으면 작성 수량을 그대로 보존합니다. 새 ID는 `'0'`으로 시작합니다. 사라진 ID는 입력과 합계에서 제거하고 기억하지 않습니다. 나중에 다시 등장해도 새 상품처럼 0으로 시작합니다.
- 최신 재고가 줄어도 수량을 **자동으로 줄이지 않습니다.** 보존된 수량을 최신 재고로 다시 검증하여 사용자가 수정하게 합니다. 가격은 새 응답 가격으로 합계를 다시 계산합니다.
- 성공 `[]`는 `지금 담을 수 있는 상품이 없어요. 다시 불러와 주세요.`를 표시하고 입력은 모두 제거합니다. 합계는 0개/0원이며 재조회 액션을 제공합니다. 오류가 아닙니다.

### 2. 상품별 수량

- 상품마다 이름·단가·현재 재고와 `상품명 수량` 라벨이 있는 **텍스트 입력**을 제공합니다. `inputMode="numeric"`를 검토하고, 단가·재고를 입력칸 라벨만으로 대체하지 않습니다. 예: `감자빵 수량`.
- 새 상품 입력은 `'0'`입니다. 조작마다 숫자(`0`~`9`)만 남기고 최대 두 자리로 제한합니다. 예: `a2b`는 `2`, `123`은 `12`입니다. 입력을 확정하는 별도 버튼이나 debounce는 없습니다.
- 편집 중 빈 문자열은 그대로 표시하고 수량 계산에서는 0으로 해석합니다. 빈 칸 자체는 오류가 아닙니다. 숫자를 입력할 때까지 0으로 강제 치환하지 않습니다.
- **앞자리 0이 있는 `02`를 입력·포커스 해제 시 어떻게 표시할지는 정하지 않았습니다.** 계산값은 2여야 합니다. 일관된 표시 기준을 정하고 note에 이유를 적으세요. 이 표시 선택을 강제하는 고정 테스트는 없습니다.
- 수량은 0 이상 현재 재고 이하에서 유효합니다. 재고와 같으면 허용합니다. 재고 0인 상품도 입력은 열어 두며, 0/빈 값은 유효하고 양수는 오류입니다.
- 재고를 넘으면 입력을 유지하고 해당 필드를 invalid로 표시하며 `상품명은 N개까지 담을 수 있어요.`를 표시합니다. 예: `감자빵은 1개까지 담을 수 있어요.`. 숫자 제한과 재고 검증을 혼동해 입력을 몰래 교정하지 않습니다.
- 오류는 입력·새 응답에 따라 즉시 갱신합니다. 유효 수량으로 바꾸면 필드 오류를 지웁니다. 수량 입력만으로 API를 호출하지 않습니다.

### 3. 합계 결과

- 접근성 이름이 `장바구니 합계`인 region을 제공합니다.
- 모든 현재 수량이 유효하면 총 수량 `N개`와 총 상품 금액 `N원`을 표시합니다. 총 수량은 상품 종류 수가 아니라 입력 수량의 합입니다. 금액은 최신 단가 × 수량을 더한 값이며 `ko-KR` 천 단위 구분을 사용합니다.
- 모두 0/빈 값이면 0개/0원입니다. 별도 상품 선택 상태는 요구하지 않습니다.
- 하나라도 재고 초과면 합계의 수량·금액 대신 `수량을 확인해 주세요.`를 표시합니다. 일부 유효 상품만 더하거나 이전 금액을 확정 합계처럼 남기지 않습니다. 모든 입력이 유효해지면 합계 표시를 복원합니다.
- 조회 중에는 이전 합계/오류 결과를 유지할 수 있지만 새 조회 완료 전까지 과거 데이터라는 맥락을 알려야 합니다. 최초 목록 전에는 합계를 숨기거나 0으로 표시할 수 있습니다. 이 최초 표현은 고정 테스트로 강제하지 않습니다.

## 작은 상황

감자빵 2개를 입력한 뒤 새로고침하니 재고가 1개가 됐습니다. 사용자가 적은 2를 없애는 것과, 2를 유지하면서 합계를 보류하는 것은 누구의 판단을 바꾸는 걸까요? 실제 화면이나 테스트를 실행해 확인해도 됩니다. 암산 과제가 아닙니다.

## 핵심 설계 질문

**재고·가격은 서버가 바꾸고 수량은 사용자가 씁니다. 둘 중 하나가 바뀌었을 때 같은 상품의 입력을 보존하면서도 검증과 합계가 최신 규칙을 따르게 하려면, 무엇을 원본으로 삼고 경계를 어디에 두겠어요?**

입력 표시 해석, 사라진 상품의 처리, 검증·합계를 함께 바꿀 이유와 선택한 책임의 비용을 직접 설명하세요. 특정 상태 구조나 폴더 분할을 답으로 지정하지 않습니다.

## API 명세

```ts
interface Product {
  id: string
  name: string
  price: number
  stock: number
}
type LoadProducts = () => Promise<Product[]>
```

`GET /api/daily/2026-10-25/products`이며 query·본문은 없습니다. 응답은 ID가 중복되지 않는 상품 배열이고 가격은 0 이상의 정수, 재고는 0~99의 정수입니다. `features/cartStock/apis/fetchProducts.ts`는 공통 HTTP 클라이언트를 사용하고 `Problem.tsx`는 세션별 API를 페이지에 주입합니다. `handlers.ts`는 공통 MSW에 자동 등록됩니다. API/MSW는 제공 환경이며 입력·검증·합계를 대신 관리하지 않습니다.

모의 API는 매번 약 0.8초가 걸립니다. 세션 첫 요청은 HTTP 503, 두 번째는 기본 목록, 세 번째 이후는 변경 목록입니다. 화면을 다시 열면 첫 실패부터 시작합니다.

| ID     | 이름     | 두 번째 요청: 가격/재고 | 세 번째 이후: 가격/재고 |
| ------ | -------- | ----------------------- | ----------------------- |
| bread  | 감자빵   | 3,500원 / 5개           | 3,500원 / 1개           |
| juice  | 사과주스 | 2,500원 / 4개           | 3,000원 / 4개           |
| soup   | 수프     | 6,000원 / 2개           | 제거                    |
| cookie | 쿠키     | 없음                    | 2,000원 / 3개           |

함수 주입 행동 테스트에서는 재조회 실패·빈 성공·품절·삭제 후 재등장을 추가로 만듭니다. 기본 모의 시나리오만 보고 오류 처리를 생략하지 마세요.

## UI와 실행 환경

375px에서 목적 → 조회 상태·새로고침 → 상품별 이름·단가·재고·수량 → 합계 순으로 읽습니다. 같은 상품의 정보와 수량은 인라인으로 묶어 입력 직전에 재고를 볼 수 있게 합니다. 모달·시트·확정 단계는 추가하지 않습니다.

| 역할                        | 설치된 공식 SEED 대응                                                              |
| --------------------------- | ---------------------------------------------------------------------------------- |
| 상품 정보 목록·상품별 묶음  | List/ListItem 공식 스니펫 또는 공개 VStack 기반 의미 있는 목록                     |
| 수량·라벨·재고 초과         | 공식 TextField/TextFieldInput 스니펫, label·invalid·errorMessage·numeric 입력 모드 |
| 새로고침·로딩·비활성        | 공식 ActionButton, 비활성 이유·진행 안내                                           |
| 조회 오류·빈 성공           | 공개 Callout 및 재시도 액션                                                        |
| 조회 중 목록 자리·계층·합계 | Skeleton/진행 안내, 공개 Text/VStack                                               |

같은 역할의 native input/button에 토큰만 입혀 대신하지 마세요. 설치된 스니펫의 실제 콜백·공개 타입을 확인하세요. 수량 입력의 접근성 이름, 오류 연결, 48px 이상의 주요 조작 영역과 가로 넘침을 실제로 검수합니다. 골격은 이 UI를 미리 완성하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily --host 127.0.0.1
pnpm --filter @frontend-lab/daily-frontend test problems/2026-10-25-cart-stock
```

오늘 PR의 별도 worktree에서 실행하고 Daily 메뉴 또는 `http://localhost:5173/#2026-10-25-cart-stock`로 접근하세요. 실제 포트는 Vite 출력 기준입니다. 별도 백엔드 설치는 필요 없습니다.
