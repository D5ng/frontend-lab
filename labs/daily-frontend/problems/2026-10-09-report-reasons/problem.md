# 시간과 예산 안에서 하루 여행 만들기

- 유형: 행동 보존 리팩터링 · 여행 일정
- 예상 시간: 30~40분
- 사용자 목표: 방문 순서와 운영 시간, 입장료 예산이 맞는 하루 일정을 구성하고 저장한다.

## 이미 완성된 사용자 흐름

**장소 조회 → 출발·예산 입력 → 장소·방문 순서 선택 → 시간·예산 확인 → 일정 저장**

pages/DayTripPage.tsx는 이미 동작합니다. 기능 추가나 버그 수정이 아니라 이 흐름의 기존 행동을 유지하면서 구조를 재구성하는 과제입니다. 상태의 원본과 계산 결과, UI와 요청·안내의 관계가 어떻게 읽히는지 먼저 분석하세요.

## 유지할 요구사항

1. 장소의 이름, 체류 시간, 입장료, 운영 시간을 서버에서 불러옵니다. 처음에는 오전 10시 출발·입장료 예산 15,000원·미선택입니다. 대기·조회 실패·빈 목록을 구분하고 실패 후 다시 조회할 수 있습니다.
2. 장소는 여러 개 고를 수 있으며 **선택한 순서**로 방문합니다. 해제하면 일정에서 빠집니다. 두 번째 이후 장소의 앞으로 버튼은 바로 앞 장소와 순서를 바꾸고 도착·종료 시각도 함께 다시 계산합니다.
3. 첫 장소에는 출발과 동시에 도착합니다. 다음 장소로 이동할 때마다 15분을 더하고 체류 시간을 누적합니다. 자동 대기·휴식·이동 비용은 없습니다.
4. 장소 도착이 개장 시각 이상이고 종료가 폐장 시각 이하일 때만 유효합니다. 폐장 시각과 정확히 같은 종료는 허용합니다. 충돌해도 선택은 보존하며 시간 안내와 출발 시각·순서 변경 안내를 표시합니다.
5. 예산은 0~1,000,000의 정수 문자열입니다. 입장료 합계가 예산을 넘으면 초과액을 표시합니다. 잘못된 숫자, 운영 시간 충돌, 예산 초과, 빈 선택이면 저장할 수 없습니다.
6. 저장 요청에는 숫자 출발 시각·예산과 순서가 유지된 장소 ID만 보냅니다. 화면의 계산 시간이나 표시용 문자열은 보내지 않습니다.
7. 저장 중 출발·예산·선택·순서 변경과 중복 저장을 막습니다. 실패 시 입력·순서를 보존하고 재시도할 수 있습니다.
8. 성공하면 마지막 저장 일정과 금액을 표시합니다. 이후 편집하면 결과 안내만 지우고 마지막 저장 결과는 유지합니다. 다음 저장 실패도 마지막 성공 결과를 바꾸면 안 됩니다.

예: 정원 → 전시관을 10시에 출발하면 10:00–11:00, 11:15–12:45이며 합계는 13,000원입니다. 전시관을 앞으로 옮기면 전시관 10:00–11:30, 정원 11:45–12:45입니다.

## 제공 환경

trip/api.ts의 createTripApi()는 getPlaces(): Promise<Place[]>와 save({ startHour, budget, placeIds }): Promise<{ id }>를 제공합니다. 조회는 0.35초, 저장은 0.7초입니다. 유효한 첫 저장은 실패하고 재시도는 성공합니다. 입력 상태 전이와 계산은 페이지 안에서 이미 동작합니다.

모든 장소·요금·운영 시간은 실습용 가상 데이터이며 실제 여행 정보가 아닙니다. API와 모의 서버는 제공 환경입니다. 기존 신고 폼 파일과 테스트는 보존하지만 이번 실습에서는 수정할 필요가 없습니다. 기존 폴더명·해시·PR을 유지했습니다.

## 화면·제공 환경과 확인 범위

SEED Design의 공식 TextField, RadioGroup, Select, List 선택 스니펫, ActionButton, Callout, Skeleton, VStack·HStack·Text·Badge를 필요한 역할에 사용합니다. native 컨트롤을 직접 꾸미지 않습니다. 선택·입력·요약·주요 행동이 한 목표로 이어지는 인라인 모바일 페이지이며, 상태 안내는 확인할 수 있도록 화면에 남깁니다. 설치된 React 2.5.1·CSS 2.8.3과 공식 v2 스니펫을 유지합니다.

API는 실제 fetch를 사용하고 날짜 폴더 handlers.ts를 MSW에서 자동 등록합니다. 모의 서버·표현용 View·preview는 제공 환경입니다. 실서버·외부 인증·실제 결제·브라우저 저장소 영속화는 범위 밖입니다. 검사·브라우저 확인 범위는 PR 본문에 명시합니다. 다른 브라우저와 스크린리더 음성 출력은 별도 확인 대상입니다.

가독성·예측 가능성·응집도·결합도는 판단 근거이지 파일·훅 개수에 대한 정답이 아닙니다. 설계 결론과 note.md의 답은 직접 작성하세요.
