# 신고 사유에 따라 함께 바뀌는 규칙

- 유형: 행동 보존 리팩터링
- 예상 시간: 30~40분
- 사용자 목표: 거래 문제의 사유에 맞는 내용만 작성해 신고를 접수하고, 실패하면 작성한 내용으로 재시도한다.

## 상황과 핵심 질문

`starter.tsx`는 이미 완전히 동작합니다. 사유에 따른 설명 문구·최소 길이·검증·전송 데이터·완료 안내가 한 컴포넌트의 여러 위치에 흩어져 있습니다.

**사유별 규칙이 바뀔 때 함께 수정되어야 하는 코드는 무엇이고, 어떤 경계가 그 변경을 쉽게 확인하게 할까요?**

UI와 로직을 다른 파일에 두는 것만으로 해결되는지, 서로 다른 규칙까지 한 함수나 설정 객체로 묶는 비용은 무엇인지 판단하세요. 정답 구조·훅 개수·파일 수는 지정하지 않습니다. [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성·예측 가능성·응집도·결합도는 참고 기준입니다.

## 보존할 행동

1. 최초 사유는 미선택, 설명은 빈 문자열입니다. 접수 버튼은 활성이고 클릭하면 사유 필드에 `신고 사유를 골라 주세요.`를 표시하며 요청하지 않습니다.
2. 사유별 계약은 다음과 같습니다. 최소 길이는 **앞뒤 공백을 뺀 문자열의 JavaScript length**이며 내부 공백·줄바꿈은 보존합니다. 설명 원본은 전송을 위해 덮어쓰지 않습니다.

| 사유                        | 설명 입력 | 최소 길이·안내                         | 요청                                               | 완료 안내                      |
| --------------------------- | --------- | -------------------------------------- | -------------------------------------------------- | ------------------------------ |
| 약속 장소에 나오지 않았어요 | 숨김      | 사유만 접수                            | `{ reason: 'no-show' }`                            | 약속 불참 신고를 접수했어요.   |
| 설명과 다른 상품을 받았어요 | 표시      | 상품이 다른 점을 5자 이상 적어 주세요. | `{ reason: 'wrong-item', description: trim한 값 }` | 상품 불일치 신고를 접수했어요. |
| 다른 문제가 있었어요        | 표시      | 신고할 상황을 10자 이상 적어 주세요.   | `{ reason: 'other', description: trim한 값 }`      | 기타 신고를 접수했어요.        |

3. 설명이 보이는 동안 현재 trim 길이와 최소 길이를 표시합니다. 짧은 설명의 접수는 해당 필드에 위 문구를 오류로 표시하고 요청하지 않습니다. 검증 오류와 API 실패는 구분합니다.
4. 사유를 바꾸면 모든 오류·결과 안내를 지우지만 설명 입력 원본은 보존합니다. 불참으로 바꾸면 설명을 숨기고, 다른 사유로 돌아오면 다시 보입니다. **숨긴 설명은 불참 요청에 절대 포함하지 않습니다.** 같은 사유를 다시 누르는 것은 변경이 아닙니다.
5. 유효한 접수는 한 번 요청하며 사유·설명·접수 버튼을 잠급니다. 진행 안내와 `신고 접수 중` 버튼 이름을 표시합니다. 실패는 사유와 원본 설명을 유지하고 `접수하지 못했어요. 작성한 내용은 그대로예요. 다시 시도해 주세요.`를 표시합니다. 재시도 시작 시 결과 안내를 지웁니다.
6. 성공은 사유와 원본 설명을 유지하고 사유별 완료 안내를 표시합니다. 입력은 다시 가능하지만 같은 내용의 연속 접수를 막습니다. 실제 사유 또는 설명 변경 시 결과 안내를 지우고 버튼을 다시 활성화합니다. 사유 변경 시 이전 필드 오류도 지웁니다.

확인 예: 상품 불일치 설명 `  상품 색이 달라요  ` 입력 → 불참 선택 → 요청에는 사유만 포함 → 다시 상품 불일치 선택 → 원래 공백까지 보존된 설명 복원. 기타 사유로 바꿨을 때는 바뀐 최소 길이 기준을 적용합니다.

## 실행·테스트

`api.ts`의 `SendReport` 주입 경계를 유지하세요. `Problem`은 첫 유효 요청만 1.8초 후 실패하고 이후 성공하는 모의 API를 연결합니다. 잘못된 입력은 API에 도달하지 않으므로 실패 횟수를 소비하지 않습니다. 실제 신고·상대방 알림·서버 저장은 전혀 없고, 화면 재진입 시 초기화합니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily
pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-09-report-reasons/Problem.spec.tsx
pnpm --filter @frontend-lab/daily-frontend build
```

Daily에서 오늘 문제를 선택하거나 `#2026-10-09-report-reasons`로 진입합니다. 테스트는 전부 활성 상태입니다. 내부 상태·파일 구조가 아니라 사용자 행동과 요청 데이터를 고정하므로 구조를 바꾸어도 유지하세요.

## 화면 맥락과 SEED 확인

사유 선택 → 필요한 설명 → 접수의 인라인 폼입니다. 선택지가 3개라 시트·Select 대신 공식 RadioGroup/RadioGroupItem(Field 통합 스니펫)을 사용합니다. 잘못된 사유로 접수하지 않도록 기본 미선택을 요구하는 것은 기본 선택 권장에 대한 명시적 예외입니다.

설명은 공식 TextField/TextFieldTextarea(Field 오류·라벨·설명 통합)이며 자동 높이 최소 96px·최대 240px을 공개 x12 토큰으로 설정합니다. 요청 진행은 공식 ActionButton large, API 오류와 접수 확인은 공식 Callout critical/positive·alert/status입니다. 확인 내용은 사라지지 않도록 인라인으로 남깁니다. VStack/HStack/Text와 공개 간격 토큰을 사용하고 native 컨트롤을 대체재로 쓰지 않습니다. 신고는 외부 부작용 없는 학습용 모의 접수이며 추가 다이얼로그·증빙 업로드는 범위 밖입니다. 지정된 SEED 기준을 출제 스킬의 Montage 지침보다 우선합니다.

| 상태         | 사용자에게 보이는 동작                                  |
| ------------ | ------------------------------------------------------- |
| 초기·빈 설명 | 미선택 또는 빈 설명; 접수 시 필드 오류, 요청 없음       |
| 사유 변경    | 해당 입력만 표시, 작성한 설명 원본 보존, 오류·결과 제거 |
| 요청 중      | 모든 입력·버튼 잠금, 진행 표시                          |
| 실패         | 작성값 보존, 다시 접수 가능                             |
| 성공         | 작성값·접수 확인 유지, 실제 편집 전까지 접수 잠금       |

## 완료 조건

1. 기존 행동 테스트를 모두 통과하고 사유 전환·숨긴 설명 제외·실패 후 재시도를 화면에서도 확인합니다.
2. 함께 변경되는 규칙과 선택한 경계의 비용을 `note.md`에 직접 기록합니다.
3. 실제로 읽기·수정하기 쉬워진 지점을 설명합니다. 파일 분리나 중복 제거 자체를 완료 근거로 삼지 않습니다.

기능 추가·정책 변경·버그 수정은 기본 과제가 아닙니다. 새로운 변경 시나리오는 첫 풀이 검토 뒤 필요할 때 별도로 다룹니다.

## 출제 시 검증 범위

- frozen lockfile 설치, 전체 lint·format 검사·TypeScript 검사 포함 build 통과.
- 오늘 행동 테스트 8개 모두 통과. Daily 전체 33개 통과·이전 직접 구현 문제 4개 의도적 skip, code-quality 22개 통과.
- 실제 브라우저 375×812에서 사유·설명 필드 오류, 설명 숨김·원본 복원, 요청 중 전체 잠금, API 실패 후 재시도, 성공 후 접수 잠금·편집 재활성화, 기타 사유 최소 길이 전환·성공을 확인했습니다. 입력 라벨 연결, radio 행 54px·버튼 52px 터치 영역, 가로 넘침 없음(scrollWidth 375px), 브라우저 error/warn 없음도 확인했습니다. 요청 데이터 내용은 행동 테스트로 검증했습니다.
- 공식 RadioGroup·TextField·ActionButton 스니펫과 Callout·레이아웃 컴포넌트의 설치본 타입·실제 렌더링을 확인했습니다. `seed-design compat` 전체 검사는 **기존 ui:list**가 최신 registry의 CSS ^3.0.0 요구와 설치된 CSS ^2.8.3이 맞지 않아 실패합니다. 오늘 문제는 List를 사용하지 않으며 패키지·lockfile·기존 스니펫을 변경하지 않았습니다. 이 남은 호환성 이슈를 명시한 Draft PR로 제공합니다.
- 검수는 데스크톱 브라우저의 모바일 뷰포트 범위입니다. 실제 휴대폰·보조 기술 전체 조합과 실제 서버 접수는 검증하지 않았습니다.
