# 2026-10-03 · 예약 취소 정책의 변경 경계

- 유형: 리팩터링형
- 예상 시간: 30~40분

## 사용자 목표

이웃 클래스 참가자가 예약별 환불 조건을 확인하고 예약을 취소한다. 요청에 실패해도 작성한 사유를 잃지 않고 재시도한다.

## 설계 질문

> 취소 수수료 규칙이 바뀌면 안내·환불 표시·전송 데이터 중 무엇을 함께 수정해야 할까요? 같은 변경 이유를 가진 부분을 어디까지 묶으면, 요청 상태나 입력 처리까지 불필요하게 결합하지 않을까요?

`starter.tsx`는 이미 모든 기능이 동작합니다. 반복된 정책 계산과 조건이 화면·요청·조작 제한에 흩어져 있습니다. 현재 책임과 변경 이유부터 읽고, 외부 동작을 유지하며 구조를 재구성하세요. 정해진 파일 수·훅 개수·공통 컴포넌트는 없습니다. [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성·예측 가능성·응집도·결합도로 선택의 장점과 비용을 설명합니다.

## 고정해야 할 외부 동작

1. 기본 선택은 내일 도자기 클래스(결제 12,000원)입니다. 전날 취소는 수수료 0원, 환불 12,000원입니다. 오늘 가죽 키링 클래스(결제 18,000원)는 수수료 2,000원, 환불 16,000원입니다. 진행 중 수채화 클래스는 금액 대신 취소·환불 불가를 표시하며 사유와 버튼을 잠급니다. 세 예약은 시간 경과와 무관한 **고정된 업무 상황**입니다.
2. 앞뒤 공백을 제외한 사유가 5자 미만이면 `취소 사유를 5자 이상 입력해 주세요.`를 필드 옆에 표시하고 요청하지 않습니다. 입력 수정은 오류·결과 안내를 지웁니다. 예약 변경은 사유·오류·결과 안내를 지웁니다.
3. 취소 요청은 `{ reservationId, reason, fee, refund }`이며 사유의 앞뒤 공백을 제거합니다. 화면의 수수료·환불 금액과 요청 금액이 같아야 합니다. 요청 중 선택·입력·버튼을 잠그고 버튼에 로딩 표시와 접근성 이름 `취소 중...`을 제공합니다. 중복 요청하지 않습니다.
4. 성공 시 해당 예약만 취소 상태로 기록하고 사유를 비웁니다. `예약을 취소했어요. 환불 예정 금액을 확인해 주세요.`와 `이미 취소한 예약이에요.`를 표시합니다. 선택은 유지하고 입력·제출은 비활성입니다. 다른 예약으로 이동했다 돌아와도 재취소할 수 없습니다. 실패 시 예약과 사유를 보존하고 `취소하지 못했어요. 입력한 사유를 확인하고 다시 시도해 주세요.`를 표시하며 조작을 복구합니다.

## 실행 환경과 시작 파일

- `starter.tsx`: 재구성할 화면과 로직. 구조는 자유롭게 변경할 수 있습니다.
- `api.ts`: 변경하지 않을 요청 타입과 모의 API. `CancellationPage`에 `cancelReservation`을 주입할 수 있어야 합니다.
- `Problem.tsx`: 공통 Daily 진입점. 모의 API는 0.9초 후 응답하며 첫 호출만 실패합니다. 문제를 나갔다 다시 들어오면 호출 횟수와 취소 상태가 초기화됩니다. 실제 결제·환불·서버 저장은 없습니다.
- `Problem.spec.tsx`: 외부 행동 7개와 모의 API 1개 테스트. 건너뛴 테스트 없이 모두 유지합니다. 금액의 `data-testid`는 구현 방식이 아닌 표시 영역을 찾는 표식입니다.
- `note.md`: 직접 작성할 판단 기록. 빈 질문에 본인의 근거를 남깁니다.

```sh
pnpm install --frozen-lockfile
pnpm dev:daily
pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-03-reservation-policy/Problem.spec.tsx
pnpm --filter @frontend-lab/daily-frontend build
```

앱에서 `예약 취소 정책의 변경 경계`를 선택하거나 `#2026-10-03-reservation-policy`로 진입합니다. 원본 풀이가 아닌 **이 문제의 별도 worktree**에서 실행하세요.

## 화면 맥락과 SEED 매핑

375px에서 예약 선택 → 환불 상세 → 사유 입력 → 취소 액션 순서입니다. 세 선택지를 비교해야 하므로 [Radio](https://seed-design.io/components/radio) 가이드의 세로 RadioGroup을 사용합니다. 선택 자체는 취소가 아니며 마지막 버튼에서 요청을 확정합니다. 안내와 입력 한 개를 함께 보도록 인라인 상세·폼을 씁니다. 취소는 모의 예약 취소일 뿐 영구 데이터 삭제가 아니며, 별도 확인 Dialog는 이번 학습 범위에서 제외합니다.

| UI 역할                  | 공식 구현 확인                                                      |
| ------------------------ | ------------------------------------------------------------------- |
| 예약 단일 선택           | 설치된 공식 RadioGroup·RadioGroupItem 스니펫, 라디오 터치 영역 48px |
| 사유·라벨·설명·필드 오류 | 공식 TextField·TextFieldInput 스니펫, 단일 입력의 underline variant |
| 취소 액션·로딩           | 공식 ActionButton 스니펫, neutralSolid·large·loading·disabled       |
| 정책·오류·성공 안내      | 설치본 Callout의 Root·Content·Description 파츠                      |
| 정보 계층·여백           | VStack·HStack·Text와 공개 x 토큰                                    |

native 버튼·라디오·입력을 토큰으로 대체 구현하지 않았습니다. 의미적 `form`은 제출 이벤트를 담당하며 내부 배치는 VStack으로 합니다. 독립된 실습 화면은 `article`로 구성해 기존 실습의 native section CSS와 분리합니다. 색상·필드 표현은 SEED가 담당하며 별도 CSS는 긴 문구 줄바꿈과 터치 영역만 보완합니다. 관련 기준은 [Action Button](https://seed-design.io/components/action-button), [Text Input](https://seed-design.io/components/text-input), [Callout](https://seed-design.io/components/callout) 및 각 React API에서 확인했습니다.

| 상태              | 화면·행동                                           |
| ----------------- | --------------------------------------------------- |
| 초기·빈 사유      | 전액 환불 안내, 입력과 제출 가능; 제출 시 사유 검증 |
| 검증 실패         | 필드 오류, 요청 없음, 입력 가능                     |
| 요청 중           | 선택·입력·제출 잠금, 로딩 표시                      |
| 요청 실패         | 사유·선택 보존, 인라인 오류, 재시도 가능            |
| 성공              | 취소된 예약·환불 안내 유지, 사유 비움, 재취소 불가  |
| 시작 후·이미 취소 | 비활성 이유 표시, 다른 예약 선택 가능               |

## 완료 조건

- 기존 테스트 8개를 유지해 통과하고, 화면·안내·요청·실패 후 재시도 행동을 보존합니다.
- 변경 이유가 같은 규칙과 별개인 책임을 구분하여 재구성한 근거 및 비용을 `note.md`에 적습니다.
- 실제 화면에서 대기·실패·재시도·재선택을 확인하고, 예상한 결과와 실제 검증을 구분합니다.

범위 밖: 기능 추가, 정책 변경, 실시간 날짜 계산, 환불 서버 구현, 요청 취소, 전역 상태 도구. **수수료 인상 등을 실제로 구현하는 것은 기본 완료 조건이 아닙니다.** 풀이 검토 후 필요할 때 별도 변경 시나리오로 설계를 점검합니다.

## 출제 시 검증 범위

별도 worktree의 최신 `origin/develop` 기준으로 `pnpm install --frozen-lockfile`과 정상 설치 훅을 완료했습니다. 최초 시도는 Node 경로가 없어 훅에서 실패했으며, 제공된 Node 경로를 연결한 재시도에서 성공했습니다. 정책·lockfile·훅은 변경하지 않았습니다.

- 저장소 전체 `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm build` 통과. 타입 검사도 build에 포함합니다.
- 오늘 테스트 8개 통과, 건너뜀 없음. Daily 전체 18개, code-quality 22개 통과.
- Chromium 실제 375×812 화면에서 초기·빈 사유 오류·시작 후 비활성·요청 중·요청 실패·재시도 성공·취소 후 재선택을 조작해 확인했습니다. 모든 검수 상태에서 문서 폭 375px로 가로 넘침 없음, 입력 라벨 연결, 라디오 라벨 48px·주 버튼 52px 터치 영역, 요청 중 조작 잠금, 실패 시 사유 보존, 성공 후 재취소 불가를 확인했습니다. 검수 중 콘솔 오류·경고와 pageerror는 없었습니다. 다른 브라우저·스크린리더·실제 환불 서버는 확인하지 않았습니다.
- `seed-design compat`는 **기존 ui:list의 React/CSS 필요 버전 경고로 실패**했습니다. 오늘 사용하는 ActionButton·RadioGroup·TextField·LoadingIndicator·ProgressCircle에서는 호환 경고가 없었습니다. 기존 List와 패키지 버전을 수정하지 않았습니다.

10월 2일 직접 구현형 PR #20은 아직 머지되지 않은 별도 과제로 읽기만 했으며, 이 PR에 그 변경이나 원본의 미커밋 풀이·별칭 설정을 섞지 않았습니다. `note.md`는 실습자가 채울 빈 질문으로 남겼습니다.
