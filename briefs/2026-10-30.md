## 클린 코드 처방

### 1. 함수와 인자 · boolean 인자로 갈리는 함수 → 함수 둘로 나누기

**상황**

```ts
function createTransfer(form: TransferForm, isScheduled: boolean) {
  const body = { to: form.account, amount: form.amount }

  if (isScheduled) {
    return api.post('/transfers/scheduled', { ...body, runAt: form.runAt })
  }
  return api.post('/transfers', body)
}

createTransfer(form, true) // true가 뭐였지?
```

**처방: 하는 일마다 함수 하나**

```ts
function transferNow(form: TransferForm) {
  return api.post('/transfers', { to: form.account, amount: form.amount })
}

function scheduleTransfer(form: TransferForm, runAt: Date) {
  return api.post('/transfers/scheduled', { to: form.account, amount: form.amount, runAt })
}

transferNow(form)
scheduleTransfer(form, runAt)
```

**왜**: 호출하는 줄만 봐서는 `true`가 무슨 뜻인지 알 수 없습니다. 함수 이름이 하는 일을 말하게 나누면 호출부가 그대로 읽히고, 예약 송금에만 필요한 `runAt`도 그 함수에만 붙습니다. 즉시 송금 폼에 `runAt?`이 따라다닐 이유가 없어집니다.

**안 해도 되는 때**: 갈리는 게 동작이 아니라 오름차순·내림차순 같은 옵션 하나라면 `sortListings(list, { descending: true })`처럼 이름 붙은 옵션 객체로도 충분합니다.

### 2. 비동기와 에러 처리 · try 안에 다 넣기 → 실패할 수 있는 곳만 감싸기

**상황**

```tsx
async function handleSubmit() {
  try {
    const result = await submitApplication(toApplicationBody(form))
    setStep('done')
    track('apply_complete', { jobId: result.jobId })
    navigate(`/applications/${result.id}`)
  } catch {
    toast('지원서를 보내지 못했어요. 다시 시도해 주세요')
  }
}
```

**처방: 메시지가 맞는 범위만 감싼다**

```tsx
async function handleSubmit() {
  const body = toApplicationBody(form)

  let result: ApplicationResult
  try {
    result = await submitApplication(body)
  } catch {
    toast('지원서를 보내지 못했어요. 다시 시도해 주세요')
    return
  }

  setStep('done')
  track('apply_complete', { jobId: result.jobId })
  navigate(`/applications/${result.id}`)
}
```

**왜**: `catch`는 `try` 안 어디서 난 에러든 다 잡습니다. 지원서는 이미 들어갔는데 `track`에서 에러가 나면, 사용자는 "보내지 못했어요"를 보고 한 번 더 지원합니다. 감싸는 범위가 곧 "이 문구가 사실인 범위"입니다.

**안 해도 되는 때**: 화면에 들어올 때 데이터 여러 개를 한꺼번에 불러오는 경우처럼, 어느 줄에서 실패하든 사용자에게 할 말이 같다면 넓게 감싸도 됩니다.

### 3. 타입으로 막기 · 따로 노는 로딩·에러·데이터 → 판별 유니온 하나로

**상황**

```tsx
const [isLoading, setIsLoading] = useState(true)
const [error, setError] = useState<Error | null>(null)
const [ride, setRide] = useState<Ride | null>(null)

if (isLoading) return <Skeleton />
if (error) return <ErrorView />
return <RideReceipt ride={ride!} /> // 여기서 ride가 null일 수는 없나?
```

**처방: status로 갈리는 상태 하나**

```tsx
type RideState = { status: 'loading' } | { status: 'error'; error: Error } | { status: 'success'; ride: Ride }

const [state, setState] = useState<RideState>({ status: 'loading' })

if (state.status === 'loading') return <Skeleton />
if (state.status === 'error') return <ErrorView />
return <RideReceipt ride={state.ride} />
```

**왜**: 따로 둔 세 값은 "로딩 중인데 에러도 있음", "끝났는데 ride가 null" 같은 말이 안 되는 조합도 받아 줍니다. 그래서 마지막 줄에 `!`가 붙습니다. 유니온으로 묶으면 가능한 상태는 셋뿐이고, `status`를 확인한 뒤에야 `state.ride`를 꺼낼 수 있습니다. 확인 없이 읽으면 `Property 'ride' does not exist on type 'RideState'.`로 막힙니다. 바꿀 때도 `setState({ status: 'success', ride })` 한 번이라 `setIsLoading(false)`를 빠뜨릴 일이 없습니다.

**안 해도 되는 때**: TanStack Query처럼 서버 상태를 맡는 라이브러리를 이미 쓰고 있다면 로딩·에러·데이터는 그쪽이 관리하니 직접 만들 일이 없습니다.

**장면**: 기획 메모를 받았습니다.

> 복약 알림 화면을 만들어 주세요. 약을 등록하고, 하루 몇 번 먹는지 정하고, 시간이 되면 알림을 받고, 먹었으면 체크해요. 지난 기록은 달력으로 봐요.

약 타입은 어떻게 짜지, 반복 규칙은, 달력 컴포넌트는, 폴더는… 다섯 기능이 한꺼번에 떠올라서 첫 줄을 못 씁니다.

**생각 순서**

1. **"사용자가 이 화면에서 제일 자주 하는 일은 뭐지?"** 약 등록은 한 번, 체크는 매일 여러 번입니다. "오늘 먹을 약을 보고 먹었다고 체크하기"가 가장 자주 쓰이고, 마침 가장 쉽습니다. 여기서 시작합니다.
2. **"그것 하나만 되려면 최소한 뭐가 있어야 하지?"** 약 목록은 코드에 박아 둔 배열 세 개면 됩니다. 저장할 값은 "오늘 무엇을 먹었는지" 하나뿐입니다. 등록 폼도 알림도 달력도 아직 없습니다.
3. **"다음 기능을 붙이니 지금 코드 어디가 불편하지?"** 달력을 붙이려고 보니 먹은 기록이 오늘 하루치만 있습니다. 날짜별로 바꿔야 합니다. 이 불편이 생긴 지금이 데이터 모양을 바꿀 이유가 생긴 때입니다. 처음부터 날짜별로 설계해 두지 않은 건 실수가 아닙니다.
4. **"아직 안 정해도 되는 건?"** "이틀마다", "식후 30분" 같은 반복 규칙은 기획자에게 물을 게 많습니다. 질문으로 적어 두고, 체크 기능을 먼저 끝냅니다.

**코드로 옮기면**


**한 줄 요약**: 다섯 기능을 다 담을 구조를 처음부터 찾지 않습니다. 가장 쉬운 하나를 끝내고, 다음 기능이 불편해지는 자리에서 구조를 바꿉니다.

## 기본기

### JavaScript · 스프레드로 복사했는데 왜 원본도 바뀔까?

```ts
const original = { title: '제주 2박 3일', places: ['성산', '우도'] }
const copy = { ...original }

copy.title = '제주 3박 4일' // original.title은 그대로
copy.places.push('한라산') // original.places도 ['성산', '우도', '한라산']
```

스프레드는 한 단계만 복사하는 얕은 복사입니다. `title` 같은 원시 값은 값이 복사되지만, `places` 같은 배열·객체는 "같은 배열을 가리키는 참조"가 복사됩니다. 두 객체가 배열 하나를 같이 쓰는 셈입니다. 바꾸는 단계까지 새로 만들려면 `{ ...original, places: [...original.places, '한라산'] }`처럼 그 단계도 펼치고, 통째로 깊게 복사해야 할 때는 `structuredClone(original)`을 씁니다.

**실무에서 만나는 장면**: `setTrip((prev) => { const next = { ...prev }; next.places.push(place); return next })`처럼 써서 이전 state까지 같이 바뀌었을 때. 개발 모드(Strict Mode)에서 항목이 두 번 들어간다면 이것부터 의심합니다. React가 업데이트 함수를 두 번 호출하는데, 두 번 다 같은 배열에 `push`하기 때문입니다.

### Next.js · `'use client'`를 붙이면 그 아래는 전부 클라이언트 컴포넌트일까?

Next.js 16 App Router 기준이고, 2026년 10월 공식 문서로 확인했습니다(App Router가 나온 13.4부터 같은 동작입니다).

```tsx
'use client' // favorite-sheet.tsx
import { PriceTag } from './price-tag' // import한 모듈은 클라이언트 번들로 간다

export function FavoriteSheet({ children }: { children: ReactNode }) {
  const [open, setOpen] = useState(false)
  // ...
}
```

```tsx
// page.tsx는 서버 컴포넌트
<FavoriteSheet>
  <ListingDetail /> {/* children으로 넘겼으니 서버에서 렌더링된다 */}
</FavoriteSheet>
```

`'use client'`는 컴포넌트 하나에 붙는 표시가 아니라 서버와 클라이언트 사이의 경계입니다. 그 파일이 import하는 모듈과 그 파일이 직접 렌더링하는 컴포넌트는 클라이언트 번들에 들어갑니다. 하지만 서버 컴포넌트가 `children`이나 다른 props로 넘긴 서버 컴포넌트는 서버에서 먼저 렌더링되고, 그 결과만 넘어갑니다.

**실무에서 만나는 장면**: 시트 하나 열고 닫으려고 `page.tsx` 맨 위에 `'use client'`를 붙이면 페이지 전체가 클라이언트 번들로 가고, 서버에서 하던 데이터 요청도 다시 짜야 합니다. 상태가 필요한 시트만 떼어 `'use client'`를 붙이고, 내용은 `children`으로 넘깁니다.

### 브라우저 · `div`에 `onClick`을 달면 `button`이랑 뭐가 다를까?

```tsx
<div onClick={like}>좋아요</div>
<button type="button" onClick={like}>좋아요</button>
```

마우스로 누를 때는 똑같고, 키보드와 스크린 리더에서 갈립니다. `button`은 Tab으로 초점이 가고, Enter나 Space로 누를 수 있고, 스크린 리더가 "버튼"이라고 읽어 줍니다. `div`는 셋 다 없어서 `role="button"`, `tabIndex={0}`, 키보드 이벤트 처리를 직접 붙여야 겨우 비슷해집니다. 누르는 것이면 `button`부터 씁니다.

**실무에서 만나는 장면**: 댓글 폼 안에 둔 "사진 추가" 버튼을 눌렀더니 댓글이 그대로 등록될 때. `type`을 안 적은 `button`은 기본이 `submit`이라서, 폼 안의 보조 버튼에는 `type="button"`을 적어 둡니다.
