## 클린 코드 처방

### 1. 비동기와 에러 처리 · 요청 함수 안에서 에러를 삼키고 빈 배열 돌려주기 → 실패는 던지고 화면이 정하기

**상황**

```ts
async function fetchPrescriptions(patientId: string): Promise<Prescription[]> {
  try {
    const res = await fetch(`/api/patients/${patientId}/prescriptions`)
    return await res.json()
  } catch (error) {
    console.error(error)
    return []
  }
}
// 화면은 빈 배열이면 '처방 내역이 없어요'를 띄운다
```

**처방: 요청 함수는 실패를 알리기만 한다**

```ts
async function fetchPrescriptions(patientId: string): Promise<Prescription[]> {
  const res = await fetch(`/api/patients/${patientId}/prescriptions`)
  if (!res.ok) throw new Error(`처방 내역 요청 실패: ${res.status}`)
  return res.json()
}
// 잡는 곳은 화면 한 곳. 실패면 '다시 시도', 빈 배열이면 '처방 내역이 없어요'
```

**왜**: 지하철에서 신호가 끊겨도 화면은 "처방 내역이 없어요"를 띄웁니다. 실패와 "없음"이 같은 `[]`가 됐기 때문입니다. 사용자는 기록이 지워진 줄 알고, 다시 시도할 버튼도 못 봅니다. 실패를 어떻게 보여 줄지(다시 시도, 토스트, 로그인 화면으로)는 화면마다 다르니, 아래쪽 함수는 실패를 위로 알리기만 하고 결정은 화면이 합니다. `fetch`는 404·500에도 throw하지 않으니 `res.ok` 확인도 여기서 같이 합니다.

**안 해도 되는 때**: "함께 본 상품"처럼 실패하면 조용히 숨기는 게 기획인 영역은 그 자리에서 잡고 비워도 됩니다. 그 결정은 요청 함수가 아니라 그 영역 컴포넌트가 합니다.

### 2. 상태와 파생 값 · 번호로 둔 단계 state → 단계 이름을 원본으로

**상황**

```tsx
const [step, setStep] = useState(0)

<ProgressBar value={(step + 1) / 3} />
{step === 0 && <ProfileStep onNext={() => setStep(1)} />}
{step === 1 && <ResumeStep onNext={() => setStep(2)} />}
{step === 2 && <ReviewStep onSubmit={submit} />}
```

**처방: 단계는 이름으로 두고, 번호는 계산한다**

```tsx
const STEPS = ['profile', 'resume', 'review'] as const
type Step = (typeof STEPS)[number]

const [step, setStep] = useState<Step>('profile')
const progress = (STEPS.indexOf(step) + 1) / STEPS.length

<ProgressBar value={progress} />
{step === 'profile' && <ProfileStep onNext={() => setStep('resume')} />}
{step === 'resume' && <ResumeStep onNext={() => setStep('review')} />}
{step === 'review' && <ReviewStep onSubmit={submit} />}
```

**왜**: 채용 지원서에 "이력서 다음에 포트폴리오 링크 단계를 넣어 주세요"가 오면, 번호 방식은 `2`를 `3`으로, `/ 3`을 `/ 4`로 여기저기 밀어야 하고 하나만 놓쳐도 엉뚱한 화면이 뜹니다. `step === 2`가 어떤 화면인지도 세어 봐야 압니다. 이름을 원본으로 두면 `STEPS`에 한 줄 넣고 그 단계로 오가는 자리만 고치면 되고, 진행률은 따라옵니다. `setStep('reveiw')` 같은 오타는 타입 오류로 잡힙니다.

**안 해도 되는 때**: 온보딩 슬라이드 다섯 장처럼 단계마다 모양이 같고 순서만 의미가 있으면 번호가 더 자연스럽습니다.

### 3. 비즈니스 로직 위치 · 화면에서 다시 계산하는 환불 금액 → 서버가 낸 금액을 보여 주기

**상황**

```tsx
function RefundNotice({ subscription, now }: Props) {
  const usedDays = Math.ceil((now.getTime() - subscription.startedAt.getTime()) / DAY_MS)
  const refund = Math.floor((subscription.price * (30 - usedDays)) / 30)

  return <p>지금 해지하면 {refund.toLocaleString()}원을 돌려드려요</p>
}
```

**처방: 화면은 정책 대신 정책의 결과를 묻는다**

```tsx
type RefundQuote = { refundAmount: number }

// 해지 화면에 들어올 때 서버에 물어본 값 (예: GET /subscriptions/:id/refund-quote)
function RefundNotice({ quote }: { quote: RefundQuote }) {
  return <p>지금 해지하면 {quote.refundAmount.toLocaleString()}원을 돌려드려요</p>
}
```

**왜**: 실제로 돈을 돌려주는 건 서버입니다. 일할 계산을 30일로 할지 그달 일수로 할지, 첫 달 할인분을 빼고 돌려줄지 같은 규칙은 결제 정책이라 자주 바뀌고, 바뀌는 곳은 서버입니다. 화면이 같은 계산을 따로 들고 있으면 정책이 두 곳이 되고, 한쪽만 바뀐 날 "4,000원 준다더니 2,800원 들어왔어요" 같은 문의가 옵니다.

**안 해도 되는 때**: 수량을 바꿀 때마다 바로 바뀌어야 하는 장바구니 합계 같은 미리보기는 화면에서 계산해도 됩니다. 결제 직전 금액만 서버 값으로 다시 확인합니다.

### 문제를 풀 때 · 키보드를 잡기 전 5분 정리

**장면**: 숙소 앱 기획 메모를 받았습니다.

> 객실 상세의 인원 선택 시트예요. 성인과 아동을 +/−로 고르고, 객실 정원을 넘으면 +를 막아 주세요. 아동만으로는 예약할 수 없어요. 적용하면 상단에 "성인 2, 아동 1"로 보여 주세요.

손은 벌써 `GuestStepper` 컴포넌트부터 만들고 싶어 합니다. 그 전에 5분만 적어 봅니다.

**생각 순서**

1. **"이 시트는 사용자에게 뭘 해 주지?"** 이 객실에 몇 명이 묵을지 정하고, 그 인원으로 예약할 수 있는지 바로 알게 해 줍니다. +/− 버튼은 그걸 위한 수단입니다. 목적을 한 줄로 적어 두면 나중에 "이 기능이 꼭 필요한가?"를 물을 기준이 생깁니다.
2. **"사용자는 어떤 순서로 움직이지?"** 시트를 연다 → +/−를 누른다 → 적용한다 → 상단 요약이 바뀐다. 순서대로 따라가다 보면 질문이 튀어나옵니다. "적용을 안 누르고 시트를 닫으면 고른 값은 버리나?" 모르는 건 기획자에게 물을 목록에 적고 넘어갑니다.
3. **"저장할 값은 뭐고, 계산하면 되는 값은 뭐지?"** 사용자가 고른 건 성인 수와 아동 수, 둘뿐입니다. 총인원, +를 막을지, "성인 2, 아동 1" 문구는 전부 이 둘에서 계산됩니다. 정원은 내가 정하는 값이 아니라 객실 정보에서 옵니다. 2번 질문의 답이 "버린다"라면 시트 안에서 고르는 중인 값과 적용된 값, 두 벌을 저장하게 됩니다.
4. **"규칙은 몇 개고, 누가 알고 있어야 하지?"** 정원을 넘지 않는다, 성인은 최소 1명이다. 두 규칙은 함수로 두고 시트는 "더할 수 있어?"만 묻습니다. 요약 문구는 그 문구를 보여 주는 상단이 만듭니다. "정원에 아기도 세나?"는 2번 목록에 하나 더 적습니다.

**코드로 옮기면**

```ts
type Guests = { adults: number; children: number }

// 저장하는 건 Guests 하나. 나머지는 계산한다
const totalGuests = (g: Guests) => g.adults + g.children
const canAddGuest = (g: Guests, capacity: number) => totalGuests(g) < capacity
const canRemoveAdult = (g: Guests) => g.adults > 1
```

**한 줄 요약**: 목적 → 행동 순서 → 저장할 값과 계산할 값 → 규칙 → 책임 순으로 5분 적어 보면, 무엇을 만들지보다 state로 두지 않아도 되는 것과 아직 물어야 할 것이 먼저 보입니다.

## 기본기

### JavaScript · `Promise.all`로 묶었더니 왜 하나만 실패해도 화면 전체가 에러일까?

```ts
// 포인트 요청 하나만 실패해도 여기서 throw. 계좌·카드 결과도 받을 수 없다
const [account, cards, points] = await Promise.all([fetchAccount(), fetchCards(), fetchPoints()])

// 셋 다 끝날 때까지 기다리고, 각각의 성공·실패를 돌려준다
const [accountResult, cardsResult, pointsResult] = await Promise.allSettled([fetchAccount(), fetchCards(), fetchPoints()])
if (pointsResult.status === 'fulfilled') showPoints(pointsResult.value)
```

`Promise.all`은 하나라도 실패하면 그 즉시 그 이유로 실패합니다. 나머지 요청이 취소되는 건 아니라서 끝까지 가긴 하지만, 그 결과는 받을 수 없습니다. `Promise.allSettled`(ES2020)는 전부 끝날 때까지 기다린 뒤 각각을 `{ status: 'fulfilled', value }`나 `{ status: 'rejected', reason }`로 돌려줍니다. TypeScript에서는 `status`를 확인하기 전에 `accountResult.value`를 꺼내면 `Property 'value' does not exist on type 'PromiseSettledResult<Account>'.` 오류가 나서, 실패 처리를 빼먹기 어렵습니다.

**실무에서 만나는 장면**: 자산 홈에서 포인트 서버 하나가 실패했는데 계좌 잔액까지 에러 화면이 될 때. 하나라도 빠지면 의미가 없는 묶음(주문서의 결제 수단과 배송지)은 `all`, 따로 보여 줄 수 있는 영역들은 `allSettled`입니다.

### Next.js · 삭제 버튼을 작성자에게만 보여 주면 서버 액션도 안전할까?

```ts
'use server'

export async function deleteListing(listingId: string) {
  const session = await getSession() // 쿠키에서 읽는다. 인자로 받지 않는다
  if (!session) throw new Error('로그인이 필요해요')

  const listing = await db.listing.findUnique({ where: { id: listingId } })
  if (listing?.sellerId !== session.userId) throw new Error('내 글만 지울 수 있어요')

  await db.listing.delete({ where: { id: listingId } })
}
```

아닙니다. `'use server'`로 만든 서버 액션은 컴포넌트에서 부르는 함수처럼 보이지만, 실제로는 POST 요청으로 불리는 서버의 입구입니다. 버튼을 숨겨도 요청은 직접 보낼 수 있고, 인자도 보내는 사람이 바꿀 수 있습니다. Next.js 공식 문서(16.x App Router, Mutating Data 가이드)도 서버 함수는 앱 화면을 거치지 않고 직접 POST 요청으로도 불릴 수 있으니, 모든 서버 함수 안에서 인증과 권한을 확인하라고 경고합니다. 누구인지는 인자가 아니라 쿠키나 헤더에서 읽습니다(`use server` 문서).

**실무에서 만나는 장면**: 중고 거래 글의 삭제 버튼은 작성자에게만 보이는데, 액션은 `listingId`만 받고 바로 지울 때. 화면의 조건은 편의이고, 막는 건 서버의 확인입니다.

### 브라우저 · `sessionStorage`에 넣은 장바구니가 왜 새 탭에서는 비어 있을까?

- **`localStorage`**: 같은 출처(프로토콜·도메인·포트가 같은 곳)의 모든 탭이 같은 저장소를 봅니다. 브라우저를 껐다 켜도 지우기 전까지 남습니다.
- **`sessionStorage`**: 탭마다 따로입니다. 새로고침해도 남지만 탭을 닫으면 사라지고, 새 탭에서 같은 주소를 열면 빈 저장소로 시작합니다. 이 탭이 `window.open`으로 연 창은 처음 값만 복사해 가고, 그 뒤로는 따로 놉니다.

다른 탭이 `localStorage`를 바꾸면 이 탭에 `storage` 이벤트가 옵니다. 값을 바꾼 그 탭에는 오지 않습니다.

```ts
window.addEventListener('storage', (event) => {
  if (event.key === 'cart') setCartCount(JSON.parse(event.newValue ?? '[]').length)
})
```

**실무에서 만나는 장면**: 비회원 장바구니를 `sessionStorage`에 넣었더니, 다른 탭에서 쇼핑몰을 열면 비어 있고 탭을 닫으면 담은 게 사라질 때. 탭끼리 나눠야 하는 값이면 `localStorage`에 두고 `storage` 이벤트로 다른 탭을 맞춥니다.
