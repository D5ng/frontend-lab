## 클린 코드 처방

### 1. 타입으로 막기 · 분기마다 모양이 다른 반환값 → 반환 타입을 먼저 적기

택시 호출 화면에서 호출 상태를 배지로 보여 주는 함수입니다.

**상황**

```ts
function getRideBadge(ride: Ride) {
  if (ride.status === 'searching') return { text: '기사님 찾는 중', tone: 'neutral' }
  if (ride.status === 'matched') return { text: '배차 완료', tone: 'positive' }
  return { text: '호출 취소' } // tone을 빠뜨렸다
}
```

함수 안에서는 아무 오류가 없습니다. TypeScript가 분기마다 돌려준 것을 모아 `{ text: string; tone: string } | { text: string; tone?: undefined }`라는 타입을 만들어 줄 뿐입니다. 오류는 한참 떨어진 곳, `<Badge tone={badge.tone}>`에서 `Type 'string | undefined' is not assignable to ...`로 납니다.

**처방: 돌려줄 모양을 타입으로 먼저 약속하기**

```ts
type RideBadge = {
  text: string
  tone: 'neutral' | 'positive' | 'critical'
}

function getRideBadge(ride: Ride): RideBadge {
  if (ride.status === 'searching') return { text: '기사님 찾는 중', tone: 'neutral' }
  if (ride.status === 'matched') return { text: '배차 완료', tone: 'positive' }
  return { text: '호출 취소' } // 오류: Property 'tone' is missing in type '{ text: string; }' but required in type 'RideBadge'.
}
```

**왜**: 반환 타입을 적으면 "이 함수는 이 모양을 돌려준다"는 약속이 먼저 생기고, 약속을 어긴 분기에서 바로 오류가 납니다. 실수한 줄과 오류가 나는 줄이 같아집니다. `'positive'`가 `string`으로 넓어지는 일도 함께 막혀서, `'postive'` 같은 오타도 그 자리에서 잡힙니다.

**안 해도 되는 때**: `return price * quantity`처럼 반환이 한 갈래이고 뻔한 함수는 추론에 맡겨도 됩니다.

### 2. 훅 · 화면에 안 그리는 타이머 번호를 state로 → `useRef`에 두기

메모 앱의 자동 저장입니다. 입력이 멈추고 0.8초 뒤에 저장합니다.

**상황**

```tsx
const [body, setBody] = useState('')
const [saveTimer, setSaveTimer] = useState<number | null>(null)

function handleChange(text: string) {
  setBody(text)
  if (saveTimer !== null) window.clearTimeout(saveTimer)
  setSaveTimer(window.setTimeout(() => saveDraft(text), 800))
}
```

**처방: 렌더링에 쓰지 않는 값은 ref로**

```tsx
const [body, setBody] = useState('')
const saveTimerRef = useRef<number | null>(null)

function handleChange(text: string) {
  setBody(text)
  if (saveTimerRef.current !== null) window.clearTimeout(saveTimerRef.current)
  saveTimerRef.current = window.setTimeout(() => saveDraft(text), 800)
}
```

**왜**: state는 "이 값이 바뀌면 화면을 다시 그려라"라는 표시입니다. 타이머 번호는 화면 어디에도 나오지 않고, 다음 입력 때 지우려고 들고 있을 뿐입니다. state에 두면 읽는 사람은 이 값이 화면 어디에 쓰이는지 찾게 되고, 값도 다음 렌더링이 돼서야 바뀝니다. ref는 다시 그리지 않고 값을 들고만 있으며, 넣자마자 읽힙니다. React 19 타입에서는 `useRef<number>()`처럼 인자를 비우면 `Expected 1 arguments, but got 0.` 오류가 나므로 `null`을 넣어 줍니다.

**안 해도 되는 때**: "저장 중…" 표시처럼 화면이 그 값을 알아야 하면 state입니다. 타이머 번호는 ref에, 저장 중인지는 state에 나눠 두기도 합니다.

### 3. 테스트하기 좋은 모양 · 테스트마다 통째로 적는 데이터 → 기본값 함수에 바뀌는 값만 넘기기

중고거래 상품 상세 화면의 테스트입니다.

**상황**

```tsx
test('예약 중인 상품은 채팅하기 대신 예약 중이라고 보여 준다', () => {
  const item: Item = { id: 'item-1', title: '접이식 자전거', price: 120000, status: 'reserved', likeCount: 3 }
  render(<ItemDetail item={item} />)

  expect(screen.getByRole('button', { name: '예약 중' })).toBeDisabled()
})
```

**처방: 테스트 데이터를 만드는 함수**

```tsx
function createItem(overrides: Partial<Item> = {}): Item {
  return { id: 'item-1', title: '접이식 자전거', price: 120000, status: 'selling', likeCount: 0, ...overrides }
}

test('예약 중인 상품은 채팅하기 대신 예약 중이라고 보여 준다', () => {
  render(<ItemDetail item={createItem({ status: 'reserved' })} />)

  expect(screen.getByRole('button', { name: '예약 중' })).toBeDisabled()
})
```

**왜**: 상황 코드에서는 다섯 값 중 무엇이 이 테스트의 조건인지 보이지 않습니다. 처방 코드에는 이 테스트가 보는 값(`status: 'reserved'`) 하나만 남아서, 테스트 이름과 본문이 같은 말을 합니다. `Item`에 필드가 늘어도 고칠 곳은 `createItem` 한 곳입니다. 단, 테스트가 기대는 값은 기본값에 맡기지 않고 꼭 넘깁니다. 가격 표시를 보는 테스트라면 기본값과 같더라도 `createItem({ price: 120000 })`라고 적어야, 누가 기본값을 바꿔도 테스트의 뜻이 남습니다.

**안 해도 되는 때**: 필드가 두세 개뿐이거나, 그 데이터를 테스트 하나에서만 쓰면 그냥 적는 편이 더 잘 보입니다.

## 생각하는 법

### 기획을 코드로 · 등급이 바뀌면 이미 잡은 예약은 어떻게 되지?

**장면**: 숙소 예약 앱의 기획 메모입니다.

> 골드 회원은 체크인 3일 전까지 무료로 취소할 수 있어요. 일반 회원은 7일 전까지예요.

**생각 순서**

1. **"이 조건은 언제 확인하지?"** 회원 등급은 시간이 지나면 바뀝니다. 예약은 골드일 때 했는데, 취소하는 날에는 일반으로 내려가 있을 수 있습니다. 조건에 이렇게 바뀌는 값이 들어 있으면, 그 값을 어느 시점에 읽을지도 정책의 일부입니다. 메모에는 그게 빠져 있습니다.
2. **"기획자에게 어떻게 묻지?"** "등급이 바뀌면 어떻게 되나요?"라고 물으면 답도 추상적으로 옵니다. 날짜가 박힌 예시 하나로 묻습니다. "11월 1일에 골드로 예약했고, 11월 10일에 일반으로 내려갔어요. 체크인은 11월 20일이에요. 11월 15일에 취소하면 무료인가요?" 골드 기준이면 무료, 일반 기준이면 유료라서 답이 갈립니다.
3. **"예약할 때 기준이면 뭘 남겨야 하지?"** 예약 시점 기준이라면, 그때 정해진 무료 취소 기한을 예약과 함께 저장해야 합니다. 나중에 지금 등급으로 다시 계산하면 그 정책을 어기게 됩니다. 취소 시점 기준이라면 반대로, 저장하지 않고 취소할 때마다 계산합니다.
4. **"화면은 어떤 값을 받아야 하지?"** 예약 시점 기준으로 정해지면, 서버가 예약 데이터에 기한을 담아 주는 편이 자연스럽습니다. 화면이 지금 로그인한 회원의 등급으로 다시 계산하기 시작하면 같은 정책이 서버와 화면 두 곳에서 다른 답을 냅니다.

**코드로 옮기면**

```ts
type Reservation = {
  checkInDate: string
  freeCancelUntil: string // 예약할 때의 등급으로 서버가 정한 기한
}

// 화면은 등급을 다시 보지 않고, 정해진 기한과 지금 시각만 비교한다
function canCancelForFree(reservation: Reservation, now: Date) {
  return now.getTime() <= new Date(reservation.freeCancelUntil).getTime()
}
```

**한 줄 요약**: 조건에 바뀌는 값(등급, 가격, 재고)이 들어 있으면 "언제 기준인지"까지가 정책입니다. 기준이 과거의 한 시점이면 그때의 결과를 저장하고, 지금이면 매번 계산합니다.

## 기본기

### TypeScript · 필드 이름을 바꿨는데 `Omit`은 왜 오류 없이 그대로일까?

```ts
type Applicant = {
  id: string
  name: string
  phoneNumber: string // phone에서 이름을 바꿨다
}

type ApplicantForReviewer = Omit<Applicant, 'phone'> // 오류 없음. phoneNumber가 그대로 남는다
type ApplicantContact = Pick<Applicant, 'phone'> // 오류: Type '"phone"' does not satisfy the constraint 'keyof Applicant'.
```

`Pick`은 키를 `K extends keyof T`로 받아서 없는 키를 막습니다. 그런데 `Omit`은 `K extends keyof any`, 즉 아무 문자열이나 받습니다. "없는 키를 빼 줘"는 오류가 아니라 "아무것도 안 뺀다"로 통과합니다. 없는 키를 막고 싶으면 `type StrictOmit<T, K extends keyof T> = Omit<T, K>`처럼 제약을 건 별칭을 하나 두면 같은 코드에서 오류가 납니다.

**실무에서 만나는 장면**: 서버 필드 이름이 바뀌어 타입을 고쳤는데, 면접관 화면용 타입에서 빼려던 연락처가 조용히 다시 들어와 있을 때. 필드 이름을 바꾼 뒤에는 `Omit`에 적힌 키도 같이 찾아봅니다.

### React · 공용 입력 컴포넌트에 `ref`를 넘기려면 아직도 `forwardRef`가 필요할까? (React 19 기준)

```tsx
function SearchInput({ ref, ...props }: ComponentProps<'input'>) {
  return <input ref={ref} className="search-input" {...props} />
}

function SearchScreen() {
  const inputRef = useRef<HTMLInputElement>(null)

  useEffect(() => {
    inputRef.current?.focus()
  }, [])

  return <SearchInput ref={inputRef} placeholder="동네 맛집 검색" />
}
```

React 18까지는 함수 컴포넌트가 `ref`를 props로 받지 못했습니다. React가 `ref`를 따로 떼어 가서, `forwardRef`로 감싸야 두 번째 인자로 받을 수 있었습니다. React 19부터는 함수 컴포넌트가 `ref`를 다른 props처럼 받습니다. 공식 문서는 새 함수 컴포넌트에는 `forwardRef`가 필요 없고, 앞으로 `forwardRef`를 deprecated할 예정이라고 안내합니다. 클래스 컴포넌트에 넘긴 `ref`는 지금도 props로 오지 않고 인스턴스를 가리킵니다.

**실무에서 만나는 장면**: 검색 화면이 열리자마자 공용 입력칸에 포커스를 줘야 할 때. 이미 있는 `forwardRef` 코드는 그대로 동작하니 당장 지울 필요는 없고, 새로 만드는 컴포넌트부터 `ref` prop으로 받습니다.

### Next.js · 예약 시각을 `toLocaleTimeString()`으로 찍었더니 왜 hydration 오류가 날까? (Next.js 16 App Router 기준)

```tsx
'use client'

export function ReservationTime({ startsAt }: { startsAt: string }) {
  // startsAt이 '2026-11-20T10:30:00Z'면 UTC 서버에서는 10시 30분, 한국 브라우저에서는 19시 30분
  return <time dateTime={startsAt}>{new Date(startsAt).toLocaleTimeString('ko-KR')}</time>
}
```

`'use client'`를 붙인 컴포넌트도 첫 화면은 서버에서 HTML로 한 번 그립니다. 그다음 브라우저가 같은 컴포넌트를 다시 그려 그 HTML에 이벤트를 붙이는데(hydration), 두 결과가 다르면 오류가 납니다. `toLocaleTimeString()`은 실행되는 곳의 시간대를 따릅니다. 배포 서버는 UTC로 돌아가는 경우가 많고 사용자 브라우저는 한국 시간이라 글자가 달라집니다. Next.js 문서도 렌더링 중의 `Date()`, `typeof window` 검사, `localStorage`를 흔한 원인으로 꼽습니다.

서비스가 한 시간대만 쓰면 `toLocaleTimeString('ko-KR', { timeZone: 'Asia/Seoul' })`처럼 시간대를 정해 양쪽이 같은 글자를 만들게 합니다. 사용자마다 자기 시간대로 보여야 하면 `useEffect`가 실행된 뒤 브라우저에서만 그립니다. `suppressHydrationWarning`은 경고만 끄고 서버가 그린 글자를 고치지 않으니, 이 경우엔 UTC 시각이 그대로 남습니다. 서버 컴포넌트에서 포맷해도 오류는 없지만 마찬가지로 서버 시간대로 굳습니다.

**실무에서 만나는 장면**: 내 컴퓨터에서 `next dev`로 볼 때는 멀쩡한데, 배포한 뒤에만 콘솔에 hydration 오류가 찍히고 예약 시각이 10시 30분으로 잠깐 보였다가 19시 30분으로 바뀔 때. 로컬 서버는 한국 시간으로 돌아서 차이가 드러나지 않습니다.
