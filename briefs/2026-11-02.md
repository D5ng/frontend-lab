## 클린 코드 처방

### 1. 컴포넌트 props · 변형마다 늘어나는 variant 분기 → 바뀌는 자리만 슬롯으로 열기

어제 드릴에서 조합으로 변형을 늘려 봤다면, 샘플에서 본 `variant` 처방과 어디서 갈리는지 같이 보면 좋습니다.

**상황**

```tsx
function JobCard({ job, variant }: { job: Job; variant: 'open' | 'applied' | 'closed' }) {
  return (
    <Card>
      <JobSummary job={job} />
      {variant === 'open' && <ApplyButton jobId={job.id} />}
      {variant === 'applied' && <Badge>지원 완료</Badge>}
      {variant === 'closed' && <Badge tone="neutral">마감</Badge>}
    </Card>
  )
}
```

**처방: 카드는 자리만, 내용은 쓰는 화면이**

```tsx
function JobCard({ job, trailing }: { job: Job; trailing?: ReactNode }) {
  return (
    <Card>
      <JobSummary job={job} />
      {trailing}
    </Card>
  )
}

<JobCard job={job} trailing={<ApplyButton jobId={job.id} />} />
<JobCard job={job} trailing={<Badge>지원 완료</Badge>} />
```

**왜**: 상황 코드에서는 "스크랩한 공고" 화면이 생길 때마다 카드 파일을 열어 분기를 하나 더 넣어야 하고, 카드가 지원 버튼과 지원 상태까지 알게 됩니다. 슬롯으로 열면 카드는 "공고 요약과 오른쪽 자리 하나"만 알고, 무엇을 넣을지는 그 화면이 정합니다. `variant`는 같은 내용의 **모양**(색, 크기)이 바뀔 때, 슬롯은 **내용 자체**가 바뀔 때 어울립니다.

**안 해도 되는 때**: 모든 화면이 같은 것을 넣는다면 열어 둘 이유가 없습니다. 열린 자리는 "아무거나 들어올 수 있다"는 뜻이기도 해서, 카드가 정해 둔 모양이 흐트러질 수 있습니다.

### 2. 비동기와 에러 처리 · 응답을 기다리는 동안 또 눌리는 버튼 → 진행 상태로 막기

**상황**

```tsx
async function handleReserve() {
  await reserveSeats(selectedSeatIds)
  navigate('/tickets/complete')
}

;<ActionButton onClick={handleReserve}>예매하기</ActionButton>
```

**처방: 보내는 중에는 누를 수 없게**

```tsx
const [isReserving, setIsReserving] = useState(false)

async function handleReserve() {
  setIsReserving(true)
  try {
    await reserveSeats(selectedSeatIds)
  } finally {
    setIsReserving(false) // 실패해도 다시 누를 수 있게
  }
  navigate('/tickets/complete')
}

;<ActionButton onClick={handleReserve} disabled={isReserving}>
  예매하기
</ActionButton>
```

**왜**: 응답이 2초 걸리면 사용자는 "안 눌렸나?" 하고 한 번 더 누릅니다. 상황 코드는 그때마다 요청을 새로 보내니 같은 좌석 예매가 두 번 나갈 수 있습니다. `disabled`된 버튼은 클릭 이벤트가 일어나지 않으니, 첫 요청이 끝날 때까지 두 번째는 시작되지도 않습니다. `finally`에서 풀어 주는 이유는 실패했을 때 버튼이 영영 잠기지 않게 하려는 것입니다. 다만 이건 화면 쪽 방어라서, 결제처럼 두 번 되면 안 되는 요청은 서버도 따로 막아야 합니다.

**안 해도 되는 때**: 검색이나 새로고침처럼 두 번 보내도 결과가 같은 요청은 막지 않아도 됩니다. TanStack Query의 `useMutation`을 쓰고 있다면 `isPending`이 이미 있으니 state를 따로 만들 필요도 없습니다.

### 3. 타입으로 막기 · string으로 받는 상태 switch → 유니온 타입과 Record로 빠짐없이

**상황**

```ts
function getStatusLabel(status: string) {
  switch (status) {
    case 'accepted':
      return '주문을 받았어요'
    case 'cooking':
      return '조리하고 있어요'
    case 'delivering':
      return '배달하고 있어요'
    default:
      return ''
  }
}
```

**처방: 가능한 값을 타입으로 적고, 문구는 표 하나로**

```ts
type OrderStatus = 'accepted' | 'cooking' | 'delivering' | 'delivered'

const STATUS_LABEL: Record<OrderStatus, string> = {
  accepted: '주문을 받았어요',
  cooking: '조리하고 있어요',
  delivering: '배달하고 있어요',
  delivered: '배달을 마쳤어요',
}
```

**왜**: `string`으로 받으면 `'cookng'` 같은 오타도 통과하고, `'delivered'`가 새로 생겨도 `default`가 빈 문자열로 삼켜서 화면에 빈칸이 뜹니다. `Record<OrderStatus, string>`은 키가 하나라도 빠지면 `Property 'delivered' is missing in type '{ ... }' but required in type 'Record<OrderStatus, string>'.`으로 막아 줍니다. 상태를 하나 늘리면 문구를 채워야 할 자리를 컴파일러가 알려 주는 셈입니다.

**안 해도 되는 때**: 갈래가 두 개뿐이고 한 곳에서만 쓰는 값이라면 삼항 연산자 하나가 더 짧고 잘 읽힙니다.

## 생각하는 법

### 기획을 코드로 · 정책 두 개가 한 주문에 같이 걸릴 때

**장면**: 쇼핑몰 배송비 기획 메모입니다.

> 멤버십 회원은 배송비가 무료예요. 제주·도서산간 지역은 추가 배송비 3,000원이 붙어요.

정책 하나씩 보면 둘 다 간단합니다. 그런데 멤버십 회원이 제주로 주문하면 배송비는 0원일까요, 3,000원일까요?

**생각 순서**

1. **"두 정책에 같이 걸리는 주문이 있나?"** 정책을 하나씩 읽고 끝내지 않고, 둘을 동시에 만족하는 주문 하나를 일부러 만들어 봅니다. 멤버십 회원, 제주 주소, 2만원짜리 주문.
2. **"if 순서가 답을 몰래 정하고 있지 않나?"** `if (isMember) return 0`을 먼저 쓰면 제주 추가 배송비는 영영 안 붙습니다. 지역 확인을 먼저 쓰면 결과가 달라집니다. 코드의 줄 순서가 정책의 우선순위가 되는 순간입니다. 이건 개발자가 고를 문제가 아니라 기획자에게 물을 질문입니다.
3. **"어떻게 물어야 바로 답이 오지?"** "우선순위가 어떻게 되나요?"보다 "멤버십 회원이 제주로 주문하면 3,000원을 내나요?"처럼 겹치는 주문 하나를 들고 갑니다. 답이 "무료는 기본 배송비만이고, 추가 배송비는 누구나 내요"라고 왔다고 해 봅니다.
4. **"답을 들으니 우선순위 문제가 맞았나?"** 알고 보니 누가 이기는 문제가 아니라, 서로 다른 두 금액을 **더하는** 문제였습니다. 그러면 if를 줄 세울 필요 없이 두 금액을 따로 구해 더합니다.

**코드로 옮기면**

```ts
function getShippingFee(order: Order, member: Member) {
  const baseFee = member.hasMembership ? 0 : BASE_SHIPPING_FEE
  const remoteAreaFee = isRemoteArea(order.address) ? REMOTE_AREA_FEE : 0
  return baseFee + remoteAreaFee
}

it('멤버십 회원도 제주로 보내면 추가 배송비 3,000원은 낸다', () => {})
```

**한 줄 요약**: 정책 두 개가 같이 걸리는 주문 하나를 만들어 기획자에게 묻습니다. 그 답이 정해지기 전에는 if 순서가 우선순위를 몰래 정하게 두지 않습니다.

## 기본기

### React · 목록 `key`에 index를 쓰면 왜 입력값이 엉뚱한 줄에 남을까?

```tsx
{
  todos.map((todo, index) => (
    <TodoRow key={index} todo={todo} /> // TodoRow 안에 메모 입력 state가 있다
  ))
}
```

맨 앞에 새 할 일을 넣으면, key `0`의 주인은 이제 새 할 일입니다. 그런데 React는 key가 같으니 "같은 컴포넌트"라고 보고, 원래 첫 줄의 `TodoRow`를 그대로 두고 `todo` props만 바꿉니다. 그래서 첫 줄에 쓰던 메모가 새 할 일 옆에 남습니다. key는 "이 컴포넌트가 어느 데이터의 것인지"를 알려 주는 이름이라 `todo.id`처럼 데이터에 붙은 값을 씁니다. 반대로 `key={Math.random()}`은 렌더링마다 다른 이름이라 매번 새로 만들어지고 state가 다 날아갑니다. React 버전과 상관없이 같은 동작입니다.

**실무에서 만나는 장면**: 맨 위에 항목을 추가하거나 하나를 지웠더니 체크 표시나 입력값이 한 칸씩 밀려 보일 때. 10월 31일 처방에서 `key`를 바꿔 폼을 새로 시작했던 것과 같은 원리를 반대로 겪는 장면입니다.

### TypeScript · `filter(Boolean)`을 했는데 왜 타입에 `undefined`가 남을까?

```ts
declare const couponId: string | undefined
declare const pointId: string | undefined

const a = [couponId, pointId].filter(Boolean) // (string | undefined)[]
const b = [couponId, pointId].filter((id) => id !== undefined) // string[]
```

실행 결과는 둘 다 `undefined`가 빠진 배열인데, 타입은 다릅니다. TypeScript는 `filter`에 넘긴 함수가 "이 값은 `string`이다"라고 알려 주는 함수(타입 술어)일 때만 결과 타입을 좁힙니다. `Boolean`은 그냥 참·거짓을 돌려줄 뿐이라 좁혀지지 않습니다. `id !== undefined` 같은 화살표 함수는 TypeScript 5.5부터 타입 술어로 추론해 줘서 `string[]`이 됩니다. 그 전 버전에서는 `(id): id is string => id !== undefined`처럼 직접 적어야 했습니다(`tsc --strict`, 6.0으로 확인).

**실무에서 만나는 장면**: 고른 쿠폰과 포인트 id를 모아 결제 요청에 넣는데 `Type '(string | undefined)[]' is not assignable to type 'string[]'.`가 뜰 때. `as string[]`로 덮기 전에 조건을 화살표 함수로 바꿔 봅니다.

### 네트워크 · `Cache-Control: no-cache`는 캐시를 안 한다는 뜻일까?

아닙니다. 이름과 달리 `no-cache`는 "저장은 해도 되지만, 쓰기 전에 매번 서버에 아직 유효한지 물어봐"입니다. 서버가 바뀌지 않았다고 답하면(`304 Not Modified`) 본문을 다시 받지 않고 저장해 둔 것을 씁니다. 아예 저장하지 말라는 건 `no-store`입니다.

- `no-store`: 저장하지 않는다. 개인 정보가 담긴 응답에.
- `no-cache`: 저장하되 쓸 때마다 확인한다. 자주 바뀌는 HTML에.
- `max-age=31536000, immutable`: 1년 동안 묻지 않고 쓴다. 파일 이름에 해시가 붙은 JS·CSS에.

**실무에서 만나는 장면**: 배포했는데 일부 사용자에게만 옛 화면이 보일 때. `index.html`이 오래 캐시되면 옛 HTML이 옛 JS 파일 이름을 계속 불러옵니다. HTML은 `no-cache`로 매번 확인하게 하고, 해시가 붙은 파일은 내용이 바뀌면 이름도 바뀌니 길게 캐시하는 조합을 흔히 씁니다.
