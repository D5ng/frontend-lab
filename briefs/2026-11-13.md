## 클린 코드 처방

### 1. 상태와 파생 값 · 부모가 가진 값을 자식이 state로 한 벌 더 들 때 → 부모 값을 그대로 받기

장바구니의 수량 버튼입니다. 수량을 바꾸면 부모가 합계를 다시 계산하고, 서버가 재고를 확인해 수량을 줄여 돌려주기도 합니다.

**상황**

```tsx
function QuantityStepper({ initialCount, onChange }: Props) {
  const [count, setCount] = useState(initialCount)

  function increase() {
    setCount(count + 1)
    onChange(count + 1)
  }

  return <Stepper value={count} onIncrease={increase} />
}
```

**처방: 값은 부모 하나가 들고, 자식은 받아서 그린다**

```tsx
function QuantityStepper({ count, onChange }: Props) {
  return <Stepper value={count} onIncrease={() => onChange(count + 1)} />
}

// 부모
;<QuantityStepper count={item.quantity} onChange={(next) => changeQuantity(item.id, next)} />
```

**왜**: 상황 코드에는 수량의 원본이 둘입니다. 자식의 `count`와 부모의 `item.quantity`입니다. `useState(initialCount)`는 처음 그릴 때 한 번만 읽히니, 서버가 "재고가 3개뿐이에요"라며 수량을 3으로 줄여도 버튼 옆 숫자는 5에 머뭅니다. 합계는 3개 값인데 화면 숫자는 5가 됩니다. 원본을 부모 하나로 두면 어긋날 틈도 없습니다.

**안 해도 되는 때**: 10월 31일의 가격 제안 폼처럼 자식이 시작값을 받아 혼자 고치다가 마지막에 한 번만 알리는 경우라면 자식 state가 맞습니다. 부모가 "지금 값"을 계속 알아야 하는지가 기준입니다.

### 2. 훅 · effect 하나에 서로 다른 일 두 개 → 일마다 effect 하나

공연 예매 대기열 화면입니다. 서버와 연결해 내 순번을 받고, 다른 탭을 보고 있어도 알 수 있게 브라우저 탭 제목에 순번을 띄웁니다.

**상황**

```tsx
useEffect(() => {
  const socket = connectQueue(queueId, setPosition)
  document.title = `${position.toLocaleString()}번째 대기 중`
  return () => socket.close()
}, [queueId, position])
```

**처방: 같이 시작하고 같이 끝나는 일끼리만 한 effect에**

```tsx
useEffect(() => {
  const socket = connectQueue(queueId, setPosition)
  return () => socket.close()
}, [queueId])

useEffect(() => {
  document.title = `${position.toLocaleString()}번째 대기 중`
}, [position])
```

**왜**: effect는 의존성 중 하나라도 바뀌면 정리하고 처음부터 다시 실행됩니다. 상황 코드는 순번이 바뀔 때마다 연결을 끊고 다시 맺습니다. 순번이 1초에 몇 번씩 줄어드는 대기열이면 1초에 몇 번씩 재연결하는 셈입니다. 연결은 `queueId`를 따라, 제목은 `position`을 따라 움직이니 서로 다른 일입니다. react.dev의 effect 생명주기 문서도 같은 때 실행된다는 이유만으로 관계없는 일을 한 effect에 넣지 말라고 안내합니다(React 18·19 공통).

**안 해도 되는 때**: 연결을 맺는 일과 그 연결에 이벤트를 다는 일처럼 한 과정의 앞뒤라면 하나로 둡니다. 억지로 나누면 둘째 effect가 첫째가 만든 연결을 찾아 써야 해서 더 꼬입니다.

### 3. 비동기와 에러 처리 · 서로 상관없는 요청을 줄 세워 기다리기 → 같이 출발시키기

부동산 앱의 매물 상세 화면입니다. 들어오면 매물 정보, 주변 시세, 내 찜 여부를 불러옵니다. 셋은 서로의 응답을 쓰지 않습니다.

**상황**

```ts
async function loadListingDetail(listingId: ListingId) {
  const listing = await getListing(listingId)
  const marketPrice = await getMarketPrice(listingId)
  const isSaved = await getIsSaved(listingId)
  return { listing, marketPrice, isSaved }
}
```

**처방: 먼저 다 보내고, 기다리기는 한 번에**

```ts
async function loadListingDetail(listingId: ListingId) {
  const [listing, marketPrice, isSaved] = await Promise.all([getListing(listingId), getMarketPrice(listingId), getIsSaved(listingId)])
  return { listing, marketPrice, isSaved }
}
```

**왜**: `await`는 그 줄의 응답이 올 때까지 다음 줄로 가지 않습니다. 요청마다 300ms가 걸리면 상황 코드는 900ms를 기다리고, 처방은 가장 느린 하나만큼인 300ms 남짓을 기다립니다. 요청이 하나 늘 때마다 차이도 커집니다. `Promise.all`은 넘긴 순서대로 결과를 돌려주니 구조 분해로 이름을 그대로 붙일 수 있고, TypeScript도 `[Listing, MarketPrice, boolean]`으로 각 자리의 타입을 압니다.

**안 해도 되는 때**: 둘째 요청이 첫 응답의 값을 써야 하면(매물의 `agentId`로 중개사 정보 조회) 순서대로 기다리는 게 맞습니다. 시세 하나가 실패해도 매물은 보여 줘야 한다면 11월 7일에 본 `allSettled`입니다.

## 생각하는 법

### 문제를 풀 때 · 비슷한 코드가 두 번 보이면 바로 묶을까?

**장면**: 병원 예약 앱에서 진료 예약 확인 화면을 끝내고, 이어서 건강검진 예약 확인 화면을 만들고 있습니다. 화면 아래 "취소 안내" 카드가 거의 똑같습니다. 제목, 안내 문구 세 줄, "예약 취소" 버튼까지. 복사해 붙이다가 손이 멈춥니다. `CancelNoticeCard` 하나로 묶어야 하지 않을까?

**생각 순서**

1. **"이 둘은 같은 이유로 바뀔까?"** 지금은 문구만 다르고 모양이 같습니다. 그런데 규정을 정하는 곳이 다릅니다. 진료 취소는 외래 접수가, 검진 취소는 검진센터가 정합니다. 정하는 사람이 다르면 바뀌는 날도 따로 옵니다.
2. **"한쪽만 바뀌는 요청이 오면 어떻게 되지?"** "검진은 금식 안내도 같이 보여 주세요"가 오는 장면을 떠올려 봅니다. 묶어 둔 카드에 `showFastingNotice` 같은 prop이 하나 붙겠지요. 이런 prop이 쉽게 떠오르면 아직 묶을 때가 아닙니다.
3. **"묶으면 이름이 뭐지?"** 둘을 다 설명하는 이름이 자연스럽게 나오는지 봅니다. `ReservationCancelNotice`가 두 화면 모두에 딱 맞는다면 같은 개념일 가능성이 큽니다. `InfoCard`처럼 생김새밖에 말하지 못하는 이름만 떠오르면, 같은 건 생김새뿐입니다.
4. **"지금 안 묶으면 잃는 게 뭐지?"** 두 군데 복사는 찾기도 고치기도 쉽습니다. 세 번째 화면이 생기고, 셋이 같이 바뀌는 요청을 한 번 겪은 뒤에 묶어도 늦지 않습니다. 잘못 묶은 것을 다시 푸는 쪽이 훨씬 어렵습니다.

**코드로 옮기면**

```tsx
// 서둘러 묶은 카드가 몇 주 뒤에 자주 하는 모양
<CancelNoticeCard policy={policy} isCheckup showFastingNotice hideSameDayCancel />
// 카드 안은 isCheckup 분기로 가득하고, 진료 쪽을 고칠 때마다 검진 화면도 열어 봐야 한다
```

**한 줄 요약**: 생김새가 같아서가 아니라 같이 바뀐다는 걸 확인했을 때 묶습니다. 확신이 없으면 일단 두 벌로 두고, 같이 바뀌는 순간이 오는지 지켜봅니다.

## 기본기

### JavaScript · `new Date('2026-11-20')`로 센 D-day가 왜 하루 더 많을까?

```ts
// 한국 시간 11월 13일, 체크인은 11월 20일
const DAY = 24 * 60 * 60 * 1000
const today = new Date(2026, 10, 13).getTime() // 오늘 0시, 월은 0부터 센다
const dDay = (date: string) => Math.ceil((new Date(date).getTime() - today) / DAY)

dDay('2026-11-20') // 8
dDay('2026-11-20T00:00') // 7
```

날짜만 쓴 문자열(`'2026-11-20'`)은 UTC 0시로 읽고, 시각까지 쓴 문자열(`'2026-11-20T00:00'`)은 기기 시간대의 그 시각으로 읽습니다. ECMAScript 명세가 정한 규칙입니다. 한국은 UTC보다 9시간 빠르니 `new Date('2026-11-20')`은 한국 시간 11월 20일 오전 9시이고, 오늘 0시와의 차이가 7일 9시간이라 올림하면 8이 됩니다. 미국처럼 UTC보다 늦은 곳에서는 같은 문자열이 전날 저녁이 됩니다.

날짜만 다루는 값은 `new Date(2026, 10, 20)`처럼 연·월·일을 나눠 만들거나, `'2026-11-09' < '2026-11-20'`처럼 문자열 그대로 비교합니다. TypeScript에서는 `Date`끼리 바로 빼면 `The left-hand side of an arithmetic operation must be of type 'any', 'number', 'bigint' or an enum type.` 오류가 나서 `getTime()`을 붙였습니다. 시간대를 바꿔 가며 Node 24에서, 타입 오류는 TypeScript 6.0 `--strict`로 확인했습니다.

**실무에서 만나는 장면**: 여행 앱의 "체크인까지 D-7"이 D-8로 보일 때. 오늘 0시 대신 `Date.now()`로 세면 오전 9시 전에는 D-8, 지나면 D-7로 바뀌어서 더 찾기 어렵습니다. 서버가 준 `'2026-11-20'`을 `new Date()`에 바로 넣고 있는지 봅니다.

### 네트워크 · 메모 저장 POST가 리다이렉트되더니 왜 GET으로 바뀔까?

```ts
// 서버가 /api/memos 를 /api/memos/ 로 옮기며 301로 답한다
await fetch('/api/memos', { method: 'POST', body: JSON.stringify(memo) })
// fetch는 /api/memos/ 로 다시 요청하는데, 메서드는 GET이고 본문은 없다
```

`fetch`는 리다이렉트를 알아서 따라갑니다. 이때 301과 302는 POST를 GET으로 바꾸고 본문을 버립니다. 원래 명세가 의도한 동작은 아니지만 브라우저들이 오래전부터 그렇게 해 왔고, Fetch 명세도 그 동작을 따릅니다. 303은 "결과는 GET으로 보러 가라"는 뜻이라 언제나 GET이 됩니다. 메서드와 본문을 그대로 두는 건 307(임시)과 308(영구)입니다. Node 24의 `fetch`로 다섯 코드를 보내 확인했고, MDN의 리다이렉트 안내와도 같습니다.

**실무에서 만나는 장면**: 저장했다고 뜨는데 메모가 생기지 않을 때. GET으로 바뀐 요청에 서버가 목록을 200으로 돌려주면 화면은 성공으로 봅니다. 개발자 도구 Network 탭에서 POST 앞에 301이 찍혀 있는지, 주소 끝 슬래시가 빠지지 않았는지 봅니다.

### 브라우저 · 피드 이미지가 뜰 때마다 왜 글이 아래로 밀릴까?

```tsx
// 크기를 모르면 자리를 거의 잡지 않았다가, 이미지가 오면 그만큼 아래를 밀어낸다
<img src={post.imageUrl} alt={post.imageAlt} />

// 원본 크기를 알려 주면 받기 전부터 그 비율만큼 자리를 잡아 둔다
<img src={post.imageUrl} alt={post.imageAlt} width={1080} height={1350} />
```

브라우저는 이미지를 받아 보기 전까지 크기를 모릅니다. 그래서 일단 이미지 자리를 거의 비워 두고 글을 배치했다가, 이미지가 도착하면 그 높이만큼 아래 내용을 밀어냅니다. `width`와 `height`를 둘 다 적으면 브라우저가 받기 전에 가로세로 비율을 계산해 자리를 잡아 둡니다. 화면에 그리는 크기는 여전히 CSS가 정하니, `width: 100%; height: auto`로 화면 폭에 맞춰도 비율만큼의 자리는 그대로 남습니다. MDN `<img>` 문서로 확인했습니다. 서버가 이미지의 가로·세로 크기를 같이 내려주면 그 값을 그대로 넣습니다.

**실무에서 만나는 장면**: 피드를 내리다 "좋아요"를 누르려는 순간 위쪽 이미지가 늦게 떠서 버튼이 밀리고 엉뚱한 곳이 눌릴 때. Lighthouse의 CLS(레이아웃 이동) 점수가 나쁘게 나올 때도 이것부터 봅니다.
