## 클린 코드 처방

### 1. 테스트하기 좋은 모양 · 함수 안에서 지금 시각 읽기 → 시각을 인자로 받기

어제 드릴에서 계산 규칙을 순수 함수로 꺼냈다면, 그다음에 자주 걸리는 자리가 여기입니다.

**상황**

```ts
// 가게 마감 30분 전부터는 '마감 임박'으로 보여 준다
function getOrderStatus(store: Store): OrderStatus {
  const now = new Date()
  const minutesLeft = (store.closesAt.getTime() - now.getTime()) / 60_000

  if (minutesLeft <= 0) return 'closed'
  if (minutesLeft <= LAST_CALL_MINUTES) return 'lastCall'
  return 'open'
}
```

**처방: "지금"은 부르는 쪽이 넘긴다**

```ts
function getOrderStatus(store: Store, now: Date): OrderStatus {
  const minutesLeft = (store.closesAt.getTime() - now.getTime()) / 60_000
  // ...아래는 그대로
}

// 화면
const status = getOrderStatus(store, new Date())

// 테스트: 시계를 조작하지 않아도 된다
expect(getOrderStatus(store, new Date('2026-10-31T21:50:00'))).toBe('lastCall')
```

**왜**: 안에서 `new Date()`를 읽으면 같은 가게를 넣어도 언제 부르느냐에 따라 답이 달라집니다. 겉모양은 순수 함수인데 실제로는 아닌 셈입니다. 시각을 인자로 받으면 함수는 규칙만 알고, "지금이 언제인지"는 화면이 정합니다. 테스트에서 "마감 10분 전" 같은 경계도 날짜 하나로 바로 만들 수 있습니다.

**안 해도 되는 때**: `createdAt: new Date()`처럼 시각을 기록만 하고 그 값으로 판단하지 않는 코드라면 굳이 인자로 뺄 필요가 없습니다.

### 2. 컴포넌트 props · props가 바뀔 때 effect로 state 맞추기 → key로 새로 시작하기

**상황**

```tsx
function PriceOfferSheet({ listing }: { listing: Listing }) {
  const [price, setPrice] = useState(listing.askingPrice)
  const [message, setMessage] = useState('')

  useEffect(() => {
    setPrice(listing.askingPrice) // 다른 매물로 바뀌면 맞춰 주기
  }, [listing])
  // ...
}
```

**처방: 다른 매물이면 다른 폼이다**

```tsx
;<PriceOfferSheet key={listing.id} listing={listing} />

function PriceOfferSheet({ listing }: { listing: Listing }) {
  const [price, setPrice] = useState(listing.askingPrice) // 매물마다 새로 시작
  const [message, setMessage] = useState('')
  // ...
}
```

**왜**: 여기서 `price`는 매물 가격을 시작값으로 받아 사용자가 고치는 값입니다. 매물이 바뀌면 "제안 폼이 하나 새로 열린 것"이니, `key`를 바꿔 React가 컴포넌트를 처음부터 만들게 합니다. effect로 맞추면 한 번은 이전 매물 가격이 그려지고, 위 코드처럼 `message`를 같이 비우는 걸 빠뜨리기 쉽습니다. 샘플에서 본 `total`은 계산하면 되는 값이라 state가 필요 없었고, 이번 `price`는 사용자가 고치니 state가 맞습니다. 다른 건 "언제 처음부터 다시 시작하느냐"입니다.

**안 해도 되는 때**: 시트를 닫을 때 언마운트되는 구조라면 열 때마다 새로 시작하니 `key`가 없어도 됩니다.

### 3. 조건문 · 길어진 조건식 → 조건마다 이름 붙이기

**상황**

```tsx
if (
  meetup.status === 'open' &&
  meetup.members.length < meetup.capacity &&
  !meetup.members.some((m) => m.id === user.id) &&
  (!meetup.minAge || user.age >= meetup.minAge)
) {
  return <JoinButton />
}
```

**처방: 기획 문장을 변수 이름으로**

```tsx
const isRecruiting = meetup.status === 'open'
const hasSeat = meetup.members.length < meetup.capacity
const isMember = meetup.members.some((m) => m.id === user.id)
const meetsMinAge = !meetup.minAge || user.age >= meetup.minAge

const canJoin = isRecruiting && hasSeat && !isMember && meetsMinAge
if (canJoin) return <JoinButton />
```

**왜**: 읽는 사람이 연산식을 머릿속에서 풀지 않고 "모집 중이고, 자리가 있고, 아직 멤버가 아니고, 나이 제한을 넘으면"으로 읽습니다. 나중에 "왜 참가 버튼이 안 보여요?"라는 문의가 오면 `hasSeat`가 거짓일 때 "자리가 다 찼어요"를 보여 주는 식으로 이름을 그대로 다시 쓸 수 있습니다.

**안 해도 되는 때**: `if (!user)`처럼 한눈에 읽히는 조건 하나에까지 이름을 붙이면 오히려 한 번 더 건너가서 읽어야 합니다.

## 생각하는 법

### 기획을 코드로 · "까지"는 그날을 포함할까?

**장면**: 공연 예매 취소 화면의 기획 메모입니다.

> 공연 3일 전까지 취소하면 전액 환불해 드려요. 그 이후에는 취소 수수료 10%가 붙어요.

`daysLeft >= 3`이라고 쓰려다 손이 멈춥니다. 3일 전 "까지"면 그날 하루 종일일까요?

**생각 순서**

1. **"경계를 만드는 말은 어디지?"** 숫자 바로 옆의 "까지", "이후", "이상", "미만"이 경계입니다. 여기서는 "3일 전까지"와 "그 이후" 두 군데입니다.
2. **"경계에 딱 걸리면 어느 쪽이지?"** 공연이 11월 10일 저녁 7시입니다. 11월 7일 저녁 8시에 취소하면 전액 환불일까요? 시각으로 72시간을 세면 7일 저녁 7시가 끝이라 수수료가 붙고, 날짜로 세면 7일 밤 11시 59분까지라 전액입니다. 둘 다 말이 됩니다. 이건 코드에서 고를 문제가 아니라 기획자가 정할 정책입니다.
3. **"어떻게 물어야 바로 답이 오지?"** "기준이 시각인가요, 날짜인가요?"보다 "11월 7일 저녁 8시 취소는 전액인가요?"처럼 경계에 걸린 예시 하나를 들고 가면 답하기 쉽습니다. 기획자도 그 질문을 받고 나서야 정하는 경우가 많습니다.
4. **"받은 답은 어디에 남기지?"** 메모나 주석보다 테스트 이름이 오래 갑니다. 정책이 바뀌면 테스트가 먼저 깨져서 알려 줍니다.

**코드로 옮기면**

```ts
// 기획 답(10/31): 날짜 기준. 공연 3일 전 날 23:59까지 전액 환불
describe('예매 취소 수수료', () => {
  it('공연 3일 전 밤 11시 59분에 취소하면 전액 환불한다', () => {})
  it('공연 2일 전 0시에 취소하면 수수료 10%를 뗀다', () => {})
})
```

**한 줄 요약**: "까지"가 포함인지 아닌지 혼자 정하지 않습니다. 경계에 딱 걸린 예시 하나를 기획자에게 묻고, 답을 테스트 이름으로 남깁니다.

## 기본기

### TypeScript · `satisfies`는 타입 주석이랑 뭐가 다를까?

```ts
type PlanConfig = { price: number; maxProfiles?: number }

const PLANS = {
  basic: { price: 9900 },
  family: { price: 15900, maxProfiles: 4 },
} satisfies Record<string, PlanConfig>

PLANS.family.maxProfiles // number
PLANS.premium // 오류: Property 'premium' does not exist on type ...
```

`const PLANS: Record<string, PlanConfig>`처럼 주석을 달면 값의 타입이 주석 타입으로 바뀝니다. 그래서 `PLANS.family.maxProfiles`는 `number | undefined`가 되고, 없는 `PLANS.premium`도 통과합니다. `satisfies`는 "이 모양을 지키는지 검사만 하고, 타입은 실제 값 그대로 둔다"입니다. `price`를 `prise`로 잘못 쓰면 둘 다 잡아 줍니다. 반면 `as`는 검사가 아니라 "내 말을 믿어"라서 `{} as PlanConfig`처럼 `price`가 빠져도 통과합니다(TypeScript 4.9부터, `tsc --strict`로 확인).

**실무에서 만나는 장면**: 요금제·카테고리·라우트처럼 코드에 박아 두는 설정 객체. 오타는 잡고 싶은데, 쓰는 쪽에서 실제 키와 값 타입이 그대로 보여야 할 때.

### React · effect의 cleanup은 언제 실행될까?

```tsx
useEffect(() => {
  const unsubscribe = subscribeRoom(roomId, addMessage)
  return () => unsubscribe()
}, [roomId])
```

cleanup이 실행되는 때는 두 가지입니다. 하나는 컴포넌트가 사라질 때, 다른 하나는 의존성(`roomId`)이 바뀌어 effect가 다시 실행되기 **직전**입니다. 이때 cleanup은 이전 렌더링의 `roomId`를 기억하고 있어서 이전 방 구독을 끊고, 그다음 새 방을 구독합니다. React 18부터 개발 모드의 Strict Mode에서는 마운트 직후 setup → cleanup → setup을 한 번 더 돌려서, cleanup이 빠졌는지 일부러 드러냅니다(React 19도 같습니다).

**실무에서 만나는 장면**: 채팅방을 옮겼더니 이전 방 메시지가 계속 섞여 들어올 때, 개발 모드에서만 알림이 두 번 올 때. 둘 다 cleanup이 비어 있다는 신호입니다.

### 네트워크 · Postman에선 되는데 브라우저에선 CORS 에러가 날까?

CORS는 서버가 거절하는 게 아니라 **브라우저가** 다른 출처의 응답을 페이지 코드에 넘겨줄지 정하는 규칙입니다. Postman이나 서버끼리 요청에는 이 검사가 없습니다.

- **단순 요청**(GET, 그리고 폼 형식 Content-Type의 POST 등): 요청은 서버까지 가고 응답도 옵니다. 응답에 `Access-Control-Allow-Origin`이 맞지 않으면 브라우저가 JS에 안 보여 줄 뿐입니다.
- **사전 요청이 붙는 요청**(`Content-Type: application/json`, `Authorization` 헤더 등): 브라우저가 먼저 `OPTIONS`로 물어보고, 허락이 없으면 본 요청은 아예 보내지 않습니다.

**실무에서 만나는 장면**: 서버 로그에 POST는 없고 `OPTIONS`만 찍혀 있을 때. 프론트 코드가 아니라 서버의 CORS 설정(허용 출처·메서드·헤더)을 봐야 합니다.
