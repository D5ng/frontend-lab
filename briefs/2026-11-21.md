## 클린 코드 처방

### 1. 비동기와 에러 처리 · 끝나지 않는 요청 → 기다릴 시간을 정해 두기

금융 앱의 환율 화면입니다. 실패하면 "다시 시도" 버튼이 뜨도록 잘 만들어 두었습니다.

**상황**

```tsx
async function loadRates() {
  setStatus('loading')
  try {
    const res = await fetch('/api/exchange-rates')
    if (!res.ok) throw new Error(`HTTP ${res.status}`)
    setRates(await res.json())
    setStatus('success')
  } catch {
    setStatus('error')
  }
}
```

**처방: `AbortSignal.timeout`으로 시간 제한 걸기**

```tsx
const RATES_TIMEOUT_MS = 8_000

async function loadRates() {
  setStatus('loading')
  try {
    const res = await fetch('/api/exchange-rates', { signal: AbortSignal.timeout(RATES_TIMEOUT_MS) })
    if (!res.ok) throw new Error(`HTTP ${res.status}`)
    setRates(await res.json())
    setStatus('success')
  } catch (error) {
    setStatus(isTimeout(error) ? 'timeout' : 'error')
  }
}

function isTimeout(error: unknown) {
  return error instanceof DOMException && error.name === 'TimeoutError'
}
```

**왜**: `fetch`에는 시간 제한 옵션이 없습니다. 서버가 연결만 붙잡고 답을 주지 않으면, 브라우저가 스스로 연결을 끊을 때까지 `await`가 끝나지 않습니다. 그동안은 `catch`로도 못 가니 "다시 시도" 버튼은 만들어 놓고도 보여 줄 기회가 없고 스피너만 돕니다. 시간을 정해 두면 "안 온다"도 실패 중 하나가 됩니다. 시간이 다 되면 이름이 `TimeoutError`인 에러로 끝나서, "연결이 느려요"처럼 서버 오류와 다른 안내도 할 수 있습니다.

**안 해도 되는 때**: 공용 요청 함수나 HTTP 클라이언트에 이미 시간 제한이 걸려 있다면 화면마다 또 걸지 않습니다. 사진 업로드처럼 원래 오래 걸리는 요청은 짧은 제한 대신 진행률을 보여 줍니다.

### 2. 함수와 인자 · 본문 곳곳에서 채우는 기본값 → 매개변수 자리에 모으기

채용 앱의 공고 검색입니다. 화면마다 조건을 일부만 넘기고, 나머지는 함수가 채웁니다.

**상황**

```ts
function buildJobQuery(options: JobSearchOptions) {
  const params = new URLSearchParams()
  params.set('page', String(options.page || 1))
  params.set('size', String(options.size ?? 20))
  if (options.sort) params.set('sort', options.sort)
  else params.set('sort', 'latest')
  return params.toString()
}
```

**처방: 구조 분해 기본값**

```ts
function buildJobQuery({ page = 1, size = 20, sort = 'latest' }: JobSearchOptions = {}) {
  return new URLSearchParams({ page: String(page), size: String(size), sort }).toString()
}
```

**왜**: "아무것도 안 넘기면 어떻게 되지?"의 답이 함수 첫 줄에 모입니다. 상황 코드는 같은 일을 `||`, `??`, `if`로 세 번 다르게 해서, 기본값 하나를 바꾸려 해도 본문을 끝까지 읽어야 합니다. 바꾸고 나면 `||`가 몰래 1로 바꾸던 `page: 0`도 그대로 나갑니다. 0을 막아야 한다면 그건 기본값이 아니라 검사가 할 일입니다. 하나 더 알아 둘 점은 구조 분해 기본값이 `undefined`일 때만 들어간다는 것입니다. 타입에 `null`이 들어 있으면 `null`은 그대로 남고, TypeScript도 `size`를 `number | null`로 봅니다. 그런 값은 들어오는 곳에서 먼저 정리합니다.

**안 해도 되는 때**: 부르는 곳마다 값이 달라서 기본값이라 할 만한 게 없다면, 기본값을 두지 말고 필수로 받습니다. 기본값이 있으면 빠뜨려도 아무도 모르고 지나갑니다.

### 3. 테스트하기 좋은 모양 · 1초 기다리고 확인하기 → 나타날 때까지 기다리기

헬스케어 앱의 진료 접수 화면입니다. 접수 버튼을 누르면 서버 응답이 온 뒤 대기 번호가 뜹니다. 테스트에서는 MSW가 응답합니다.

**상황**

```tsx
test('접수하면 대기 번호를 보여 준다', async () => {
  render(<CheckInPage />)
  await user.click(screen.getByRole('button', { name: '진료 접수' }))

  await new Promise((resolve) => setTimeout(resolve, 1000))
  expect(screen.getByText('대기 번호 12번')).toBeInTheDocument()
})
```

**처방: `findBy`로 기다리기**

```tsx
test('접수하면 대기 번호를 보여 준다', async () => {
  render(<CheckInPage />)
  await user.click(screen.getByRole('button', { name: '진료 접수' }))

  expect(await screen.findByText('대기 번호 12번')).toBeInTheDocument()
})
```

**왜**: 1초는 "이쯤이면 왔겠지"라는 추측입니다. 응답이 30ms 만에 와도 남은 시간을 버리고, 이런 테스트가 쌓이면 그 1초도 쌓입니다. 줄이면 느린 CI에서 가끔 깨집니다. `findBy`는 50ms마다 다시 찾다가 나타나는 순간 통과하고, 기본 1초가 지나도 없으면 실패합니다. 무엇을 기다리는지가 코드에 적히는 것도 덤입니다.

**안 해도 되는 때**: 클릭하자마자 바로 바뀌는 화면이면 `getBy`로 충분합니다. 디바운스처럼 정말 시간이 흘러야 하는 동작은 가짜 타이머로 시간을 당깁니다.

## 생각하는 법

### 문제를 풀 때 · 이 state는 어디에 둬야 하지?

**장면**: 공연 좌석 선택 화면을 만드는 중입니다. 좌석 맵부터 만들면서 고른 좌석을 `SeatMap` 안의 `useState`에 뒀습니다. 이제 하단 바에 "2석 · 132,000원"을 띄우려는데 손이 멈춥니다. "이 값을 어떻게 밖으로 꺼내지?"

**생각 순서**

1. **"이 값을 읽는 건 누구지?"** 고른 자리를 칠하는 좌석 맵, 개수와 금액을 보여 주는 하단 바. 둘입니다. 읽는 곳이 하나면 그 안에 두면 끝이지만, 둘이 되는 순간 물어야 할 것은 "어떻게 꺼내지?"가 아니라 "어디에 둬야 하지?"로 바뀝니다.
2. **"바꾸는 건 누구지?"** 지금은 좌석을 누르는 좌석 맵뿐입니다. 하단 바에 "선택 해제"가 생기면 바꾸는 곳도 둘이 됩니다. 바꾸는 쪽은 값을 들고 있지 않아도 "이 좌석을 눌렀어요"만 알리면 됩니다.
3. **"둘을 모두 품는 가장 가까운 곳은?"** 좌석 맵과 하단 바를 함께 그리는 `SeatPage`입니다. 여기에 둡니다. 더 위, 앱 전체 store에 두면 화면을 나갔다 와도 값이 남아서, 다른 회차를 열었는데 아까 고른 자리가 칠해져 있는 일이 생깁니다.
4. **"이 중에 계산하면 되는 건?"** 좌석 수와 금액은 고른 좌석에서 나옵니다. state로 둘 건 `selectedIds` 하나뿐입니다.

**코드로 옮기면**

```tsx
function SeatPage({ seats }: { seats: Seat[] }) {
  const [selectedIds, setSelectedIds] = useState<string[]>([])
  const selectedSeats = seats.filter((seat) => selectedIds.includes(seat.id))

  function toggle(id: string) {
    setSelectedIds((ids) => (ids.includes(id) ? ids.filter((selected) => selected !== id) : [...ids, id]))
  }

  return (
    <>
      <SeatMap seats={seats} selectedIds={selectedIds} onToggle={toggle} />
      <PayBar count={selectedSeats.length} total={sumPrice(selectedSeats)} />
    </>
  )
}
```

**한 줄 요약**: state는 읽는 곳과 바꾸는 곳을 모두 품는 가장 가까운 자리에 둡니다. 더 위로 올리는 건 그 위에서도 읽어야 할 이유가 생긴 뒤입니다.

## 기본기

### JavaScript · `setTimeout(…, 0)`인데 왜 `then`보다 늦게 실행될까?

```ts
console.log('1')
setTimeout(() => console.log('2'), 0)
Promise.resolve().then(() => console.log('3'))
console.log('4')
// 1 → 4 → 3 → 2
```

JavaScript는 지금 돌고 있는 코드를 끝까지 실행한 뒤에야 줄 서 있는 일을 꺼냅니다. 줄은 두 종류입니다. `then` 콜백과 `await` 다음 줄은 마이크로태스크 줄에 서고, 지금 코드가 끝나자마자 이 줄이 빌 때까지 전부 실행됩니다. `setTimeout` 콜백은 그다음 차례인 태스크 줄에 섭니다. 0ms는 "바로"가 아니라 "적어도 0ms 뒤에 줄을 세운다"는 뜻입니다. 브라우저가 화면을 그리는 것도 지금 코드가 끝난 뒤에야 차례가 옵니다.

**실무에서 만나는 장면**: "내보내는 중…"을 띄우고 바로 무거운 계산을 돌렸더니 문구는 안 보이고 화면이 굳었다가, 계산이 끝나서야 한꺼번에 바뀔 때. 계산이 끝나야 화면을 그릴 차례가 옵니다.

### 네트워크 · `JSON.stringify`로 보냈는데 서버는 왜 body가 비었다고 할까?

```ts
await fetch('/api/posts/42/comments', {
  method: 'POST',
  body: JSON.stringify({ content: '저도 갈래요' }),
})
// 요청 헤더 → Content-Type: text/plain;charset=UTF-8
```

`JSON.stringify`의 결과는 그냥 문자열이라, 브라우저는 그게 JSON인지 모릅니다. Fetch 표준은 body가 문자열이면 `text/plain;charset=UTF-8`을 붙이게 정해 두었습니다. 서버는 이 헤더를 보고 body를 어떻게 읽을지 정하는데, Express의 `express.json()`처럼 JSON 파서는 기본으로 `application/json`일 때만 읽으니 body가 비어 보입니다. `headers: { 'Content-Type': 'application/json' }`을 직접 적어야 합니다. 11월 15일의 `FormData`와는 반대입니다. 그쪽은 브라우저가 구분 문자열까지 붙여야 해서 적으면 안 되고, 문자열은 브라우저가 내용을 모르니 적어야 합니다.

**실무에서 만나는 장면**: 공용 요청 함수를 거친 곳은 되는데, `fetch`를 바로 쓴 댓글 작성만 "내용을 입력해 주세요" 400이 올 때. Network 탭의 요청 헤더에서 `Content-Type`부터 봅니다.

### 브라우저 · 체크박스 옆 글자를 눌렀는데 왜 체크가 안 될까?

```tsx
<label>
  <input type="checkbox" checked={agreed} onChange={(e) => setAgreed(e.target.checked)} />
  마케팅 정보 수신에 동의해요
</label>
```

글자를 `span`으로 옆에 두기만 하면 브라우저는 그게 이 체크박스의 설명인지 모릅니다. 위처럼 `label`로 감싸거나, 떨어져 있어야 하면 `input`의 `id`와 `label`의 `htmlFor`(HTML의 `for`)로 잇습니다. 이어지면 글자를 눌러도 체크되어 누를 수 있는 영역이 넓어지고, 스크린 리더는 이 글자를 체크박스의 이름으로 읽습니다. 한 화면에 같은 컴포넌트가 여러 번 나와도 `id`가 겹치지 않게, React 18부터 있는 `useId`로 만듭니다.

**실무에서 만나는 장면**: 모바일에서 작은 네모만 정확히 눌러야 체크된다는 QA가 올 때, 테스트에서 `getByRole('checkbox', { name: '마케팅 정보 수신에 동의해요' })`가 요소를 못 찾을 때. 둘 다 `label`이 없다는 신호입니다.
