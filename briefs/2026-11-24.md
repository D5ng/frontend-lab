## 클린 코드 처방

### 1. 비동기와 에러 처리 · 성공·실패 콜백을 받는 요청 함수 → Promise를 돌려주기

교육 앱의 강의 상세 화면입니다. "수강 신청"을 누르면 신청을 보내고, 성공하면 시트를 닫고 토스트를 띄웁니다.

**상황**

```ts
function enrollCourse(courseId: string, onSuccess: () => void, onError: () => void) {
  fetch(`/api/courses/${courseId}/enroll`, { method: 'POST' })
    .then((res) => (res.ok ? onSuccess() : onError()))
    .catch(onError)
}

enrollCourse(
  course.id,
  () => {
    closeSheet()
    showToast('수강 신청했어요')
  },
  () => showToast('신청하지 못했어요'),
)
```

**처방: 끝났다는 사실만 돌려주고, 끝난 뒤 할 일은 부르는 쪽이 적기**

```ts
async function enrollCourse(courseId: string) {
  const res = await fetch(`/api/courses/${courseId}/enroll`, { method: 'POST' })
  if (!res.ok) throw new Error(`수강 신청 실패: ${res.status}`)
}

async function handleEnroll() {
  try {
    await enrollCourse(course.id)
  } catch {
    showToast('신청하지 못했어요')
    return
  }
  closeSheet()
  showToast('수강 신청했어요')
}
```

**왜**: 콜백으로 받으면 "끝나면 무엇을 할지"가 요청 함수의 인자가 됩니다. 신청 뒤에 내 강의 목록도 다시 불러와야 하면 콜백 안을 늘려야 하고, 진행 상태를 끄려면 두 콜백에 같은 줄을 적어야 합니다. 상황 코드에는 숨은 문제도 하나 있습니다. `closeSheet()`가 에러를 던지면 `.catch`가 그것까지 잡아서, 신청은 됐는데 "신청하지 못했어요"가 뜹니다. Promise를 돌려주면 `await`, `try`, `finally`, `Promise.all`을 그대로 쓸 수 있고, 처방처럼 실패할 수 있는 줄만 감쌀 수도 있습니다(10월 30일 처방).

**안 해도 되는 때**: 업로드 진행률이나 실시간 위치처럼 결과가 여러 번 오는 일은 한 번 끝나는 Promise로 나타낼 수 없으니 `onProgress` 같은 콜백이 맞습니다.

### 2. 테스트하기 좋은 모양 · 테스트 안에서 도는 for 문 → `it.each`로 경우마다 하나씩

공연 예매 앱의 관람료입니다. 미취학 아동은 무료, 청소년은 9,000원, 성인은 15,000원, 65세 이상은 7,000원입니다.

**상황**

```ts
it('나이에 따라 관람료가 달라진다', () => {
  const cases = [
    [7, 0],
    [13, 9000],
    [20, 15000],
    [65, 7000],
  ]
  for (const [age, price] of cases) {
    expect(getTicketPrice(age)).toBe(price)
  }
})
```

**처방: 경우마다 이름이 붙은 테스트로**

```ts
it.each([
  [7, 0],
  [13, 9000],
  [20, 15000],
  [65, 7000],
])('만 %i세는 %i원', (age, price) => {
  expect(getTicketPrice(age)).toBe(price)
})
```

**왜**: 청소년 요금 계산이 틀렸다고 해 봅시다. for 문 쪽은 "나이에 따라 관람료가 달라진다" 하나가 실패하고 메시지는 `expected 8000 to be 9000`뿐이라, 몇 살에서 틀렸는지는 표를 다시 대조해야 압니다. 첫 실패에서 멈추니 65세 요금도 같이 틀렸는지는 고치고 다시 돌려야 알 수 있습니다. `it.each`는 경우마다 테스트가 하나씩 생겨서 "만 13세는 9000원"이라는 이름으로 실패하고, 나머지 경우도 각자 결과가 나옵니다. Vitest와 Jest 모두 같은 모양으로 씁니다.

**안 해도 되는 때**: 경우마다 준비할 것이나 확인할 것이 다르면 표에 억지로 넣지 말고 테스트를 따로 씁니다. 표는 "입력만 다르고 확인하는 방법은 같다"일 때 쓰는 도구입니다.

### 3. 타입으로 막기 · `Partial<Member>`로 받는 수정 함수 → 바꿀 수 있는 필드만 골라 받기

커뮤니티 앱의 프로필 수정 화면입니다. 사용자가 고칠 수 있는 건 닉네임과 소개 글뿐입니다.

**상황**

```ts
type Member = {
  id: string
  nickname: string
  bio: string
  grade: 'basic' | 'gold'
}

function updateProfile(patch: Partial<Member>) {
  return api.patch('/me', patch)
}

updateProfile({ nickname, grade: 'gold' }) // 통과
```

**처방: 바꿀 수 있는 필드에 이름을 붙이기**

```ts
type ProfilePatch = Partial<Pick<Member, 'nickname' | 'bio'>>

function updateProfile(patch: ProfilePatch) {
  return api.patch('/me', patch)
}

updateProfile({ nickname, grade: 'gold' })
// 오류: 'grade' does not exist in type 'Partial<Pick<Member, "nickname" | "bio">>'.
```

**왜**: `Partial<Member>`는 "Member의 필드 아무거나 몇 개"라서 id도 등급도 받습니다. 서버가 막아 준다 해도, 화면 코드만 봐서는 "프로필 수정으로 등급을 바꿀 수 있나?"에 답할 수 없습니다. `ProfilePatch`라는 타입이 "이 화면에서 바꿀 수 있는 것"이라는 정책을 말하고, 다른 필드를 넣으면 컴파일러가 바로 알려 줍니다. 다만 11월 10일 기본기처럼 객체를 변수에 담아 넘기면 넘치는 속성 검사가 꺼지니, 마지막으로 막는 곳은 여전히 서버입니다.

**안 해도 되는 때**: 관리자 도구처럼 거의 모든 필드를 고치는 곳이라면 못 바꾸는 쪽을 빼는 `Omit`이 더 짧습니다. 11월 16일에 본 것처럼 `Omit`은 빼는 키 이름을 검사하지 않는다는 점만 기억해 둡니다.

### 기획을 코드로 · 예약을 취소하면 쓴 쿠폰은 돌아올까?

**장면**: 숙소 예약 앱 기획 메모에 이렇게 적혀 있습니다.

> 신규 가입 쿠폰(1만 원)은 한 번만 쓸 수 있어요.

쿠폰을 고르는 화면은 금방 만들었는데, 예약 취소 화면을 만들다가 손이 멈춥니다. 취소하면 이 쿠폰은 어떻게 되지?

**생각 순서**

1. **"이 정책을 거꾸로 돌리는 행동은 뭐가 있지?"** 기획 문장은 쿠폰을 쓰는 순간만 말합니다. 그런데 사용자는 예약을 취소하고, 숙소는 예약을 거절하고, 결제는 중간에 실패합니다. "한 번만"이 이런 경우에도 한 번으로 세는지가 문장에 없습니다. 정책이 걸리는 행동마다 그걸 되돌리는 행동을 짝지어 적어 봅니다.
2. **"누가 취소했는지에 따라 달라질까?"** 숙소가 거절한 예약 때문에 쿠폰이 사라지면 사용자는 억울합니다. 결제가 실패했는데 쿠폰만 써 버린 것도 이상합니다. 반면 사용자가 직접 취소했을 때 돌려줄지는 회사가 고를 문제입니다. 경우가 갈리면 질문도 경우마다 하나씩 만듭니다.
3. **"돌려준다면, 원래 모습 그대로일까?"** 11월 30일까지 쓸 수 있는 쿠폰을 12월 2일에 돌려받으면 쓸 수 있을까요? 되돌리기는 "원래대로"가 무엇인지까지 정해야 끝납니다.
4. **"화면은 무엇을 알아야 하지?"** 돌려줄지는 서버가 정하는 정책이고, 화면이 할 일은 취소 버튼을 누르기 전에 그 결과를 알려 주는 것입니다. "쿠폰은 돌려드려요"를 보여 주려면 서버가 그 답을 줘야 하니, 응답에 무엇이 필요한지도 같이 묻습니다.

```text
- 숙소가 예약을 거절하거나 결제가 실패하면요?
- 돌려줄 때 유효기간이 이미 지났다면요?
```

```ts
type CancelPreview = {
  refundAmount: number
```

## 기본기

### TypeScript · `typeof error === 'object'`로 확인했는데 왜 아직 `null`일 수 있다고 할까?

결제 SDK가 던진 에러에서 `code`를 꺼내려고 합니다.

```ts
function getErrorCode(error: unknown) {
  if (typeof error === 'object' && 'code' in error) {
    return error.code
  }
}
// 오류: 'error' is possibly 'null'. ('code' in error 자리에서)
```

JavaScript에서 `typeof null`은 `'object'`입니다. 초창기부터 이어진 동작이라 지금도 바꿀 수 없습니다. TypeScript는 이걸 알고 있어서 `typeof x === 'object'`를 통과한 값을 `object | null`로 좁힙니다. `null`까지 걸러 내야 `object`가 됩니다.

```ts
if (typeof error === 'object' && error !== null && 'code' in error) {
  return error.code // unknown. 쓰기 전에 한 번 더 확인한다
}
```

**실무에서 만나는 장면**: `catch`로 잡은 에러나 `JSON.parse` 결과처럼 `unknown`인 값이 객체인지 확인할 때. 배열도 `typeof`가 `'object'`라서, 배열을 가려야 하면 `Array.isArray`를 따로 씁니다.

### React · `await` 뒤에서 setState를 두 번 하면 화면도 두 번 그려질까? (React 19 기준)

배달 앱 주문 내역 화면입니다.

```tsx
async function handleRefresh() {
  setIsLoading(true)
  const orders = await fetchOrders()
  setOrders(orders)
  setIsLoading(false)
}
```

React 18부터는 한 번입니다. React는 setState를 받을 때마다 그리지 않고 모아 두었다가, 지금 실행 중인 코드가 끝나면 한 번에 다시 그립니다(batching). 그래서 `await` 앞의 `setIsLoading(true)`로 한 번, `await` 뒤의 두 줄을 모아 한 번 그립니다. React 17까지는 이벤트 핸들러 안에서만 모았고 Promise나 `setTimeout` 안의 업데이트는 하나씩 그려서, "주문은 새로 왔는데 로딩 표시는 아직 켜진" 화면이 한 번 끼어들 수 있었습니다. React 18의 `createRoot`부터는 어디서 부르든 모으고, React 19는 예전 `ReactDOM.render`가 없어져서 늘 이렇게 동작합니다.

**실무에서 만나는 장면**: 채팅에 새 메시지를 넣고 바로 맨 아래로 스크롤하려는데 새 메시지가 아직 DOM에 없을 때. 모아서 그리느라 아직 안 그린 것이니, 그 한 번만 `flushSync`로 감싸 바로 그리게 합니다.

### Next.js · 없는 매물이면 "없는 매물이에요"를 그냥 그리면 안 될까? (Next.js 16 App Router 기준)

```tsx
// app/items/[id]/page.tsx
import { notFound } from 'next/navigation'

export default async function ItemPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const item = await getItem(id)
  if (!item) notFound()

  return <ItemDetail item={item} />
}
```

직접 그려도 화면은 같아 보이지만, 응답은 "정상 페이지"인 200이라 검색 엔진은 그 빈 매물을 진짜 페이지로 받아 갈 수 있습니다. `notFound()`는 에러를 던져 렌더링을 멈추고 가장 가까운 `not-found.tsx`를 그립니다. 그 폴더에 없으면 위쪽으로 올라가 찾고, 끝까지 없으면 Next.js 기본 404 화면입니다. 응답 스트리밍이 시작되기 전에 불렸다면 상태 코드도 404이고, 이미 시작된 뒤라면 200으로 남지만 어느 쪽이든 `noindex` 메타 태그를 넣어 줍니다. 반환 타입이 `never`라 `return notFound()`로 쓸 필요가 없고, 그 아래에서 `item`은 있는 값으로 좁혀집니다. 11월 1일의 `redirect()`처럼 에러를 던지는 방식이니 `try` 안에 두지 않습니다.

**실무에서 만나는 장면**: 판매 완료로 지워진 중고 매물 링크를 누가 공유했을 때. 빈 상세 대신 "찾는 매물이 없어요"와 목록으로 가는 버튼이 있는 `not-found.tsx`를 보여 줍니다.
