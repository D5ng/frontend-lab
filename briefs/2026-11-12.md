## 클린 코드 처방

### 1. 조건문 · 역할 검사가 화면 곳곳에 흩어질 때 → 역할마다 컴포넌트 나누기

중고 거래 글 상세 화면의 하단 바입니다. 같은 글이라도 판매자가 보면 "글 수정하기"가, 구매자가 보면 찜 버튼과 가격, "채팅하기"가 보입니다.

**상황**

```tsx
function ItemBottomBar({ item, isSeller, onEdit, onChat }: Props) {
  return (
    <footer>
      {!isSeller && <LikeButton itemId={item.id} />}
      <p>{isSeller ? `관심 ${item.likeCount}` : `${item.price.toLocaleString()}원`}</p>
      <ActionButton onClick={isSeller ? onEdit : onChat}>{isSeller ? '글 수정하기' : '채팅하기'}</ActionButton>
    </footer>
  )
}
```

**처방: 한 번 갈라서 각자 그리기**

```tsx
function ItemBottomBar({ item, isSeller, onEdit, onChat }: Props) {
  return isSeller ? <SellerBottomBar item={item} onEdit={onEdit} /> : <BuyerBottomBar item={item} onChat={onChat} />
}

function SellerBottomBar({ item, onEdit }: { item: Item; onEdit: () => void }) {
  return (
    <footer>
      <p>관심 {item.likeCount}</p>
      <ActionButton onClick={onEdit}>글 수정하기</ActionButton>
    </footer>
  )
}
// BuyerBottomBar는 찜, 가격, 채팅하기만 그린다
```

**왜**: 상황 코드에서 판매자 화면이 어떻게 생겼는지 알려면 `isSeller`가 나오는 네 곳을 하나씩 머릿속에서 접어 봐야 합니다. 판매자에게 "끌어올리기" 버튼이 생기면 분기가 하나 더 붙습니다. 맨 위에서 한 번 갈라 두면 각 컴포넌트는 한 사람이 보는 화면만 그리고, 판매자 쪽을 고치다가 구매자 화면을 건드릴 일도 없어집니다.

**안 해도 되는 때**: 두 사람의 화면이 문구 하나만 다르다면 삼항 하나가 낫습니다. 나누면 같이 바뀌어야 하는 공통 틀(여백, 배치)이 두 벌이 될 수 있습니다.

### 2. 컴포넌트 props · input 속성을 하나씩 다시 적는 입력 컴포넌트 → 원래 속성은 그대로 통과시키기

송금 화면의 금액 입력칸입니다. 화면마다 필요한 속성이 생길 때마다 props가 한 줄씩 늘었습니다.

**상황**

```tsx
type AmountInputProps = {
  label: string
  value: string
  onChange: (value: string) => void
  placeholder?: string
  disabled?: boolean
  autoFocus?: boolean // 송금 화면에서 필요해서 추가
  onBlur?: () => void // 한도 검사 때문에 추가
  maxLength?: number // 이번 주에 추가
}
```

**처방: 이 컴포넌트가 바꾸는 것만 적기**

```tsx
type AmountInputProps = Omit<ComponentProps<'input'>, 'onChange'> & {
  label: string
  onChange: (value: string) => void
}

function AmountInput({ label, onChange, ...inputProps }: AmountInputProps) {
  return (
    <label>
      {label}
      <input {...inputProps} inputMode="numeric" onChange={(e) => onChange(e.target.value)} />
    </label>
  )
}
```

**왜**: `input`이 원래 받는 속성을 다시 적으면, 어느 화면이 `name`이나 `aria-describedby`를 원할 때마다 이 파일을 고쳐야 하고 받아서 넘기는 줄도 하나씩 늘어납니다. 원래 속성은 `ComponentProps<'input'>`으로 받아 그대로 넘기고, 이 컴포넌트가 더하거나 바꾸는 것만 적으면 props 타입이 곧 "이 컴포넌트가 하는 일" 목록이 됩니다. `onChange`는 받는 값을 문자열로 바꿨으니 `Omit`으로 원래 것을 빼고 새로 적습니다. 숫자 키패드(`inputMode`)는 이 컴포넌트가 정하는 것이라 펼친 뒤에 적어 덮어씁니다.

**안 해도 되는 때**: 디자인 시스템의 버튼처럼 `className`이나 `style`로 모양을 바꾸지 못하게 일부러 막아야 하는 컴포넌트는 허용할 것만 적습니다.

### 3. 테스트하기 좋은 모양 · `beforeEach`에서 화면까지 그려 두기 → 테스트마다 부르는 준비 함수

진료 예약 화면의 테스트입니다. 처음엔 테스트마다 같은 준비를 하니 `beforeEach`로 모았습니다.

**상황**

```tsx
beforeEach(() => {
  server.use(http.get('/api/slots', () => HttpResponse.json(SLOTS)))
  render(<BookingScreen />)
})

test('마감된 시간은 고를 수 없다', async () => {
  expect(await screen.findByRole('button', { name: '14:00 마감' })).toBeDisabled()
})

test('모든 시간이 마감이면 다른 날짜를 고르라고 안내한다', async () => {
  // 응답을 바꾸고 싶은데, 화면을 그리면서 요청이 이미 나갔다
})
```

**처방: 준비를 함수로 만들고 테스트 첫 줄에서 부르기**

```tsx
function renderBookingScreen(slots: Slot[] = SLOTS) {
  server.use(http.get('/api/slots', () => HttpResponse.json(slots)))
  render(<BookingScreen />)
}

test('모든 시간이 마감이면 다른 날짜를 고르라고 안내한다', async () => {
  renderBookingScreen(SLOTS.map((slot) => ({ ...slot, isFull: true })))
  expect(await screen.findByText('이날은 예약이 모두 찼어요')).toBeInTheDocument()
})
```

**왜**: `beforeEach`가 화면까지 그려 버리면 "다 마감된 날"처럼 다른 응답이 필요한 테스트는 끼어들 틈이 없습니다. 테스트 본문만 읽어서는 어떤 데이터로 그렸는지도 보이지 않아서, 위로 올라가 `beforeEach`를 찾아야 합니다. 준비를 함수로 만들어 테스트 안에서 부르면 조건은 인자로 넘기고, 읽는 사람은 테스트 하나만 보면 됩니다. 이 저장소 드릴 테스트의 `renderProblem(notifications)`도 같은 모양입니다.

**안 해도 되는 때**: `server.resetHandlers()`처럼 모든 테스트가 똑같이 하고 결과에 영향을 주지 않는 정리는 `afterEach`가 맞는 자리입니다.

## 생각하는 법

### 기획을 코드로 · "~에서만 할 수 있어요"는 막으라는 뜻일까?

**장면**: 공유 킥보드 앱의 반납 기획 메모입니다.

> 반납은 주차 가능 구역에서만 할 수 있어요. 구역 밖에 세우면 견인비 5,000원이 붙어요.

반납 버튼을 만들려다 손이 멈춥니다. 구역 밖에서는 버튼을 막아야 할까요?

**생각 순서**

1. **"이 문장이 정하는 건 뭐지?"** "~에서만"이 정책 신호입니다. 첫 문장만 읽으면 구역 밖 반납은 막아야 합니다. 그런데 둘째 문장은 구역 밖에 세우는 일이 일어난다고 보고 그때의 대가를 정합니다. 두 문장이 서로 다른 답을 하고 있습니다.
2. **"어기면 무슨 일이 일어나지?"** 정책에는 "되나, 안 되나"와 함께 "어기면 어떻게 하나"가 붙어 있습니다. 보통 셋 중 하나입니다. 아예 못 하게 막기, 알리고 확인받은 뒤 하게 두기, 하게 두고 나중에 대가 매기기. 무엇이냐에 따라 화면이 달라집니다. 막으면 비활성 버튼과 안내 문구, 확인이면 다이얼로그, 대가면 이용 내역에 한 줄입니다.
3. **"기획자에게 뭘 묻지?"** 셋 중 무엇인지를 한 문장으로 묻습니다. "구역 밖에서 반납을 누르면 막나요, 견인비를 알리고 확인받은 뒤 반납되게 하나요?" 질문이 구체적이면 답도 한 줄로 옵니다. "견인비는 반납할 때 바로 결제되나요?"도 같이 적어 둡니다.
4. **"답을 받으면 판정 결과는 어떤 모양이지?"** "확인받고 반납"이라는 답을 받았다면 `canReturn: boolean`으로는 담기지 않습니다. 되긴 되는데 확인이 필요한 갈래가 하나 더 있기 때문입니다.

**코드로 옮기면**

```ts
// 기획자 답: "구역 밖이면 견인비를 알리고, 확인하면 반납돼요"
type ReturnCheck = { kind: 'free' } | { kind: 'needsConfirm'; towingFee: number }

function checkReturn(isInParkingZone: boolean, towingFee: number): ReturnCheck {
  return isInParkingZone ? { kind: 'free' } : { kind: 'needsConfirm', towingFee }
}
// 화면은 needsConfirm일 때만 "견인비 5,000원이 붙어요. 반납할까요?" 다이얼로그를 띄운다
```

**한 줄 요약**: 정책 문장을 읽을 때는 "되나, 안 되나"만 찾지 말고 "어기면 어떻게 되나"까지 찾습니다. 막기, 확인받기, 대가 매기기 중 무엇인지가 화면 모양과 판정 결과의 타입을 정합니다.

## 기본기

### TypeScript · `Object.keys`로 돌렸는데 왜 `obj[key]`에 빨간 줄이 생길까?

```ts
const DELIVERY_FEE = { standard: 3000, express: 5000, dawn: 4000 }

Object.keys(DELIVERY_FEE).forEach((key) => {
  console.log(DELIVERY_FEE[key]) // 오류
})
```

오류는 `Element implicitly has an 'any' type because expression of type 'string' can't be used to index type '{ standard: number; express: number; dawn: number; }'.`입니다. `Object.keys`가 `(keyof T)[]`가 아니라 `string[]`을 돌려주기 때문입니다. TypeScript의 객체 타입은 "이 속성들이 있다"는 뜻이지 "이것만 있다"는 뜻이 아니라서, 실제 객체에는 키가 더 있을 수 있습니다. 11월 10일에 본 것처럼 변수에 담아 넘기면 남는 속성 검사도 없으니, `{ standard: number; express: number }` 타입인 값의 키가 실제로는 `['standard', 'express', 'promoCode']`일 수 있습니다.

키가 정해진 목록이라면 `const DELIVERY_TYPES = ['standard', 'express', 'dawn'] as const`처럼 목록을 원본으로 두고 그 배열을 돕니다. 값만 필요하면 `Object.values`나 `Object.entries`로 충분합니다(값은 `number`로 나옵니다). TypeScript 6.0 `--strict`로 확인했습니다.

**실무에서 만나는 장면**: 배송 방식별 요금표를 화면에 늘어놓으려고 `Object.keys`로 돌렸는데 `FEE[key]`에 빨간 줄이 생길 때. `as`로 덮기 전에 키 목록을 원본으로 둘 수 있는지 먼저 봅니다.

### React · 수정 화면에서 왜 "uncontrolled input to be controlled" 경고가 뜰까? (React 19 기준)

```tsx
// 프로필을 받아 오기 전에는 profile이 undefined
<input value={profile?.nickname} onChange={handleChange} />
```

`value`가 `undefined`면 React는 이 입력칸을 비제어(uncontrolled) 입력으로 봅니다. 값을 React가 아니라 DOM이 들고 있다는 뜻입니다. 응답이 와서 문자열이 들어오면 제어(controlled) 입력으로 바뀌는데, 한 입력칸이 도중에 방식을 바꾸면 React는 콘솔에 `A component is changing an uncontrolled input to be controlled.`로 시작하는 경고를 띄웁니다. 어제 본 `??`로 처음부터 빈 문자열을 주면(`value={profile?.nickname ?? ''}`) 끝까지 제어 입력입니다. `value={null}`도 따로 경고가 나니 빈 값은 `''`로 줍니다. React 19.2를 jsdom에 렌더링해 두 경고를 확인했습니다.

**실무에서 만나는 장면**: 서버 값이 늦게 오는 수정 폼, `useState<string>()`처럼 초기값 없이 시작한 입력칸. 응답이 온 뒤에 폼을 그리는 것(그동안은 스켈레톤)도 방법입니다.

### Next.js · 상품 상세 페이지에 `'use client'`를 붙였더니 왜 `metadata`를 못 쓸까? (Next.js 16 App Router 기준)

```tsx
// app/products/[id]/page.tsx — 'use client'를 떼고 서버 컴포넌트로 둔다
type Props = { params: Promise<{ id: string }> }

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { id } = await params
  const product = await getProduct(id)
  return { title: product.name }
}

export default async function ProductPage({ params }: Props) {
  const { id } = await params
  return <ProductDetail product={await getProduct(id)} /> // 찜 버튼처럼 state가 필요한 곳만 'use client'
}
```

`metadata` 객체와 `generateMetadata`는 서버 컴포넌트에서만 지원됩니다. 공식 문서는 이유로 페이지 컴포넌트를 그리기 전에 서버에서 메타데이터를 정해야 한다는 점을 듭니다. 그래서 찜 버튼 하나 때문에 `page.tsx` 전체에 `'use client'`를 붙이면 탭 제목과 공유 미리보기를 정할 자리가 사라집니다. 10월 30일에 본 것처럼 경계는 필요한 곳에만 두고, 페이지는 서버 컴포넌트로 남깁니다. `getProduct`를 두 번 불러도 같은 `fetch` 요청은 자동으로 메모되고, DB를 직접 읽는 함수라면 React `cache`로 감싸면 한 번만 실행됩니다.

**실무에서 만나는 장면**: 상품 링크를 메신저에 공유했더니 미리보기 제목이 상품 이름이 아니라 사이트 기본 제목으로 나올 때. 그 페이지 맨 위에 `'use client'`가 있는지부터 봅니다.
