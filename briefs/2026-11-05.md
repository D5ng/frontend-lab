## 클린 코드 처방

### 1. 테스트하기 좋은 모양 · 결제 핸들러 안의 금액 계산 → 계산을 순수 함수로 꺼내기

**상황**

```tsx
async function handlePay() {
  const subtotal = selectedSeats.reduce((sum, seat) => sum + seat.price, 0)
  const discount = coupon ? Math.floor(subtotal * coupon.rate) : 0
  const total = subtotal - discount + selectedSeats.length * 2000

  setIsPaying(true)
  await requestPayment({ showId, seats: selectedSeats, total })
  router.push('/tickets/complete')
}
```

**처방: 계산은 입력과 출력만 있는 함수로**

```ts
const BOOKING_FEE = 2000

export function calculateTicketTotal(seats: Seat[], couponRate = 0) {
  const subtotal = seats.reduce((sum, seat) => sum + seat.price, 0)
  const discount = Math.floor(subtotal * couponRate)
  return subtotal - discount + seats.length * BOOKING_FEE
}

// 핸들러에는 한 줄만 남는다
const total = calculateTicketTotal(selectedSeats, coupon?.rate)
```

**왜**: 지금은 금액이 맞는지 보려면 화면을 띄우고, 좌석을 고르고, 결제 버튼을 눌러야 합니다. 계산만 꺼내면 "R석 154,000원과 S석 132,000원에 10% 쿠폰이면 261,400원"을 `expect(calculateTicketTotal(seats, 0.1)).toBe(261400)` 한 줄로 확인할 수 있고, 쿠폰 없음이나 좌석 0장 같은 경우도 금방 늘릴 수 있습니다. 결제 요청과 화면 이동처럼 바깥을 건드리는 일은 핸들러에 남깁니다.

**안 해도 되는 때**: `count + 1`처럼 한 줄이고 한 곳에서만 쓰는 계산은 꺼내도 얻는 게 별로 없습니다.

### 2. 비동기와 에러 처리 · 검색어를 빨리 바꿀 때 늦게 온 응답이 덮어쓰기 → 지난 요청의 응답은 버리기

**상황**

```tsx
useEffect(() => {
  searchRooms(keyword).then((result) => {
    setRooms(result)
  })
}, [keyword])
```

**처방: cleanup에서 "이 응답은 이제 필요 없다"고 표시하기**

```tsx
useEffect(() => {
  let ignore = false

  searchRooms(keyword).then((result) => {
    if (!ignore) setRooms(result)
  })

  return () => {
    ignore = true
  }
}, [keyword])
```

**왜**: '역삼'을 치고 이어서 '역삼동'을 쳤는데 '역삼' 요청이 더 늦게 돌아오면, 입력창은 '역삼동'인데 목록은 '역삼' 결과가 됩니다. 응답은 보낸 순서대로 온다는 보장이 없습니다. `keyword`가 바뀌면 React가 이전 effect의 cleanup을 먼저 실행하니, 이전 요청의 `ignore`가 `true`가 되어 늦게 온 응답은 화면에 닿지 않습니다. React 공식 문서(Synchronizing with Effects)의 데이터 가져오기 예시도 같은 모양입니다.

**안 해도 되는 때**: TanStack Query나 SWR 같은 데이터 패칭 라이브러리, 프레임워크의 데이터 가져오기 기능을 쓰고 있다면 이 처리를 이미 해 줍니다.

### 3. 컴포넌트 props · 같이 와야 하는 optional props 두 개 → 한 묶음으로

**상황**

```tsx
type NoticeBannerProps = {
  title: string
  actionLabel?: string
  onAction?: () => void
}

// onAction을 빠뜨려도 타입 오류가 없다. 눌러도 아무 일이 없는 버튼이 생긴다
const banner = <NoticeBanner title="무료 체험이 3일 남았어요" actionLabel="구독하기" />
```

**처방: 같이 다니는 props는 객체 하나로**

```tsx
type NoticeBannerProps = {
  title: string
  action?: { label: string; onClick: () => void }
}

const banner = <NoticeBanner title="무료 체험이 3일 남았어요" action={{ label: '구독하기', onClick: openPlans }} />
```

**왜**: 라벨과 핸들러는 둘 다 있거나 둘 다 없어야 말이 됩니다. 묶어 두면 `action={{ label: '구독하기' }}`처럼 하나만 넘길 때 `Property 'onClick' is missing ...` 오류가 납니다. 컴포넌트 안에서도 `action &&` 확인 한 번이면 둘 다 있다고 믿을 수 있습니다.

**안 해도 되는 때**: `subtitle?`, `icon?`처럼 하나만 와도 말이 되는 optional props는 따로 둡니다.

## 생각하는 법

### 문제를 풀 때 · 성공 화면보다 실패·빈 상태·두 번 누르기부터 떠올리기

**장면**: 중고거래 앱 기획 메모입니다.

> 상품 상세에서 하트를 누르면 찜 목록에 담겨요. 찜 목록 탭에서 모아 볼 수 있어요.

하트를 채우는 코드는 5분이면 끝납니다. 그런데 메모에 적힌 건 성공했을 때뿐입니다.

**생각 순서**

1. **"요청이 실패하면 하트는 어떤 모양이지?"** 누르자마자 채웠다면 실패했을 때 되돌리고 알려야 합니다. 응답을 받은 뒤에 채운다면 그동안 눌렸다는 표시가 필요합니다. 둘 중 하나를 고르는 것부터가 설계입니다.
2. **"응답을 기다리는 동안 또 누르면?"** 찜과 찜 취소가 빠르게 연달아 가면 서버의 마지막 상태가 화면과 달라질 수 있습니다. 기다리는 동안 막을지, 마지막 것만 보낼지 정합니다.
3. **"찜 목록이 비어 있으면 뭘 보지?"** 처음 쓰는 사람은 언제나 이 화면부터 봅니다. 빈 화면 대신 "마음에 드는 물건에 하트를 눌러 보세요"와 둘러보기 버튼을 둡니다.
4. **"판매 완료된 물건은 목록에 남을까?"** 모르는 결정은 코드로 정하지 말고 기획자에게 물을 질문으로 적어 둡니다.

**코드로 옮기면**

```tsx
async function handleWishClick() {
  if (isPending) return // 두 번 누르기

  const prev = isWished
  setIsWished(!prev)
  setIsPending(true)
  try {
    await updateWish(itemId, !prev)
  } catch {
    setIsWished(prev) // 실패하면 되돌리고 알린다
    showToast('찜하지 못했어요. 잠시 후 다시 시도해 주세요')
  } finally {
    setIsPending(false)
  }
}
```

**한 줄 요약**: 기획 메모에는 성공 흐름만 적혀 있을 때가 많습니다. 코드를 쓰기 전에 실패, 빈 상태, 두 번 누르기를 먼저 물으면 state 모양이 처음부터 맞게 잡힙니다.

## 기본기

### JavaScript · `0.1 + 0.2`는 왜 `0.3`이 아닐까?

```ts
0.1 + 0.2 // 0.30000000000000004
0.1 + 0.2 === 0.3 // false
4.35 * 100 // 434.99999999999994
```

JavaScript의 `number`는 64비트 부동소수점(IEEE 754)입니다. 0.1은 2진수로 쓰면 끝없이 이어지는 수라서 가장 가까운 근삿값으로 저장되고, 계산하면 그 오차가 드러납니다. JavaScript만의 버그가 아니라 같은 방식으로 수를 저장하는 대부분의 언어에서 똑같습니다. 그래서 돈은 원이나 센트처럼 가장 작은 단위의 정수로 계산하고, 화면에 보여 줄 때만 소수로 바꿉니다.

**실무에서 만나는 장면**: 4.35달러를 센트로 바꾸려고 `Math.floor(4.35 * 100)`을 했더니 435가 아니라 434가 나올 때. `Math.round`를 쓰거나 처음부터 센트 정수로 받습니다.

### Next.js · 환경 변수가 서버에서는 읽히는데 브라우저에서는 왜 없을까?

Next.js 공식 문서 Environment Variables(App Router, 2026년 8월 갱신본) 기준입니다. 이 규칙은 9.4부터 같습니다.

```ts
// 클라이언트 컴포넌트에서
process.env.NEXT_PUBLIC_MAP_KEY // next build 때 실제 값으로 바뀌어 번들에 들어간다
process.env.PAYMENT_SECRET // 서버에서만 읽을 수 있다
```

환경 변수는 기본적으로 서버에서만 읽힙니다. 브라우저에 보이려면 이름이 `NEXT_PUBLIC_`으로 시작해야 하고, 이 값은 `next build` 때 코드에 글자 그대로 박힙니다. 그래서 빌드한 뒤에 값을 바꿔도 반영되지 않고 다시 빌드해야 합니다. `process.env[name]`처럼 변수로 찾으면 박히지 않습니다.

**실무에서 만나는 장면**: 결제 비밀 키가 클라이언트에서 안 읽힌다고 `NEXT_PUBLIC_`을 붙이면, 그 키가 누구나 내려받는 번들에 들어갑니다. 비밀 키는 라우트 핸들러나 서버 액션처럼 서버에서만 씁니다.

### 브라우저 · `<script>`의 `async`와 `defer`는 뭐가 다를까?

둘 다 HTML을 읽는 동안 스크립트를 함께 내려받아서, 내려받는 동안 파싱을 멈추지 않습니다. 차이는 실행하는 때입니다.

- **async**: 다 받는 즉시 실행합니다. 여러 개면 먼저 받은 것부터라 순서가 보장되지 않습니다.
- **defer**: HTML을 끝까지 읽은 뒤, `DOMContentLoaded` 전에, 적힌 순서대로 실행합니다.

`type="module"` 스크립트는 따로 적지 않아도 `defer`처럼 동작합니다.

**실무에서 만나는 장면**: 다른 코드와 상관없는 분석 스크립트는 `async`로, DOM이나 다른 라이브러리에 기대는 코드는 `defer`로 둡니다. `async`로 넣은 스크립트가 가끔 "is not defined" 오류를 낸다면 먼저 실행돼야 할 스크립트보다 앞서 실행된 경우가 많습니다.
