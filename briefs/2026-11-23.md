## 클린 코드 처방

### 1. 조건문 · 플래그를 켜고 끄는 반복문 → `some`과 `every`로 묻기

배달 앱 장바구니입니다. 품절 메뉴가 하나라도 있으면 주문 버튼을 막고, 모든 메뉴가 포장될 때만 "포장 주문" 탭을 엽니다.

**상황**

```ts
let hasSoldOut = false
for (const item of cart.items) {
  if (item.soldOut) {
    hasSoldOut = true
    break
  }
}

let canPickUp = true
for (const item of cart.items) {
  if (!item.pickupAvailable) canPickUp = false
}
```

**처방: 묻는 말을 그대로 메서드로**

```ts
const hasSoldOut = cart.items.some((item) => item.soldOut)
const canPickUp = cart.items.length > 0 && cart.items.every((item) => item.pickupAvailable)
```

**왜**: "하나라도 품절이야?"는 `some`, "전부 포장돼?"는 `every`입니다. 플래그를 켜고 끄는 반복문은 끝까지 읽어야 무엇을 묻는지 알 수 있고, `let`이라 그 아래에서 또 바뀌지 않는지도 봐야 합니다. `some`은 찾는 순간, `every`는 아닌 것을 만나는 순간 멈추니 `break`도 필요 없습니다. 하나 기억할 점은 빈 배열의 `every`가 `true`라는 것입니다. 빈 장바구니에 "전부 포장돼?"라고 물으면 "네"가 나옵니다. 상황 코드도 초기값 `true` 때문에 똑같았는데 눈에 띄지 않았을 뿐입니다. 처방에 `length > 0`을 붙인 이유입니다.

**안 해도 되는 때**: 한 번 도는 동안 품절 메뉴 이름, 포장 안 되는 메뉴 개수처럼 여러 결과를 같이 모아야 한다면 반복문 하나가 더 읽기 쉽습니다.

### 2. 상태와 파생 값 · 빈 배열로 시작하는 목록 → "아직 모름"과 "없음"을 가르기

헬스케어 앱의 복약 알림 목록입니다. 알림이 하나도 없으면 "알림 추가하기" 버튼이 있는 빈 화면을 보여 줍니다.

**상황**

```tsx
const [reminders, setReminders] = useState<Reminder[]>([])

useEffect(() => {
  fetchReminders().then(setReminders)
}, [])

if (reminders.length === 0) return <EmptyReminders />
return <ReminderList reminders={reminders} />
```

**처방: 아직 모르는 값은 `null`로 시작하기**

```tsx
const [reminders, setReminders] = useState<Reminder[] | null>(null)

useEffect(() => {
  fetchReminders().then(setReminders)
}, [])

if (reminders === null) return <ReminderListSkeleton />
if (reminders.length === 0) return <EmptyReminders />
return <ReminderList reminders={reminders} />
```

**왜**: `[]`는 "받아 왔더니 없더라"는 답입니다. 아직 묻지도 않은 첫 렌더링에 그 답을 미리 넣어 두었으니, 알림이 다섯 개인 사용자도 화면을 열 때마다 "등록한 알림이 없어요"를 잠깐 보고, 그 사이 "알림 추가하기"를 누를 수도 있습니다. `null`로 시작하면 "아직 모름"이 값으로 남습니다. 타입에 `null`이 들어가니 확인 없이 `reminders.length`를 쓰면 TypeScript가 `'reminders' is possibly 'null'.`로 막아 주는 것도 덤입니다.

**안 해도 되는 때**: 서버에서 받아 오지 않고 이 화면에서 처음부터 채워 가는 목록(새 복약 일정에서 고르는 시간 목록 같은)은 `[]`로 시작하는 게 맞습니다. 실패와 재시도까지 보여 줘야 한다면 `null` 하나로는 모자라니 10월 30일의 판별 유니온으로 갑니다.

### 3. 비즈니스 로직 위치 · 표시 함수 안에 숨은 가격 계산 → 계산하고 나서 보여 주기

구독 앱의 요금제 화면입니다. 월 9,900원 요금제를 연간으로 결제하면 17% 할인하고, 10원 단위 아래는 버립니다. 카드에는 연간 금액을, 배지에는 아끼는 금액을 보여 줍니다.

**상황**

```ts
// 요금제 카드
function formatYearlyPrice(plan: Plan) {
  const price = Math.floor((plan.monthlyPrice * 12 * 0.83) / 10) * 10
  return `연 ${price.toLocaleString('ko-KR')}원`
}

// 연간 결제 배지. 숫자가 필요해서 한 번 더 계산한다
const savingLabel = `${(plan.monthlyPrice * 12 * 0.17).toLocaleString('ko-KR')}원 아껴요`
```

**처방: 금액을 내는 함수와 보여 주는 함수를 나누기**

```ts
const YEARLY_RATE = 0.83

function getYearlyPrice(plan: Plan) {
  return Math.floor((plan.monthlyPrice * 12 * YEARLY_RATE) / 10) * 10
}

function formatWon(amount: number) {
  return `${amount.toLocaleString('ko-KR')}원`
}

const yearlyPrice = getYearlyPrice(plan)
const saving = plan.monthlyPrice * 12 - yearlyPrice
```

**왜**: 98,600이라는 숫자는 정책(연간 17% 할인, 10원 아래 버림)이 내고, "연 98,600원"은 그 숫자를 보여 주는 방법입니다. 둘이 한 함수에 있으면 숫자만 필요한 곳은 그 함수를 못 쓰니 정책을 한 벌 더 적게 되고, 그 사본은 버림 규칙을 빠뜨립니다. 그래서 카드는 "연 98,600원", 배지는 "20,196원 아껴요"가 되어 둘을 더해도 원래 금액 118,800원이 안 나옵니다. 계산을 먼저 꺼내 두면 할인율이 바뀌어도 고칠 곳은 하나고, "월 환산 금액" 같은 문구가 새로 생겨도 같은 숫자에서 시작합니다.

**안 해도 되는 때**: 서버가 요금제마다 연간 금액과 할인 금액을 내려 준다면 화면에는 계산할 정책이 없으니 `formatWon`만 있으면 됩니다. 11월 7일 환불 금액처럼, 돈이 오가는 숫자는 서버가 정한 값을 받아 쓰는 편이 더 안전하기도 합니다.

## 생각하는 법

### 문제를 풀 때 · 정리도 하고 싶고 기능도 넣어야 할 때, 무엇부터 하지?

**장면**: 공연 예매 앱의 회차 선택 화면에 "매진된 회차에는 '대기 신청' 버튼을 보여 주세요"라는 요청이 왔습니다. 회차 카드를 열어 보니 `isSoldOut`, `isClosed`, `isOpenSoon`을 보는 삼항 연산자가 버튼 문구, 버튼 색, 비활성 여부에 세 번 흩어져 있습니다. 대기 신청을 끼워 넣으려면 세 군데를 다 고쳐야 하고, 고치는 김에 전부 갈아엎고 싶어집니다.

**생각 순서**

1. **"지금 바꾸려는 게 동작이야, 모양이야?"** 대기 신청 버튼은 사용자가 보는 동작이 바뀌는 일이고, 흩어진 분기를 모으는 건 동작은 그대로 두고 모양만 바꾸는 일입니다. 둘을 한 번에 하면 테스트가 깨졌을 때 어느 쪽 때문인지 가를 수 없습니다.
2. **"기능을 넣기 쉬운 모양이 따로 있나?"** 새 상태 하나를 세 군데에 끼워 넣어야 한다면, 먼저 회차 상태를 한 번 계산하고 문구·색·비활성을 그 상태에서 꺼내는 모양으로 바꿉니다. 이 걸음에서는 화면이 하나도 달라지면 안 되고, 사용자 행동을 확인하는 기존 테스트도 손대지 않은 채 통과해야 합니다. 테스트를 고쳐야 통과한다면 모양만 바꾼 게 아닙니다.
3. **"바꾸고 나니 기능은 몇 줄이지?"** 회차 상태에 `'waitlist'` 하나를 더하고 그 상태의 버튼을 적으면 끝나야 합니다. 이제 기능을 넣고, "매진된 회차에는 대기 신청 버튼이 보인다" 테스트를 하나 더합니다.
4. **"이번 기능과 상관없는 정리는?"** 날짜 포맷 함수가 마음에 안 들어도 대기 신청이 닿지 않는 곳이면 메모만 하고 넘어갑니다. 모양 바꾸기는 지금 넣을 기능이 쉬워지는 만큼만 합니다.

**코드로 옮기면**

```text
refactor: 회차 카드의 상태 분기를 회차 상태 하나로 모은다   ← 화면 그대로, 테스트 그대로
feat: 매진된 회차에 대기 신청 버튼을 보여 준다              ← 테스트 하나 추가
```

커밋을 이렇게 나누면 리뷰하는 사람도 첫 커밋에서는 "동작이 안 바뀌었나"만, 두 번째에서는 "기능이 맞나"만 보면 됩니다.

**한 줄 요약**: 넣기 어려우면 먼저 넣기 쉬운 모양으로 바꾸고, 그다음에 쉽게 넣습니다. 한 걸음에는 동작과 모양 중 하나만 바꿉니다.

## 기본기

### JavaScript · 다시 불러온 찜 목록에서 왜 `includes`가 `false`일까?

```ts
const saved = { id: 'room-17', title: '역세권 투룸' }
const fetched = { id: 'room-17', title: '역세권 투룸' }
const favorites = [saved]

saved === fetched // false
favorites.includes(fetched) // false
favorites.some((item) => item.id === fetched.id) // true
```

객체를 `===`로 비교하면 내용이 아니라 "같은 객체인가"를 봅니다. 서버에서 다시 받은 매물은 내용이 같아도 응답 JSON을 풀어 새로 만든 객체라서 `false`입니다. `includes`, `indexOf`, `Set`의 `has`도 객체는 같은 방식으로 비교합니다. 그래서 목록에서 찾을 때는 바뀌지 않는 값인 id로 비교합니다. React도 effect 의존성 배열을 `Object.is`로 비교하니, 렌더링마다 새로 만든 객체를 넣으면 내용이 같아도 effect가 매번 다시 돕니다.

**실무에서 만나는 장면**: 매물 목록을 다시 불러왔더니 찜해 둔 하트가 전부 빈 하트로 돌아갈 때. 찜 상태를 객체 대신 id로 들고 있으면 생기지 않는 일입니다(11월 1일 처방 "id만 담고 찾기"와 같은 이야기입니다).

### 네트워크 · `C++`로 검색했는데 서버는 왜 `C`를 받았을까?

교육 앱의 강의 검색입니다.

```ts
fetch(`/api/courses?q=${keyword}`)
// 'C++' → 서버가 읽은 q는 'C  ' (C 뒤에 공백 두 칸)
// 'C#'  → 서버가 읽은 q는 'C'
// 'R&D' → q는 'R', 그리고 'D'라는 이름의 값이 하나 더

fetch(`/api/courses?${new URLSearchParams({ q: keyword })}`)
// 'C++' → q=C%2B%2B, 'C#' → q=C%23, 'R&D' → q=R%26D
```

문자열을 그대로 이어 붙이면 검색어 속 글자가 주소 문법으로 읽힙니다. 쿼리스트링에서 `&`는 값과 값을 나누고, `#`부터는 서버로 가지 않는 조각(fragment)이고, `+`는 대부분의 서버가 공백으로 읽습니다. 한글은 브라우저가 알아서 `%EC%9E%90…`처럼 바꿔 주니 오히려 문제가 없는데, 이 세 글자는 주소에서 원래 뜻이 있는 글자라 그대로 둡니다. `URLSearchParams`로 만들면 값 안의 글자를 인코딩해서, 서버는 사용자가 친 그대로 받습니다.

**실무에서 만나는 장면**: "C++ 강의를 찾았는데 C 언어 강의만 나와요"라는 문의가 올 때. 검색어처럼 사용자가 친 값을 주소에 넣는 곳은 이어 붙이지 말고 `URLSearchParams`나 `encodeURIComponent`로 만듭니다.

### 브라우저 · 메뉴에 `z-index: 9999`를 줬는데 왜 다음 카드 밑에 깔릴까?

커뮤니티 앱 피드에서 카드의 "⋯" 메뉴를 열면, 메뉴 아래쪽이 다음 카드에 가려집니다.

```css
.feed-card {
  position: relative;
  z-index: 1;
}

.more-menu {
  position: absolute;
  z-index: 9999;
}
```

`z-index`는 같은 쌓임 맥락(stacking context) 안에서만 순서를 정합니다. `position`과 `z-index`를 함께 준 카드는 저마다 쌓임 맥락을 만들고, 그 안의 9999는 "이 카드 안에서 맨 위"라는 뜻일 뿐입니다. 카드끼리는 둘 다 `z-index: 1`이라 문서에서 나중에 나오는 다음 카드가 위에 그려지고, 첫 카드의 메뉴는 카드째로 그 밑에 깔립니다. `z-index` 없이 `transform`만 걸어도, `opacity`가 1보다 작아도 쌓임 맥락이 생깁니다. 고치려면 카드의 `z-index`를 빼거나, 메뉴를 연 카드만 올리거나, React의 `createPortal`로 메뉴를 `body` 바로 아래에 그립니다.

**실무에서 만나는 장면**: 등장 애니메이션으로 `transform`을 건 카드 안의 드롭다운이 옆 카드에 가려질 때. 9999를 99999로 올려도 그대로라면 숫자가 아니라 쌓임 맥락을 봐야 한다는 신호입니다.
