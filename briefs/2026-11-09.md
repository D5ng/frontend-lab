## 클린 코드 처방

### 1. 조건문 · 목록이 비었을 때 0이 찍히는 `&&` → 비교로 true/false 만들기

**상황**

```tsx
function UnreadBadge({ notices }: { notices: Notice[] }) {
  return <div>{notices.length && <span>새 알림 {notices.length}</span>}</div>
}
```

**처방: 조건을 명시적인 비교로 쓰기**

```tsx
function UnreadBadge({ notices }: { notices: Notice[] }) {
  const hasNotices = notices.length > 0

  return <div>{hasNotices && <span>새 알림 {notices.length}</span>}</div>
}
```

**왜**: `0 && ...`의 결과는 `0`이고, React는 숫자 `0`을 화면에 그립니다. 알림이 없을 때 배지 대신 `0`이 덜렁 찍힙니다. `> 0`으로 비교하면 결과가 항상 `true`/`false`라서 이 사고가 구조적으로 사라집니다.

**안 해도 되는 때**: 값이 `string | null`처럼 0이 나올 수 없는 타입이면 `name && <Name />`도 괜찮습니다. 빈 문자열 `''`은 아무것도 그리지 않습니다.

### 2. 컴포넌트 props · `setIsOpen`을 그대로 내려주기 → 일어난 일을 알리는 콜백

**상황**

```tsx
function ReviewPage() {
  const [isOpen, setIsOpen] = useState(false)

  return <ReviewSheet isOpen={isOpen} setIsOpen={setIsOpen} />
}

// ReviewSheet 안
;<button onClick={() => setIsOpen(false)}>닫기</button>
```

**처방: 무슨 일이 있었는지만 알린다**

```tsx
<ReviewSheet isOpen={isOpen} onClose={() => setIsOpen(false)} />

// ReviewSheet 안
<button onClick={onClose}>닫기</button>
```

**왜**: `setIsOpen`을 받은 자식은 `true`로도 `false`로도, 함수로도 바꿀 수 있습니다. 부모의 state 모양에 자식이 묶입니다. `onClose`는 "닫아 달라는 요청이 있었다"만 알리니, 부모가 state를 라우터 주소로 바꿔도 자식은 그대로입니다.

**안 해도 되는 때**: 부모와 자식이 한 파일 안에서 늘 같이 바뀌는 작은 조각이면 setter를 넘겨도 큰 문제가 없습니다.

### 3. 타입으로 막기 · 전부 `string`인 id → 이름이 다른 id 타입

**상황**

```ts
function cancelOrder(orderId: string, userId: string) {
  // ...
}

cancelOrder(user.id, order.id) // 순서를 바꿔도 통과한다
```

**처방: 브랜드 타입**

```ts
type UserId = string & { readonly __brand: 'UserId' }
type OrderId = string & { readonly __brand: 'OrderId' }

function cancelOrder(orderId: OrderId, userId: UserId) {
  // ...
}

cancelOrder(user.id, order.id)
// Argument of type 'UserId' is not assignable to parameter of type 'OrderId'.
```

**왜**: 둘 다 `string`이면 인자 순서가 바뀌어도 컴파일러가 모릅니다. 서버 응답을 받는 한 곳에서만 `as UserId`로 도장을 찍고, 그 뒤로는 타입이 구분해 줍니다. 위 오류 문구는 tsc `--strict`로 확인했습니다.

**안 해도 되는 때**: id를 섞어 쓸 일이 없는 작은 화면이면 `string`으로 충분합니다. 도장을 찍는 `as`가 늘어나는 비용이 더 클 수 있습니다.

## 생각하는 법

### 문제를 풀 때 · 모르는 결정은 미루고 기록하기

**장면**: 구현 중에 막혔습니다. 환불 버튼을 만드는데 "이미 배송이 시작된 주문도 환불되나?"를 아무도 정해 주지 않았습니다.

**생각 순서**

1. **"이건 내가 정할 수 있는 건가?"** 변수 이름이나 파일 위치는 내가 정합니다. 환불 가능 여부는 정책이라서 내가 추측해서 정할 일이 아닙니다.
2. **"지금 모르면 다음 줄을 못 쓰나?"** 대부분은 쓸 수 있습니다. 판정만 함수 하나로 분리하고 안은 임시 값으로 채우면 나머지 화면은 계속 만들 수 있습니다.
3. **"어디에 적어 두지?"** 코드 한 줄 옆 주석이 아니라, 내가 나중에 반드시 다시 보는 곳(메모 파일, PR 설명)에 질문 형태로 적습니다. "배송 시작 후 환불 가능? 가능하면 배송비는?"
4. **"임시 값은 뭘로 하지?"** 가장 보수적인 쪽(아직 환불 불가)으로 두고, 임시라는 것이 코드에서 보이게 합니다. 나중에 답이 오면 이 함수 하나만 고치면 됩니다.

**코드로 옮기면**

```ts
// 미정: 배송 시작 후 환불 가능 여부 (질문 목록 #3)
function canRefund(order: Order) {
  return order.status === 'paid'
}
```

**한 줄 요약**: 모르는 것을 아는 척 정하지 않고, 한 곳에 가둬서 미루고, 질문으로 남깁니다.

## 기본기

### JavaScript · `['1', '2', '3'].map(parseInt)`는 왜 `[1, NaN, NaN]`일까?

`map`은 콜백에 `(값, 인덱스, 배열)` 세 개를 넘깁니다. `parseInt(문자열, 진법)`의 두 번째 인자가 진법이라서 실제로는 `parseInt('1', 0)`, `parseInt('2', 1)`, `parseInt('3', 2)`가 불립니다. 0은 기본값(10진법)으로 취급되어 1이 나오고, 1진법은 없는 진법이라 `NaN`, 2진법에 `3`은 올 수 없는 숫자라 `NaN`입니다. 직접 실행해 확인했습니다.

해결은 `map((s) => parseInt(s, 10))`처럼 필요한 인자만 명시하거나 `map(Number)`를 쓰는 것입니다.

**실무에서 만나는 장면**: 쿼리스트링으로 받은 id 목록을 `ids.map(parseInt)`로 숫자로 바꿨더니 두 번째부터 `NaN`이 나올 때.

### 네트워크 · 401과 403은 뭐가 다를까?

401은 "누구인지 모르겠다"입니다. 로그인하지 않았거나 토큰이 만료된 경우라서, 다시 로그인하면 해결됩니다. 403은 "누구인지는 알지만 권한이 없다"입니다. 다시 로그인해도 같은 결과입니다.

그래서 클라이언트도 다르게 처리합니다. 401이면 로그인 화면으로 보내거나 토큰을 갱신해 다시 시도하고, 403이면 "권한이 없어요" 안내를 보여 줍니다. 둘을 같은 에러 화면으로 뭉치면 사용자는 로그인을 다시 해 봐야 하는지 알 수 없습니다.

**실무에서 만나는 장면**: 일반 회원이 관리자 페이지 주소를 직접 입력했는데 로그인 화면으로 계속 튕길 때.

### 브라우저 · `position: sticky`가 왜 안 붙을까?

`sticky`는 가장 가까운, 스크롤되는 조상을 기준으로 붙습니다. 조상 중에 `overflow: hidden`, `auto`, `scroll`이 있으면 그 요소가 기준이 되는데, 정작 그 요소는 스크롤되지 않으니 붙을 일이 없습니다. 또 `top` 같은 기준 값이 없으면 어디에 붙을지 몰라서 동작하지 않습니다.

확인은 개발자 도구에서 sticky 요소의 부모를 한 단계씩 올라가며 `overflow` 값을 보면 됩니다. 가로 넘침을 막으려고 `body`나 래퍼에 `overflow-x: hidden`을 걸어 둔 경우가 흔한 원인입니다.

**실무에서 만나는 장면**: 목록 위에 고정하려던 필터 바가 스크롤을 따라오지 않고 같이 올라가 버릴 때.
