## 클린 코드 처방

### 1. 비즈니스 로직 위치 · 응답 변환에서 화면 문구까지 만들기 → 변환은 의미 있는 값까지만

어제 드릴에서 응답을 받자마자 앱이 쓰는 모양으로 바꿨다면, 다음 질문은 "그 변환 함수는 어디까지 해야 하지?"입니다.

**상황**

```ts
function toStay(res: StayResponse): Stay {
  return {
    id: res.stay_id,
    name: res.stay_name,
    price: `${res.price_per_night.toLocaleString()}원 / 1박`,
    checkIn: res.check_in_time ? `${res.check_in_time}부터` : '체크인 시간 문의',
  }
}
```

**처방: 경계는 서버 말을 앱 말로만 옮긴다**

```tsx
function toStay(res: StayResponse): Stay {
  return {
    id: res.stay_id,
    name: res.stay_name,
    pricePerNight: res.price_per_night, // 숫자 그대로
    checkInTime: res.check_in_time, // null도 "정해진 시간 없음"이라는 뜻이다
  }
}

// 문구는 그 값을 보여 주는 화면이 정한다
;<Price>{formatWon(stay.pricePerNight)} / 1박</Price>
```

**왜**: 경계가 할 일은 필드 이름, 단위, `null`의 뜻처럼 "서버 사정"을 걷어내는 것까지입니다. 가격을 문자열로 만들어 두면 낮은 가격순 정렬과 "3박 합계"를 계산하려고 문자열을 다시 숫자로 되돌려야 합니다. 목록은 "1박 8만원", 결제 화면은 "총 240,000원"처럼 같은 값을 다르게 말하는 것도 흔합니다.

**안 해도 되는 때**: 서버가 이미 표시용 문구로 내려 주는 값(`badge_text: '오늘 특가'` 같은)은 계산할 일이 없으니 문자열 그대로 둡니다.

### 2. 상태와 파생 값 · 고른 객체를 통째로 state에 담기 → id만 담고 찾기

**상황**

```tsx
const rides = useRideOptions(route) // 30초마다 새 요금으로 갱신된다
const [selected, setSelected] = useState<RideOption | null>(null)

<RideList rides={rides} onSelect={(ride) => setSelected(ride)} />
<CallButton>{selected?.name} 호출 · {formatWon(selected?.fare)}</CallButton>
```

**처방: 원본은 목록 하나, 선택은 id 하나**

```tsx
const rides = useRideOptions(route)
const [selectedId, setSelectedId] = useState<string | null>(null)
const selected = rides.find((ride) => ride.id === selectedId) ?? null

<RideList rides={rides} onSelect={(ride) => setSelectedId(ride.id)} />
```

**왜**: 객체를 통째로 담으면 같은 차종이 목록과 `selected` 두 군데에 있게 됩니다. 요금이 갱신되면 목록에는 새 요금이, 호출 버튼에는 고른 순간의 요금이 보입니다. id만 담으면 버튼도 늘 목록에서 찾아 그리니 어긋날 틈이 없고, 그 차종이 목록에서 빠지면 `selected`가 `null`이 되어 버튼을 막을 수도 있습니다.

**안 해도 되는 때**: "이 요금으로 호출할게요"를 누른 뒤 요금을 고정하는 것처럼, 고른 순간의 값을 붙잡는 게 정책이라면 그때는 객체를 담는 게 맞습니다.

### 3. 훅 · 버튼이 state를 바꾸고 effect가 요청 보내기 → 핸들러에서 바로 보내기

**상황**

```tsx
const [requestedPlan, setRequestedPlan] = useState<PlanId | null>(null)

useEffect(() => {
  if (!requestedPlan) return
  changePlan(requestedPlan).then(() => showSnackbar('요금제를 바꿨어요'))
}, [requestedPlan])

<ActionButton onClick={() => setRequestedPlan(selectedPlan)}>변경하기</ActionButton>
```

**처방: 누른 게 이유면 누른 자리에서**

```tsx
async function handleChangePlan() {
  await changePlan(selectedPlan)
  showSnackbar('요금제를 바꿨어요')
}

;<ActionButton onClick={handleChangePlan}>변경하기</ActionButton>
```

**왜**: 이 요청이 나가는 이유는 "사용자가 변경하기를 눌러서"입니다. effect를 거치면 그 이유가 "state 값이 바뀌어서"로 바뀝니다. 그래서 요청이 실패한 뒤 같은 요금제로 다시 누르면 state가 그대로라 effect가 돌지 않고, 아무 일도 일어나지 않습니다. 핸들러에 두면 누를 때마다 보내고, 읽는 사람도 버튼 하나만 따라가면 됩니다.

**안 해도 되는 때**: 채팅방 구독이나 "상세 화면을 열면 최근 본 상품에 남기기"처럼 화면이 보인 것 자체가 이유인 일은 effect가 맞는 자리입니다.

## 생각하는 법

### 문제를 풀 때 · 막혔을 때 시간 순서로 화면 따라가기

**장면**: 병원 진료 접수 앱입니다. 접수 상세에서 "접수 취소"를 누르면 스낵바까지 잘 뜨는데, 뒤로 가면 목록에 그 접수가 그대로 있습니다. 새로고침하면 사라집니다. 30분째 훅 파일, API 파일, 목록 컴포넌트를 번갈아 열고 있습니다.

**생각 순서**

1. **"사용자는 무엇을 누르고 무엇을 봤지?"** 파일 순서가 아니라 손가락 순서로 적습니다. 목록 진입 → 접수 하나 탭 → 상세 → 취소 → 확인 → 스낵바 → 뒤로 가기 → 목록.
2. **"각 칸에서 화면은 무슨 값을 보고 그리지?"** 목록은 어디서 받은 배열로 그리는지, 상세에서 취소하면 그 배열을 누가 바꾸는지 칸마다 한 줄씩 적습니다.
3. **"기대와 실제가 처음 갈라지는 칸은 어디지?"** 취소 요청은 성공했고 스낵바도 맞습니다. 뒤로 갔을 때 목록이 들고 있는 배열은 처음 진입할 때 받은 그대로입니다. 서버는 바뀌었는데 목록은 다시 묻지 않았습니다. 여기서 갈라집니다.
4. **"그 칸 하나만 확인하려면?"** 갈라진 칸을 찾았으면 그 칸만 봅니다. 목록에 로그 한 줄을 찍거나, 그 흐름을 테스트 하나로 재현합니다. 고치는 방법(목록을 다시 불러올지, 취소 성공 때 목록에서 뺄지)은 이 칸을 찾은 다음에 고릅니다.

**코드로 옮기면**

```ts
// 1. 목록 진입: GET /receptions → [A, B]          맞음
// 2. A 상세 → 취소: DELETE /receptions/A          맞음, 스낵바도 뜸
// 3. 뒤로 가기: 목록은 1번에서 받은 [A, B] 그대로   여기서 갈라진다

it('접수를 취소하고 목록으로 돌아오면 그 접수가 보이지 않는다', async () => {})
```

**한 줄 요약**: 막히면 코드를 파일 단위로 뒤지지 않습니다. 사용자가 누른 순서대로 화면을 따라가며 기대와 실제가 처음 갈라지는 칸 하나를 찾습니다.

## 기본기

### JavaScript · 숫자 배열을 `sort()`했는데 왜 105000이 9000보다 앞에 올까?

```ts
const prices = [12000, 9000, 105000]

prices.sort() // [105000, 12000, 9000]
prices.sort((a, b) => a - b) // [9000, 12000, 105000]
```

비교 함수 없이 부르면 요소를 문자열로 바꿔 사전 순으로 비교합니다. `'1'`이 `'9'`보다 앞이라 105000이 먼저 옵니다. 그리고 `sort`는 새 배열을 만들지 않고 원본을 바꾼 뒤 그 원본을 돌려줍니다. 원본을 그대로 두려면 `[...prices].sort(...)`나 ES2023의 `prices.toSorted((a, b) => a - b)`를 씁니다.

**실무에서 만나는 장면**: `setRooms(rooms.sort(byPrice))`를 했는데 화면이 안 바뀔 때. 정렬된 배열이 이전 state와 같은 배열이라 React가 바뀐 게 없다고 보고 다시 그리지 않습니다.

### Next.js · `redirect()`를 `try` 안에 넣으면 왜 이동이 안 될까?

Next.js 16 App Router 기준이고, 2026년 11월 공식 문서로 확인했습니다(`redirect`가 나온 13.0부터 같은 방식입니다).

```ts
'use server'
export async function createReview(formData: FormData) {
  try {
    const review = await saveReview(formData)
    redirect(`/reviews/${review.id}`) // 에러를 던져서 이동한다
  } catch {
    return { message: '리뷰를 저장하지 못했어요' } // 그 에러를 여기서 잡아 버린다
  }
}
```

`redirect()`는 값을 돌려주는 함수가 아니라 `NEXT_REDIRECT`라는 에러를 던지고, Next.js가 그 에러를 받아 이동시키는 방식입니다. 그래서 `try` 안에서 부르면 `catch`가 먼저 잡아 삼키고, 리뷰는 저장됐는데 "저장하지 못했어요"가 뜹니다. 공식 문서도 `try` 밖에서 부르라고 안내합니다. `notFound()`도 에러를 던지는 방식이라 똑같이 걸립니다.

**실무에서 만나는 장면**: 서버 액션에서 저장 성공 뒤 상세로 보내려는데 이동은 안 되고 실패 메시지가 보일 때. 10월 30일 처방처럼 `try`는 저장 호출만 감싸고, `redirect`는 그 아래로 뺍니다.

### 브라우저 · `localStorage`에 객체를 넣었더니 왜 `"[object Object]"`가 될까?

```ts
const recent = ['강남역', '판교']
localStorage.setItem('recentSearches', JSON.stringify(recent))

const saved = localStorage.getItem('recentSearches') // string | null, 없으면 null
const list: string[] = saved ? JSON.parse(saved) : []
```

`localStorage`는 키와 값을 문자열로만 저장합니다. 다른 값을 넣으면 문자열로 바꿔 저장하니 객체는 `"[object Object]"`, 숫자 3은 `'3'`이 됩니다. 그래서 넣을 때 `JSON.stringify`, 꺼낼 때 `JSON.parse`를 짝으로 씁니다. TypeScript는 `setItem`에 배열을 넣으면 `Argument of type 'string[]' is not assignable to parameter of type 'string'.`으로 막아 주지만, `any`로 들어온 값은 그대로 통과합니다.

**실무에서 만나는 장면**: 최근 검색어 화면을 다시 열었더니 "[object Object]" 한 줄만 보일 때. 그리고 `JSON.parse` 결과는 `any`라서, 앱을 업데이트한 뒤 예전 모양으로 저장된 값이 들어와도 타입이 막아 주지 못합니다. 꺼내는 자리에서 한 번 확인하는 편이 안전합니다.
