## 클린 코드 처방

### 1. 상태와 파생 값 · 입력할 때마다 켜는 `isDirty` → 처음 값과 비교해서 계산하기

중고 거래 앱의 판매글 수정 화면입니다. 나가기 전에 "수정한 내용이 사라져요"를 띄우려고 플래그를 둡니다.

**상황**

```tsx
const [title, setTitle] = useState(post.title)
const [price, setPrice] = useState(post.price)
const [isDirty, setIsDirty] = useState(false)

function handleTitleChange(next: string) {
  setTitle(next)
  setIsDirty(true)
}
// handlePriceChange도 똑같이 setIsDirty(true)
```

**처방: 바뀌었는지는 처음 값과 비교해서 계산한다**

```tsx
const [title, setTitle] = useState(post.title)
const [price, setPrice] = useState(post.price)

const isDirty = title !== post.title || price !== post.price
```

**왜**: 플래그는 "한 번이라도 입력했다"만 기억하고 "지금 처음과 다르다"는 모릅니다. 제목을 고쳤다가 원래대로 되돌려도 `isDirty`는 계속 true라서, 바꾼 게 없는데 나가기 확인 창이 뜹니다. 입력란이 하나 늘 때마다 `setIsDirty(true)`를 빠뜨릴 자리도 하나 늘어납니다.

**안 해도 되는 때**: "한 번이라도 건드린 칸에만 에러를 보여 준다"처럼 정말 '건드렸는지'가 필요하면, 그 기록 자체가 원본이라 state로 둡니다.

### 2. 훅 · 훅을 부르지 않는 `use` 함수 → 그냥 함수로

숙소 예약 화면에서 숙박 일수를 계산하는 함수입니다.

**상황**

```tsx
function useNightCount(checkIn: Date, checkOut: Date) {
  const ms = checkOut.getTime() - checkIn.getTime()
  return Math.round(ms / (24 * 60 * 60 * 1000))
}

function StayPrice({ stay }: { stay: Stay }) {
  const nights = useNightCount(stay.checkIn, stay.checkOut)
  return (
    <p>
      {nights}박 · {formatWon(stay.pricePerNight * nights)}
    </p>
  )
}
```

**처방: 안에서 훅을 부르지 않으면 `use`를 뗀다**

```tsx
function getNightCount(checkIn: Date, checkOut: Date) {
  const ms = checkOut.getTime() - checkIn.getTime()
  return Math.round(ms / (24 * 60 * 60 * 1000))
}

// 조건문 안에서도, 컴포넌트 밖 유틸이나 테스트에서도 부를 수 있다
const nights = stay ? getNightCount(stay.checkIn, stay.checkOut) : 0
```

**왜**: `use`로 시작하는 이름은 "안에서 state나 effect를 쓰니 훅 규칙을 지켜 달라"는 약속입니다. 실제로는 훅을 안 쓰는데 이름만 훅이면, 린터가 조건문 안이나 일반 함수 안에서 부르는 것을 막아 쓸 자리가 좁아지고, 읽는 사람은 숨은 state가 있는지 열어 봐야 합니다. React 공식 문서도 훅을 부르지 않는 함수에는 `use`를 붙이지 말라고 권합니다.

**안 해도 되는 때**: 지금은 테스트용 고정값을 돌려주지만 곧 `useContext`로 바꿀 `useAuth`처럼, 훅이 될 자리라면 `use`를 미리 붙여 둡니다. 공식 문서의 예시도 이 경우입니다.

### 3. 테스트하기 좋은 모양 · API 함수를 mock하고 호출만 확인하기 → 화면에 보이는 결과로 확인하기

공연 예매 결제 화면에서 할인 코드를 적용하는 테스트입니다.

**상황**

```tsx
vi.mock('./api', () => ({ applyPromoCode: vi.fn().mockResolvedValue({ discount: 5000 }) }))

it('할인 코드를 적용한다', async () => {
  render(<TicketCheckout />)
  await user.type(screen.getByLabelText('할인 코드'), 'SPRING')
  await user.click(screen.getByRole('button', { name: '적용' }))

  expect(applyPromoCode).toHaveBeenCalledWith('SPRING')
})
```

**처방: 서버는 MSW에 맡기고, 사용자가 보는 결과를 확인한다**

```tsx
// 서버 응답은 MSW 핸들러가 { discount: 5000 }으로 돌려준다
it('할인 코드를 적용하면 결제 금액에서 할인액만큼 빠진다', async () => {
  render(<TicketCheckout />)
  await user.type(screen.getByLabelText('할인 코드'), 'SPRING')
  await user.click(screen.getByRole('button', { name: '적용' }))

  expect(await screen.findByText('할인 -5,000원')).toBeInTheDocument()
  expect(screen.getByText('결제 금액 45,000원')).toBeInTheDocument()
})
```

**왜**: 첫 테스트는 "요청을 보냈다"까지만 봅니다. 응답을 받아 금액을 다시 그리는 코드가 망가져도 통과하고, 반대로 `applyPromoCode`의 이름이나 인자 모양만 바꿔도 기능은 그대로인데 깨집니다. 두 번째 테스트는 사용자가 확인하는 할인액과 결제 금액이 맞는 한, 안쪽을 어떻게 고쳐도 통과합니다.

**안 해도 되는 때**: 분석 이벤트 전송처럼 화면에 아무 흔적도 남지 않는 일은 호출 자체가 결과라서 호출을 확인합니다.

## 생각하는 법

### 기획을 코드로 · "3만 원 이상"의 3만 원은 무슨 금액일까?

**장면**: 장보기 앱의 기획 메모입니다.

> 3만 원 이상 주문하면 배송비가 무료예요. 장바구니에서 쿠폰도 쓸 수 있어요.

`subtotal >= 30000`이라고 쓰려다 멈춥니다. `subtotal`은 쿠폰을 쓰기 전 금액일까요, 쓴 뒤 금액일까요?

**생각 순서**

1. **"이 숫자는 무엇을 잰 값이지?"** 장바구니 화면에는 금액이 여러 개 있습니다. 상품 금액 합계, 쿠폰을 뺀 금액, 적립금까지 쓴 결제 금액. 메모는 "3만 원"이라는 숫자만 정했지 어느 금액인지는 말하지 않았습니다.
2. **"어느 쪽이냐에 따라 사용자는 뭘 겪지?"** 쿠폰을 뺀 금액이 기준이면, 31,000원을 담고 3,000원 쿠폰을 쓰는 순간 28,000원이 되어 배송비 3,000원이 다시 붙습니다. 쿠폰을 썼는데 결제 금액은 31,000원 그대로입니다. 의도한 정책일 수도 있지만, 기획자가 이 장면을 보고 정한 건지는 확인해야 합니다.
3. **"같은 기준을 쓰는 정책이 또 있나?"** 최소 주문 금액, 적립, 카드 할인도 저마다 기준 금액이 있습니다. 하나씩 따로 묻지 말고 금액 단계를 한 줄로 적어 같이 묻습니다. "상품 금액 → 쿠폰 → 적립금 → 결제 금액 중에서 무료 배송, 최소 주문, 적립은 각각 어디를 보나요?"
4. **"받은 답은 어디에 남기지?"** 단계마다 금액에 이름을 붙이고, 정책 함수가 어떤 금액을 받는지 인자 이름으로 드러냅니다. `subtotal`처럼 뜻이 넓은 이름은 방금 물은 질문을 다시 숨깁니다.

**코드로 옮기면**

```ts
// 기획 답(11/10): 무료 배송은 쿠폰 적용 전 상품 금액 기준
function getShippingFee(itemsAmount: number) {
  return itemsAmount >= FREE_SHIPPING_MIN_AMOUNT ? 0 : SHIPPING_FEE
}

const itemsAmount = sumItemPrices(cart.items)
const afterCouponAmount = itemsAmount - couponDiscount
const paymentAmount = afterCouponAmount + getShippingFee(itemsAmount)
```

**한 줄 요약**: 기획의 금액 기준은 "몇 원"보다 "무슨 금액의 몇 원"을 먼저 묻습니다. 계산 단계마다 금액에 이름을 붙이면, 정책이 어느 단계를 보는지 코드에서 바로 읽힙니다.

## 기본기

### TypeScript · 오타 난 속성이 바로 넘기면 잡히는데, 변수에 담아 넘기면 왜 통과할까?

```ts
type SearchOptions = {
  keyword: string
  maxPrice?: number
}

searchRooms({ keyword: '제주', maxPirce: 100000 })
// 오류: Object literal may only specify known properties,
// but 'maxPirce' does not exist in type 'SearchOptions'. Did you mean to write 'maxPrice'?

const options = { keyword: '제주', maxPirce: 100000 }
searchRooms(options) // 통과
```

TypeScript는 구조로 타입을 맞춥니다. `options`에는 `keyword`가 있으니 `SearchOptions` 자리에 들어갈 수 있고, 남는 속성은 문제 삼지 않습니다. 다만 객체 리터럴을 그 자리에서 바로 쓸 때만은 "모르는 속성은 오타일 것"이라고 보고 한 번 더 검사합니다(초과 속성 검사). 변수에 먼저 담으면 이 검사가 빠지고, `maxPrice`는 optional이라 없어도 오류가 아니니 오타 난 조건이 조용히 사라집니다. 만들 때부터 `const options: SearchOptions = { ... }`처럼 타입을 붙이면 그 자리에서 잡힙니다.

**실무에서 만나는 장면**: 검색 조건을 변수로 모아 두었다가 넘겼더니 가격 필터만 안 먹을 때.

### React · `memo`로 감쌌는데 왜 계속 다시 렌더링될까? (React 19 기준)

```tsx
const ListingCard = memo(ListingCardView)

// 부모가 렌더링될 때마다
<ListingCard listing={listing} onSave={() => save(listing.id)} />
```

`memo`는 props를 하나씩 이전 값과 `Object.is`로 비교해서, 전부 같을 때만 렌더링을 건너뜁니다. `() => save(listing.id)`는 부모가 렌더링될 때마다 새로 만들어지는 함수라서 내용이 같아도 이전 함수와 다른 값입니다. 그 자리에서 만든 객체 `{ ... }`도 마찬가지입니다. props 하나가 매번 새로 만들어지면 `memo`는 하는 일이 없습니다. 함수는 부모에서 `useCallback`으로, 객체는 `useMemo`로 유지하거나, 객체 대신 필요한 값만 따로 넘깁니다. React Compiler를 켜면 이런 메모이제이션을 컴파일러가 알아서 해 주니 직접 `memo`를 붙일 일이 거의 없어집니다.

**실무에서 만나는 장면**: 매물 목록 카드에 `memo`를 붙였는데 검색어 한 글자마다 카드 백 개가 전부 다시 렌더링될 때.

### Next.js · 페이지를 옮겼는데 레이아웃의 검색창 입력값이 왜 그대로 남아 있을까? (Next.js 16 App Router 기준)

```tsx
// app/(shop)/layout.tsx
// SearchBar는 'use client' 컴포넌트이고, 안에서 useState로 검색어를 들고 있다
export default function ShopLayout({ children }: { children: ReactNode }) {
  return (
    <>
      <SearchBar />
      {children}
    </>
  )
}
```

같은 레이아웃을 쓰는 페이지 사이를 이동하면 Next.js는 바뀐 페이지 부분만 새로 그리고, 레이아웃은 다시 렌더링하지 않습니다. 레이아웃 안의 클라이언트 컴포넌트도 그대로 살아 있어서 state가 남습니다. 이동할 때마다 새로 시작하게 하려면 `layout.tsx` 대신 `template.tsx`를 씁니다. 템플릿은 그 아래 화면이 바뀔 때마다 새 key를 받아 다시 마운트되므로 안의 state와 effect가 처음부터 시작합니다. 단, 검색 파라미터(`?q=`)만 바뀔 때는 다시 마운트되지 않습니다. 같은 이유로 레이아웃은 `searchParams`를 받지 않으니, 현재 경로나 쿼리가 필요하면 클라이언트 컴포넌트에서 `usePathname`, `useSearchParams`로 읽습니다.

**실무에서 만나는 장면**: 카테고리 탭을 옮겨도 검색창에 지난 검색어가 남아 있을 때. 남는 게 원하는 동작이면 레이아웃, 매번 비워야 하면 템플릿입니다.
