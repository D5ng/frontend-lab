## 클린 코드 처방

### 1. 함수와 인자 · 검사 함수 안에서 토스트까지 띄우기 → 검사는 답만 돌려주기

**상황**

```tsx
function isValidPhone(phone: string) {
  const valid = /^010\d{8}$/.test(phone)
  if (!valid) toast.error('휴대폰 번호를 확인해 주세요')
  return valid
}

// 예매 버튼 핸들러에서 쓰던 함수를, 입력란 아래 안내 문구에도 썼다
const showPhoneHint = phone.length > 0 && !isValidPhone(phone)
```

**처방: 묻는 함수는 묻기만 한다**

```tsx
function isValidPhone(phone: string) {
  return /^010\d{8}$/.test(phone)
}

const showPhoneHint = phone.length > 0 && !isValidPhone(phone)

function handleReserve() {
  if (!isValidPhone(phone)) {
    toast.error('휴대폰 번호를 확인해 주세요')
    return
  }
  reserve(phone)
}
```

**왜**: `isValidPhone`이라는 이름은 "맞는 번호야?"라고 묻기만 할 것 같습니다. 그런데 안에서 토스트를 띄우니, 렌더링 중에 부르는 순간 예매자가 번호를 한 글자 칠 때마다 토스트가 뜹니다. 부르는 쪽은 이름만 보고 그걸 알 수 없습니다. 검사는 답만 돌려주고, 그 답으로 무엇을 할지(토스트, 안내 문구, 버튼 끄기)는 부른 쪽이 정하면 같은 함수를 어디서든 안심하고 씁니다. 11월 4일에 본 "버튼과 핸들러가 판정 함수 하나를 같이 쓰기"도 그 함수가 이렇게 답만 돌려줄 때 성립합니다.

**안 해도 되는 때**: 검사와 알림이 늘 붙어 다니는 제출 한 곳에서만 쓴다면, 나누는 대신 `checkPhoneOrNotify`처럼 알림까지 이름에 드러내도 충분합니다.

### 2. 훅 · 값 네 개를 배열로 돌려주는 훅 → 객체로 돌려주기

**상황**

```tsx
function useOrderHistory() {
  // ...
  return [orders, isLoading, error, refetch] as const
}

// 주문 내역 화면
const [orders, isLoading] = useOrderHistory()
// 홈의 "최근 주문" 카드: 실패했을 때 다시 시도만 필요하다
const [, , error, refetch] = useOrderHistory()
```

**처방: 이름으로 꺼내게 한다**

```tsx
function useOrderHistory() {
  // ...
  return { orders, isLoading, error, refetch }
}

const { orders, isLoading } = useOrderHistory()
const { error, refetch } = useOrderHistory()
```

**왜**: 배열은 자리가 곧 이름입니다. `[, , error, refetch]`는 쉼표를 세어 봐야 읽히고, 배달 주문 내역에 `isRefetching` 같은 값이 하나 끼어들면 쓰는 곳마다 다시 세어야 합니다. `isLoading`과 `isRefetching`처럼 같은 boolean끼리 자리가 바뀌면 타입도 잡아 주지 못합니다. 객체로 돌려주면 필요한 것만 이름으로 꺼내고, 값이 늘어도 쓰는 쪽은 그대로입니다.

**안 해도 되는 때**: `useState`나 `useToggle`처럼 값이 두 개이고 쓰는 곳마다 이름을 바꿔 붙이는 훅은 배열이 더 편합니다. `const [isSheetOpen, toggleSheet] = useToggle()`이 `const { value: isSheetOpen, toggle: toggleSheet } = useToggle()`보다 짧습니다.

### 3. 타입으로 막기 · 받은 배열을 그 자리에서 정렬하는 함수 → readonly로 받기

**상황**

```tsx
function sortByPrice(listings: Listing[]) {
  return listings.sort((a, b) => a.price - b.price)
}

function CheapestListings({ listings }: { listings: Listing[] }) {
  const cheapest = sortByPrice(listings).slice(0, 3)
  // 위에 "가장 싼 매물 3개"를 보여 준다
}
```

**처방: 받은 배열은 읽기만 한다고 타입에 적기**

```ts
function sortByPrice(listings: readonly Listing[]) {
  // listings.sort(...)는 이제 오류:
  // Property 'sort' does not exist on type 'readonly Listing[]'.
  return [...listings].sort((a, b) => a.price - b.price)
}
```

**왜**: `sort`는 새 배열을 만들지 않고, 받은 배열 자체를 바꾼 뒤 그걸 돌려줍니다. 돌려받은 값만 보면 새 배열 같아서, 부모가 가진 최신순 매물 목록까지 가격순으로 섞인 걸 한참 뒤에 알아챕니다. `readonly`를 붙이면 `sort`, `push`, `splice`처럼 원본을 바꾸는 메서드가 타입에서 사라져, 실수가 저장 전에 빨간 줄로 보입니다. `readonly Listing[]` 자리에 그냥 `Listing[]`을 넘겨도 되니 부르는 쪽은 고칠 게 없습니다. ES2023의 `toSorted()`도 새 배열을 돌려주지만, 이 저장소처럼 `lib`이 ES2022면 타입 오류가 납니다.

**안 해도 되는 때**: 함수 안에서 직접 만든 배열을 정렬할 때는 그 배열이 함수 것이라 바로 `sort`해도 됩니다.

## 생각하는 법

### 기획을 코드로 · 정책을 테스트 이름으로 쓰기

**장면**: 온라인 강의 앱의 기획 메모입니다.

> 강의를 80% 이상 들으면 수료증을 신청할 수 있어요. 수강 기간이 끝나면 신청할 수 없어요.

판정 함수를 만들고 테스트 파일을 열었더니, 손이 먼저 `it('canRequestCertificate는 true를 반환한다')`부터 씁니다.

**생각 순서**

1. **"이 메모가 약속하는 건 몇 개지?"** 80% 이상이면 신청할 수 있다, 기간이 끝나면 못 한다. 약속이 두 개면 테스트도 적어도 두 개입니다. 테스트 목록이 정책 목록과 같아지게 씁니다.
2. **"테스트 이름만 읽어도 기획 메모가 다시 써지나?"** `canRequestCertificate는 true를 반환한다`는 함수 이름이 바뀌면 같이 틀리고, 기획자가 읽어도 무슨 약속인지 모릅니다. 구현 말 대신 기획 말로 씁니다. "강의를 80% 이상 들으면 신청할 수 있다."
3. **"경계는 이름에 들어 있나?"** "80% 이상"이면 딱 80%는 됩니다. 80%와 79%를 각각 이름에 적다 보면 "기간이 끝나는 마지막 날 당일은?" 같은 질문도 같이 나옵니다. 답을 모르면 `it.todo`로 남기고 기획자에게 묻습니다.
4. **"정책이 바뀌면 어떤 테스트가 깨져야 하지?"** 80%가 70%로 바뀌면 이름에 80이 들어간 테스트만 깨지고, 그 이름을 고치는 일이 곧 정책 변경 기록이 됩니다. 기간 정책은 그대로인데 기간 테스트까지 깨진다면, 한 테스트가 약속을 여러 개 들고 있다는 신호입니다.

**코드로 옮기면**

```ts
describe('수료증 신청', () => {
  it('강의를 80% 이상 들으면 신청할 수 있다', () => {
    expect(canRequestCertificate({ progressPercent: 80, isExpired: false })).toBe(true)
  })
  it('79%까지 들었으면 신청할 수 없다', () => {
    expect(canRequestCertificate({ progressPercent: 79, isExpired: false })).toBe(false)
  })
  it('수강 기간이 끝나면 다 들었어도 신청할 수 없다', () => {
    expect(canRequestCertificate({ progressPercent: 100, isExpired: true })).toBe(false)
  })
  it.todo('수강 기간 마지막 날에도 신청할 수 있다')
})
```

**한 줄 요약**: 테스트 이름은 기획 메모를 다시 쓴 문장입니다. 이름만 모아 읽었을 때 정책이 보이면, 정책이 바뀌는 날 어디를 고칠지도 보입니다.

### React · 컴포넌트 안에서 컴포넌트를 만들면 왜 한 글자마다 포커스가 풀릴까?

```tsx
function CommentSheet() {
  const [text, setText] = useState('')

  // CommentSheet가 렌더링될 때마다 새 함수가 만들어진다
  function CommentInput() {
    return <input value={text} onChange={(e) => setText(e.target.value)} />
  }

  return <CommentInput />
}
```

React는 같은 자리에 같은 컴포넌트가 오면 그 state와 DOM을 이어 씁니다. "같은 컴포넌트"인지는 같은 함수인지로 봅니다. 안에서 정의한 `CommentInput`은 렌더링마다 새로 만들어진 다른 함수라서, 한 글자를 칠 때마다 `setText` → `CommentSheet` 다시 렌더링 → "다른 컴포넌트가 왔다"고 보고 이전 `input`을 지운 뒤 새로 붙입니다. 포커스가 빠지고, `CommentInput` 안에 state가 있었다면 그것도 처음으로 돌아갑니다. React 공식 문서(react.dev, Preserving and Resetting State)도 컴포넌트 함수는 항상 맨 위 수준에 선언하고 정의를 중첩하지 말라고 합니다. React 19.2 기준이고, 이전 버전에서도 같습니다. 고칠 때는 `CommentInput`을 밖으로 꺼내고 `text`와 `onChange`를 props로 넘깁니다.

**실무에서 만나는 장면**: 커뮤니티 앱의 댓글 바텀시트에서 한 글자 치면 키보드가 내려가 버릴 때. 모바일에서는 포커스가 빠지면 키보드가 닫힙니다.

### TypeScript · `'riding'`이라고 썼는데 왜 `string`이라고 할까?

```ts
type RideStatus = 'waiting' | 'riding' | 'finished'
type Ride = { id: string; status: RideStatus }

const ride = { id: 'R-1', status: 'riding' }
showRide(ride)
// Argument of type '{ id: string; status: string; }' is not assignable to parameter of type 'Ride'.
//   Types of property 'status' are incompatible.
//     Type 'string' is not assignable to type 'RideStatus'.
```

`const status = 'riding'`이면 타입은 `'riding'`입니다. 하지만 객체의 속성은 나중에 `ride.status = 'finished'`처럼 바꿀 수 있어서, TypeScript는 따로 알려 주지 않으면 `string`으로 넓혀 둡니다. `let`으로 선언한 값도 같은 이유로 `string`이 됩니다. 함수에 객체를 바로 넣으면 오류가 없는 것도 같은 원리입니다. 받을 타입이 정해진 자리라서 처음부터 `'riding'`으로 읽습니다. 고칠 때는 만들 때 타입을 알려 줍니다.

```ts
const ride: Ride = { id: 'R-1', status: 'riding' }
const ride2 = { id: 'R-1', status: 'riding' } satisfies Ride // 검사만 하고 'riding'은 그대로
```

**실무에서 만나는 장면**: 테스트나 스토리에서 목 데이터를 변수로 빼자마자 빨간 줄이 생길 때. 바로 넣을 땐 괜찮았던 같은 객체라서 더 헷갈립니다.

### 네트워크 · 로그인은 됐는데 왜 `document.cookie`에 세션 쿠키가 안 보일까?

서버가 `Set-Cookie: session=abc123; HttpOnly; Secure; Path=/`처럼 `HttpOnly`를 붙여 보냈기 때문입니다.

- **`HttpOnly`**: 자바스크립트가 이 쿠키를 읽지 못합니다. `document.cookie`에는 안 보이지만, 브라우저는 요청을 보낼 때 알아서 실어 보냅니다. MDN(Set-Cookie)도 `fetch()`로 보내는 요청에 HttpOnly 쿠키가 그대로 실린다고 적어 둡니다. 화면 코드에 XSS 구멍이 생겨도 세션을 꺼내 가기 어렵게 하려는 장치입니다.
- **`Secure`**: `https:` 요청에만 실립니다. localhost는 예외입니다.

다만 `fetch`의 `credentials` 기본값은 `'same-origin'`이라, 다른 출처의 API로 보내는 요청에는 쿠키가 실리지 않습니다. 그때는 `credentials: 'include'`를 주고, 서버도 `Access-Control-Allow-Credentials: true`와 `*`가 아닌 구체적인 `Access-Control-Allow-Origin`을 보내야 합니다.

**실무에서 만나는 장면**: 로그인 뒤 토큰을 꺼내 `Authorization` 헤더에 넣으려는데 아무리 찾아도 없을 때. 그 쿠키는 꺼내 쓰라고 준 게 아니라 브라우저가 대신 실어 보내라고 준 것입니다. 로그인했는지는 `/me` 같은 API에 물어봅니다.
