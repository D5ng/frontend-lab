## 클린 코드 처방

### 1. 함수와 인자 · 주석으로 단계를 나눈 핸들러 → 주석을 함수 이름으로

어제 드릴에서 한 컴포넌트 안의 추상화 높이를 맞춰 봤다면, 같은 생각을 핸들러 하나에 대 보면 좋습니다.

**상황**

```ts
async function handleCheckIn() {
  // 접수 가능 시간인지 확인
  const hour = now.getHours()
  if (hour < 9 || hour >= 18) {
    showToast('지금은 접수 시간이 아니에요')
    return
  }

  // 보험 정보를 서버 형식으로 바꾸기
  const insurance = { type: form.insuranceType.toUpperCase(), number: form.insuranceNo.trim() }

  await checkIn({ patientId, insurance })
  navigate('/check-in/done')
}
```

**처방: 주석이 하던 말을 이름이 하게**

```ts
async function handleCheckIn() {
  if (!isWithinReceptionHours(now)) {
    showToast('지금은 접수 시간이 아니에요')
    return
  }

  await checkIn({ patientId, insurance: toInsurancePayload(form) })
  navigate('/check-in/done')
}
```

**왜**: 코드 덩어리 위에 주석이 붙어 있다면, 그 덩어리는 이미 이름이 있는 한 단계라는 신호입니다. 이름을 함수로 옮기면 핸들러에는 "시간 확인 → 접수 → 이동"이라는 흐름만 같은 높이로 남고, 시각 계산이나 대문자 변환 같은 세부는 그 이름 뒤로 들어갑니다. 주석은 코드가 바뀌어도 같이 고쳐진다는 보장이 없지만, 함수 이름은 부르는 자리마다 보이니 어긋나면 눈에 띕니다.

**안 해도 되는 때**: "서버가 빈 문자열을 null로 바꿔서 여기서 막는다"처럼 **왜** 그렇게 했는지 남기는 주석은 이름으로 옮길 수 없으니 그대로 둡니다. 함수로 옮길 것은 **무엇을** 하는지 설명하는 주석입니다.

### 2. 훅 · 훅이 setter를 그대로 내보낼 때 → 할 수 있는 일만 내보내기

**상황**

```ts
function useCart() {
  const [items, setItems] = useState<CartItem[]>([])
  return { items, setItems }
}

// 메뉴 상세 화면
setItems((prev) => [...prev, { menuId, quantity: 1 }])
```

**처방: 동작 이름으로 좁히기**

```ts
function useCart() {
  const [items, setItems] = useState<CartItem[]>([])

  function addItem(menuId: string) {
    setItems((prev) =>
      prev.some((item) => item.menuId === menuId)
        ? prev.map((item) => (item.menuId === menuId ? { ...item, quantity: item.quantity + 1 } : item))
        : [...prev, { menuId, quantity: 1 }],
    )
  }

  return { items, addItem }
}
```

**왜**: `setItems`를 내보내면 "같은 메뉴를 또 담으면 줄이 늘지 않고 수량이 오른다"는 규칙을 부르는 화면마다 다시 써야 합니다. 메뉴 상세는 줄을 추가하고 추천 메뉴 카드는 수량을 올리면, 장바구니에 같은 메뉴가 두 줄로 생깁니다. 훅이 `addItem`만 내주면 규칙은 훅 안 한 곳에만 있고, 부르는 쪽은 "담는다"만 말하면 됩니다.

**안 해도 되는 때**: 검색어 입력처럼 "새 값으로 덮어쓰기" 말고는 할 일이 없는 state라면 setter를 그대로 내보내도 충분합니다. 지킬 규칙이 생겼을 때 좁혀도 늦지 않습니다.

### 3. 조건문 · `!isNotRentable` 같은 이중 부정 → 긍정형 이름

**상황**

```tsx
const isNotRentable = scooter.battery < MIN_BATTERY || scooter.status !== 'idle'

if (!isNotRentable) {
  showRentGuide()
}

;<ActionButton disabled={isNotRentable}>대여하기</ActionButton>
```

**처방: 묻는 말을 긍정으로**

```tsx
const canRent = scooter.battery >= MIN_BATTERY && scooter.status === 'idle'

if (canRent) {
  showRentGuide()
}

;<ActionButton disabled={!canRent}>대여하기</ActionButton>
```

**왜**: `!isNotRentable`은 읽는 사람이 머릿속에서 부정을 두 번 뒤집어야 뜻이 나옵니다. 긍정형 이름이면 `if`는 그대로 읽히고, 반대가 필요한 곳에만 `!` 하나가 붙습니다. 뒤집을 때는 `||`가 `&&`로, `<`가 `>=`로 바뀌니 경계값(배터리가 딱 `MIN_BATTERY`일 때 빌릴 수 있는지)이 그대로인지 한 번 확인합니다.

**안 해도 되는 때**: `isSoldOut`, `isExpired`처럼 도메인에서 원래 부정 쪽이 이름인 상태는 억지로 `isInStock`으로 뒤집지 않아도 됩니다. 이름 안에 `Not`이 들어 있을 때만 바꿔도 충분합니다.

### 문제를 풀 때 · 시스템 말을 사용자 질문으로 다시 읽기

**장면**: 중고 거래 앱의 판매글 작성 화면입니다. 요구사항은 이렇게 적혀 있습니다.

> 폼 상태가 초기값과 다를 경우, 화면 이탈 시 확인 모달을 노출한다.

그대로 옮기면 `isDirty`를 하나 만들고 끝날 것 같습니다.

**생각 순서**

1. **"이 순간 사용자는 속으로 뭘 묻고 있지?"** 뒤로 가기를 누른 사람이 궁금한 건 "폼이 초기값과 다른가"가 아니라 **"지금 나가면 쓴 거 날아가?"**입니다. 모달은 그 질문에 대한 답입니다.
2. **"그 질문으로 다시 읽으면 어떤 경우가 달라지지?"** 판매 글을 올리고 성공 화면으로 넘어가는 순간에도 폼은 초기값과 다릅니다. 시스템 문장대로면 모달이 뜨지만, 사용자 질문으로 보면 이미 올렸으니 날아갈 게 없습니다. 임시저장이 된 뒤라면 마찬가지입니다.
3. **"그럼 비교 기준은 뭐지?"** "처음 값"이 아니라 **"마지막으로 저장된 값"**입니다. 제출이나 임시저장이 성공하면 그 기준이 지금 값으로 바뀌니, 따로 예외를 두지 않아도 모달이 뜨지 않습니다.
4. **"이름도 그 질문에서 가져올 수 있나?"** `isDirty`보다 `hasUnsavedInput`이 "날아갈 게 있나?"에 더 가까운 답입니다. 이름이 질문을 닮으면 다음 사람이 조건을 고칠 때도 같은 질문으로 판단합니다.

**코드로 옮기면**

```ts
// "처음 값과 다른가"가 아니라 "마지막으로 저장된 뒤 바뀐 게 있나"
const hasUnsavedInput = !isSameDraft(form, lastSavedDraft)

it('판매 글을 올린 뒤에는 화면을 나가도 확인 모달이 뜨지 않는다', () => {})
```

**한 줄 요약**: 요구사항 문장을 그대로 옮기기 전에, 그 기능을 만나는 사람이 속으로 묻는 질문으로 바꿔 읽으면 문장에 없던 경우가 보입니다.

## 기본기

### JavaScript · `forEach` 안에서 `await`했는데 왜 기다려 주지 않을까?

```ts
async function uploadReviewPhotos(files: File[]) {
  files.forEach(async (file) => {
    await uploadPhoto(file)
  })
  showToast('사진을 모두 올렸어요') // 업로드가 끝나기 전에 뜬다
}
```

`forEach`는 콜백이 돌려준 Promise를 기다리지도, 모으지도 않습니다. 각 콜백은 `await`에서 멈춘 채 Promise를 돌려주고, `forEach`는 그걸 버린 채 바로 끝납니다. 그래서 다음 줄이 먼저 실행됩니다. 하나씩 순서대로 올리려면 `for (const file of files) await uploadPhoto(file)`, 동시에 올리고 다 끝날 때를 기다리려면 `await Promise.all(files.map(uploadPhoto))`를 씁니다. 같은 이유로 `forEach` 바깥을 `try/catch`로 감싸도 업로드 실패는 잡히지 않습니다.

**실무에서 만나는 장면**: 여러 장을 올리고 "완료" 화면으로 넘어갔는데, 서버에는 사진이 절반만 들어가 있을 때.

### Next.js · 상세 페이지에서 `params.id`가 왜 비어 있을까?

Next.js 16 App Router 기준입니다.

```tsx
// app/concerts/[id]/page.tsx
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const concert = await getConcert(id)
  return <ConcertDetail concert={concert} />
}
```

Next.js 15부터 `page`의 `params`와 `searchParams`는 Promise입니다. 15에서는 예전 코드가 깨지지 않도록 `params.id` 같은 동기 접근을 임시로 허용했지만, 16에서는 그 호환이 완전히 빠졌습니다. 그래서 Promise에서 `.id`를 바로 꺼내면 값이 없습니다. 서버 컴포넌트에서는 `await params`로, `async`를 쓸 수 없는 클라이언트 컴포넌트에서는 React의 `use(params)`로 꺼냅니다. 타입을 `Promise<{ id: string }>`로 적어 두면 `params.id`에서 바로 `Property 'id' does not exist on type 'Promise<{ id: string; }>'.`로 막힙니다.

**실무에서 만나는 장면**: 14 시절 블로그 예제를 16 프로젝트에 붙였더니 상세 페이지가 `undefined`로 요청을 보낼 때.

### 브라우저 · 버튼에 단 `data-id`가 왜 가끔 `undefined`일까?

```tsx
;<button data-coupon-id="WELCOME10" onClick={handleClick}>
  <TicketIcon />
  <span>쿠폰 받기</span>
</button>

function handleClick(e: MouseEvent<HTMLButtonElement>) {
  e.target // 실제로 누른 가장 안쪽 요소: 글자를 누르면 span
  e.currentTarget.dataset.couponId // 'WELCOME10', 핸들러가 달린 button
}
```

클릭 이벤트는 실제로 누른 가장 안쪽 요소에서 시작해 바깥으로 올라갑니다(버블링). `e.target`은 그 시작점이라 아이콘이나 글자를 누르면 `span`이 되고, `span`에는 `data-coupon-id`가 없으니 `undefined`입니다. `e.currentTarget`은 지금 이 핸들러가 달린 요소라서 어디를 눌러도 `button`입니다. TypeScript도 이 차이를 알아서, `e.target.dataset`에는 `Property 'dataset' does not exist on type 'EventTarget'.`를 띄웁니다.

**실무에서 만나는 장면**: 목록 버튼마다 `data-id`를 달고 핸들러 하나로 처리했는데, 버튼 가장자리를 누르면 되고 아이콘을 누르면 안 될 때.
