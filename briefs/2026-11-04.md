## 클린 코드 처방

### 1. 상태와 파생 값 · 열림 여부와 대상을 따로 두기 → 대상 하나로

**상황**

```tsx
const [isCancelSheetOpen, setIsCancelSheetOpen] = useState(false)
const [cancelTarget, setCancelTarget] = useState<Reservation | null>(null)

function openCancelSheet(reservation: Reservation) {
  setCancelTarget(reservation)
  setIsCancelSheetOpen(true)
}

function closeCancelSheet() {
  setIsCancelSheetOpen(false) // cancelTarget은 그대로 남는다
}
```

**처방: "열려 있다"를 "대상이 있다"로 읽기**

```tsx
const [cancelTarget, setCancelTarget] = useState<Reservation | null>(null)

{
  cancelTarget && <CancelSheet reservation={cancelTarget} onClose={() => setCancelTarget(null)} />
}
```

**왜**: state가 둘이면 "열렸는데 대상이 없다", "닫혔는데 대상이 남아 있다" 같은 말이 안 되는 조합이 생깁니다. 취소 시트는 취소할 예약이 있을 때만 의미가 있으니, 대상 하나만 두면 열림 여부는 저절로 따라옵니다. `CancelSheet` 안에서 `reservation`이 `null`인지 다시 확인할 필요도 없어집니다.

**안 해도 되는 때**: 닫히는 애니메이션 동안 내용이 화면에 남아 있어야 하는 시트라면, 열림과 내용을 따로 둘 이유가 있습니다.

### 2. 비즈니스 로직 위치 · 버튼 비활성 조건과 제출 검사가 따로 놀 때 → 판정 함수 하나를 같이 쓰기

**상황**

```tsx
;<Button disabled={!form.resume || !form.agreed}>지원하기</Button>

function handleSubmit() {
  if (!form.resume || !form.agreed || form.phone.length < 10) {
    showToast('필수 항목을 확인해 주세요')
    return
  }
  submitApplication(form)
}
```

**처방: "지원할 수 있나?"에 이름 하나**

```tsx
function canSubmitApplication(form: ApplicationForm) {
  return form.resume !== null && form.agreed && form.phone.length >= 10
}

;<Button disabled={!canSubmitApplication(form)}>지원하기</Button>

function handleSubmit() {
  if (!canSubmitApplication(form)) return
  submitApplication(form)
}
```

**왜**: 상황 코드에서는 전화번호 검사가 핸들러에만 있어서, 버튼은 켜져 있는데 누르면 토스트가 뜹니다. 같은 규칙이 두 군데 있으면 바뀔 때 한쪽만 고쳐지기 쉽습니다. 규칙을 함수 하나에 두면 버튼과 핸들러가 같은 답을 듣고, 화면 없이 그 함수만 따로 테스트할 수도 있습니다.

**안 해도 되는 때**: 조건이 `!form.agreed` 하나뿐이고 한 곳에서만 쓰인다면, 그 자리에 바로 쓰는 편이 더 짧고 잘 읽힙니다.

### 3. 함수와 인자 · 인자가 네 개를 넘을 때 → 객체 하나로 받기

**상황**

```ts
function searchFlights(from: string, to: string, departDate: string, returnDate: string | null, adults: number, children: number) {}

searchFlights('ICN', 'NRT', '2026-12-20', null, 2, 1)
```

**처방: 이름 붙은 인자**

```ts
type FlightSearch = {
  from: string
  to: string
  departDate: string
  returnDate?: string
  passengers: { adults: number; children: number }
}

function searchFlights(search: FlightSearch) {}

searchFlights({ from: 'ICN', to: 'NRT', departDate: '2026-12-20', passengers: { adults: 2, children: 1 } })
```

**왜**: 부르는 쪽에서 `null, 2, 1`이 각각 무엇인지 보이지 않습니다. 게다가 `from`과 `to`, `adults`와 `children`처럼 타입이 같은 인자는 순서를 바꿔 넣어도 타입 검사가 잡지 못합니다. 객체로 받으면 이름이 같이 적히고, 편도처럼 없는 값은 그냥 빼면 됩니다.

**안 해도 되는 때**: `clamp(value, min, max)`처럼 인자가 적고 순서가 누구에게나 익숙한 함수는 그대로 둡니다.

## 생각하는 법

### 기획을 코드로 · 이 숫자는 누가 바꾸지?

**장면**: 노트 앱 구독 기획 메모입니다.

> 무료 체험은 14일이에요. 체험 중에는 노트북을 3개까지 만들 수 있어요. 체험이 끝나기 며칠 전에 알림을 받을지는 직접 고를 수 있어요.

숫자 셋을 상수로 적고 시작하고 싶어지는 메모입니다.

**생각 순서**

1. **"여기 정책 값이 몇 개지?"** 14일, 3개, 그리고 사용자가 고르는 "며칠 전". 문장은 하나씩이지만 값이 오는 곳은 셋 다 다를 수 있습니다.
2. **"이 숫자가 내일 바뀌면 누가 바꾸지?"** 14일은 프로모션 때 30일로 늘 수 있습니다. 그걸 앱 배포 없이 바꿔야 한다면 서버가 알려 주는 값입니다. 3개는 어차피 서버가 막아야 하는 값입니다. 화면만 막으면 API를 직접 부르는 요청은 통과하니까요. 그러면 화면은 서버가 준 한도를 받아 쓰기만 합니다. "며칠 전"은 사용자가 정하는 값이라 설정에 저장하고, 앱에는 기본값만 둡니다.
3. **"내가 정해도 되는 건가?"** 2번은 짐작입니다. "체험 기간은 프로모션 때 바뀌나요?", "노트북 한도는 서버에서도 막나요?"를 기획자와 서버 개발자에게 묻습니다. 아무도 바꿀 일이 없다는 답이 오면, 그때 이름 붙은 상수 하나로 둡니다.
4. **"화면이 값의 출처를 알아야 하나?"** 아닙니다. 화면은 `policy.maxNotebooks`만 읽으면 됩니다. 상수였던 값이 나중에 서버로 옮겨 가도 화면 코드는 그대로입니다.

**코드로 옮기면**

```ts
type TrialPolicy = { trialDays: number; maxNotebooks: number } // 서버가 알려 준다
type ReminderSetting = { daysBefore: number } // 사용자가 고른다
const DEFAULT_REMINDER_DAYS_BEFORE = 3 // 앱이 정한 기본값

function canCreateNotebook(notebookCount: number, policy: TrialPolicy) {
  return notebookCount < policy.maxNotebooks
}
```

**한 줄 요약**: 기획 메모의 숫자를 보면 상수로 적기 전에 "이게 바뀌면 누가 바꾸지?"를 먼저 묻습니다. 배포 없이 바뀌어야 하면 서버, 사용자가 고르면 설정, 아무도 안 바꾸면 이름 붙은 상수입니다.

## 기본기

### TypeScript · `label?: string`과 `label: string | undefined`는 같을까?

```ts
type WithOptional = { label?: string }
type WithUndefined = { label: string | undefined }

const a: WithOptional = {} // 통과
const b: WithUndefined = {} // 오류
// Property 'label' is missing in type '{}' but required in type 'WithUndefined'.
```

값을 읽을 때는 둘 다 `string | undefined`라 같아 보입니다. 다른 건 **키를 빼도 되느냐**입니다. `?`는 키를 아예 안 써도 되고, `| undefined`는 키는 꼭 적되 값으로 `undefined`를 넣을 수 있다는 뜻입니다. 덧붙여 `exactOptionalPropertyTypes` 옵션을 켜면 `?` 쪽에 `{ label: undefined }`를 넣는 것도 막힙니다. 이 옵션은 `strict`에 들어 있지 않습니다(`tsc --strict`, 6.0으로 확인).

**실무에서 만나는 장면**: 위 처방 3의 `returnDate`를 `returnDate: string | undefined`로 두면, 부르는 쪽이 편도인지 왕복인지 생각하지 않고 빠뜨리는 일을 타입이 막아 줍니다. 빠뜨려도 괜찮은 값이면 `?`, 꼭 한 번 생각하게 하고 싶은 값이면 `| undefined`입니다.

### React · `useState(readDraft())`와 `useState(readDraft)`는 뭐가 다를까?

```tsx
const [draft, setDraft] = useState(readDraft()) // 렌더링할 때마다 readDraft 실행
const [draft, setDraft] = useState(readDraft) // 처음 한 번만 실행
```

React는 초기값을 처음 한 번만 쓰고 그다음 렌더링부터는 무시합니다. 그런데 `readDraft()`라고 쓰면 무시될 값을 만들려고 렌더링마다 함수가 실행됩니다. 함수 자체를 넘기면 React가 컴포넌트를 처음 만들 때만 부릅니다(초기화 함수). 인자가 필요하면 `useState(() => readDraft(postId))`처럼 감쌉니다. 개발 모드의 Strict Mode에서는 초기화 함수가 일부러 두 번 불리지만, 결과 하나는 버려지고 배포 환경에서는 한 번입니다(react.dev의 `useState` 문서 기준. 18과 19에서 같습니다).

**실무에서 만나는 장면**: 중고 거래 글쓰기 화면에서 임시 저장 글을 `localStorage`에서 꺼내 `JSON.parse`하는데, 제목을 한 글자 칠 때마다 그 파싱이 다시 돌고 있을 때.

### 네트워크 · `fetch`는 404가 와도 왜 `catch`로 안 갈까?

```ts
async function getCoupon(id: string) {
  const response = await fetch(`/api/coupons/${id}`)
  if (!response.ok) throw new Error(`쿠폰 조회 실패: ${response.status}`)
  return response.json()
}
```

`fetch`의 Promise는 요청 자체가 실패할 때만 거부됩니다. 네트워크가 끊겼거나 URL이 잘못된 경우입니다. 서버가 404나 500으로 **응답했다면** 요청은 성공한 것이라 Promise는 정상으로 끝나고, `response.ok`가 `false`일 뿐입니다(`ok`는 상태 코드가 200~299일 때 `true`). 그래서 실패로 다루고 싶으면 직접 확인해서 던져야 합니다. axios는 기본 설정에서 2xx가 아니면 거부해서, 둘을 오가면 헷갈리기 쉽습니다(MDN `fetch()` 문서로 확인).

**실무에서 만나는 장면**: 만료된 쿠폰을 조회했더니 에러 화면 대신 빈 쿠폰 카드가 뜰 때. 404 응답의 에러 JSON이 그대로 쿠폰 데이터로 쓰여서 `coupon.name`이 `undefined`였던 경우입니다.
