## 클린 코드 처방

### 1. 조건문 · 금액 구간마다 이어지는 if → 구간 표 하나로

배달 앱 장바구니입니다. 주문 금액이 커질수록 배달팁이 내려가고, 장바구니 위에는 "얼마 더 담으면 배달팁이 내려가요" 배너가 있습니다.

**상황**

```tsx
function getDeliveryTip(orderAmount: number) {
  if (orderAmount >= 30000) return 0
  if (orderAmount >= 20000) return 1000
  if (orderAmount >= 15000) return 2000
  return 3000
}

// 장바구니 배너
const tipBanner = orderAmount < 15000 && <p>{15000 - orderAmount}원 더 담으면 배달팁 2,000원</p>
```

**처방: 구간 표**

```ts
const BASE_TIP = 3000
// find가 위에서부터 찾으니 금액이 큰 구간부터 적는다
const TIP_TIERS = [
  { minAmount: 30000, tip: 0 },
  { minAmount: 20000, tip: 1000 },
  { minAmount: 15000, tip: 2000 },
]

function getDeliveryTip(orderAmount: number) {
  return TIP_TIERS.find((tier) => orderAmount >= tier.minAmount)?.tip ?? BASE_TIP
}

// 아직 못 넘은 구간 중 가장 가까운 것. 배너는 이 값으로 그린다
function getNextTier(orderAmount: number) {
  return TIP_TIERS.findLast((tier) => orderAmount < tier.minAmount)
}
```

**왜**: 15000, 20000 같은 경계가 계산 함수와 배너에 따로 적혀 있으면, 구간이 바뀔 때 한 곳만 고치기 쉽습니다. 상황 코드의 배너는 이미 첫 구간만 안내하고 있기도 합니다. 표로 옮기면 배달팁 계산과 배너가 같은 표를 읽고, 가게마다 구간이 다르면 이 모양 그대로 서버에서 받으면 됩니다.

**안 해도 되는 때**: 구간이 두세 개이고 그 숫자를 읽는 곳이 함수 하나뿐이면, `if` 세 줄이 표보다 바로 읽힙니다.

### 2. 함수와 인자 · 객체를 통째로 받는 함수 → 쓰는 값만 받기

채용 앱의 공고 카드에 "D-3", "오늘 마감"을 붙이는 함수입니다. 지원 내역 화면에도 같은 표시가 필요해졌는데, 거기에는 공고 객체가 없고 마감일만 있습니다.

**상황**

```ts
function getDeadlineLabel(job: JobPosting, now: Date) {
  const days = daysBetween(now, job.closesAt)
  if (days < 0) return '마감'
  if (days === 0) return '오늘 마감'
  return `D-${days}`
}

// 지원 내역: 공고 객체가 없어서 모양만 흉내 낸다
getDeadlineLabel({ closesAt: application.closesAt } as JobPosting, now)
```

**처방: 쓰는 값만 받기**

```ts
function getDeadlineLabel(closesAt: Date, now: Date) {
  const days = daysBetween(now, closesAt)
  if (days < 0) return '마감'
  if (days === 0) return '오늘 마감'
  return `D-${days}`
}

getDeadlineLabel(job.closesAt, now)
getDeadlineLabel(application.closesAt, now)
```

**왜**: `JobPosting`을 통째로 받으면 "공고 객체가 있어야 부를 수 있다"는 조건이 따라붙습니다. 실제로 쓰는 건 마감일 하나라서, 마감일만 받으면 지원 내역·찜 목록·알림 어디서든 부를 수 있고 테스트도 날짜 두 개면 됩니다. `as JobPosting`은 TypeScript가 막지 않아서, 나중에 함수가 `job.title`을 읽기 시작하면 지원 내역 화면에서만 조용히 `undefined`가 됩니다.

**안 해도 되는 때**: `canApply(job, user)`처럼 공고의 여러 필드를 함께 보고 판단하는 함수는 객체를 받는 편이 읽기 쉽습니다. 값을 하나씩 꺼내 넘기다 인자가 넷을 넘으면 거꾸로 가는 것입니다.

### 3. 타입으로 막기 · onChange에서 `as`로 되돌리는 Select → 제네릭으로 값 타입 이어 주기

부동산 앱 매물 목록의 정렬 선택입니다. `SortKey`는 `'recent' | 'priceLow' | 'areaLarge'`입니다.

**상황**

```tsx
type SelectProps = {
  options: { value: string; label: string }[]
  value: string
  onChange: (value: string) => void
}

const SORT_OPTIONS = [
  { value: 'recent', label: '최신순' },
  { value: 'areaLage', label: '넓은 면적순' }, // 오타인데 아무 말이 없다
]

<Select options={SORT_OPTIONS} value={sort} onChange={(value) => setSort(value as SortKey)} />
```

**처방: 제네릭 props**

```tsx
type SelectProps<T extends string> = {
  options: { value: T; label: string }[]
  value: T
  onChange: (value: T) => void
}

const SORT_OPTIONS: { value: SortKey; label: string }[] = [
  { value: 'recent', label: '최신순' },
  { value: 'areaLage', label: '넓은 면적순' },
  // 오류: Type '"areaLage"' is not assignable to type 'SortKey'. Did you mean '"areaLarge"'?
]

<Select options={SORT_OPTIONS} value={sort} onChange={setSort} />
```

**왜**: `as SortKey`는 "믿어 달라"는 말이라, 옵션에 오타가 있어도 통과하고 사용자가 그 옵션을 고르면 `'areaLage'`로 정렬 요청이 나갑니다. 제네릭으로 받으면 옵션·현재 값·콜백이 같은 타입으로 묶여서 어긋나는 줄에 빨간 줄이 생기고, `onChange={setSort}`처럼 그대로 넘길 수 있습니다. 옵션 배열에도 `SortKey`를 붙여 둡니다. 안 붙이면 값이 `string`으로 넓어져서, 오타가 없어도 `onChange={setSort}`에서 오류가 납니다.

**안 해도 되는 때**: 사용자가 직접 만든 태그 목록처럼 값이 정말 아무 문자열이나 될 수 있으면 `string` 그대로가 맞습니다.

## 생각하는 법

### 기획을 코드로 · 같은 단어가 두 문장에서 다른 뜻일 때

**장면**: 공연 예매 앱 기획 메모입니다.

> 예매 내역에서는 지금까지 한 예매를 모두 볼 수 있어요.
> 예매가 남아 있으면 회원 탈퇴를 할 수 없어요.

**생각 순서**

1. **"두 문장의 '예매'가 같은 걸 가리키나?"** 첫 문장의 예매는 기록입니다. 지난 공연도, 취소한 예매도 들어갑니다. 두 번째 문장의 예매는 아직 끝나지 않은 거래입니다. 작년에 본 공연 때문에 탈퇴를 못 하게 하려는 뜻은 아닐 겁니다.
2. **"그럼 어떤 상태가 들어가지?"** 예매 상태를 늘어놓고 문장마다 표시해 봅니다. 결제 완료(관람 전), 관람 완료, 취소, 환불 진행 중. 탈퇴를 막는 쪽에 결제 완료는 확실히 들어가고, 환불 진행 중이 애매합니다.
3. **"애매한 건 뭐라고 묻지?"** "예매가 있으면이 무슨 뜻이에요?"보다 상태 이름을 들고 묻습니다. "환불 진행 중인 예매가 있어도 탈퇴를 막나요?"라고 물으면 기획자도 예, 아니오로 답할 수 있습니다.
4. **"코드에서도 같은 이름으로 불러도 될까?"** 둘 다 `bookings`라고 부르면 다음 사람이 탈퇴 조건에 전체 목록을 씁니다. 두 번째 뜻에는 정책이 드러나는 이름을 따로 붙입니다. 실제로 탈퇴를 막는 건 서버지만, 화면에서 미리 안내하려면 같은 기준이 필요합니다.

**코드로 옮기면**

```ts
type BookingStatus = 'confirmed' | 'used' | 'canceled' | 'refunding'

// 예매 내역: 상태와 상관없이 전부 보여 준다
// 탈퇴를 막는 예매: 아직 끝나지 않은 거래만 (refunding은 기획 확인 중)
const BLOCKS_WITHDRAWAL: BookingStatus[] = ['confirmed', 'refunding']

function hasBookingThatBlocksWithdrawal(bookings: Booking[]) {
  return bookings.some((booking) => BLOCKS_WITHDRAWAL.includes(booking.status))
}
```

**한 줄 요약**: 기획서에 같은 단어가 두 번 나오면 같은 범위라고 가정하지 않습니다. 상태 목록을 펼쳐 놓고 문장마다 어디까지인지 표시하면, 물을 질문과 코드 이름이 같이 나옵니다.

## 기본기

### TypeScript · `as const` 배열에 `includes`를 했더니 왜 빨간 줄이 생길까?

```ts
const TABS = ['home', 'reviews', 'qna'] as const
type Tab = (typeof TABS)[number] // 'home' | 'reviews' | 'qna'

function readTab(value: string): Tab {
  if (TABS.includes(value)) return value
  // 오류: Argument of type 'string' is not assignable to parameter of type '"home" | "reviews" | "qna"'.
  return 'home'
}
```

`as const` 배열은 `readonly ['home', 'reviews', 'qna']`라서 `includes`도 그 셋 중 하나만 받습니다. 아직 모르는 `string`을 확인하려는 건데, 이미 확인된 값만 넣으라고 하는 셈입니다. 게다가 `includes`는 `true`가 나와도 `value`를 `Tab`으로 좁혀 주지 않습니다. 그래서 확인과 좁히기를 같이 하는 함수를 하나 둡니다.

```ts
function isTab(value: string): value is Tab {
  return (TABS as readonly string[]).includes(value)
}
```

**실무에서 만나는 장면**: `?tab=reviews` 같은 쿼리스트링이나 `localStorage`에 저장해 둔 탭 이름을 읽어서 화면 탭으로 쓸 때.

### React · 로딩 중에 먼저 `return` 했더니 왜 "Rendered more hooks" 에러가 날까? (React 19 기준)

```tsx
function OrderSummary({ orderId }: { orderId: string }) {
  const { order, isLoading } = useOrder(orderId)
  if (isLoading) return <Spinner />

  const [memo, setMemo] = useState('') // 로딩이 끝난 뒤에만 불린다
  // ...
}
```

React는 훅을 이름이 아니라 부른 순서로 기억합니다. "이 컴포넌트의 첫 번째 훅, 두 번째 훅" 하는 식이라 렌더링마다 같은 순서로 같은 개수가 불려야 합니다. 로딩 중에는 `useState`까지 닿지 않다가 로딩이 끝나면 하나가 더 불리니, React는 `Rendered more hooks than during the previous render.` 에러를 던집니다. 개발 모드에서는 그 전에 "React has detected a change in the order of Hooks" 경고도 찍힙니다.

고치는 법은 훅을 모두 조건부 `return`보다 위로 올리는 것입니다. 공식 문서의 훅 규칙에도 조건부 `return` 뒤에서 훅을 부르지 말라는 항목이 따로 있고, `eslint-plugin-react-hooks`를 켜 두면 저장 전에 잡힙니다. React 19의 `use`는 훅이 아니라서 `if` 안에서도 부를 수 있지만, 그것도 컴포넌트나 훅 안에서만 씁니다.

**실무에서 만나는 장면**: 로딩·빈 상태를 가드 절로 먼저 내보내고 그 아래에 입력용 `useState`를 더했더니, 데이터가 오는 순간 화면이 하얗게 될 때. 에러 경계가 없으면 화면 전체가 사라집니다.

### Next.js · `loading.tsx`를 만들었는데 왜 이전 화면에서 멈춰 있을까? (Next.js 16 App Router 기준)

```tsx
// app/mypage/layout.tsx
export default async function MyPageLayout({ children }: { children: ReactNode }) {
  const user = await getCurrentUser() // 안에서 cookies()로 로그인 정보를 읽는다
  return (
    <>
      <MyPageHeader user={user} />
      {children}
    </>
  )
}

// app/mypage/loading.tsx
export default function Loading() {
  return <MyPageSkeleton />
}
```

`loading.tsx`는 같은 폴더의 `layout.tsx` 안쪽에 들어가서, `page.tsx`와 그 아래를 `<Suspense>`로 감쌉니다. 같은 폴더의 레이아웃은 감싸지 않습니다. 그래서 레이아웃이 `cookies()`나 캐시하지 않은 `fetch`를 기다리는 동안에는 스켈레톤을 보여 줄 자리가 아직 없고, Cache Components를 켜지 않은 기본 설정에서는 레이아웃이 다 그려질 때까지 이동이 멈춥니다.

공식 문서가 권하는 방법은 둘입니다. 그 데이터 요청을 `page.tsx`로 옮기거나, 레이아웃 안에서 그 부분만 따로 `<Suspense>`로 감쌉니다. Cache Components를 켰다면 이렇게 감싸지 않은 경우를 빌드할 때 오류로 알려 줍니다.

**실무에서 만나는 장면**: 홈에서 마이페이지 탭을 눌렀는데 스켈레톤 없이 1~2초 동안 홈 화면에 머물다가 한 번에 바뀔 때. 레이아웃의 헤더가 사용자 정보를 기다리고 있는지부터 봅니다.
