## 클린 코드 처방

### 1. 타입으로 막기 · 검사하고 결과를 버리는 함수 → 검사하면서 좁힌 값을 돌려주기

**상황**

```ts
type ApplyForm = { name: string; email: string; resumeFileId: string | null }

function isValid(form: ApplyForm) {
  return form.name.trim() !== '' && form.resumeFileId !== null
}

async function handleSubmit() {
  if (!isValid(form)) return
  await submitApplication({ ...form, resumeFileId: form.resumeFileId! })
}
```

**처방: 검사를 통과하면 제출할 모양을 돌려준다**

```ts
type ApplyPayload = { name: string; email: string; resumeFileId: string }

function toPayload(form: ApplyForm): ApplyPayload | null {
  if (form.name.trim() === '' || form.resumeFileId === null) return null
  return { name: form.name.trim(), email: form.email, resumeFileId: form.resumeFileId }
}

async function handleSubmit() {
  const payload = toPayload(form)
  if (!payload) return
  await submitApplication(payload)
}
```

**왜**: `isValid`는 "이력서가 있다"는 걸 확인해 놓고 `true` 하나만 돌려줍니다. 타입은 그 사실을 모르니 결국 `!`로 덮게 되고, 누군가 검사를 빼먹어도 컴파일러는 조용합니다. 좁힌 값을 돌려주면 `submitApplication`은 `ApplyPayload`만 받으니, `form`을 그대로 넘기면 `Type 'string | null' is not assignable to type 'string'` 오류가 납니다. 검사를 건너뛸 길이 사라집니다.

**안 해도 되는 때**: 이메일 모양 확인처럼 검사를 통과해도 타입이 그대로인 경우는 boolean 검사로 충분합니다.

### 2. 훅 · 의존성 경고를 끄고 effect 밖 함수 부르기 → 함수를 effect 안으로

**상황**

```tsx
const [slots, setSlots] = useState<Slot[]>([])

async function loadSlots() {
  setSlots(await fetchSlots(clinicId, date))
}

useEffect(() => {
  loadSlots()
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [clinicId])
```

**처방: effect가 읽는 값이 effect 안에서 다 보이게**

```tsx
const [slots, setSlots] = useState<Slot[]>([])

useEffect(() => {
  async function loadSlots() {
    setSlots(await fetchSlots(clinicId, date))
  }
  loadSlots()
}, [clinicId, date])
```

**왜**: 진료 예약 화면에서 날짜를 바꿔도 시간표가 그대로입니다. `loadSlots`가 `date`를 읽는데 의존성에는 `clinicId`만 있으니까요. 경고를 끈 순간부터 "이 effect가 뭘 읽는지"를 확인하는 사람이 없어집니다. 함수를 effect 안에 두면 린터가 `date`가 빠졌다고 바로 알려 줍니다. React 공식 문서(Removing Effect Dependencies)도 같은 방법을 권합니다.

**안 해도 되는 때**: 같은 불러오기를 "다시 시도" 버튼에서도 불러야 하면 effect 밖에 두고 `useCallback`으로 감싸 의존성 배열에 넣습니다. 경고를 끄는 대신입니다.

### 3. 테스트하기 좋은 모양 · 클래스 이름으로 요소 찾기 → 사용자가 보는 이름으로 찾기

**상황**

```tsx
it('쿠폰 적용', async () => {
  const { container } = render(<CouponSheet orderAmount={12000} />)
  await user.click(container.querySelector('.coupon-item:first-child button')!)
  expect(container.querySelector('.price-total')!.textContent).toBe('9,000원')
})
```

**처방: 역할과 이름으로 찾고, 테스트 이름은 행동으로**

```tsx
it('3,000원 쿠폰을 적용하면 결제 금액이 9,000원이 된다', async () => {
  render(<CouponSheet orderAmount={12000} />)
  await user.click(screen.getByRole('button', { name: '3,000원 할인 쿠폰 적용' }))
  expect(screen.getByText('결제 금액 9,000원')).toBeInTheDocument()
})
```

**왜**: 클래스 이름과 DOM 순서는 디자인을 손보면 바뀝니다. 쿠폰 순서를 바꿨을 뿐인데 테스트가 깨지면, 테스트가 기능이 아니라 마크업을 지키고 있던 겁니다. 버튼 이름과 화면 문구는 기능이 그대로면 그대로라서, 테스트가 깨지는 이유가 "기능이 깨졌을 때"만 남습니다. 역할로 찾히지 않는다면 스크린 리더도 그 버튼을 못 찾는다는 신호이기도 합니다.

**안 해도 되는 때**: 차트 캔버스나 장식 아이콘처럼 화면에 이름이 없는 요소는 `data-testid`가 현실적입니다.

## 생각하는 법

### 기획을 코드로 · 정책과 화면 문구를 가르기

**장면**: 공연 예매 앱 기획 메모입니다.

> 잔여석이 20석 이하면 예매 버튼 위에 "마감 임박! n석 남았어요"를 띄워 주세요. 0석이면 "매진"으로 바꾸고 버튼을 막아 주세요.

이대로 옮기면 컴포넌트 안에서 `remaining <= 20` 같은 조건과 "마감 임박!" 문구가 한 줄에 엉킵니다.

**생각 순서**

1. **"이 문장에서 규칙은 뭐고, 글자는 뭐지?"** 규칙은 "20석 이하", "0석이면 매진", "매진이면 예매 불가"입니다. "마감 임박! n석 남았어요"와 "매진"은 그 규칙을 사람에게 보여 주는 말입니다. n은 정책이 아니라 서버가 준 데이터입니다.
2. **"마케팅에서 문구만 바꿔 달라고 하면 어디를 고치지?"** "서두르세요! n석 남음"으로 바뀌어도 20이라는 기준은 그대로여야 합니다. 반대로 기준이 10석으로 바뀌어도 문구는 그대로입니다. 바뀌는 이유가 다르니 자리도 따로 둡니다.
3. **"같은 판단을 다른 화면도 쓰나?"** 공연 목록 카드에는 "마감 임박" 배지만, 상세에는 남은 좌석 수까지 보여 준다면 판단은 하나고 문구가 둘입니다. 판단은 한 번 만들고 화면마다 자기 말로 옮깁니다.
4. **"'매진'과 '버튼 막기'는 같은 규칙일까?"** 예매 오픈 전에도 버튼은 막힙니다. 버튼 비활성의 이유가 하나가 아니라면, 매진 여부와 예매 가능 여부를 따로 물어 둡니다.

**코드로 옮기면**

```ts
const ALMOST_SOLD_OUT_SEATS = 20

type SeatStatus = { kind: 'soldOut' } | { kind: 'almostSoldOut'; remaining: number } | { kind: 'available' }

function getSeatStatus(remaining: number): SeatStatus {
  if (remaining === 0) return { kind: 'soldOut' }
  if (remaining <= ALMOST_SOLD_OUT_SEATS) return { kind: 'almostSoldOut', remaining }
  return { kind: 'available' }
}

// 문구는 화면에서. 목록 카드는 'almostSoldOut'을 '마감 임박' 배지로만 옮긴다
```

**한 줄 요약**: 기획 문장에는 규칙과 문구가 같이 들어 있습니다. 판단은 의미 있는 값(`'almostSoldOut'`)까지만 만들고, 글자는 그 값을 보여 주는 화면이 정합니다.

## 기본기

### React · 배열에 `push`하고 `setItems(items)`를 했는데 왜 화면이 그대로일까?

```tsx
function addMember(member: Member) {
  members.push(member)
  setMembers(members) // 화면이 안 바뀐다
}

setMembers([...members, member]) // 새 배열이라 다시 그린다
```

React는 setter에 넘긴 값이 지금 state와 같은지 `Object.is`로 비교하고, 같으면 다시 렌더링하지 않습니다(React 18·19 공통, react.dev `useState` 문서). `push`는 같은 배열을 고치기만 하니 참조가 그대로이고, React는 "바뀐 게 없다"고 봅니다. 그래서 배열과 객체 state는 고치지 말고 새로 만들어 넘깁니다.

**실무에서 만나는 장면**: 모임 멤버를 추가했는데 목록은 그대로이다가, 다른 state가 바뀌어 다시 그려질 때 갑자기 나타날 때. 원본을 직접 고친 흔적입니다.

### TypeScript · `Record<string, Price>`에서 없는 키를 꺼내도 왜 타입 오류가 없을까?

```ts
const nightlyPrices: Record<string, Price> = {}
const price = nightlyPrices['2026-12-24'] // 타입은 Price
price.amount.toFixed() // strict여도 통과. 실행하면 터진다
```

인덱스로 꺼낸 값의 타입은 "그 키가 있다"고 믿고 `Price`로 잡힙니다. 배열 `list[0]`도 같습니다. `--strict`에는 이 검사가 들어 있지 않고, `noUncheckedIndexedAccess`를 따로 켜야 `'price' is possibly 'undefined'.` 오류가 납니다(TypeScript 6.0.3에서 확인). 이 저장소의 `legacy/code-quality/tsconfig.json`에도 켜져 있습니다.

**실무에서 만나는 장면**: 날짜별 숙박 요금표에서 요금이 없는 날을 고르자 화면이 하얗게 될 때. 옵션을 켜면 "그 날짜에 요금이 없으면?"을 코드를 쓸 때 묻게 됩니다.

### 네트워크 · PUT과 PATCH는 뭐가 다를까?

- **PUT**: "이 자원을 지금 보낸 것으로 통째로 바꿔 줘." 보내지 않은 필드는 비워질 수 있습니다.
- **PATCH**: "보낸 부분만 바꿔 줘."

PUT은 멱등입니다. 같은 요청을 두 번 보내도 결과가 같아서, 응답을 못 받았을 때 다시 보내도 안전합니다. PATCH는 "재고 1 빼기" 같은 변경도 담을 수 있어 멱등이 보장되지 않습니다(RFC 9110, RFC 5789). 다만 실제 동작은 서버 구현이 정하니 API 문서를 먼저 봅니다.

**실무에서 만나는 장면**: 프로필에서 닉네임만 바꿨는데 소개글이 지워졌다면, PUT에 닉네임만 담아 보낸 경우가 많습니다. 일부만 바꿀 때는 PATCH를 쓰거나, PUT이라면 전체를 담아 보냅니다.
