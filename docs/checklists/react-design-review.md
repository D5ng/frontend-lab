# React 설계 리뷰 체크리스트

매 실습에서 모든 항목을 기계적으로 확인하지 않는다. 짧은 실습에서는 핵심 질문을 사용하고, 트랙이나 큰 변경이 끝났을 때 전체 항목을 점검한다.

## 핵심 질문

1. 사용자의 목적을 UI 이름이 아닌 행동으로 설명할 수 있는가?
2. 각 상태의 source of truth는 어디인가?
3. 중요한 정책은 어디에서 결정되는가?
4. 각 모듈의 책임을 한 문장으로 설명할 수 있는가?
5. 실패, 지연, 중복 동작을 어떻게 처리하는가?
6. 요구사항 하나가 바뀌면 어떤 코드가 왜 변경되는가?

## 요구사항과 상태

- happy path 외의 시나리오와 암묵적인 전제를 확인했는가?
- 서버 데이터를 로컬 상태에 복사하거나 같은 정보를 두 상태로 표현하지 않는가?
- 새로고침, 공유, 뒤로가기가 필요한 값을 URL과 중복 관리하지 않는가?
- 계산 가능한 값을 별도 상태로 저장하지 않는가?

## 책임과 경계

- UI 표현과 정책 결정이 한 컴포넌트에 섞여 있지 않은가?
- 서로 다른 사용자 흐름이 하나의 모듈에서 함께 변경되지 않는가?
- 컴포넌트를 줄 수나 재사용 가능성만으로 분리하지 않았는가?
- Custom Hook이 React 생명주기나 Hook 조합을 숨기는가, 아니면 단순히 코드를 이동했는가?
- 특정 도메인을 알아야 하는 코드를 범용 `shared`로 올리지 않았는가?

## 코드 품질

- 읽는 사람이 한 번에 기억해야 할 맥락이 과도하지 않은가?
- 이름, 인자, 반환 값과 실제 동작이 일치하는가?
- 함께 변경되어야 하는 정책이 여러 위치에 흩어져 있지 않은가?
- 한 모듈의 변경이 관련 없는 모듈까지 퍼지지 않는가?
- 추상화가 실제 변경 위험을 낮추는가, 아니면 읽는 단계를 늘리기만 하는가?

## 비동기와 API

- pending, success, error를 사용자에게 어떻게 표현하는가?
- 빠른 연속 요청과 중복 클릭에서 최종 상태가 올바른가?
- mutation 성공과 이후 캐시 동기화 성공을 같은 의미로 취급하지 않는가?
- API enum과 요청 형식이 UI 곳곳에 직접 노출되지 않는가?
- optimistic update가 실제 UX 이득을 제공하며 실패 시 복구 가능한가?

## 권한과 접근성

- 역할 이름과 실제 권한을 같은 개념으로 취급하지 않는가?
- 버튼을 숨기는 프론트엔드 처리를 보안 검증으로 오해하지 않는가?
- 올바른 HTML 요소, label, 키보드 조작, 포커스 복원을 고려했는가?
- 색상만으로 상태를 표현하거나 오류를 시각적으로만 알리지 않는가?

## 변경 시뮬레이션

1. 현재 구조에서 변경 비용이 가장 클 것 같은 요구사항을 하나 고른다.
2. 변경된 파일과 이유를 기록한다.
3. 같은 이유의 변경이 불필요하게 퍼졌는지 확인한다.
4. 기존 추상화가 변경을 도왔는지 방해했는지 비교한다.
5. 지금 리팩터링할 근거가 충분한지 판단한다.

## 리뷰 결과 구분

- **확인된 문제:** 현재 요구사항이나 사용자 행동이 잘못되는 결함
- **설계 위험:** 특정 변경 시 비용이 커질 근거가 있는 구조
- **제안:** 현재도 유효하지만 다른 트레이드오프를 선택할 수 있는 대안
- **컨벤션:** 팀이 일관성을 위해 선택할 수 있으나 정답은 아닌 기준
