# Frontend Fundamentals 참고 기준

이 문서는 Frontend Fundamentals를 대신하지 않는다. 실습과 리뷰에서 사용할 질문을 프로젝트 문맥에 맞게 요약하고, 상세 예시는 원문에서 확인한다.

- [좋은 코드를 위한 4가지 기준](https://frontend-fundamentals.com/code-quality/code/)
- [toss/frontend-fundamentals](https://github.com/toss/frontend-fundamentals)

## 가독성

- 코드를 이해하기 위해 동시에 기억해야 하는 맥락이 과도한가?
- 같은 시점에 실행되지 않는 흐름이 한곳에 섞여 있는가?
- 이름과 위에서 아래로 이어지는 흐름이 실제 동작을 드러내는가?
- 추상화가 구현 상세를 숨기는가, 중요한 맥락까지 감추는가?

## 예측 가능성

- 이름, 파라미터와 반환 타입만 보고 사용법을 예상할 수 있는가?
- 비슷한 이름의 함수와 컴포넌트가 일관된 계약을 따르는가?
- 호출부가 알 수 없는 부수 효과나 암묵적인 상태 변경이 있는가?

## 응집도

- 함께 변경되어야 하는 코드와 데이터가 같은 경계 안에 있는가?
- 한 정책을 바꿀 때 여러 위치를 기억해서 수동으로 맞춰야 하는가?
- 공통화가 실제 동시 변경을 보장하는가?

## 결합도

- 한 모듈의 변경이 영향을 주는 범위를 예측할 수 있는가?
- 하위 모듈이 상위 화면이나 특정 사용 흐름을 불필요하게 알고 있는가?
- 재사용이나 중복 제거가 서로 다른 변경 이유를 묶고 있지 않은가?

## 함께 비교할 트레이드오프

- 공통화는 응집도를 높일 수 있지만 읽는 단계와 결합을 늘릴 수도 있다.
- 중복 허용은 변경 범위를 좁힐 수 있지만 동시 수정 누락의 위험을 만든다.
- 책임 분리는 각 흐름을 단순하게 만들 수 있지만 전체 동작을 찾는 비용을 늘릴 수 있다.
- 상태를 가까이 두면 흐름이 선명해질 수 있지만 여러 소비자가 생기면 동기화 문제가 나타날 수 있다.

따라서 네 기준을 각각 최대화하지 않는다. 현재 요구사항과 예상되는 변경에서 어떤 위험을 우선 줄일지 근거를 남긴다.
