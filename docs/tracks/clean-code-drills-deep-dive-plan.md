# 계획: 드릴을 골라서 깊게 파기

상태: 계획 (2026-11-03). 아직 트랙 문서와 스킬에는 반영하지 않았습니다.

## 왜

10/30 드릴(적금 계산기)을 다 푼 뒤 "그래도 코드가 지저분하다"에서 시작해 화면 하나를 열한 단계에 걸쳐 다듬었습니다. 오늘 실제로 기준이 늘어난 곳은 문제 세 개를 푼 시간이 아니라 이 과정이었습니다.

> 지저분하다 → 왜 그런지 진단 → 한 단계 고침 → 리뷰 → 반박하거나 다시 고침 → 다음 단계

드릴은 기법 하나를 30분 안에 적용하는 연습이라 이런 판단이 나올 틈이 없습니다. 상태 위치, 타입과 런타임 데이터, 중복이 위험한 때, 추상화 높이 같은 판단은 냄새가 여러 겹인 화면에서 하나를 고치고 나서야 다음 게 보일 때 생깁니다.

드릴 루틴은 지금 그대로 둡니다. 대신 **마음에 남는 드릴 하나를 골라 깊게 파는 길**을 선택지로 엽니다.

## 무엇을 하나

|         | 드릴                 | 깊게 파기                        |
| ------- | -------------------- | -------------------------------- |
| 시작점  | 문제가 준 시작 코드  | 드릴을 다 푼 내 코드             |
| 하는 일 | 기법 하나 적용       | 화면 하나를 여러 기준으로 다듬기 |
| 끝      | 문제 3개 + `note.md` | 내가 멈추기로 할 때              |
| 시간    | 문제당 15~30분       | 정하지 않음                      |
| 하는 날 | 매일                 | 고를 때만                        |

## 언제, 어떻게 고르나

- 드릴 문제 3과 `note.md`까지 끝낸 뒤, 더 보고 싶은 드릴이 있으면 "깊게 파자"라고 말한다. 지난 드릴을 골라도 된다.
- 한 번에 하나만 판다. 하나를 멈추기 전에는 다른 드릴을 시작하지 않는다.
- **드릴 루틴을 막지 않는다.** 깊게 파는 동안에도 아침 드릴은 그대로 나온다. 깊게 파기는 "기록이 비어 있음" 판단에 세지 않는다.

## 진행 흐름 (10/30에서 한 그대로)

1. **진단부터**: 코드를 고치기 전에 "어디가, 왜 복잡하게 느껴지나"를 먼저 말로 쓴다. 코치는 리뷰 질문 네 개(이름을 믿을 수 있나, 규칙이 한 곳에 있고 테스트되나, 약속을 코드가 지키나, 나눈 이유를 말할 수 있나)로 후보를 보고 **지금 판단을 바꿀 한두 개만** 고른다.
2. **한 단계씩**: 한 번에 하나만 고친다. 구조만 바꾸고 테스트를 돌린 뒤 동작을 바꾼다.
3. **단계마다 리뷰**: `tsc`, 테스트, lint를 돌리고, 화면이 바뀌면 개발 서버에서 직접 본다. 리뷰는 "검증된 결함 → 설계 위험 → 개선 제안 → 관례" 순서로 받는다.
4. **반박해도 된다**: 리뷰를 그대로 받지 않고 실제 변경으로 대 본다. 10/30에서 "그냥 `calculateAppliedRate` 안에서 고치면 되는 거 아니야?"가 맞았던 것처럼.
5. **단계마다 커밋**: 바뀐 이유마다 따로 커밋한다. 파일 이동과 구조 변경은 나눈다. 커밋 메시지에 무엇이 흩어져 있었고 왜 바꿨는지 쓴다.
6. **멈출 때 정리**: 일반화할 수 있는 판단은 옵시디언 `클린코드` 폴더에 남긴다.

## 누가 무엇을 하나

| 사용자                          | 코치(Claude)                                        |
| ------------------------------- | --------------------------------------------------- |
| 진단을 먼저 말한다              | 우선순위 한두 개와 판단 기준을 준다                 |
| 코드를 고친다                   | 단계마다 실행해 보고 리뷰한다                       |
| 멈출지, 되돌릴지 정한다         | 할 일을 하나로 줄이고 "여기서 멈춰도 된다"를 말한다 |
| 테스트·커밋·푸시를 맡길 수 있다 | 맡긴 단계만큼만 직접 한다                           |

코드를 대신 짜지 않습니다. "같이 해 보자"는 사용자가 구현한다는 뜻이고, 직접 쓰는 건 "너가 해 줘"처럼 그 단계를 맡겼을 때뿐입니다.

## 남는 곳

새 파일을 만들지 않고 이미 있는 곳을 씁니다.

- **커밋**: 단계 하나에 커밋 하나. 단계의 "왜"가 남는다.
- **풀이 PR**: 그 드릴의 풀이 PR에 이어서 올린다. PR 본문에 "깊게 판 것" 단락을 더한다.
- **옵시디언 `클린코드`**: 드릴을 넘어 다시 쓸 판단만 남긴다. 유형별 폴더(설계 판단 / 이름과 모양 / 진행 방법)에 넣는다.
- **`나의 기준.md`**: 깊게 판 뒤 기준 한 줄이 생기면 여기에 쓴다. 쓰지 않아도 된다.

## 끝내는 기준

정해진 끝은 없습니다. 이 중 하나면 멈춥니다.

- 리뷰 질문 네 개에 막힘 없이 답할 수 있다.
- 남은 개선이 "관례"뿐이다.
- 그만하고 싶다.

## 반영할 곳 (이 계획을 확정하면)

1. `clean-code-drills.md`의 "일주일의 리듬" 표 아래에 "깊게 파기 (선택)" 단락을 더한다. 루틴을 막지 않는다는 규칙은 "예약 실행"에도 한 줄 넣는다.
2. 코치 스킬(`frontend-code-quality-coach`)에 "깊게 파기" 모드를 더한다. 진단 먼저, 한두 개만, 사용자 구현, 단계별 실행·리뷰·커밋 순서를 적는다.
3. 풀이 PR 본문에 "깊게 판 것" 단락을 쓰는 방법을 정한다. PR 템플릿은 바꾸지 않고 본문 안에서 단락으로 더한다.

## 지금은 하지 않는 것

- **문제를 낼 때 "깊게 팔 거리"를 미리 숨겨 두기**: 10/30의 진단은 사용자의 "지저분하다"는 느낌에서 시작했습니다. 미리 정해 두면 그 느낌을 따라가는 연습이 사라집니다. 고른 드릴에서 팔 거리가 너무 적으면 그때 다시 봅니다.
- **복잡도별 난이도 단계**: 얽힌 축의 수(화면 하나 → 화면 여러 개 → 공유 상태와 시간 축)로 난이도를 나눌 수 있지만, 깊게 파기를 두세 번 해 본 뒤에 정합니다.
- **따로 폴더를 두는 새 트랙**: 드릴 폴더와 풀이 PR로 충분한지 먼저 봅니다.
