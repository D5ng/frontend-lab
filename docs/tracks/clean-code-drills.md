# Clean Code Drills

daily-frontend에서 한꺼번에 섞여 나오던 설계 판단을 기법 하나씩 떼어 내 연습하는 트랙입니다. 목표는 문제를 많이 푸는 것이 아니라 **복합 문제를 만났을 때 꺼내 쓸 나만의 기준**을 만드는 것입니다.

## 왜 이렇게 하나

daily 문제가 어려웠던 이유는 두 가지가 겹쳐서입니다.

1. **지식이 비어 있는 채로 판단을 요구받았다.** "응집도를 높여라"라는 말을 들어도 응집도가 무엇이고, 어떤 신호가 보이면 낮은 것인지 모르면 판단할 근거가 없습니다.
2. **한 문제에 여러 판단이 섞여 있었다.** 비동기 상태, 화면 분리, 규칙 위치, 폴더 구조가 한 번에 나오니 무엇을 기준으로 골랐는지 스스로도 설명하기 어렵습니다.

그래서 대부분의 날에는 **지식을 먼저 읽고, 기법 하나만 적용하고, 변경으로 확인**하는 드릴을 풉니다. 일주일에 한 번은 그동안 쌓은 기준을 들고 **요구사항 분석부터 페이지 하나를 끝까지** 만드는 과제를 풉니다.

## 일주일의 리듬

요일에 묶지 않습니다. 드릴 여섯 번, 과제 한 번이 한 바퀴입니다.

| 언제                    | 분량             | 무엇을                                               |
| ----------------------- | ---------------- | ---------------------------------------------------- |
| 매일                    | 브리핑 7개, 12분 | 클린 코드 처방 3개 + 생각하는 법 1개 + 기본기 3개    |
| 드릴 날 (한 바퀴에 6번) | 3문제, 각 30분   | 기법 하나를 지식 → 리마인드 → 적용 → 확인 순서로     |
| 과제 날 (한 바퀴에 1번) | 1문제, 2~3시간   | 사용자 목적만 받고 요구사항 분석부터 페이지 완성까지 |

- 드릴을 여섯 번 풀면 다음은 과제입니다. 과제를 풀면 다시 드릴 여섯 번이 시작됩니다.
- 날짜가 아니라 푼 횟수로 셉니다. 바쁜 날을 건너뛰어도 순서가 꼬이지 않고, 과제가 원치 않는 요일에 떨어져도 하루 미루면 그만입니다.

## 드릴: 하루 3문제

### 하루의 흐름

| 순서   | 역할                                          | 분량              |
| ------ | --------------------------------------------- | ----------------- |
| 지식   | 개념, 낮을 때 보이는 신호, 흔한 오해          | 읽기 5분          |
| 문제 1 | **리마인드**: 작은 코드로 개념을 손에 붙인다  | 15~20분, 순수 TS  |
| 문제 2 | **적용**: 앱 화면 하나에 같은 기법을 쓴다     | 30분, React + MSW |
| 문제 3 | **확인**: 내 판단이 변경 앞에서 버티는지 본다 | 20~30분           |
| 기준   | `나의 기준.md`에 한 줄                        | 2분               |

역할 순서는 고정하고, **문제 유형은 매일 바꿉니다.** 같은 "시작 코드 정리하기"만 반복하면 기법이 아니라 그 유형의 요령이 늘기 때문입니다.

### 문제 유형

| 유형      | 하는 일                                                            | 주로 쓰는 자리 |
| --------- | ------------------------------------------------------------------ | -------------- |
| 리팩터링  | 동작하는 코드를 테스트를 지키며 정리한다                           | 1, 2           |
| 직접 구현 | 요구사항과 API만 받고 처음부터 만든다                              | 2              |
| 설계 먼저 | 코드 전에 상태·책임 표를 쓰고, 그다음 작게 구현한다                | 2              |
| 비교 판단 | 같은 기능의 두 구현 A·B 중 주어진 변경에 강한 쪽과 근거를 쓴다     | 1, 3           |
| 코드 리뷰 | 동료의 PR diff를 읽고 리뷰 코멘트 두세 개를 쓴다. 코드는 안 고친다 | 1, 3           |
| 버그 추적 | 규칙이 흩어져서 생긴 버그를 재현하고, 다시 안 생기게 고친다        | 3              |
| 변경 요청 | 이전 문제 결과 위에 기획 변경을 구현한다                           | 3              |

출제 규칙

- 하루 세 문제는 서로 다른 유형을 쓴다.
- 전날과 같은 유형 조합을 내지 않는다.
- 일주일에 직접 구현이 최소 한 번, 코드 리뷰나 비교 판단이 최소 한 번 들어간다.

### 기법 주머니 (1단계 · 기법 하나씩)

정해진 순서 없이, 매일 아래 주머니에서 기법 하나를 무작위로 뽑습니다.

| 기준          | 기법                                                        |
| ------------- | ----------------------------------------------------------- |
| 비즈니스 로직 | 무엇이 비즈니스 로직이고 무엇이 화면 로직인지 구분하기      |
| 비즈니스 로직 | 계산 규칙을 컴포넌트 밖 순수 함수로 꺼내기                  |
| 비즈니스 로직 | 사용자 행동의 흐름(검증 → 요청 → 결과 처리)을 화면에서 떼기 |
| 응집도        | 함께 바뀌는 것을 함께 두기                                  |
| 상태          | 상태의 원본과 계산하면 되는 값 구분하기                     |
| 상태          | 서버 상태와 화면 상태 구분하기 (커스텀 훅)                  |
| 추상화        | 구현 상세 감추기 (무엇을 하는지만 보이게)                   |
| 추상화        | 한 컴포넌트 안에서 추상화 높이 맞추기                       |
| 추상화        | 잘못된 추상화 되돌리기 (너무 일찍 합친 컴포넌트·훅)         |
| 결합도        | 서버 응답 모양과 화면이 쓰는 모양 분리하기                  |
| 결합도        | 데이터를 가져오는 곳과 보여 주는 곳 나누기                  |
| 결합도        | Props Drilling을 조합과 Context로 비교하기                  |
| 확장성        | 늘어나는 분기를 객체 매핑으로 바꾸기                        |
| 확장성        | 조합으로 변형 늘리기 (children, 슬롯)                       |
| 공통화        | 중복을 허용할 때와 합칠 때                                  |

뽑는 규칙

- 뽑은 기법은 주머니에서 뺍니다. 주머니가 비면 다시 다 채웁니다. 그래야 무작위여도 한 기법만 계속 나오거나 오래 안 나오는 일이 없습니다.
- 기록을 보고 기법을 다르게 이해한 흔적이 있으면 그 기법을 주머니에 다시 넣습니다. 바로 다음 날이 아니라 며칠 뒤 다른 화면으로 다시 만나게 됩니다. 잊을 만할 때 다시 보는 쪽이 기준으로 남기 쉽습니다.
- 도메인과 화면도 기법과 따로 무작위로 고릅니다. 규칙은 아래 [도메인](#도메인)에 있습니다.
- 이미 낸 기법은 드릴 폴더 `knowledge.md` 첫 줄의 기법 이름과 `[Drill]` PR 제목으로 확인합니다.

순서가 없으니 "잘못된 추상화 되돌리기"가 "구현 상세 감추기"보다 먼저 나올 수도 있습니다. 괜찮습니다. 문제마다 지식 설명이 따로 붙어 있어서 앞 기법을 몰라도 풀 수 있게 냅니다.

비즈니스 로직 분리는 한 번에 다루기엔 커서 세 장으로 나눴습니다. "어디까지가 비즈니스 로직인가"를 모르면 무엇을 꺼낼지 정할 수 없고, 계산을 꺼내는 일과 흐름을 떼는 일은 꺼낸 뒤의 모양이 다르기 때문입니다. 계산은 입력을 받아 값을 돌려주는 순수 함수가 되고, 흐름은 요청과 실패 처리가 들어간 함수나 훅이 됩니다.

### 그다음

- **2단계 · 두 기법이 부딪히는 문제**: 주머니를 한 바퀴 다 돌고 나면 섞기 시작합니다. "규칙을 한곳에 모으면(응집도) 그 모듈을 여러 화면이 알게 된다(결합도)"처럼 1단계 기준 두 개가 다른 답을 내는 장면입니다. `나의 기준.md`가 판단 근거가 됩니다.
- **3단계 · daily로 돌아가기**: `legacy/daily-frontend`에서 이미 푼 문제를 다시 읽고, 어떤 기법이 섞여 있었는지 먼저 나눈 뒤 드릴이나 과제로 다시 냅니다.

## 과제: 페이지 하나를 끝까지

채용 과제처럼 페이지 하나를 혼자 설계하고 완성하는 유형입니다. **화면은 다 그려진 채로 주고, 동작은 하나도 주지 않습니다.**

| 주는 것                                                                                                              | 주지 않는 것                                  |
| -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 사용자의 최종 목적, 화면 흐름, 기획 메모                                                                             | 상태, 요청, 규칙 계산                         |
| **모든 화면의 UI**: SEED 컴포넌트와 Stackflow로 그린 화면, 예시 값이 박힌 목록·입력·결과                             | 이벤트 핸들러의 내용 (`() => {}`로 비워 둔다) |
| **다른 상태의 UI**: 빈 결과, 오류, 결과 화면처럼 처음엔 안 보이는 부분은 주석으로 넣고 언제 보여 줄지 한 줄로 적는다 | 폴더 구조와 컴포넌트 나누기                   |
| 모의 API (MSW)                                                                                                       | 테스트                                        |

UI를 다 주는 이유는 과제의 주제가 화면 그리기가 아니라 **그려진 화면 뒤에 상태와 규칙을 어떻게 놓을지**이기 때문입니다. 실제 채용 과제도 이 모양으로 옵니다. 받은 화면 파일을 그대로 쓸지, 나눌지, 옮길지는 직접 정합니다.

1. 요구사항 분석을 `note.md`에 먼저 쓴다: 사용자의 목적, 행동 순서, 기능별 입력과 출력, 저장할 값과 계산할 값, 반드시 지킬 규칙, 역할과 책임
2. 그려진 화면에 동작을 붙여 끝까지 완성한다: 로딩·오류·빈 상태 포함
3. 행동 테스트를 직접 쓴다
4. 직전 드릴 여섯 번 동안 쌓은 `나의 기준.md`에서 실제로 쓴 기준에 표시한다

요구사항은 "상태", "파생 값" 같은 말 없이 기획자 말투의 메모로 줍니다. 메모를 규칙으로 바꾸는 것까지가 과제입니다. 과제는 하루로 끝내고, 이어지는 변경 요청은 필요해지면 그때 다시 넣습니다.

샘플: [동네 미용실 예약](./clean-code-drills-assignment-sample.md)

주제 예시: 미용실 예약, 대출 상환 계산기, 항공권 좌석·수하물 선택, 모임 일정 투표, 구독 요금제 변경, 중고거래 판매글 작성, 병원 진료 접수, 택시 호출과 요금 안내.

## 매일 브리핑: 읽기만 하는 12분

문제를 푸는 시간과 별개로, 매일 아침 가볍게 읽을 짧은 글 일곱 개를 받습니다. 풀 것도 쓸 것도 없습니다. 출퇴근길에 휴대폰으로 읽을 수 있는 분량이 기준입니다.

샘플: [브리핑 하루치](./clean-code-drills-brief-sample.md)

### 받는 곳과 남는 곳

- **받기**: Claude 데스크톱의 예약 작업이 매일 아침 실행되면 사이드바에 새 세션이 생기고, 그 세션이 오늘 브리핑을 파일 카드로 띄웁니다. 데스크톱 옆 패널에서 바로 읽고, 다른 기기에서 앱을 보고 있으면 거기서도 읽습니다.
- **남기기**: 저장소 루트의 `briefs/YYYY-MM-DD.md`에 하루 한 파일로 쌓습니다. 다음 날 브리핑을 만들 때 이전 파일을 읽고 같은 주제를 피합니다.
- **커밋**: 예약 작업은 파일만 만들고 커밋하지 않습니다. 모아서 커밋할지는 그때 정합니다.
- 예약 작업은 앱이 켜져 있을 때 실행됩니다. 아침에 앱이 꺼져 있었다면 다음에 앱을 열 때 실행됩니다.

### 클린 코드 처방 3개

"이런 상황에서는 이렇게 하면 좋다"를 한 장씩 보여 줍니다. 한 장의 모양은 항상 같습니다.

1. **상황**: 흔히 보는 코드 5~10줄
2. **처방**: 바꾼 코드 5~10줄과 처방의 이름
3. **왜**: 한두 줄
4. **안 해도 되는 때**: 한 줄. 처방은 규칙이 아니라 선택지라서, 언제 쓰지 않는지가 같이 있어야 기준이 됩니다.

다루는 범위: 조건문, 함수와 인자, 상태와 파생 값, 컴포넌트 props, 훅, 비동기와 에러 처리, 타입으로 막기, 비즈니스 로직 위치, 테스트하기 좋은 모양.

예시 목록 (처음 몇 주 분량이고, 쓰면서 늘립니다)

- 중첩된 if → 먼저 빠져나가기(가드 절)
- boolean 인자로 동작이 갈리는 함수 → 함수 둘로 나누기
- 인자가 네 개 이상 → 객체 하나로 받기
- boolean props가 늘어나는 컴포넌트 → 선택지(variant) 하나로
- useEffect로 다른 state를 맞춰 주기 → 렌더링 중에 계산하기
- `isLoading`, `isError`, `data`가 따로 노는 상태 → 판별 유니온 하나로
- 화면마다 반복되는 null 확인 → 데이터가 들어오는 경계에서 한 번 변환하기
- try 안에 너무 많은 코드 → 실패할 수 있는 곳만 감싸기
- switch가 여러 파일에 반복 → 객체 매핑으로 한곳에
- 주석으로 설명하는 코드 → 설명을 함수나 변수로 옮기기
- 클릭 핸들러 안의 할인 계산 → 계산을 순수 함수로 꺼내기
- 저장 중 두 번 눌리는 버튼 → 진행 상태로 막기

출제 규칙

- 세 장 중 하나는 **전날 푼 드릴 기법과 이어지는 처방**으로 냅니다. 푼 다음 날 읽으면 복습이 되고, 풀기 전에 답을 보는 일이 없습니다.
- 그날 드릴의 정답이 되는 처방은 그날 내지 않습니다.

### 생각하는 법 1개

처방이 "코드를 이렇게 바꾼다"라면, 이쪽은 **코드를 쓰기 전에 머릿속에서 무엇을 묻는가**입니다. 주제는 두 갈래를 번갈아 냅니다.

| 갈래                     | 다루는 것                                                                                                                                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기획을 코드로 옮기기     | 기획 문장에서 정책 찾기, 한 문장에 든 정책 여러 개 가르기, 정책과 화면 문구 구분, 정책 값이 오는 곳(고정·서버·사용자), 경계값(이상·초과, 포함·제외)을 기획자에게 묻기, 정책끼리 겹칠 때 우선순위, 정책을 테스트 이름으로 쓰기                                    |
| 문제를 풀 때의 사고 방식 | 구현 전 5분 정리(목적 → 행동 순서 → 저장할 값과 계산할 값 → 규칙 → 책임), 시스템 말이 아니라 사용자 질문으로 다시 읽기, 가장 쉬운 기능 하나부터 쌓기, 막혔을 때 시간 순서로 화면 따라가기, 실패·빈 상태·두 번 누르기부터 떠올리기, 모르는 결정은 미루고 기록하기 |

한 장의 모양

1. **장면**: 기획 메모 한두 줄이나 막히는 순간 하나
2. **생각 순서**: 3~4단계. 각 단계는 사람이 실제로 묻는 질문으로 씁니다("이 숫자가 내일 바뀌면 어디를 고치지?").
3. **코드로 옮기면**: 필요할 때만 몇 줄
4. **한 줄 요약**

하나만 내는 이유는 다른 두 갈래보다 한 장이 길기 때문입니다. 읽어 보고 더 원하면 늘립니다.

### 기본기 3개

질문 하나에 짧은 답 하나입니다. 한 개에 1~2분.

1. **질문**: 실무에서 실제로 궁금해지는 한 줄 ("setState를 세 번 불렀는데 왜 1만 오르지?")
2. **답**: 3~5줄, 필요하면 코드 몇 줄
3. **실무에서 만나는 장면**: 한 줄

| 영역       | 예시 주제                                                                           |
| ---------- | ----------------------------------------------------------------------------------- |
| JavaScript | 클로저, 이벤트 루프, this, 얕은 복사와 깊은 복사, 비교(`==`, `Object.is`), Promise  |
| TypeScript | 타입 좁히기, 판별 유니온, 제네릭, `unknown`과 `any`, `satisfies`, 유틸리티 타입     |
| React      | 리렌더링 조건, key, state 스냅샷, effect 의존성, 메모이제이션이 필요한 때, Suspense |
| Next.js    | 서버·클라이언트 컴포넌트, 캐싱과 재검증, 라우트 핸들러, 서버 액션, 메타데이터       |
| 네트워크   | HTTP 메서드와 상태 코드, 캐시 헤더, CORS, 쿠키·세션·토큰, HTTPS, DNS                |
| 브라우저   | 렌더링 과정, 이벤트 위임, 저장소(localStorage·쿠키), 접근성 기본                    |

출제 규칙

- 하루 세 개는 서로 다른 영역에서 고릅니다.
- 이미 낸 주제는 다시 내지 않습니다. 같은 주제를 더 깊게 볼 때만 "2편"으로 냅니다.
- 버전에 따라 답이 바뀌는 주제(특히 Next.js와 React)는 어느 버전 기준인지 적고, 공식 문서를 확인한 뒤 씁니다.

## 도메인

같은 기법도 도메인이 바뀌면 다르게 보입니다. 배달 앱에서 익힌 "함께 바뀌는 것을 함께 두기"를 금융 앱에서 다시 만나면, 그때 기법이 요령이 아니라 기준이 됩니다. 그래서 도메인을 넓게 돌립니다.

| 도메인 군   | 대표 장면                                      | 그 도메인이 자연스럽게 만드는 설계 질문     |
| ----------- | ---------------------------------------------- | ------------------------------------------- |
| 커머스      | 장바구니, 옵션 선택, 쿠폰, 결제 수단           | 할인 규칙은 어디에 모이나, 분기가 늘어난다  |
| 배달·외식   | 메뉴 담기, 최소 주문, 배달팁, 주문 추적        | 서버가 준 정책 값과 계산 규칙의 자리        |
| 금융        | 송금, 가계부, 대출·적금·환율 계산기, 카드 실적 | 금액 반올림·한도 같은 규칙, 숫자 입력 처리  |
| 여행·숙박   | 날짜 범위 선택, 인원, 숙소 필터, 항공 좌석     | 날짜 계산, 검색 조건과 서버 상태의 경계     |
| 예약        | 미용실, 병원, 운동 수업, 식당                  | 시간 겹침, 마감 충돌, 선택이 바뀔 때의 처리 |
| 모빌리티    | 택시 호출, 킥보드, 주차, 이용 내역             | 요금 구간, 진행 상태가 여러 단계인 화면     |
| 티켓·공연   | 좌석 선택, 대기열, 예매 내역                   | 선택 제한, 실시간으로 바뀌는 서버 값        |
| 커뮤니티    | 피드, 댓글, 알림함, 모임                       | 목록 아이템 변형, 좋아요의 낙관적 반영      |
| 채용·교육   | 공고 목록, 지원서, 강의 수강, 출석             | 긴 폼의 단계 나누기, 같은 카드의 다른 쓰임  |
| 부동산·중고 | 매물 상세, 판매글 작성, 가격 제안              | 서버 응답과 화면 모양, 사진 첨부와 검증     |
| 헬스케어    | 복약 알림, 진료 접수, 걸음 수 기록             | 반복 일정 규칙, 켜고 끄는 설정의 저장 시점  |
| 생산성      | 할 일, 캘린더, 메모, 습관 기록                 | 원본과 파생 값, 정렬·필터 조합              |
| 구독·멤버십 | 요금제 변경, 해지 방어, 혜택 안내              | 요금제별 분기, 날짜 기준 일할 계산          |

출제 규칙

- 드릴 하루 안에서 문제 1과 문제 2는 다른 도메인을 쓴다. 문제 3은 문제 2를 이어받는다.
- 같은 도메인 군은 한 바퀴(드릴 여섯 번 + 과제 한 번)에 두 번까지만 쓴다. 과제는 직전 드릴 여섯 번에 안 쓴 도메인에서 고른다.
- 도메인은 표에 없어도 된다. 표는 "늘 같은 장면만 나오지 않게" 하려는 목록이지 제한이 아니다.
- 실제 서비스처럼 만들되 특정 회사의 화면이나 문구를 그대로 옮기지 않는다.

## 앱 화면과 SEED

모든 화면은 **모바일 앱의 한 화면**처럼 만듭니다. 웹 페이지처럼 위에서 아래로 폼을 늘어놓지 않습니다.

- 상단 앱 바, 하단 고정 버튼, 바텀시트, 탭, 스낵바처럼 앱에서 쓰는 화면 틀을 씁니다.
- 지금 문제들은 SEED 컴포넌트 90여 개 중 TextField, List, RadioGroup, Select, ActionButton 위주로 열 개 남짓만 썼습니다. 앞으로는 화면이 자연스럽게 필요로 하는 컴포넌트를 넓게 고릅니다.

| 화면 장면                  | 어울리는 SEED 컴포넌트                              |
| -------------------------- | --------------------------------------------------- |
| 목록 위 필터               | ChipTabs, ControlChip, SegmentedControl, TagGroup   |
| 선택지가 많은 입력         | BottomSheet, MenuSheet, ActionSheet, SelectBox      |
| 날짜·시간·수량             | DatePicker, TimePicker, WheelPicker, QuantityPicker |
| 사진 첨부                  | AttachmentInput, AttachmentDisplay, ImageFrame      |
| 켜고 끄는 설정             | Switch, ToggleButton                                |
| 되돌릴 수 있는 결과 / 확인 | Snackbar, Dialog, ContentDialog                     |
| 피드                       | PullToRefresh, Fab, Skeleton, ReactionButton        |
| 사람·신뢰 표시             | Avatar, MannerTemp, MannerTempBadge, Badge          |
| 안내                       | Callout, InlineBanner, PageBanner, HelpBubble       |
| 범위 조절                  | Slider                                              |

출제 규칙

- 문제마다 `problem.md`에 쓴 SEED 컴포넌트를 적는다.
- 같은 핵심 컴포넌트 조합을 이틀 연속 쓰지 않는다.
- 학습 질문을 가릴 만큼 컴포넌트를 억지로 넣지 않는다. 컴포넌트는 화면 장면에서 고른다.
- 앱 바와 화면 전환은 SEED의 Stackflow 연동(`AppScreen`, `AppBar`)으로 만든다. 쓰는 법은 [Drills README](../../labs/drills/README.md#앱-화면-stackflow)에 있다.

## 폴더

드릴과 과제는 서로 다른 앱입니다. 문제 폴더 이름 앞에 날짜를 붙입니다. 이전 방식의 실습(`daily-frontend`, `code-quality`)은 `legacy/`에 보관만 합니다.

```text
labs/
  drills/problems/                       드릴 앱
    2026-11-02-change-together/          하루 한 폴더
      knowledge.md                       첫 줄 제목이 기법 이름
      problem-1/  problem-2/  problem-3/   문제마다 problem.md와 note.md
  assignments/problems/                  과제 앱
    2026-11-08-salon-booking/            과제 하나
      problem.md
      handlers.ts
      App.tsx                            이 약속 하나만 지키고 구조는 자유
      note.md
docs/나의 기준.md                         드릴과 과제를 잇는 곳
```

- **드릴과 과제를 나누는 이유**: 생김새가 다릅니다. 드릴은 시작 코드와 테스트가 있는 문제 세 개이고, 과제는 메모만 있는 문제 하나입니다. 과제는 폴더 구조를 정하는 것부터가 풀이라서, 정해진 틀이 적은 앱에 따로 둡니다.
- **이어지는 것은 같은 폴더에**: 문제 3은 문제 2를 이어받으니 같은 날 폴더에 둡니다.
- **둘을 잇는 것은 폴더가 아니라 `나의 기준.md`**: 드릴에서 기준을 한 줄씩 쌓고, 과제에서 실제로 쓴 기준에 표시합니다.
- **날짜를 앞에 두는 이유**: 이름순으로 정렬하면 한 바퀴가 모여 보입니다. 특정 기법만 모아 보려면 `knowledge.md` 첫 줄의 기법 이름으로 검색합니다.
- **등록 파일이 없습니다**: 두 앱 모두 문제 폴더를 자동으로 찾습니다. 문제마다 Draft PR이 따로 열리므로, 한 파일에 목록을 적으면 PR끼리 충돌하기 때문입니다.
- 폴더 이름은 영어로 씁니다. 화면 주소와 import 경로에 그대로 쓰이기 때문입니다. 문제마다 용어집이 붙으니 이름 짓기가 막히면 거기서 고릅니다.

## 예약 실행

2026-10-30에 둘 다 등록했습니다.

| 시간 | 예약                     | 하는 일                                   |
| ---- | ------------------------ | ----------------------------------------- |
| 7:30 | `frontend-daily-problem` | 드릴 또는 과제를 만들어 Draft PR로 올린다 |
| 8:00 | `frontend-daily-brief`   | 브리핑을 `briefs/날짜.md`로 만든다        |

문제를 브리핑보다 먼저 내는 이유는 브리핑이 오늘 드릴의 기법을 처방으로 내지 않기 위해서입니다. 문제 예약은 사용자가 풀고 있는 체크아웃을 건드리지 않도록 git worktree에서 문제를 만듭니다.

- **매일 아침 · 브리핑**: 하루치(클린 코드 처방 3개 + 생각하는 법 1개 + 기본기 3개)를 만든다. 문제와 달리 전날 기록이 비어 있어도 만든다. 읽기만 하는 것이라 밀려도 부담이 쌓이지 않는다.
- **매일 아침 · 문제**: 마지막 과제 뒤로 드릴이 여섯 개 쌓였으면 과제 1개를, 아니면 기법 주머니에서 하나를 뽑아 드릴(지식 + 문제 3개)을 만든다. 예약 작업 하나가 둘 중 무엇을 낼지 정한다.
- 마지막으로 낸 드릴의 기록이 비어 있으면 새 드릴을 만들지 않는다. 밀린 문제가 쌓이면 다시 "어렵다"로 돌아가기 때문이다.
- **과제는 드릴을 막지 않는다.** 드릴은 하루 루틴이라서, 과제가 남아 있거나 과제 기록이 비어 있어도 드릴은 그대로 낸다. "오늘 이미 냈는가"도 드릴은 드릴끼리, 과제는 과제끼리 센다.
- 전날 기록에서 기법을 다르게 이해한 흔적이 있으면 그 기법을 주머니에 다시 넣는다.
- 정답 코드와 힌트는 만들지 않는다.
- **문제를 내면 항상 Draft PR로 올린다.** develop에서 `feature/YYYY-MM-DD-slug` 브랜치를 만들어 커밋하고, 푸시한 뒤 develop을 향한 Draft PR을 연다. 제목은 드릴이면 `[Drill] MM/DD 기법 이름`, 과제면 `[Assignment] MM/DD 과제 이름`이다. 풀이는 그 PR 브랜치에서 이어 한다.
- 드릴 수와 마지막 기록은 develop만이 아니라 아직 열려 있는 드릴·과제 Draft PR 브랜치까지 함께 보고 센다. 풀이가 합쳐지기 전에는 기록이 PR 브랜치에만 있기 때문이다.
