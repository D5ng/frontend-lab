# React 설계 학습 원칙

좋은 설계는 폴더 수, 컴포넌트 길이, 중복 제거율로 판정하지 않는다. 요구사항이 바뀔 때 어떤 코드가 왜 변경되는지 설명하고, 그 영향 범위를 예측할 수 있는지를 본다.

## 구현 전 질문

1. 사용자가 달성하려는 목적은 무엇인가?
2. 화면에서 관찰할 수 있는 행동은 무엇인가?
3. 정보의 원본은 서버, URL, 현재 UI 중 어디인가?
4. 다른 값으로 계산할 수 있는데 별도 상태로 저장한 값은 없는가?
5. 비즈니스 규칙과 UI 표현 규칙은 무엇인가?
6. 지연, 실패, 중복 요청과 같은 예외 상황은 무엇인가?
7. 현재 예상하는 책임 경계는 무엇이며, 어떤 가정에 의존하는가?

예상 경계는 정답이 아니라 첫 번째 가설로 기록한다.

## 책임과 변경 이유

컴포넌트와 모듈의 책임은 한 문장으로 설명한다. 설명에 서로 다른 사용자 흐름이나 정책 결정이 함께 등장하면 분리 여부를 검토한다.

코드를 묶는 기준은 같은 화면이나 같은 도메인 이름이 아니라 같은 이유로 함께 변경되는지 여부다. 변경 이유에는 도메인 정책, 사용자 흐름, UI, API 계약, 권한, 접근성, 기술 변경이 모두 포함될 수 있다.

## 상태 판단

- 서버가 원본인 데이터는 서버 상태로 취급하고 불필요하게 로컬 상태에 복사하지 않는다.
- 공유, 새로고침, 뒤로가기에 복원되어야 하는 값은 URL 상태 후보로 검토한다.
- 열림 여부나 임시 선택처럼 현재 표현에 필요한 값은 UI 상태로 둔다.
- 다른 값으로 계산할 수 있는 값은 파생 상태로 두고 저장을 피한다.

상태 이름보다 중요한 것은 source of truth를 하나로 유지하는 것이다.

## 추상화와 재사용

중복을 발견한 즉시 공통화하지 않는다.

```text
중복 관찰 → 함께 변경되는지 확인 → 정책적 의미 확인 → 추상화 판단
```

공통화가 함께 수정되어야 할 값을 구조적으로 묶는다면 응집도를 높일 수 있다. 반대로 우연히 비슷한 코드를 묶으면 서로 다른 변경을 결합할 수 있다. 중복 유지와 추상화 모두 상황에 따라 유효한 선택이다.

## 검증과 회고

- 테스트는 사용자의 입력, 선택, 제출, 결과와 같은 행동을 우선한다.
- 첫 구현 뒤에는 기존 설계를 흔드는 요구사항을 하나 이상 추가한다.
- 수정된 파일 수 자체보다 각 파일이 같은 이유로 변경되었는지를 본다.
- 회고에는 처음 판단에서 맞았던 점, 잘못된 전제, 선택하지 않은 대안과 다음 판단 기준을 기록한다.
