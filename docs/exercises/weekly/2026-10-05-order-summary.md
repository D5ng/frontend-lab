# 1주차: 요구사항 변경에 견디는 주문 요약 화면

- 주제: 요구사항 변경
- 예상 시간: 60~75분
- 목표: 정책 하나가 바뀌었을 때 수정할 위치와 영향을 설명할 수 있는 구조를 만든다.
- 서버 요청과 결제 연동은 생략한다.

## 초기 구현 과제

상품 목록에서 수량을 조절하면 상품 합계, 배송비, 최종 결제 금액이 바뀌는 화면을 만든다.

```ts
type CartItem = {
  id: string
  name: string
  unitPrice: number
  quantity: number
}

const initialItems: CartItem[] = [
  { id: 'goods', name: '캐릭터 굿즈', unitPrice: 15_000, quantity: 3 },
  { id: 'gift-card', name: '모바일 상품권', unitPrice: 10_000, quantity: 1 },
]
```

금액은 모두 원 단위 정수다.

- 상품별 수량은 1~10개이며 증가와 감소 버튼으로 변경한다.
- 상품 합계는 각 상품의 `unitPrice × quantity`를 더한 값이다.
- 상품 합계가 20,000원 이상이면 주문할 수 있다.
- 배송비는 3,000원이며 상품 합계가 50,000원 이상이면 무료다.
- 최종 결제 금액은 상품 합계에 배송비를 더한 값이다.
- 주문할 수 없다면 버튼을 비활성화하고 최소 주문 금액까지 부족한 금액을 보여준다.
- 주문 버튼을 누르면 현재 상품 목록과 금액 요약을 화면에 표시한다.
- 이후 수량을 바꿔도 이미 표시된 주문 결과는 그대로 유지한다. 다시 주문하면 새 제출 결과로 교체한다.

완료 조건은 수량 제한이 지켜지고 금액과 버튼 상태가 입력 변경에 따라 일관되게 갱신되는 것이다. 구조는 직접 결정하고 계산값마다 별도 상태가 필요한지 검토한다.

## 초기 구현 이후 적용할 변경 1개

모바일 상품권 금액은 무료 배송 기준 금액에서 제외한다. 상품 합계, 최소 주문 금액 판정, 최종 결제 금액에는 계속 포함한다.

`CartItem`에 상품 종류를 추가한다.

```ts
type ProductKind = 'physical' | 'giftCard'

// CartItem에 추가할 속성
// kind: ProductKind
```

초기 데이터에서 굿즈는 `physical`, 상품권은 `giftCard`로 지정한다. 이 과제에서는 상품권만 주문해도 기본 배송비 규칙을 그대로 적용한다.

| 장바구니 구성 | 상품 합계 | 변경 전 배송비 | 변경 후 배송비 |
| --- | ---: | ---: | ---: |
| 굿즈 45,000원 + 상품권 10,000원 | 55,000원 | 0원 | 3,000원 |
| 굿즈 60,000원 + 상품권 10,000원 | 70,000원 | 0원 | 0원 |
| 굿즈 15,000원 + 상품권 10,000원 | 25,000원 | 3,000원 | 3,000원 |

마지막 경우에는 변경 후에도 주문할 수 있어야 한다. 무료 배송 기준 금액과 최소 주문 기준 금액을 혼동하지 않는지 확인한다.

추가로 최소 주문 금액 20,000원과 무료 배송 기준 금액 50,000원의 바로 아래, 정확히 같은 값, 바로 위를 계산 수준에서 확인한다. 수량 1과 10에서 제한을 확인하고 제출 이후 수량 변경이 기존 주문 결과에 영향을 주지 않는지 확인한다.

## 리뷰 질문

1. 변경을 적용하면서 어떤 파일과 함수를 수정했는가? 각 수정이 필요한 이유를 설명할 수 있는가?
2. 상품 합계와 무료 배송 기준 금액을 같은 값으로 취급했던 지점은 어디였는가?
3. 배송비 계산과 “무료 배송” 문구를 만드는 코드는 같은 이유로 변경되는가?
4. 계산을 컴포넌트 안에 둘 때와 순수 함수로 분리할 때 각각 읽기 쉬워지는 부분과 번거로워지는 부분은 무엇인가?
5. 현재 장바구니와 주문 결과가 서로 다른 수명을 갖는다는 점을 어떻게 표현했는가?

## 스스로 점검할 판단 기준

- [ ] 최소 주문 정책과 무료 배송 정책을 각각 변경할 수 있다.
- [ ] 정책을 바꿀 때 같은 조건을 여러 곳에서 찾아 수정할 필요가 없다.
- [ ] 상품 합계, 배송비처럼 현재 입력으로 계산할 수 있는 값을 불필요하게 상태로 중복 저장하지 않는다.
- [ ] 제출 시점의 주문 결과는 별도로 보존하며 현재 입력에서 계산하는 요약과 구분한다.
- [ ] 금액 계산이 통화 표시 형식이나 안내 문구에 의존하지 않는다.
- [ ] 분리한 함수나 컴포넌트가 어떤 복잡함을 줄이는지 설명할 수 있다.

함수나 컴포넌트의 개수와 파일 배치는 팀 관례와 설계 선택에 해당한다. 개수를 늘렸다는 사실보다 변경의 영향 범위가 명확해졌는지로 평가한다.

계산을 화면 가까이에 두면 흐름을 한곳에서 읽기 쉽다. 순수 함수로 분리하면 정책을 독립적으로 검증하기 쉽지만 파일 이동과 인자 전달 비용이 생긴다. 실제 변경 이유를 근거로 선택한다.
