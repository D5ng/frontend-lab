# 실습 문제 출제

제품으로서의 화면 설계가 끝난 뒤에 읽는다. 여기서는 그 화면을 학습 문제로 바꾼다.

## 산출물

`labs/code-quality/src/exercises/<번호>-<주제>/`

| 파일 | 내용 | 누가 쓰는가 |
| --- | --- | --- |
| `requirements.md` | 목표, 화면 맥락, 관찰 가능한 요구사항, 상태, 범위 밖, 완료 기준 | 출제자 |
| `Problem.tsx` | 동작하는 스타터 코드. 학습 질문이 드러나는 구조 | 출제자 |
| `Problem.spec.tsx` | 사용자 행동 기준 테스트 | 출제자 |
| `hints.md` | 높은·중간·낮은 추상화 레벨 힌트, 변경 시나리오 | 출제자 |
| `note.md` | 설계 판단 기록 | **실습자.** 대신 쓰지 않는다 |

추가로 `labs/code-quality/README.md`에 실습 절을 넣고, `src/App.tsx`가 새 문제를 렌더링하게 한다.

## 학습 질문 고르기

문제 하나에 학습 질문은 하나다. 기존 문제와 겹치지 않게 고른다.

- 01 같이 실행되지 않는 코드 분리 — 가독성
- 02 임시 저장과 게시의 정책 분리 — 응집도
- 03 파생 상태와 섣부른 공통화 — 응집도·결합도

다음 후보: 예측 가능성(숨은 부수효과, 이름과 실제 동작의 차이), 서버 상태와 화면 상태의 경계, 목록과 상세의 상태 공유, 낙관적 업데이트와 되돌리기.

## 스타터 코드에 질문 심기

스타터는 **동작은 맞고 구조에 판단거리가 있는** 코드다. 버그를 심지 않는다.

좋은 재료

- 파생값을 상태로 두고 여러 곳에서 수동 동기화한다 — 동기화 누락 위험
- 항상 함께 바뀌는 두 값을 따로 보관한다 — 응집도
- 모양이 같지만 규칙이 다른 항목을 나란히 반복한다 — 공통화 판단
- 검증·변환·요청·안내를 한 함수에 담는다 — 책임 분리
- 화면 입력 모델과 서버 도메인 모델을 같은 타입으로 쓴다 — 경계

지켜야 할 선

- 구조가 학습 주제의 정답을 미리 보여 주지 않는다. "묶을 것인가"가 질문이면 스타터가 이미 묶여 있으면 안 된다.
- UX 패턴이 늘면 관리할 상태도 는다. 학습 주제와 무관한 패턴은 넣지 않는다.
- 냄새는 읽히되 과장하지 않는다. 같은 코드 여섯 벌보다, 인자 목록이 모든 것을 알아야 하는 함수 하나가 낫다.

## 테스트 작성

- **사용자에게 관찰되는 것만** 검증한다. 상태 이름, 훅, 파일 구조를 검증하지 않는다. 실습자가 구조를 바꿔도 테스트는 통과해야 한다.
- 쿼리는 role 우선이다. Montage의 role과 접근성 이름은 [카탈로그](montage-catalog.md)에서 확인한다.
- 비동기 작업은 주입한다. 진행 중 상태는 해결되지 않는 Promise, 실패는 거부되는 Promise로 고정한다.

```tsx
function createDeferred() {
  let resolve: (() => void) | undefined
  const promise = new Promise<void>((complete) => {
    resolve = complete
  })
  return { promise, resolve: () => resolve?.() }
}
```

- 날짜·시간처럼 실행 시점에 달라지는 값은 테스트에서 같은 방식으로 계산해 비교한다. 고정 날짜를 하드코딩하지 않는다.
- 테스트 이름은 사용자 문장으로 쓴다. `켜지 않은 조건은 기본 운영 방식으로 저장한다`

## 문서 작성

`requirements.md` 구성

1. **목표** — 사용자 목표 한 문장과 이 실습의 범위
2. **화면 맥락** — 뷰포트, 화면 구조, 패턴 선택 근거
3. **입력과 규칙** — 기본값, 보존 규칙, 검증 순서와 문구를 그대로
4. **상태** — Empty / Loading / Error / Disabled / Success 전이
5. **요청** — 서버로 보내는 데이터 형태
6. **범위 밖** — 하지 않기로 한 것
7. **완료 기준** — 테스트 통과와 구조 자유

`hints.md` 구성

1. **높은 레벨** — 도메인 개념과 사용자 의도. 질문 2~3개
2. **중간 레벨** — 행동, 정책, 책임, 변경 이유. 질문 3~4개
3. **낮은 레벨** — 현재 구현 세부사항. 질문 2~4개
4. **변경 시나리오** — 지금 구조를 시험할 변경 4~5개
5. **답안 요청 방법**

정답 코드를 힌트에 넣지 않는다. 각 레벨은 질문으로 끝난다.

## 검증

```bash
pnpm lint
pnpm format:check
pnpm test
pnpm build
```

명령이 통과해도 끝이 아니다. 375px 뷰포트에서 실제로 띄워 다음을 확인한다.

- 켜기·끄기, 입력, 시트 열기·고르기·적용, 제출, 성공·실패 안내
- 고정 하단 바가 내용을 가리지 않는가
- Toast가 버튼과 겹치지 않는가
- 스크롤 끝에서 잘리는 요소가 없는가
