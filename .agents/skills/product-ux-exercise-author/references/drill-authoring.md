# 드릴 출제

제품으로서의 화면 설계가 끝난 뒤에 읽는다. 여기서는 기법 하나를 하루 세 문제로 바꾼다. 어떤 기법과 유형을 낼지는 `docs/tracks/clean-code-drills.md`가 정한다.

## 산출물

`labs/drills/problems/YYYY-MM-DD-slug/`

| 파일 | 내용 | 누가 쓰는가 |
| --- | --- | --- |
| `knowledge.md` | 첫 줄 `# 기법 이름`. 개념, 낮을 때 보이는 신호, 흔한 오해, 용어집. 5분 분량 | 출제자 |
| `problem-1/` | 리마인드. 순수 TS 함수와 테스트, `problem.md`. 화면 없음 | 출제자 |
| `problem-2/` | 적용. `problem.md`, `Problem.tsx`, 필요하면 `handlers.ts`와 테스트 | 출제자 |
| `problem-3/` | 확인. 유형에 따라 `problem.md`만 있거나 건너뛴 테스트가 함께 있다 | 출제자 |
| `note.md` | 문제마다 질문 하나. 답 칸은 비워 둔다 | **실습자가 답한다** |

- 등록 파일은 없다. `problem-N/Problem.tsx`가 있으면 앱 목록에 자동으로 나온다. 목록 이름은 `problem.md` 첫 줄 제목이다.
- `problem-N/Problem.tsx`는 `Problem` 컴포넌트를 내보낸다.
- `handlers.ts`는 `problems/` 아래 어디에 있든 자동 등록된다. API 경로는 `/api/drills/YYYY-MM-DD/...`처럼 날짜를 넣어 다른 문제와 겹치지 않게 한다.
- Stackflow는 stable API(`@stackflow/react`)로 문제마다 Stack을 만든다. future API는 쓰지 않는다. 이유는 [SEED 카탈로그](seed-catalog.md#앱-화면-stackflow)에 있다.

## 세 문제의 역할

| 문제 | 역할 | 분량 | 코드 |
| --- | --- | --- | --- |
| 1 | 리마인드: 작은 코드로 개념을 손에 붙인다 | 15~20분 | 순수 TS 30~50줄 |
| 2 | 적용: 앱 화면 하나에 같은 기법을 쓴다 | 30분 | React + MSW + Stackflow |
| 3 | 확인: 문제 2의 판단이 변경 앞에서 버티는지 본다 | 20~30분 | 문제 2 코드 위에서 |

- 문제 1과 문제 2는 다른 도메인을 쓴다. 문제 3은 문제 2를 이어받는다.
- 세 문제는 서로 다른 유형을 쓴다. 유형 목록과 돌리는 규칙은 계획 문서를 따른다.

## 유형별 시작 코드

| 유형 | 주는 것 |
| --- | --- |
| 리팩터링 | 동작하는 시작 코드와 이미 통과하는 행동 테스트 |
| 직접 구현 | 요구사항, API, 빈 `Problem.tsx`. 테스트는 행동을 고정할 만큼만 주고 처음엔 `it.skip` |
| 설계 먼저 | 요구사항과 상태·책임 표의 빈 칸. 표를 채운 뒤 작게 구현한다 |
| 비교 판단 | 같은 기능의 두 구현 A·B와 변경 시나리오 하나. 코드는 고치지 않는다 |
| 코드 리뷰 | `problem.md` 안의 diff. 리뷰 코멘트 두세 개를 `note.md`에 쓴다 |
| 버그 추적 | 규칙이 흩어져서 생긴 버그가 있는 코드와 재현 방법. 이 유형만 버그를 심는다 |
| 변경 요청 | 기획 변경 요청과 새 행동을 고정하는 `it.skip` 테스트. 실습자가 skip을 지운다 |

`it.skip`을 쓰는 이유: Draft PR의 CI가 처음부터 빨간색이면 실습자가 무엇을 깨뜨렸는지 구분할 수 없다.

## 시작 코드에 질문 심기

시작 코드는 **동작은 맞고 구조에 판단거리가 있는** 코드다. 버그 추적 유형이 아니면 버그를 심지 않는다.

좋은 재료

- 파생값을 상태로 두고 여러 곳에서 수동 동기화한다
- 항상 함께 바뀌는 값을 여러 곳에 따로 둔다
- 모양이 같지만 규칙이 다른 항목을 나란히 반복한다
- 검증·변환·요청·안내를 한 함수에 담는다
- 서버 응답 모양을 화면이 그대로 쓴다

지켜야 할 선

- 고칠 곳이 이름이나 주석으로 드러나지 않게, 실무에서 흔한 모양으로 쓴다. 숨은그림찾기가 되면 판단이 아니다.
- 구조가 학습 주제의 정답을 미리 보여 주지 않는다.
- 냄새는 읽히되 과장하지 않는다. 같은 코드 여섯 벌보다, 모든 것을 알아야 하는 함수 하나가 낫다.

## `knowledge.md`

1. **개념**: 한 문장 정의와, 그것을 사람의 질문으로 바꾼 한 줄 ("이 정책이 바뀌면 어디를 열어야 하지?")
2. **낮을 때 보이는 신호**: 3~4개
3. **흔한 오해**: 1~2개. 기법을 과하게 쓰는 쪽의 오해를 꼭 넣는다
4. **더 읽을거리**: 있으면 링크 하나
5. **용어집**: 이 도메인에서 쓸 영어 이름. 실습자가 이름 짓기에서 막히지 않게 한다

예시: `docs/tracks/clean-code-drills-day01-sample.md`

## 테스트 작성

- **사용자에게 관찰되는 것만** 검증한다. 상태 이름, 훅, 파일 구조를 검증하지 않는다. 실습자가 구조를 바꿔도 테스트는 통과해야 한다.
- 쿼리는 role 우선이다.
- 서버 응답은 MSW로 준다. 실패와 지연은 테스트 안에서 `server.use(...)`로 핸들러를 덮어 고정한다.
- 날짜·시간처럼 실행 시점에 달라지는 값은 서버 응답의 `now` 같은 값으로 고정한다.
- 테스트 이름은 사용자 문장으로 쓴다. `최소 주문 금액보다 적게 담으면 주문할 수 없다`

## `note.md`

문제마다 질문 하나와 빈 답 칸. 답은 2~3줄을 기대한다는 것만 적는다. 마지막에 `나의 기준.md`에 한 줄 쓰라는 안내를 둔다.

## 검증

```bash
pnpm --filter @frontend-lab/drills lint
pnpm --filter @frontend-lab/drills format:check
pnpm --filter @frontend-lab/drills test
pnpm --filter @frontend-lab/drills build
```

명령이 통과해도 끝이 아니다. 375px 뷰포트에서 문제 2 화면을 띄워 흐름을 직접 눌러 본다.
