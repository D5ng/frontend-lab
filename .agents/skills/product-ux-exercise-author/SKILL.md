# 제품 수준 UX 실습 문제 출제자

이 저장소의 실습 화면은 연습용 목업이 아니다. 실제로 출시된 모바일 앱 수준의 흐름을 먼저 설계하고, 그 화면에 학습 질문을 심어 문제로 만든다.

두 가지를 동시에 만족해야 한다.

- **제품으로서**: 사용자 목표가 분명하고, 한 화면에 하나의 목적이 있으며, 모든 상태가 설계되어 있다.
- **문제로서**: 실습자가 판단해야 할 설계 질문이 코드에 드러나 있다.

## 이 스킬이 맡는 것과 맡지 않는 것

**무엇을 낼지**는 이 스킬이 정하지 않는다. 오늘 드릴인지 과제인지, 어떤 기법을 뽑을지, 어떤 도메인과 문제 유형을 쓸지, 브랜치와 Draft PR을 어떻게 올릴지는 `docs/tracks/clean-code-drills.md`를 따른다. 규칙을 이 스킬에 옮겨 적지 않는다. 두 곳에 있으면 어긋난다.

이 스킬은 **정해진 문제를 제품 수준으로 잘 만드는 법**만 맡는다.

## 진행 순서

순서를 건너뛰지 않는다. 특히 1~2단계를 생략하고 컴포넌트부터 고르지 않는다.

1. **사용자 목표를 한 문장으로 쓴다.** 누가, 어떤 상황에서, 무엇을 끝내려고 이 화면에 왔는가. 목표가 둘 이상이면 화면을 나눈다.
2. **흐름을 설계한다.** [UX 원칙](references/ux-principles.md)을 읽고 List → Detail → Action 구조를 먼저 검토한다. 한 화면에 모든 정보를 펼치지 않는다.
3. **패턴을 고른다.** 같은 문서의 패턴 선택 기준으로 바텀시트, 다이얼로그, 스낵바, 인라인 중 무엇을 쓸지 정하고, **왜 그 패턴인지 한 줄로 적는다.** 설명하지 못하면 고르지 않는다.
4. **상태를 설계한다.** [화면 상태 설계](references/screen-states.md)로 Empty, Loading, Error, Disabled, Success를 빠짐없이 정한다. 이 단계를 건너뛴 화면은 제품이 아니다.
5. **컴포넌트를 매핑한다.** [SEED 카탈로그](references/seed-catalog.md)에서 실제 export 이름과 props, 스니펫이 있는지 확인한다. 추측하지 않는다.
6. **문제로 전환한다.**
   - 드릴이면 [드릴 출제](references/drill-authoring.md)
   - 과제면 [과제 출제](references/assignment-authoring.md)

## 설계 검토 체크

구현을 시작하기 전에 스스로 답한다. 하나라도 막히면 1단계로 돌아간다.

- 이 화면의 주요 목적은 하나인가? 하단 주 버튼이 그 목적과 일치하는가?
- 처음 진입한 사용자에게 지금 필요 없는 정보를 보여 주고 있지 않은가?
- 각 UX 결정에 "왜 이 패턴인가"를 한 줄로 설명할 수 있는가?
- Empty, Loading, Error, Disabled 상태에서 화면이 무엇을 보여 주는가?
- 실제로 쓰이는 앱에서 이 흐름을 본 적이 있는가? 없다면 왜 여기서는 다른가?

## 구현 규칙

- SEED 컴포넌트와 토큰을 우선 사용한다. 커스텀 CSS는 레이아웃 배치(고정 바, 여백)에 한정하고, 색·타이포·간격은 토큰으로 해결한다.
- 화면 틀과 이동은 Stackflow의 `AppScreen`, `AppBar`로 만든다. 웹 페이지처럼 위에서 아래로 폼을 늘어놓지 않는다.
- 모든 화면은 너비 375px 뷰포트를 기준으로 구현하고 검증한다.
- 한국어 UI 문구는 `~해요` 체를 쓰고, 오류 문구는 사용자가 다음에 할 행동을 담는다.
- 화면을 구성하는 방식이 학습 주제의 정답을 미리 드러내서는 안 된다. "이 셋은 같은 구조다"라는 판단이 학습 질문이라면, 시작 코드가 이미 공통 컴포넌트로 묶여 있으면 안 된다.
- 특정 회사의 화면, 문구, 채용 과제를 그대로 옮기지 않는다.

## 하지 않을 것

- 실습자의 풀이를 코칭하거나 리뷰하지 않는다. 그 역할은 `frontend-code-quality-coach`가 맡는다.
- 정답 코드와 힌트를 만들지 않는다. 막히면 실습자가 채팅으로 묻는다.
- 실습자가 쓸 기록(`note.md`)의 답을 대신 쓰지 않는다. 질문이나 빈 제목만 둔다.
- 사용자 목표와 흐름을 정하기 전에 컴포넌트 목록부터 나열하지 않는다.
- 실제로 확인하지 않은 SEED props나 export 이름을 쓰지 않는다. 설치된 패키지의 타입 선언이 근거다.
- 학습 주제와 무관한 복잡성을 UX 명분으로 추가하지 않는다. 패턴 하나마다 관리할 상태가 늘어난다.
- `legacy/` 아래 파일을 고치지 않는다.

## 완료 기준

- 화면이 사용자 목표 한 문장, 패턴 선택 근거, 다섯 가지 상태 설계를 문서로 갖는다.
- 해당 앱의 `lint`, `format:check`, `test`, `build`가 통과한다.
- 375px 뷰포트에서 실제로 렌더링해 확인했다.
