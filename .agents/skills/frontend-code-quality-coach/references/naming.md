# 네이밍 검토

구조를 리뷰할 때 이름도 함께 본다. 이름은 가독성과 예측 가능성의 첫 번째 단서이고, 잘못된 이름은 잘못된 경계를 드러내는 경우가 많다.

## 판단 기준

### 1. 도메인의 말로 부르는가

일반적인 단어보다 이 기능에서 맡은 역할을 드러내는 이름이 낫다.

- `useProducts`는 상품 조회처럼 읽힌다. 장바구니의 수량 변경과 합계를 다룬다면 `useCart`, 목록만 다룬다면 `useCartItems`처럼 범위를 드러낸다.
- `data`, `info`, `list`, `handleChange`처럼 무엇이든 담을 수 있는 이름은, 담긴 것이 무엇인지 드러나는 이름으로 바꿀 수 있는지 본다.

### 2. 한 개념에 한 단어를 쓰는가

같은 개념을 여러 이름으로 부르면 읽는 사람은 서로 다른 개념이라고 오해한다.

- 타입은 `CartProduct`, 컴포넌트는 `CartProductItem`, CSS와 `id`는 `cart-item`처럼 한 개념이 여러 이름을 가지면 하나로 맞춘다.
- 개념 자체가 다른지도 확인한다. 이름·가격처럼 어디서나 같은 **상품**과, 수량처럼 담긴 곳에만 있는 **장바구니 항목**은 다른 개념이다. 속성(`quantity`)이 어느 개념에 속하는지 보면 구분된다.

### 3. 이름이 약속한 대로 동작하는가

이름만 보고 예상한 동작과 실제 동작이 다르면 예측 가능성 문제다.

- `formatPrice`가 쉼표만 찍고 `원`은 호출부에서 붙인다면, 이름보다 덜 하는 함수다.
- `getUser`가 조회처럼 보이는데 상태를 바꾸거나 요청을 보낸다면, 이름보다 더 하는 함수다.
- 훅·컴포넌트 이름이 실제 책임보다 좁거나 넓지 않은지 본다.

### 4. 값과 행동을 구분하는가

- 행동(부수효과, 상태 변경)은 동사: `increaseQuantity`, `submitOrder`
- 값은 명사: `updatedItems`(바뀐 목록), `totalPrice`
- 값을 돌려주기만 하는 계산 함수는 주변 코드의 관례를 따른다. 동사를 쓰는 코드베이스라면 `getIncreasedQuantity`, `calculateTotalPrice`처럼 쓴다.
- `updateProducts`처럼 값에 동사 이름을 붙이면 함수로 오해된다.

### 5. 형태를 드러내는가

- 배열·목록은 복수형: `items`, `INITIAL_CART_ITEMS` (`DEFAULT_PRODUCT`처럼 배열에 단수형을 쓰지 않는다)
- 참·거짓은 `is`, `has`, `can`, `should`: `isOpen`, `canDecreaseQuantity`
- 처음 값은 `DEFAULT`보다 `INITIAL`이 나을 때가 많다. 기본값(설정이 없을 때 쓰는 값)과 초기값(처음 담겨 있는 값)은 다르다.

### 6. React와 주변 관례를 따르는가

- 커스텀 훅은 `use`로 시작한다.
- 컴포넌트가 받는 이벤트 props는 `on`으로 시작한다: `onIncreaseQuantity`
- 이벤트에 반응하며 여러 동작을 조율하는 함수는 `handle`로 시작한다: `handleSubmit`. 한 가지 행동만 한다면 행동 이름이 더 잘 읽힌다: `onClick={increaseQuantity}`
- `set`으로 시작하는 이름은 `useState`의 setter로 오해되기 쉽다.
- 파일 이름은 내보내는 이름과 같게 둔다. `useProduct.ts`가 `useProducts`를 내보내면 찾을 때 헷갈린다.
- 경로에서 같은 말을 반복하지 않는다: `model/cart.model.ts`

일반 관례와 이 코드베이스의 관례가 다르면 **코드베이스의 관례를 우선**한다. 이름은 "어느 쪽이 맞나"보다 "주변 코드와 같은 방식인가"가 더 중요하다.

## 제안하는 방법

- **전부 나열하지 않는다.** 효과가 큰 순서로 1~3개만 제안한다. 다른 이름을 연쇄적으로 정리해 주는 개념 이름(예: `CartItem`으로 통일)이 있다면 그것을 먼저 제안한다.
- **현재 → 제안 → 이유**를 함께 쓴다. 이유는 위 기준 중 무엇에 해당하는지로 설명한다.
  - 예: `useProducts` → `useCart`. 합계와 수량 변경까지 돌려주니 목록보다 장바구니 전체를 다룬다. (기준 1, 3)
- **후보가 둘 이상이면** 각각이 어떤 범위를 약속하는지 비교하고 하나를 추천한다.
- **분류를 밝힌다.** 이름이 실제 동작과 달라 오해를 부른다면 설계 위험이다. 일관성이나 취향의 문제라면 관례로 분류하고, 지금 바꾸지 않아도 된다고 말한다.
- **미래를 대비해 이름을 바꾸지 않는다.** `totalPrice`를 배송비가 생길 때를 대비해 미리 `productsTotalPrice`로 바꾸지 않는다. 의미가 실제로 갈라질 때 나눈다.
- **잘 지은 이름도 짚는다.** 무엇을 유지해야 하는지 알면 다음 이름을 지을 때 기준이 된다.
- 사용자가 요청하지 않았다면 이름을 직접 바꾸지 않는다. 제안만 하고, 연습 중이라면 어떤 이름이 좋을지 먼저 묻는 것도 좋다.
