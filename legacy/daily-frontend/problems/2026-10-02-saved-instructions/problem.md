# 2026-10-02 · 작성 중인 안내와 저장된 안내

- 유형: 직접 구현형
- 예상 시간: 30~40분

## 사용자 목표

판매자가 이웃에게 공개할 거래 안내를 수정하고, 저장에 실패해도 작성한 내용을 잃지 않은 채 다시 저장한다.

## 핵심 설계 질문

> 작성 중인 값과 서버가 저장을 확정한 값은 언제 같아지고 언제 달라지나요? 이 경계를 어디에서 관리하면 저장 실패와 되돌리기가 서로 영향을 주지 않을까요?

## 시작 위치

`starter.tsx`의 `InstructionsEditor`에 로직과 구조를 직접 구현합니다. 현재는 초기 화면만 그리며 입력·저장·되돌리기 동작은 연결되지 않았습니다. `view.tsx`는 SEED 화면 표현을 제공하고, `api.ts`는 요청 계약과 모의 API를 제공합니다. 표현용 props와 같은 이름의 상태를 모두 만들 필요는 없습니다. 컴포넌트·훅·함수의 분리 방식은 자유입니다.

## 사용자에게 보이는 요구사항

1. 진입 시 현재 공개된 안내와 입력값은 `INITIAL_INSTRUCTIONS`입니다. 입력의 앞뒤 공백을 제거한 값이 공개값과 같으면 저장과 되돌리기 버튼은 비활성입니다.
2. 수정해도 공개된 안내는 저장 성공 전까지 유지합니다. `되돌리기`는 가장 최근에 저장된 안내를 입력에 복원하고 오류·결과 안내를 지웁니다. 공백만 있는 입력은 저장 클릭 시 필드 옆에 `거래 안내를 입력해 주세요.`를 표시하며 요청하지 않습니다. 다른 변경은 오류·결과 안내를 지웁니다.
3. 저장 시 앞뒤 공백을 제거한 `{ text }`를 한 번 전송합니다. 진행 중 입력과 두 버튼을 잠그고 `저장 중...`을 표시합니다. 성공하면 **응답의 text**로 공개값과 입력을 갱신하고 `거래 안내를 저장했어요.`를 표시합니다. 실패하면 공개값과 입력을 보존하고 `저장하지 못했어요. 다시 시도해 주세요.`를 표시합니다. 재시도할 수 있어야 합니다.

## 요청 계약

```ts
type SaveInstructions = (request: { text: string }) => Promise<{ text: string }>
```

`Problem.tsx`가 안정적인 모의 함수를 전달합니다. 브라우저 모의 API는 0.8초 뒤 응답하고, 첫 호출만 실패하며 이후에는 성공합니다. 문제를 나갔다 다시 선택하면 모의 호출 횟수가 초기화됩니다. 실제 서버 저장이나 새로고침 후 복원은 없습니다. 테스트에서는 다른 요청 함수를 주입합니다.

## 화면 맥락과 상태

375px 화면에서 현재 공개된 안내 → 수정 입력 → 되돌리기·저장 순서입니다. 입력 한 개와 저장 결과를 함께 볼 수 있도록 인라인 폼을 씁니다. 오류는 조치가 필요하므로 사라지는 토스트 대신 화면에 남깁니다.

| 상태           | 필요한 화면과 행동                                       |
| -------------- | -------------------------------------------------------- |
| 초기·변경 없음 | 공개된 안내와 입력을 표시하고 저장·되돌리기를 비활성화   |
| 편집           | 공개값은 유지하고 두 버튼 활성화                         |
| 빈 입력 오류   | 필드 옆 오류 표시, 요청 없음, 입력 수정 가능             |
| 저장 중        | 입력·버튼 잠금, 진행 표시, 공개값 유지                   |
| 저장 실패      | 작성값·공개값 보존, 재시도 안내, 조작 복구               |
| 성공           | 응답값을 공개·입력에 반영, 성공 안내, 변경 없음으로 전환 |

## UI 컴포넌트 확인

공식 [SEED Text Field Textarea](https://seed-design.io/react/components/text-field-textarea) 스니펫으로 라벨·설명·오류·입력을 구성합니다. 버튼은 공식 ActionButton 스니펫, 안내는 설치본의 Callout 파츠, 배치는 VStack·HStack·Box, 제목·본문은 Text를 사용합니다. 별도 Select·Radio·Dialog는 이 화면에 필요하지 않습니다. `style.css`는 긴 내용 줄바꿈과 버튼 배치만 다룹니다. native 입력·버튼을 별도로 대체 구현하지 않았습니다.

공식 컴포넌트 기준은 [입력 가이드](https://seed-design.io/components/text-input), [액션 위계](https://seed-design.io/components/action-button), [Callout](https://seed-design.io/components/callout)에서 확인했습니다. 구조 선택은 [Frontend Fundamentals의 네 기준](https://frontend-fundamentals.com/code-quality/code/)으로 설명하되 파일 수나 훅 수를 목표로 삼지 않습니다.

앱에서 `작성 중인 안내와 저장된 안내`를 선택합니다. 주소의 hash는 `#2026-10-02-saved-instructions`입니다.

`Problem.spec.tsx`에는 두 묶음이 있습니다. 출제자가 제공한 UI·API 테스트는 바로 실행합니다. 구현할 행동 테스트는 `describe.skip`으로 표시했습니다. 구현을 시작할 때 `.skip`을 제거해 실패를 확인하고, 요구사항을 만족시켜 통과시키세요. 건너뛴 상태는 풀이 통과가 아닙니다.

각 화면의 정적인 모습은 주소의 query를 `?ui-preview=initial`, `editing`, `empty`, `loading`, `error`, `success`로 바꾸어 확인할 수 있습니다. 예: `/?ui-preview=loading#2026-10-02-saved-instructions`. 검수용 고정값이며 실제 사용자 흐름이나 정답 로직이 아닙니다. 직접 풀이할 때는 query를 지웁니다.

### 출제 시 검증 범위

오늘 파일의 ESLint·형식·TypeScript 검사와 별도 진입점의 Vite 빌드가 통과했습니다. UI·API 테스트는 7개 통과, 구현 행동 테스트는 4개 건너뜀입니다. 375px 실제 브라우저에서 정적 초기·편집·빈 입력·로딩·실패·성공 화면의 가로 넘침 없음, 입력 라벨 연결, 52px 버튼과 비활성 표현을 확인했습니다. 실습자가 구현할 상태 전이·저장 흐름을 검증한 것은 아닙니다.

공통 앱 전체 빌드는 기존 풀이의 `2026-10-01-order-boundaries/hooks/useOrderForm.ts:36` 구문 오류(`TS1005`)로 실패했습니다. 전체 테스트에서도 기존 주문 문제의 금액 표시·픽업 수량 기대값 2개가 실패했습니다. 이전 풀이를 수정하지 않기 위해 오늘 화면만 별도 진입점에서 확인했습니다. 공통 실행에는 이전 문제 오류 확인이 필요합니다. 기존 List 스니펫의 CSS 버전 호환 경고도 남아 있으며, 오늘 화면은 해당 스니펫을 사용하지 않습니다.
