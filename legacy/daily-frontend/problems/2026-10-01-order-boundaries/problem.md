# 2026-10-01 · 배송과 픽업, 어디까지 함께 둘까?

- 유형: 리팩터링 · 동작 유지
- 예상 시간: 30~40분
- 기준: [Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 가독성·예측 가능성·응집도·결합도

## 사용자 목표

커피를 구매하는 사용자는 배송 또는 매장 픽업을 선택하고, 필요한 정보를 입력해 표시된 금액으로 주문을 완료한다.

## 과제

`starter.tsx`는 이미 동작하는 코드다. 새 기능을 추가하거나 주문 규칙을 바꾸지 말고, 기존 동작과 `OrderRequest` 계약을 유지하면서 구조를 재구성한다. `Problem.spec.tsx`는 구조와 무관하게 사용자 행동을 검증한다.

핵심 질문: **배송과 픽업은 비슷한 화면과 제출 흐름을 가진다. 어디까지 함께 관리하고, 어떤 규칙은 독립적으로 바뀌도록 둘 것인가?**

먼저 현재 구조의 문제와 유지할 부분을 적고 시작한다. 훅·컴포넌트·함수 추출을 정답으로 지정하지 않는다. 네 기준 모두를 억지로 개선할 필요는 없다.

## 유지할 규칙

- 상품은 한 상자 6,000원, 수량은 1~5개다. 처음에는 배송·1개·빈 주소이며, 픽업 매장은 미선택, 날짜는 오늘이다.
- 배송: 상품 금액 10,000원 이상이어야 하며 주소가 필요하다. 최소 금액을 먼저 검사하고 주소를 검사한다. 요청의 주소는 앞뒤 공백을 제거한다.
- 배송비는 3,000원이고 상품 금액 30,000원부터 무료다. 화면의 배송비·결제 예정 금액과 요청 금액은 일치해야 한다.
- 픽업: 최소 금액 제한과 배송비가 없다. 매장을 먼저 검사하고 날짜·수량을 검사한다. 오늘은 3개까지, 내일은 5개까지 가능하다.
- 배송과 픽업을 오가도 입력한 주소·매장·날짜·수량을 유지한다. 현재 방식에 필요한 필드만 표시하고 요청한다.
- 입력을 바꾸면 이전 안내를 지운다. 검증 실패 시 요청하지 않는다.
- 요청 중에는 모든 입력과 제출을 잠그고 `처리 중...`을 표시한다. 성공·실패 후 입력을 유지하고 안내를 표시하며 다시 조작할 수 있다.
- `sendOrder`로 주입한 요청 함수는 성공·실패를 모두 지원한다. 버튼 재클릭으로 실패한 주문을 다시 시도할 수 있다.

정확한 안내 문구와 요청 형태는 시작 코드 및 테스트를 기준으로 보존한다.

## 화면 맥락과 상태

375px 화면에서 받는 방법 선택 → 필요한 정보 입력 → 금액 확인 → 제출 흐름이다. 항목이 적고 입력을 함께 확인해야 하므로 인라인 폼을 사용한다. 추가 시트나 다이얼로그는 필요 없다. SEED Design의 React 컴포넌트와 공개 토큰을 사용한 모바일 UI를 제공한다. 이번 과제에서는 시각 디자인을 변경하지 않는다.

| 상태         | 화면과 행동                                                             |
| ------------ | ----------------------------------------------------------------------- |
| 초기·빈 입력 | 기본값과 필요한 필드를 표시한다. 제출 시 어떤 입력이 필요한지 안내한다. |
| 입력 오류    | 현재 시작 코드의 순서대로 검증하고 요청하지 않는다. 안내를 유지한다.    |
| 요청 중      | 입력·제출을 잠그고 처리 중 표시를 한다.                                 |
| 요청 실패    | 재시도 안내와 입력을 유지한다. 버튼을 다시 누를 수 있다.                |
| 성공         | 완료 안내와 입력을 유지한다. 입력이 바뀌면 안내를 지운다.               |

## 완료 조건

1. 테스트·lint·build가 통과하고 기존 사용자 행동과 요청 계약이 유지된다.
2. 현재 코드의 구체적인 문제를 최소 하나 설명하고, 재구성이 어떤 기준을 개선하는지 근거를 남긴다.
3. 공통화하거나 분리한 경계의 장점과 비용, 그대로 유지한 부분의 이유를 `note.md`에 기록한다.

미래 변경은 평가용 가정으로만 생각한다. 예를 들어 배송의 무료 기준만 바뀌면 어디가 함께 수정되는가, 픽업에만 규칙이 추가되면 어디까지 영향이 가는가? 이번에 그 기능을 미리 구현하지 않는다.

## 실행과 검사

저장소 루트에서 실행한다.

```sh
pnpm dev:daily
pnpm --filter @frontend-lab/daily-frontend test -- problems/2026-10-01-order-boundaries/Problem.spec.tsx
pnpm --filter @frontend-lab/daily-frontend lint
pnpm --filter @frontend-lab/daily-frontend build
```

앱에서 오늘 문제를 선택한다. 기본 모의 요청은 0.6초 뒤 성공한다. 실패와 대기 상태는 테스트에서 요청 함수를 주입해 재현한다. 실제 결제나 서버 저장은 없다.

범위 밖: 새 기능, 디자인 변경, 주문 정책 변경, 새로운 라이브러리 도입. 설계 풀이와 정답 코드는 제공하지 않는다.
