# 풀이 기록

리팩터링하면서 내린 결정마다 멘토가 "어떤 근거로, 왜 그렇게 했어요?"를 묻습니다. 각 항목의 **상황**은 문제나 코드에 있는 사실이고, 그 아래 질문에 본인 말로 답합니다. 꼬리 질문은 첫 답을 쓴 뒤에 읽어도 됩니다. 줄 번호는 `pages/ProductReservationPage.tsx` 기준입니다.

## 1. 요약은 보이는 상품 기준일까, 선택한 상품 기준일까

**상황**: 책상(12,000원)과 화분(나눔)을 선택한 뒤 `나눔` 필터로 바꿨다. 목록에는 화분만 보인다. 동료가 "요약은 화면에 보이는 상품만 세자"며 요약 영역(116번째 줄부터 129번째 줄)의 `products`만 아래처럼 `visibleProducts`로 바꿨다. 숨겨진 선택 안내(131번째 줄부터)와 예약 요청(21번째 줄부터)은 그대로 `products`를 쓴다.

```tsx
const visibleProducts = products.filter((product) => filter === 'all' || product.price === 0)

<Text textStyle="t5Bold">선택 {visibleProducts.filter((product) => selectedIds.includes(product.id)).length}개</Text>
// 상품 금액, 상품 이름도 같은 식으로 visibleProducts에서 계산한다
```

> "이때 요약 영역에는 개수·금액·이름이 어떻게 보이고, 그 아래 숨겨진 선택 안내는 뭐라고 말해요? 이 상태에서 예약 버튼을 누르면 어떤 요청이 나가죠?"

요약 화면은 화면에 보이는 상품만 세기 때문에, 책상과 화분을 선택한 2개가 아닌, 화분 1개만 표시하게 돼요. 금액은 0원, 이름은 화분이라고 나와요. 숨겨진 선택 안내에서는 현재 목록에 숨겨진 1개도 예약에 포함된다고 말해요.
이 상태에서 예약 버튼을 누르게된다면, 실제 서버로 요청이 갈 때 선택 상품 2개, 금액은 12,000원 책상과 화분이라는게 나와요. 즉 사용자에게 요약해 알려주는 정보와 실제 서버의 데이터가 다르다는 문제가 발생해요.

---

**멘토**: 정확해요. 요약은 1개·0원·화분, 숨겨진 안내는 1개, 요청은 2개·12,000원이에요. 장면에 나온 값을 하나씩 넣어서 답했기 때문에, 마지막 문장 "요약해 알려주는 정보와 실제 서버의 데이터가 다르다"가 추측이 아니라 확인된 결론이 됐어요. 사용자 입장에서는 0원짜리 나눔만 받는 줄 알고 눌렀는데 책상까지 예약된 장면이에요.

이 결론을 리팩터링한 코드와 이어서 적으면 이 항목이 완성돼요. 어긋난 원인은 같은 "선택한 상품"이라는 범위를 요약은 `visibleProducts`로, 요청은 `products`로 **따로 계산한 것**이었어요. 그래서 지금 요약과 요청이 둘 다 `selectedProducts` 하나를 보게 만든 게, 바로 이 장면을 막는 결정이에요.

> 꼬리 질문: "요구사항 2번은 이름과 요청 ID를 '원래 상품 목록 순서'로 둔다고 정했어요. 이걸 '선택한 순서'로 바꾸라는 요구가 오면 `ProductReservationPage.tsx`에서 같이 고쳐야 하는 줄은 어디예요? 그중 한 줄을 빠뜨리면 사용자가 보는 이름 순서와 서버가 받는 `productIds` 순서가 어떻게 어긋나요?"

원래 상품 목록 순서가 아닌, 선택한 순서로 변경해야한다면, `selectedIds`를 기준으로 `map`을 사용하면 화면에 보여줘야해요. 기존 코드에 products.filter 부분들을 확인해보면 예약 요약 부분에서 126-127번 부분을 고쳐야 사용자가 보는 이름 순서와 일치하게 돼요. 그리고 서버에서는 데이터를 배열로 보내기 때문에 22번째 줄도 함께 고쳐야 올바른 데이터로 서버로 보낼 수 있어요.

사용자가 화분과 책상을 선택했다면, 서버쪽에서는 ['desk', 'plant']와 같이 서버로 보내기 때문에 잘못된 값으로 요청이 갈 수 있어요.

---

**멘토**: 이번엔 줄을 정확히 찾았어요. 이름(126·127번째 줄)과 요청의 `productIds`(22번째 줄), 이 두 곳이 순서가 곧 결과인 값이에요. `products.filter`가 나오는 곳을 다 모아 놓고 하나씩 따져 본 방법이 통한 거예요. 개수나 합계처럼 순서와 상관없는 줄을 고를 대상에서 뺀 것도 맞아요.

뒷부분 "한 줄을 빠뜨리면 어떻게 어긋나요?"도 장면으로 답했어요. 화분을 먼저 고르면 화면은 "작은 화분, 접이식 책상"인데 서버는 `['desk', 'plant']`를 받아요. 사용자가 보는 순서와 서버가 받는 순서가 갈라지는 거예요. 1번 답에서 찾은 "요약과 서버 데이터가 다르다"와 같은 종류의 문제라, 두 답을 나란히 두면 이 문제가 무엇을 묻는지가 잘 보여요. 그리고 지금 구조에서는 이름과 요청이 모두 `getSelectedProducts`를 거치니까, 이 요구가 와도 그 함수 한 곳만 고치면 돼요.

## 2. 선택을 비웠는데 남아 있는 실패 안내

**상황**: 책상을 선택하고 예약했다. 모의 API는 첫 요청만 실패하므로 0.8초 뒤 빨간 안내 "예약하지 못했어요. 선택한 상품은 그대로예요. 다시 시도해 주세요."가 뜬다. 이때 동료가 상품 목록 위에 아래 `전체 해제` 버튼을 추가했다. `ProductReservationPage.tsx`에는 없는 코드다.

```tsx
<button type="button" onClick={() => setSelectedIds([])}>
  전체 해제
</button>
```

> "실패 안내가 떠 있는 상태에서 `전체 해제`를 누르면 요약과 결과 안내는 각각 어떻게 보여요? 필터를 바꾸거나 상품을 누를 때(52·53번째 줄, 84·85번째 줄)와 비교하면 이 버튼은 무엇을 빠뜨렸죠?"

현 상황에서 전체 해제를 누르면, 선택 0개, "예약할 상품을 선택해주세요"가 요약에서 보이고, 결과 안내는 그대로 실패로 보여요. 현재 버튼은 `failed`와 `message` 상태를 초기값으로 돌려야해요.

---

**멘토**: 화면을 먼저 적고 나서 고칠 곳을 말한 순서가 좋아요. 요약은 "선택 0개"와 "예약할 상품을 선택해 주세요."로 바뀌고 실패 안내는 그대로 남는다는 것도, 그래서 `message`와 `failed`를 돌려야 한다는 것도 정확해요.

"실패로 보여요"를 사용자 눈으로 한 번만 더 읽어 볼게요. 빨간 안내의 문구는 "선택한 상품은 그대로예요"예요. 바로 위 요약은 선택이 0개라고 말하고요. 한 화면이 서로 반대되는 말을 하는 거예요. 이게 이 버튼이 만든 진짜 문제예요. 52·53번째 줄과 84·85번째 줄은 "선택이나 필터가 바뀌면 이전 결과 안내를 지운다"는 요구사항 3번을 지키고 있는데, 이 버튼은 `setSelectedIds`를 직접 불러서 그 규칙만 건너뛰었어요.

지금 리팩터링한 코드에서는 이 실수가 생기기 어려워졌어요. 훅이 `setSelectedIds`를 밖으로 내보내지 않고, 선택을 바꾸는 길이 결과를 지우는 `toggleProductSelection` 하나뿐이니까요. `전체 해제`를 추가하려면 훅 안에 새 행동을 만들어야 하고, 그 자리에서 `setResult(null)`이 바로 옆에 보여요. 이 내용을 이 답의 결론으로 적어 두면 좋아요.

## 3. form으로 감싼 범위

**상황**: 출제 때(파일 이름이 `starter.tsx`였을 때)는 예약 버튼이 `onClick={() => void submit()}`으로 요청을 보냈다. 지금은 상품 목록·요약·결과 안내·예약 버튼을 `<form onSubmit>`(67번째 줄) 안에 넣고 버튼을 `type="submit"`으로 바꿨다. 보기 필터(45번째 줄)는 form 밖에 남겼다. 필터도 요청 중에는 잠기고, 바꾸면 결과 안내를 지운다.

> "form으로 감싸기 전과 후에 사용자가 화면에서 할 수 있는 일이나 보는 것 중 달라진 게 있나요? 필터를 form 밖에 둔 기준은 뭐예요?"

`form`은 사용자가 입력한 내용들을 서버로 보내는 태그에요. 필터는 UI에서 구분하기 위해 필요한거지, 실제 서버로 보내야할 데이터는 아니라고 생각했어요. 마크업(문서) 관점으로도 생각해보았을 때 필터를 폼에 넣는건 의미적으로 좋지않다고 판단했어요

---

**멘토**: 기준이 분명해요. "서버로 보낼 데이터인가"로 form 안과 밖을 가른 거라, 다음에 새 컨트롤이 생겨도 같은 질문으로 둘 곳을 정할 수 있어요. 필터가 요청 중에 잠기고 결과 안내를 지우는 등 form과 상태를 공유한다는 사실과, form 태그 안에 있어야 하는가는 별개의 문제예요. 그걸 섞지 않은 점이 좋아요.

앞 질문인 "사용자 입장에서 달라진 게 있나"는 "거의 없다"가 답이에요. 클릭해서 예약하는 흐름도, 요청 중 잠금도 그대로예요. 체크박스에 포커스가 있을 때 Enter로 제출되는지 정도는 브라우저마다 다를 수 있는데, 이건 실제 화면에서 눌러 보고 적으면 돼요. 그러니 이건 동작이 아니라 의미와 구조를 위한 선택이었다고 한 줄 덧붙이면, 기준을 그렇게 정한 이유까지 설명돼요.
