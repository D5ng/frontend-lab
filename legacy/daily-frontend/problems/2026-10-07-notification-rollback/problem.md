# 관심 상품을 고르고 알림 만들기

- 유형: 행동 보존 리팩터링
- 예상 시간: 30~40분
- 사용자 목표: 관심 상품 중 가격 소식을 받을 상품을 고르고, 받는 방식과 시간을 정해 알림 설정을 저장한다.

## 이번 과제

`pages/NotificationSettingsPage.tsx`는 아래 사용자 흐름이 이미 완성된 시작 코드입니다.

**관심 상품 불러오기 → 검색·상품 선택 → 알림 방식 설정 → 요약 확인 → 저장 결과 확인**

기능을 새로 만들거나 버그를 고치는 과제가 아닙니다. 화면, 데이터 가공, 선택, 안내, 요청이 한 페이지 안에서 연결되어 있습니다. 기존 행동을 유지하면서 무엇을 함께 읽고 변경할지 판단해 재구성하세요. 파일 수나 훅 수는 평가 기준이 아닙니다.

## 관찰 가능한 요구사항

### 1. 상품 탐색과 선택

- 서버에서 상품의 이름·동네·가격·거래 가능 여부를 불러옵니다. 처음에는 선택한 상품이 없고, 받는 방식은 바로 받기입니다.
- 검색어 앞뒤 공백과 영문 대소문자를 무시해 상품 이름을 검색합니다. 검색은 추가 서버 요청 없이 현재 목록에 적용합니다.
- 상품 행 전체를 눌러 여러 상품을 선택·해제합니다. 거래완료 상품은 이유를 표시하고 선택을 막습니다.
- 검색으로 숨겨진 상품도 선택은 유지합니다. 상단 개수, 요약과 저장 대상은 화면에 보이는 상품만이 아니라 전체 선택을 따릅니다.
- 검색 결과 없음과 서버 목록 자체가 비어 있음을 구분합니다. 검색 결과가 없으면 전체 상품 보기로 검색어를 지울 수 있습니다.

### 2. 알림 방식과 요약

- 바로 받기는 `가격이 내려가면 바로`, 모아 받기는 `매일 오전 9시에 한 번` 또는 `매일 오후 8시에 한 번`으로 안내합니다.
- 모아 받기를 선택했을 때만 받을 시간 선택을 표시합니다. 기본 시간은 오전 9시입니다.
- 방식을 왕복해도 마지막으로 고른 시간은 유지합니다. 단, 바로 받기 요청에는 숨겨진 시간을 보내지 않습니다.
- 요약에는 전체 선택의 상품명·개수와 현재 받을 방식을 표시합니다. 상품명은 서버 목록 순서로 표시합니다.

### 3. 저장과 결과

- 선택이 없거나 목록을 불러오는 중·조회 실패·저장 중이면 저장할 수 없습니다.
- 저장 중에는 검색, 상품 선택, 방식과 시간 입력, 중복 제출을 막고 버튼에 진행 상태를 표시합니다.
- 실패하면 입력·선택과 마지막 저장 결과를 보존하고 다시 시도할 수 있습니다.
- 성공하면 입력을 유지하고 저장 완료 안내와 마지막으로 저장한 상품·방식을 보여줍니다. 이후 새로 편집하더라도 마지막 저장 결과는 다음 저장 성공 전까지 바뀌지 않습니다.
- 입력이나 선택을 바꾸면 이전 저장 성공·실패 안내를 지웁니다. 단순히 검색어를 지우는 경우도 같습니다.
- 목록 조회 실패에는 다시 불러오기 동작을 제공합니다. 목록을 불러오는 동안은 검색과 알림 방식 입력도 비활성화합니다.

## 실행 환경과 제공 API

저장소 루트에서 `pnpm install --frozen-lockfile`, `pnpm dev:daily`를 실행합니다. 문제 주소의 해시는 기존과 같은 `#2026-10-07-notification-rollback`입니다. 기존 PR과 링크를 유지하기 위해 폴더 이름은 바꾸지 않습니다.

`features/notificationSettings/apis/createNotificationMock.ts`의 공장 함수는 `getProducts()`와 `savePlan(plan)`을 제공합니다. 실제 `fetch`를 사용하며 이 문제의 `handlers.ts`가 MSW로 HTTP 응답을 제공합니다.

| 요청                                                       | 계약                                 |
| ---------------------------------------------------------- | ------------------------------------ |
| `GET /api/daily/2026-10-07-notification-rollback/products` | 0.5초 뒤 상품 목록 반환              |
| `POST /api/daily/2026-10-07-notification-rollback/plans`   | 아래 요청으로 저장하고 `{ id }` 반환 |

```ts
type NotificationPlan = { productIds: string[]; delivery: 'instant' } | { productIds: string[]; delivery: 'digest'; hour: '09' | '20' }
```

저장은 0.9초 뒤 응답하며, 유효한 첫 요청은 실패하고 재시도는 성공합니다. 오류 상태를 직접 확인하기 위한 실습 시나리오입니다. 화면을 나갔다 돌아오면 초기화되며 실제 설정 저장·알림 발송은 하지 않습니다. 상품 조회 실패·빈 목록은 테스트에서 API를 대체해 재현합니다. 모의 서버 구현은 풀이 대상이 아닙니다.

## 핵심 설계 질문

**알림 방식의 규칙이 바뀔 때, 입력 UI·요약·저장 요청·저장 완료 결과 중 무엇을 함께 수정해야 하며 그 관계가 코드에서 충분히 드러나나요?**

가독성·예측 가능성·응집도·결합도를 참고하되 특정 구조를 정답으로 전제하지 마세요. 단순히 큰 컴포넌트를 여러 파일로 옮기는 것과 변경 이유에 맞게 책임을 나누는 것의 차이를 설명해 보세요.

## 완료 조건

1. 제공된 모든 활성 행동·HTTP 테스트를 삭제하거나 건너뛰지 않고 통과시킵니다.
2. 위 사용자 흐름과 화면 결과를 보존하며 구조를 재구성하고, 실제 변경 이유와 선택의 비용을 `note.md`에 직접 기록합니다.
3. 검색으로 숨겨진 선택, 방식 왕복, 저장 실패·재시도·성공 후 편집을 화면에서 확인합니다.

```sh
pnpm --filter @frontend-lab/daily-frontend exec vitest run problems/2026-10-07-notification-rollback
pnpm --filter @frontend-lab/daily-frontend lint
pnpm --filter @frontend-lab/daily-frontend build
```

## 화면과 범위

375px 모바일 화면에서 탐색 → 방식 → 요약 순으로 읽는 인라인 폼입니다. 상품 선택과 받는 설정을 함께 저장하므로 즉시 적용을 약속하는 스위치 대신 체크박스와 라디오를 사용합니다. 오류와 저장 결과는 사라지지 않아야 하므로 인라인으로 표시합니다. 별도 시트·확인 다이얼로그는 이 흐름에 필요하지 않아 추가하지 않습니다.

| 역할                | 사용한 공식 SEED 컴포넌트                                     |
| ------------------- | ------------------------------------------------------------- |
| 검색 입력·라벨      | TextField / TextFieldInput                                    |
| 상품 다중 선택      | List / ListCheckItem / Checkbox.Control·Indicator             |
| 받는 방식           | RadioGroup / RadioGroupItem                                   |
| 받을 시간           | SelectRoot / SelectTrigger / SelectItem                       |
| 조회 대기·결과 안내 | Skeleton / Callout                                            |
| 배치·구분·제목·저장 | VStack / HStack / Box / Divider / Text / Badge / ActionButton |

설치된 React 2.5.1·CSS 2.8.3과 기존 공식 v2 스니펫을 사용합니다. 공통 앱·패키지 업그레이드, 실서버 연동, 실제 알림 발송은 범위 밖입니다. 이번 개정의 검사 결과와 브라우저 확인 범위는 PR의 검증 항목에 기록합니다.
