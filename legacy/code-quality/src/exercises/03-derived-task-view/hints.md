# Exercise 03 힌트

필요한 단계까지만 읽습니다. 이 문서는 완성 코드를 제공하지 않습니다.

## 높은 레벨: 사용자가 바꾸는 것과 화면이 보여 주는 것

사용자는 할 일의 완료 상태, 검색어와 필터를 바꾼다. 남은 개수나 진행률을 직접 입력하지는 않는다.

먼저 답해 보세요.

1. 사용자가 직접 바꾸지 않는 값도 상태로 저장해야 하나요?
2. 완료 상태 하나가 바뀌면 화면의 어느 부분들이 함께 달라져야 하나요?
3. 그 부분들이 서로 다른 시점에 갱신될 가능성은 없나요?

## 중간 레벨: 원본과 파생값

어떤 값이 다른 상태와 props만으로 항상 결정된다면 파생값일 가능성이 높다. 다만 “계산할 수 있다”는 이유만으로 무조건 별도 함수나 메모이제이션이 필요한 것은 아니다.

먼저 답해 보세요.

1. `tasks`, `todoCount`, `completionPercent` 중 나머지를 복원할 수 있는 최소 정보는 무엇인가요?
2. `visibleTasks`를 상태로 저장하면 검색어, 필터, 완료 상태가 바뀔 때 무엇을 기억해야 하나요?
3. 계산 비용이 충분히 작다면 `useMemo`는 어떤 문제를 해결하나요?

## 낮은 레벨: 현재 코드 읽기

- `tasks`는 각 할 일의 현재 완료 여부를 포함한다.
- `statusFilter`와 `searchQuery`는 사용자가 고른 화면 조건이다.
- 진행 숫자, 필터 개수와 `visibleTasks`는 위 값들로부터 계산된다.
- 완료 처리와 정리는 식별자를 기준으로 원본 목록을 변경한다.

먼저 답해 보세요.

1. 현재 계산식이 `Problem`에 모여 있어 흐름을 읽기 어려운가요, 아니면 한 화면의 규칙을 한 번에 보기 쉬운가요?
2. 계산을 함수로 분리한다면 어떤 입력과 출력을 가져야 숨은 의존성이 없을까요?
3. `TaskItem`을 분리할 변경 이유가 지금 존재하나요? 분리했을 때 잃는 문맥은 무엇인가요?

## 판단 기준

현재 요구사항에서는 상태를 더 많이 만드는 것이 책임 분리는 아니다. 반대로 모든 표현을 한 줄에 넣는 것도 좋은 응집도가 아니다.

- 상태에는 사용자의 선택과 원본 데이터를 둔다.
- 파생값은 원본과 조건을 입력으로 계산한다.
- 계산 규칙에 이름이 필요해지거나 여러 소비자가 같은 정책을 사용하면 함수 경계를 검토한다.
- 메모이제이션은 정확성을 위한 기본 장치가 아니다. 측정된 계산 비용이나 참조 안정성 요구가 있을 때 검토한다.
- 컴포넌트 분리는 길이보다 독립적인 변경 이유와 필요한 문맥을 기준으로 판단한다.
